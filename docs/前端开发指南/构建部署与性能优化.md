## 简介

DNSPlane 前端是 Next.js 16.2.4（React 19.2.4）项目，采用**纯静态导出**模式：`next build` 产出 `web/out/` 静态目录，经同步脚本落入 `main/web/`，最终由 Go 的 `//go:embed all:web` 编译进单一二进制，运行时由 gin 路由直接分发。整个链路没有 Node.js 服务端运行时，部署产物只有一个可执行文件或一个 distroless 镜像。

本文覆盖四条主线：

- 开发模式（Turbopack）与 CI 构建模式（webpack + 同步脚本）的行为差异
- 静态导出产物落位与 Go embed 装配链路（以 `main/main.go` 实测为准）
- 产物体积实测数据、HTTP 缓存策略与 Lighthouse 关注点
- Docker 多阶段多架构构建与常见构建失败的排查方法

所有行号均来自当前工作区实际读取；体积数据来自 `du` 实测；未实机验证的项目（如 Lighthouse 得分）均已如实标注。

## 核心组件

### npm scripts 逐条解析

实测 `web/package.json` 第 5-11 行的 scripts 段：

| 脚本 | 定义（行号） | 构建器 | 行为 |
| --- | --- | --- | --- |
| `dev` | `next dev --turbopack`（:6） | Turbopack | 本地开发服务器，增量编译，不产出静态文件 |
| `build` | `set "ANALYZE=true" && next build && powershell ...`（:7） | webpack（默认） | Windows 手工路径：设环境变量后经 powershell 拷贝 `out` 到 `..\main\web` |
| `build:ci` | `next build --webpack && node scripts/sync-main-web.cjs`（:8） | webpack（显式） | 跨平台 CI 路径：导出后调用 node 同步脚本 |
| `start` | `next start`（:9） | — | 启动 Next 服务器；静态导出模式下基本无用 |
| `lint` | `eslint`（:10） | — | 代码检查 |

关键差异：`dev` 用 Turbopack，`build:ci` 显式锁 `--webpack`。两者是不同编译管线，理论上存在「dev 正常、build 报错」的行为分叉面（见故障排查）。

`build` 脚本中的 `ANALYZE=true` 需要如实说明：该变量只是被设置，但 `web/next.config.ts` 全文 16 行中没有任何 bundle 分析器包装，`package.json` 依赖中也没有 `@next/bundle-analyzer`。**当前仓库中 ANALYZE=true 未接线，不会产出体积分析报告**（结论来源：逐行读取两个文件；如需启用见附录）。

```ts
// web/next.config.ts 核心配置（:4-8）
const nextConfig: NextConfig = {
  output: 'export',        // 静态导出，无服务端运行时
  trailingSlash: true,     // 与 Go 侧目录/index.html 查找逻辑对齐
  images: { unoptimized: true }, // 导出模式无 /_next/image 优化器
};
```

### 同步脚本 sync-main-web.cjs

13 行的脚本承担产物落位的唯一契约（实测行号）：

- `:4` `out = web/out` —— 来源目录
- `:5` `dest = main/web` —— 目标目录（相对脚本位置向上两级再进 `main/web`）
- `:7-10` 若 `web/out` 不存在，打印 `missing out/ — run next build first` 并 `exit 1`
- `:12-13` `rmSync(dest)` 后 `cpSync(out, dest, {recursive:true})`，即**先删后拷的全量替换**

一个容易忽略的副作用：在 Docker 构建环境中该相对路径被重新解释。`Dockerfile` 第 5 行 `WORKDIR /build/web`，于是 `:5` 的 `../..` 解析为 `/build`，产物落在 `/build/main/web`；第 22 行 `COPY --from=web /build/main/web ./web` 正好消费这一位置。仓库布局（`dns/web` 与 `dns/main` 平级）与 Docker 布局（`/build/web` 与 `/build/main` 平级）保持了同构，这是该脚本能在两个环境复用的前提。

## 详细组件分析

### dev 与 build:ci 的差异

| 维度 | dev（Turbopack） | build:ci（webpack） |
| --- | --- | --- |
| 编译管线 | Turbopack 增量打包 | webpack 全量构建 |
| 是否产出 `web/out` | 否，纯内存服务 | 是（`output:'export'` 强制静态导出） |
| 类型检查 | 即时反馈但可被绕过 | 构建期硬失败（H-2 决策后不再吞错） |
| 产物同步 | 无 | `sync-main-web.cjs` 落 `main/web` |
| Go embed | 不参与 | 必须先完成，否则 `go build` 失败 |
| 典型不一致 | HMR 状态残留 | show/hide 表单联动只在导出后暴露 |

开发时的正确心智模型：`npm run dev` 验证交互，**提交前必须至少跑一次 `npm run build:ci`**，因为线上跑的是导出产物 + Go 分发，与 dev 服务器是两套运行时（Go 侧静态服务的查找逻辑见下一节）。

`web/app/(dashboard)` 这类路由组不会出现在 URL 中；导出产物以「目录 + index.html」形态组织（`trailingSlash: true`，next.config.ts:5），与 `router.go` 的 NoRoute 查找顺序严格对应：

```go
// main/internal/api/router.go NoRoute 摘要（:411-428）
// 1) 直接路径当文件试            tryServeFile(c, filePath)
// 2) 以 / 结尾补 index.html      filePath + "index.html"
// 3) 无尾斜杠也补 "/index.html"  filePath + "/index.html"
// 4) 动态路由兜底 /dashboard/domains/[id]/ → dashboard/domains/_/index.html（:427-428）
```

根路径 `/` 在 `:408` 直接 302 到 `/login`，不经过 NoRoute。

### 静态导出对代码的硬约束

`output: 'export'` 意味着构建期枚举全部路由，因此：

- 禁止使用依赖服务端运行时的能力（Route Handler 动态响应、`cookies()` 读写、middleware 重写等）。项目将动态性全部收敛到客户端组件与后端 API。
- `images.unoptimized: true`（next.config.ts:6-8）：导出产物没有 `/_next/image` 服务，`next/image` 退化为原生 `img`。新增图片优化需求只能走 CDN 或预处理。
- 动态段以占位目录落地：`[id]` 段导出为 `_`，由 Go 侧 `router.go:427-428` 回填路由。
- 类型必须干净：next.config.ts 第 10-14 行注释记录了安全审计 H-2——曾有的 `typescript.ignoreBuildErrors` 已移除，任何类型错误都会使 CI 构建失败；个别确需绕过的文件应使用 `// @ts-expect-error` 局部豁免。

### Go 侧缓存策略

`router.go` 的 `tryServeFile`（:385 起）实现了两级缓存语义：

| 文件类别 | Cache-Control | 行号 | 依据 |
| --- | --- | --- | --- |
| `.html` / `.txt` | `no-cache` | :392 | 内容哈希变化必须立即可见，交由 ETag 验证 |
| 其余静态资源 | `public, max-age=31536000` | :394 | `_next/static` 带哈希，可永久缓存 |
| 所有文件 | `ETag: sha256(内容)` | :396-398 | 304 响应也携带 ETag（RFC 9110，:397 注释） |

条件请求命中 `If-None-Match` 时返回 304（:399-401）。Content-Type 由内置 `getContentType`（:350-381）按扩展名映射，未识别类型回落 `application/octet-stream`。

该策略的可感知后果：页面 HTML 每次访问都会回源验证（304 仍有一次 RTT），但验证成本极低——文件已在二进制内，无磁盘 IO；而哈希资源命中一年期缓存后浏览器完全不发起请求。

### Lighthouse 关注点

以下为基于代码事实的**关注点清单，未实机运行 Lighthouse，得分一律未知**，不得当作实测结论引用：

- FCP/LCP：产物无代码分割之外的服务端渲染加成，首屏依赖 `_next/static` 中哈希 chunk 的下载；HTML `no-cache` 意味着每次进站先吃一次 304 往返。
- TBT：客户端组件为主（`'use client'，见 DynamicForm.tsx:1`），React 19 hydration 成本集中在 dashboard 大页。
- CLS：`images.unoptimized` 下若新增图片忘记显式宽高，将直接引入布局偏移。
- 可访问性/SEO：静态导出对 SEO 友好，但登录墙后的 dashboard 页面本身不需要被索引。
- 建议验证方式：对 `go run` 起的本地实例或 Docker 实例跑 `npx lighthouse http://localhost:8080/login`，将结果补录为实测数据。

## 性能考虑

### 构建性能

- Docker 前端阶段只在 `$BUILDPLATFORM` 构建一次（Dockerfile:2 注释），多架构发布不重复 `npm ci`；Go 用 `TARGETOS/TARGETARCH/TARGETVARIANT` 交叉编译（:13-15, :24-27 含 GOARM 处理）。
- 依赖层与源码层分离：`COPY package.json lock` → `npm ci`（:6-8）先于 `COPY web/`（:9）；Go 同理 `go mod download`（:20）先于 `COPY main/`（:21）。改业务代码不触发依赖重装。
- npm 网络重试参数已在镜像内预设（:7 `fetch-retries 5` 等），弱网 CI 无需再做。
- 本地可用 bun 加速：`build.sh` 检测到 `bun` 与 `bun.lock` 时改走 `bun install --frozen-lockfile && bun run build:ci`（:23-26）。

### 运行时性能

- 静态资源在服务二进制内，`fs.ReadFile` 无磁盘 IO；ETag 为内容 sha256，代价是每次请求重算哈希（文件在内存中，属可接受交换）。
- 单二进制分发使冷启动只有 Go 运行时开销，无 Node 启动、无端口二级代理。
- 前端体积治理抓手：6.7M 产物中 `_next/static` 占 2.6M；因 ANALYZE 未接线，chunk 级归因未知，建议按附录先接线再决策。

## 结论

- 前端构建是「webpack 静态导出 → main/web → go:embed」三段单向链，**dev 的 Turbopack 与 CI 的 webpack 是两套管线**，验收必须以 `build:ci` 产物为准。
- 缓存策略由 Go 侧统一实现：HTML 不缓存 + ETag 验证，哈希资源一年强缓存，二者组合与内容哈希文件名互相咬合，无失效死角。
- 体积实测：嵌入产物 6.7M（`_next/static` 2.6M），对单二进制分发完全可接受；chunk 级归因因 ANALYZE 未接线而未知，属下一步工作。
- 本链路的脆弱点集中在三处相对路径契约：`sync-main-web.cjs:5` 的 `../../main/web`、`Dockerfile:22` 的 `/build/main/web`、`main.go:63` 的 `all:web`，改动任一处必须同时验证另两处。
