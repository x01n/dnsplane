## 简介

DNSPlane `1.0.11`（见 [VERSION](file://VERSION)）是自托管的 DNS 与 TLS 证书生命周期管理平台，
以单一 Go 二进制交付：前端 Next.js 静态导出产物在编译期被 `//go:embed all:web` 打进可执行文件
（[main.go:63-64](file://main/main.go#L63-L64)），运行时由同一个 Gin 进程同时提供 `/api` 与页面
（[router.go:344](file://main/internal/api/router.go#L344)）。本文给出从零到「浏览器可登录」的最短路径。

| 项 | 值 | 证据 |
|----|----|------|
| 后端语言与版本 | Go `1.26.2`（模块名 `main`） | [go.mod:1-3](file://main/go.mod#L1-L3) |
| 前端框架与版本 | Next.js `16.2.4` + React `19.2.4` | [package.json:34](file://web/package.json#L34)、[package.json:38](file://web/package.json#L38) |
| 官方镜像 Node 版本 | `node:22-bookworm-slim` | [Dockerfile:4](file://Dockerfile#L4)、[build.yml:50](file://.github/workflows/build.yml#L50) |
| 默认监听地址 | `0.0.0.0:8080`（本机工作区覆盖为 `8800`） | [config.go:88-92](file://main/internal/config/config.go#L88-L92)、[config.json:3](file://main/config.json#L3) |
| 数据存储 | SQLite（默认）/ MySQL（仅主库） | [database.go:82-101](file://main/internal/database/database.go#L82-L101) |
| 首次访问标志 | `GET /` 返回 302 且 `Location: /login` | [router.go:407-408](file://main/internal/api/router.go#L407-L408) |
| 安装完成标志 | `GET /api/install/status` 返回 `{"code":0,"data":{"installed":true}}` | [auth.go:575-583](file://main/internal/api/handler/auth.go#L575-L583) |

文中「实测」指本次在当前工作区真实执行的验证：`go build -o /tmp/dnsplane-qc .` 退出码 0；以临时配置
启动该二进制；`curl` 探测 `/`、`/api/install/status`、`POST /api/install`、`POST /api/login`、
`OPTIONS /api/install`；`SIGTERM` 关停；只读工作目录失败复现。未执行的部分一律标注「推断」。

## 详细组件分析

### 本地开发环境启动

最短路径是「先出前端产物，再由后端同源服务」，共四步。README 第 40-68 行顺序基本一致，
但其中的 `bun run build` 在 Linux/macOS 不可用，本文以脚本实际内容为准。

```bash
# 步骤 1：后端依赖（对应 go.mod:1-86；仓库无 vendor 目录）
cd main && go mod download

# 步骤 2：前端依赖（对应 package.json:12-53）
cd ../web
bun install            # 走 bun.lock
# 或：npm ci           # 走 package-lock.json，与 Dockerfile:6-8 / build.yml:56-59 一致

# 步骤 3：构建前端并同步到 main/web（对应 package.json:8 与 sync-main-web.cjs:4-13）
bun run build:ci       # next build --webpack && node scripts/sync-main-web.cjs

# 步骤 4：启动后端（对应 main.go:66-156；默认读同目录 config.json）
cd ../main && go run .
```

[next.config.ts:3-14](file://web/next.config.ts#L3-L14) 也无 `rewrites`；另实测

[auth.go(middleware):516-534](file://main/internal/api/middleware/auth.go#L516-L534)）。

### 前端构建产物同步

`build:ci` 是唯一跨平台可用的入口，`build` 脚本用了 `set` 与 `powershell`
（[package.json:7-8](file://web/package.json#L7-L8)），在 Linux/macOS 直接失败。
同步器语义（[sync-main-web.cjs:1-13](file://web/scripts/sync-main-web.cjs#L1-L13)）：源为 `web/out`
（第 4 行）、目标为 `../main/web`（第 5 行）；`out` 不存在时打印
`missing out/ — run next build first` 并退出码 1（第 7-10 行）；随后 `fs.rmSync` 递归删除目标、
`fs.cpSync` 全量复制（第 12-13 行），因此不做增量合并。`main/web/` 与 `web/out/` 均不入库
（[.gitignore:16](file://.gitignore#L16)、[.gitignore:33](file://.gitignore#L33)），
故干净检出后直接 `go build` 会报 `pattern all:web: no matching files found`
（本次以最小临时模块实测复现）。

```bash
# 验证产物落位（期望 index.html 存在、总数约 454）；只改后端时跳过前端（build.sh:20-33）
```

### 首次安装向导

需要先纠正一个常见误解：**前端不存在 `/install` 路由页**。`web/app/(auth)/` 下只有 `login`、
`register`、`forgot-password` 等目录，安装态由登录页复用；`/install` 与 `/install/status`
只是后端端点（[router.go:75-76](file://main/internal/api/router.go#L75-L76)）。

### Docker 一键启动

镜像三阶段：`node:22-bookworm-slim` 出前端、`golang:1.26.2-bookworm` 交叉编译、
`gcr.io/distroless/static-debian12:nonroot` 运行。运行阶段 `WORKDIR /app` 由 root 持有却以

```bash

# 一键启动：卷映射宿主目录，密钥经环境变量注入，工作目录切到可写卷
docker run -d --name dnsplane \
  -p 127.0.0.1:8080:8080 \
  -v $HOME/dnsplane-data:/data \
  -w /data \
  -e DNSPLANE_JWT_SECRET='{JWT_SECRET_占位}' \
  -e DNSPLANE_MASTER_KEY='{MASTER_KEY_占位}' \
  dnsplane:local -config /data/config.json

# 验证：新卷首启应返回 installed=false；多架构推送走 docker-build.sh
curl -s http://127.0.0.1:8080/api/install/status
scripts/docker-build.sh --push v1.0.11
```

## 性能考虑

- **开发冷启动**：`next dev --turbopack`（[package.json:6](file://web/package.json#L6)）增量快，
  但生产构建显式走 `next build --webpack`（[package.json:8](file://web/package.json#L8)），
  目的是让本地产物与 CI 及镜像一致；不要为求快把 `build:ci` 换成 turbopack。
- **构建层缓存**：依赖清单与源码分层，`go mod download` 独立成层
  （[Dockerfile:19-20](file://Dockerfile#L19-L20)），前端同理（[Dockerfile:6-9](file://Dockerfile#L6-L9)）；
  层序颠倒会击穿缓存。前端只在 `BUILDPLATFORM` 构建一次（[Dockerfile:2-4](file://Dockerfile#L2-L4)），
  以规避多架构并行 `npm ci` 拖垮网络。
- **仅改后端时跳过前端**：`SKIP_FRONTEND=1 scripts/build.sh` 复用现有 `main/web/`
  （[build.sh:20-33](file://scripts/build.sh#L20-L33)），省掉一次完整 Next.js 构建；清理 `main/main`
  与 `main/data/` 等残留还可缩短 `docker build` 的上下文传输时间。
- **SQLite 吞吐**：DSN 固定 `journal_mode(WAL)`、`busy_timeout(5000)`、`mmap_size(67108864)`
  （[database.go:39-46](file://main/internal/database/database.go#L39-L46)），连接池上限 8
  （[database.go:54](file://main/internal/database/database.go#L54)），并全局关闭 GORM 默认事务
  （[database.go:78](file://main/internal/database/database.go#L78)）；三库分离让日志写入与业务
  写入互不排队（[database.go:105-118](file://main/internal/database/database.go#L105-L118)）。
- **Redis 收益与降级**：开启后请求日志与配置读取走缓存，`PING` 超时 3 秒即回退内存
  （[cache.go:69-83](file://main/internal/cache/cache.go#L69-L83)），功能不减但多实例不共享。
- **静态资源缓存头**：HTML 与 txt 为 `no-cache`，其余 `max-age=31536000` 并以 SHA-256 作 `ETag`
  支持 304（[router.go:384-405](file://main/internal/api/router.go#L384-L405)），
  与内容哈希文件名配套——只有 HTML 变更会被立即感知。

## 故障排查指南

### 问题 1：端口被占用，进程活着但没有服务

**症状**：日志先出现「服务器启动于 …」，紧接
`ERROR main.go:142 HTTP服务启动失败: listen tcp ...: bind: address already in use`；进程不退出。

**可能原因**：`ListenAndServe` 的错误只记日志、不触发退出（[main.go:140-144](file://main/main.go#L140-L144)）；
旧实例或其他程序占用同一端口。本次实测复现：第二次启动打印该错误且进程持续存活。

**排查步骤**：
1. `ss -ltnp | grep 8080` 看占用者，`pgrep -af dnsplane` 看自己的实例
2. 改 `server.port` 或用 `-config` 指定另一份配置，而不是盲目杀进程

**解决方案**：停掉旧实例后重启；生产环境用 systemd 或 compose 的 `restart` 策略保证单实例。
排障命令为 `ss -ltnp | grep -E '8080|8800'` 与 `curl -s http://127.0.0.1:8080/api/install/status`。

### 问题 3：CGO_ENABLED=0 与本地构建习惯冲突

**症状**：本地 `go build` 能出包，但交叉编译到 `arm` 或 `386` 时报找不到 C 编译器；
或照搬 `CGO_ENABLED=1` 后产物不再静态、目标机缺对应 glibc。

**可能原因**：本项目 SQLite 驱动是纯 Go 实现（[go.mod:9](file://main/go.mod#L9)、
[go.mod:85](file://main/go.mod#L85)），全仓无 `import "C"`，官方链路一律 `CGO_ENABLED=0`
（[Dockerfile:24](file://Dockerfile#L24)、[build.sh:52](file://scripts/build.sh#L52)、
[build.yml:140](file://.github/workflows/build.yml#L140)）；一旦开启 CGO，交叉编译就要求目标架构的 GCC。

**排查步骤**：
1. `go env CGO_ENABLED` 看当前默认
2. `grep -rn 'import "C"' main --include=*.go`（期望无输出）
3. 确认是否自行引入了 CGO 版 SQLite 驱动

**解决方案**：保持 `CGO_ENABLED=0`；确需 CGO 时改用目标架构的交叉工具链，
并接受产物不再完全静态。

## 结论

按「`go mod download` → `npm ci` → `npm run build:ci` → `go run .` → 浏览器 `/login` 初始化」四步，
即可得到可登录的 DNSPlane；这条链路每个环节都定位到了行号，编译、启动、安装、访问、关闭
五个可观察点均经本次实测确认。三点值得强调：

- **单一产物是设计核心**：前端只在构建期参与一次（`sync-main-web.cjs` 到 `go:embed`），
  运行期没有前后端两套进程，这也决定了「必须先建前端再编后端」的硬顺序。
- **同源假设贯穿全局**：`API_BASE = '/api'` 加静态导出让界面与后端同端口，代价是 `next dev`
  单独使用无法联调接口，且预检链路未覆盖 `OPTIONS`。
- **默认安全的取舍**：密钥随机生成、`0600` 落盘、不再硬编码默认账号、口令强度与 bcrypt 成本 12、
  登录默认带验证码——首启多几步操作，换来的是不存在默认凭据。

改进建议（本次未改动任何源码）：README 的 `bun run build` 与「Go 1.23+ / Node 20+」口径应与
`build:ci`、`go.mod:3`、`Dockerfile:4` 对齐；`.dockerignore` 建议补 `main/main`、`main/data/`、
`main/logs/`、`main/config.json`；若需版本自证应显式声明 `var Version` 并暴露只读端点。

[本节为总结，无需特定文件来源]

### Docker Compose 示例

仓库未提供任何 compose 文件（实测 `find` 全仓无 `*compose*`），以下示例按
[Dockerfile:32-37](file://Dockerfile#L32-L37) 的运行阶段约束与
[config.go:122-128](file://main/internal/config/config.go#L122-L128) 的环境变量口径编写。
启用其中 Redis 时，`config.json` 的 `redis.addr` 需写成 `redis:6379`；连接失败只告警并
回退内存缓存，不阻断启动（[cache.go:69-83](file://main/internal/cache/cache.go#L69-L83)）。

```yaml
services:
  dnsplane:
    image: dnsplane:local
    container_name: dnsplane
    restart: unless-stopped
    ports: ["127.0.0.1:8080:8080"]
    working_dir: /data
    command: ["-config", "/data/config.json"]
    environment:
      DNSPLANE_JWT_SECRET: "{JWT_SECRET_占位}"
      DNSPLANE_MASTER_KEY: "{MASTER_KEY_占位}"
    volumes: ["./dnsplane-data:/data"]
    networks: [dnsplane]

  redis:
    image: redis:7-alpine
    container_name: dnsplane-redis
    restart: unless-stopped
    command: ["redis-server", "--appendonly", "yes"]
    volumes: ["./dnsplane-redis:/data"]
    networks: [dnsplane]

networks:
  dnsplane:
    driver: bridge
```
