## 简介

DNSPlane 的插件化能力由**四个注册表扩展点**承载：DNS Provider（解析服务商）、Cert Provider（证书签发/账户提供商）、Deploy Provider（证书部署器）、Notify Channel（通知渠道）。四者共享同一套 Registry 模式：宿主包定义接口（`interface.go`）与注册函数（`registry.go` 的 `Register`/`RegisterChannel`），各实现子包在 `func init()` 中自我注册，入口 `main/main.go` 以 blank import 保证子包被链接进二进制。

本文是四个扩展点的**总览与选型指南**：给出共性骨架、逐项差异对照、装配行号取证，以及 Cloudflare「逃逸到独立 handler」这一反模式的原因与代价。逐扩展点的 step-by-step 实现教程由以下子文档承担（尚未生成，链接先行）：

- [DNS服务商扩展.md](./DNS服务商扩展.md)
- [证书提供商扩展.md](./证书提供商扩展.md)

## 详细组件分析

### DNS Provider 扩展

接口本体（实测 `dns/interface.go:41` 起）是「域名与解析记录 CRUD」抽象：`GetError`、`Check`、`GetDomainList`、`GetDomainRecords`、`GetSubDomainRecords`、`GetDomainRecordInfo`、`AddDomainRecord` 等 15 个方法（方法总数为素材口径，逐行清点见素材 interface.go:41-86）。

表单侧数据结构（实测行号）：

- `ProviderConfig`（:130）：`Type/Name/Icon/Note/Config/Features`
- `ConfigField`（:140）：`Name/Key/Type(input,select,radio)/Placeholder/Required/Options/Value`
- `ConfigOption`（:151）、`ProviderFeatures`（:157，9 个特性位：`Remark`(0/1/2)、`Status`、`Redirect`、`Log`、`Weight`、`Page`、`Add`、`RecordGroup`、`DomainAlias`）

可选接口按能力断言启用，不实现即不支持：`RecordGrouper`（:102）、`DomainAliaser`（:109）、`SubdomainDelegator`（:123）。

新增服务商的最小骨架：

```go
// main/internal/dns/providers/example/example.go
package example

import "main/internal/dns"

func init() {
	dns.Register("example", NewProvider, dns.ProviderConfig{
		Type: "example", Name: "示例服务商",
		Config: []dns.ConfigField{
			{Name: "API Token", Key: "token", Type: "input", Required: true},
		},
		Features: dns.ProviderFeatures{Page: true},
	})
}

type Provider struct{ token string }

func NewProvider(config map[string]string, domain, domainID string) dns.Provider {
	return &Provider{token: config["token"]}
}
// 其余至 15 个接口方法...
```

配套动作：在 `main.go:31-52` 字母序插入 `_ "main/internal/dns/providers/example"`。表单枚举与实例构造均由注册表驱动，**无需改动 handler 或路由**（素材口径：消费点 `handler/account.go:445`）。

### Cert Provider 扩展

证书扩展点是四个中唯一存在**两段协议**的：`cert` 包自身的 `providers.go` 在包级 `init()` 先注册完整表单（`ProviderConfig`），实现子包（acme/aliyun/huoshan/tencent）在各自 `init()` 中 `cert.Register` 补工厂——同 name 二次覆盖 map 项，后注册者以「带工厂的配置」覆盖「仅有表单的配置」。


### Deploy Provider 扩展

部署器的真实宿主是 `deploy/base`（`DeployProvider` 接口 base.go:45，工厂 :77，`Register(name, factory)` :85，`GetProvider` :92）。`deploy/registry.go` 仅做两件事：类型别名与函数包装保持向后兼容（:9-16），以及实现**四段键解析**（:27 起，实测逐段）：

1. 直接用账户类型查（如 `doge`、`qiniu` 无子产品类型）
2. `taskConfig["product"]` 组合 `{type}_{product}`（如 `tencent` + `cdn` → `tencent_cdn`）
3. `accConfig["product"]` 同样组合（兼容旧数据）
4. 常见后缀回退 `cdn/acm/cloudfront`

配套的配置合并（`config.go` 及 `config_cloud/selfhosted/server.go`、`MergeDeployProviderConfigsForAPI`）负责把 cert 视图与 `DeployProviderConfig`（Class/Inputs/TaskInputs）对齐；素材将「两份配置 + 四段回退」列为**当前最脆弱的扩展点**——探针显示 `deployCfgWithoutImpl` 有 11 项、`baseImplsWithoutCertDeployCfg` 有 52 项（数量素材口径）。

### Notify Channel 扩展

通知渠道是设计上的正面样板：`Channel` 接口把「渠道标识 / 显示名 / 配置键 / 启用开关 / 容灾告警开关 / 构造方式」聚合在一处（channel_registry.go:20-33 的 6 方法），使装载方遍历注册表而不写 if 块。文件头注释（:8-18）明说动机：此前 monitor、dashboard 等三处装载各自维护渠道清单且已发生分叉。

实测注册方式：同包单文件 `channel_adapters.go` 的 `init()` 一次性 `RegisterChannel` 13 个渠道（:330-344，逐行确认：mail、telegram、webhook、customWebhook、discord、bark、wechatWork、dingTalk、feishu、wxWorkApp、wxTpl、wxPusher、qqBot）。`Build` 返回 `(Notifier, bool)`，配置不全或渠道关闭时 `ok=false`，把「装不上」与「出错」分离。

新增渠道只需两步：实现 `Channel` 6 方法 + 在 `init()` 加一行注册。**无需 blank import（同包），重复 Type 会 panic（素材口径）**，配置键清单由 `ChannelConfigKeys`（:108）自动推导，素材称其为「全库唯一满足开闭原则的扩展点」。专项教程见 [部署器扩展.md](./部署器扩展.md) 与 [DNS服务商扩展.md](./DNS服务商扩展.md) 之外的第四篇：[面板集成扩展.md](./面板集成扩展.md) 不涉及通知；通知渠道的 step-by-step 归入本总览的附录检查表。

show 条件求值的核心实现（逐字实测）：

```ts
// web/lib/deploy-config-form.ts（evalOne 片段，:12-24）
const evalOne = (condition: string): boolean => {
  const c = condition.trim()
  if (c.includes('!=')) {
    const [key, val] = c.split('!=').map(stripQuotes)
    return (values[key] ?? '') !== val
  }
  if (c.includes('==')) {
    const [key, val] = c.split('==').map(stripQuotes)
    return (values[key] ?? '') === val
  }
  return true
}
```

### Cloudflare 为何逃逸到独立 handler

DNS Provider 注册表假设能力可被「记录 CRUD + 固定特性位」表达，Cloudflare 是实测反例（构件规模素材口径，路由面为工作区实测）：

| 构件 | 规模 | 与抽象的关系 |
| --- | --- | --- |
| `providers/cloudflare/cloudflare.go` | 503 行 | 正常实现 `dns.Provider`，未实现可选接口 |
| `handler/cloudflare.go` | **2509 行，全库第一大文件** | **完全绕过 `dns.Provider`**，走 `service.EnhanceService` |
| `service/cloudflare_enhance.go` | 733 行 | 自建 HTTP 客户端/认证/分页 |
| `handler/acceleration.go` | 498 行 | `Platform: "cloudflare"` 硬编码 |
| `models/cloudflare.go` | 79 行 | 4 张专属表（Hostname/Tunnel/CIDRRoute/HostnameRoute） |

逃逸的三点根因（均为接口层面的硬缺口）：

1. `dns.Provider` 是解析记录抽象（interface.go:41-86 全为域名/记录方法），自定义主机名、Tunnel、CIDR 路由、DCV 委派、Fallback Origin **没有能落进该接口的形状**，三个可选接口也仍是记录语义。
2. `ProviderFactory` 入参只有 `(config, domain, domainID)`（registry.go:9），**账户级、跨 zone 资源无法用该签名构造**——Tunnel/CIDR 都是 account 级，抽象缺 `AccountProvider` 这一层。
3. `ProviderFeatures` 是固定布尔位（interface.go:157-167），无法声明「支持隧道」这类新维度，加位即触碰全部 provider。

代价（实测路由 + 素材取证）：认证逻辑与 base URL 各两份实现；「逃逸文件」仍反向依赖被逃逸的抽象 3 处（取显示名、默认线路、挑战记录）；`account.Type != "cloudflare"` 硬门使同类能力必须复制 handler；`main/internal/api/router.go:297-316` 为其注册了 20 条专属路由，新增能力同时触碰 router/service/handler 三层。

交叉阅读：[Cloudflare DNS.md](../DNS管理功能/支持的DNS服务商/Cloudflare%20DNS.md)。选型启示：**新服务商若能力仍是「记录 CRUD 变体」，走注册表；若引入账户级新资源维度，先评估是否会被迫走 Cloudflare 模式**。

## 性能考虑

注册表本身的运行期成本可以忽略，但有三处值得知晓的取舍（实测代码）：

- **锁策略一致**：写路径（Register）持写锁且只发生在 init 阶段，读路径（GetProvider 等）用读锁；热路径实际是无竞争的只读 map 查询。
- **快照拷贝**：`GetAllProviderConfigs`（dns/registry.go:48-55）每次返回新建 map 深一层拷贝，防止外部改写注册表；调用频率为表单枚举级（低频），代价可接受。
- **注册即常驻**：map 项生命周期等于进程，工厂按次调用构造实例（dns/registry.go:36），实例不缓存——每次操作服务商都是新对象，避免共享可变状态，代价是重复构造（字符串 map 级开销，可忽略）。
- **新增服务商的成本模型**：纯编译期增量（多一个包、init 多执行一次 Register），无运行时开关、无动态加载；想「不重编译换服务商」在本架构下不存在。

## 结论

- 四扩展点共享「接口 + Register + init 自注册 + blank import 链接」骨架，但成熟度分层明显：**notify 最干净（开闭原则成立）→ dns 规整（注册表全驱动）→ cert 依赖无守护的初始化次序 → deploy 最脆弱（双层配置 + 四段键回退）**。
- 最大的静默风险是 blank import 遗漏（main.go:31-52 为唯一链接保证，ucloud 是现成反例）；唯一的显性风险是 notify 的重复 Type panic。
- Cloudflare 证明了抽象边界的价值与局限：接口表达不了的账户级新资源会催生 2509 行独立 handler；扩展选型前必须先判定能力形状。
- 子文档落地后，本文的 step-by-step 细节（含示例代码、完整方法清单）应移入四篇扩展教程，本文保持总览职责。
