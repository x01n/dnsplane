## 简介

本文是「新增一个证书签发渠道」的端到端实现教程。与 DNS 扩展点最大的差别在于：
证书注册表同时容纳「签发」与「部署」两类视图，并存在**表单与工厂分离的双阶段注册**约定。
全部结论来自当前工作区实测。关键事实：

- `cert.Provider` 接口共 9 个方法，声明在 `main/internal/cert/interface.go:52-79`。
  注册入口 `cert.Register(name, factory, config)`（`cert/registry.go:23-35`）不是简单覆盖：
  `factory != nil` 才写工厂（`:27`）；`config.Type == "" && hadCfg` 时跳过配置写入（`:31-33`）。
  这两条构成「先登记表单、后补工厂」的语义基础。
- 装配靠 `main/main.go:27-30`，**只有 4 行**：`acme`、`aliyun`、`huoshan`、`tencent`。
  `ucloud` 不在其中，其 `init()`（`ucloud.go:24`）永不执行，注册表里的 `ucloud` 实际来自
  `providers.go:549`（`IsDeploy: true`、工厂 `nil`）。这是本仓库现存的活反例。
- **证书账户创建不校验渠道是否存在**：`handler/cert.go:152` 的 `CreateCertAccount`
  只做 JSON 绑定与入库，不像 DNS 侧 `handler/account.go:216` 那样查注册表白名单。
  未注册的渠道能建账户，直到真正签发时才在 `cert.GetProvider` 报错。
- 签发与部署的边界由 `ProviderConfig.IsDeploy`（`interface.go:91`）切分，
  两个视图分别由 `GetCertProviderConfigs()`（`registry.go:71-81`）与
  `GetDeployProviderConfigs()`（`registry.go:95-105`）导出。

## 详细组件分析

本节按「一个实现一节」推进，每节内部拆为接口约定、注册写法、调用与消费。

### 新增证书渠道文件模板

#### 接口约定

最小可编译骨架，采用「子包带完整表单」写法（`huoshan` 风格）：

```go
package myca

import (
	"context"
	"main/internal/cert"
)

/* Provider 示例证书渠道 */
type Provider struct {
	appKey string
	secret string
	logger cert.Logger
	// apiURL 独立成字段便于测试注入本地服务端，生产路径始终用默认端点
	apiURL string
}

func init() {
	cert.Register("myca", NewProvider, cert.ProviderConfig{
		Type: "myca",
		Name: "示例 CA",
		Note: "签发前需在控制台完成实名认证",
		Config: []cert.ConfigField{
			{Name: "AppKey", Key: "app_key", Type: "input", Required: true},
			{Name: "AppSecret", Key: "app_secret", Type: "input", Required: true},
		},
		CNAME:    false,
		IsDeploy: false,
	})
}

/* NewProvider 工厂签名必须与 registry.go:9 一致 */
func NewProvider(config, ext map[string]interface{}) cert.Provider {
	return &Provider{appKey: getString(config, "app_key"), secret: getString(config, "app_secret")}
}
```

`apiURL` 不是可选装饰。`aliyun/aliyun.go:46-47` 与 `tencent/tencent.go:52-53` 都用
「端点做成可注入字段」来支撑 `httptest` 假服务端，`aliyun_test.go:53-60` 的
`newTestProvider` 直接把它指到 `srv.URL + "/"`。不预留该字段，测试只能打真实 CA。

#### 注册写法

两种风格必须择一，不可混用同一条 `Register`：

| 风格 | 代表 | 写法 | 适用 |
| --- | --- | --- | --- |
| 子包带完整表单 | `huoshan.go:27`、`ucloud.go:24` | `cert.Register(key, NewProvider, cert.ProviderConfig{Type: key, ...})` | 新渠道首选，自包含 |
| 表单在宿主、工厂在子包 | `tencent.go:42`、`aliyun.go:37`、`acme.go:70/73/76` | 子包传 `cert.ProviderConfig{}`，`Type` 留空 | 表单已在 `providers.go` 登记时 |

选第二种的前提是 Go 的包初始化顺序：`cert` 包 `init()` 必定早于其依赖者
（`acme`/`tencent`/`aliyun`/`huoshan`）执行，所以「先有表单、后补工厂」成立。
`providers.go:45-50` 的注释显式锁定该约定并警告：若移除该处登记而子包不带完整表单，
`/api/cert/providers` 会丢字段。**该前提没有任何测试守护。**

#### 调用与消费

`CNAME` 与 `IsDeploy` 决定渠道出现在哪个视图：`IsDeploy` 由 `registry.go:76`/`:88`/`:100`
路由到签发视图或部署视图，`CNAME` 由 `handler/cert.go:673` 读取以决定是否允许 CNAME 凭证签发，
`DeployConfig` 经 `merge_deploy_api.go` 供 `deploy/page.tsx:125` 渲染部署任务字段。
`huoshan.go:36-38` 记录了一个易错点：同一名字可在签发视图与部署视图各有一份定义——
火山的部署用途由 `deploy/config_cloud.go` 提供并经 `MergeDeployProviderConfigsForAPI`
输出到 `deploy` 视图，与 `cert/huoshan/huoshan.go` 的签发注册互不覆盖。

### CertProvider 九方法逐项实现

#### 接口清单与契约

按 `interface.go:52-79` 声明顺序：

| 方法 | 声明行 | 返回契约 | 实测要点 |
| --- | --- | --- | --- |
| `Register(ctx)` | 54 | `(map[string]interface{}, error)` | 返回值实测四处全为 `nil` map，仅作凭据探测 |
| `BuyCert(ctx, domains, order)` | 57 | `error` | 语义是「额度/前置资源检查」，不是真购买 |
| `CreateOrder(ctx, domains, order, keyType, keySize)` | 60 | `(map[string][]DNSRecord, error)` | 唯一返回验证记录的方法 |
| `AuthOrder(ctx, domains, order)` | 63 | `error` | 触发 CA 校验 |
| `GetAuthStatus(ctx, domains, order)` | 66 | `(bool, error)` | 返回「是否全部通过」，非终态返回 `false, nil` |
| `FinalizeOrder(...)` | 69 | `(*CertResult, error)` | 产出 PEM |
| `Revoke(ctx, order, pem)` | 72 | `error` | 吊销 |

四条跨方法硬约定：`OrderInfo` 是**跨请求可变载体**，`CreateOrder` 必须把上游订单标识写进
`order.OrderURL` 等字段供后续方法续接（`handler/cert.go:668-670` 在返回后立即
`json.Marshal(orderInfo)` 落库）；返回 map 的键是域名、值是该域名需要的记录列表，
`certCountChallengeRecords`（`cert.go:341`）据此统计 DNS 类与 http-01 类条数；
`getMainDomain` 在三个包内各自存在（`aliyun.go:505`、`tencent.go:488`、`acme.go:799`）
用于裁掉验证记录名的主域后缀，`aliyun_test.go:260` 专门锁定该裁剪；
`buildCertResult` 同样包内各自实现（`aliyun.go:486`、`tencent.go:469`），
负责解析 PEM 填 `ValidFrom`/`ValidTo`。

#### 分渠道实现差异

九个方法中真正分化的是 `Register`、`BuyCert`、`CreateOrder`、`FinalizeOrder`：

| 方法 | `acme` | `aliyun_cert` | `tencent` | `huoshan` |
| --- | --- | --- | --- | --- |
| `Register` | `acme.go:487` 真实注册账户，返回账户 URL 与私钥 | `aliyun.go:89` 校验必填后打 `ListInstances` | `tencent.go:100` 校验必填后打 `DescribeCertificates` | `huoshan.go:78` 直接打 `CertificateGetInstance`，**不校验必填** |
| `BuyCert` | `acme.go:573` 空实现 | `aliyun.go:102` 查 `InactiveCount`，为 0 报「请先购买测试证书」 | `tencent.go:111` 直接 `return nil` | `huoshan.go:87` 查组织模板，缺失报「请先添加信息模板」 |
| `CreateOrder` | `acme.go:577` 走 new-order，返回 DNS-01 TXT | `aliyun.go:122` 申请后轮询 `GetTaskAttribute` 再 `GetInstanceDetail` 组装 | `tencent.go:118` 申请后由 `buildDNSRecords`(`:158`) 组装 | `huoshan.go:114` 在 `:179` 组装 `dnsRecords` |
| `FinalizeOrder` | `acme.go:887` finalize + 轮询下载 | `aliyun.go:281` 取回证书内容 | `tencent.go:240` **下载 zip 再解包**：`download`(`:397`) → `extractCertificate`(`:421`) → `readZipEntry`(`:456`) | `huoshan.go:255` |

`Register` 的 map 返回值设计上是「预留位」：ACME 需要把 `account_key`/`account_url`
回填到 `ext` 供下次实例化使用，云证书渠道无账户概念故统一返回 `nil`。
新渠道若无状态可回填，返回 `nil, nil` 即可，但**必须做凭据探测**，
否则表单填错要到签发时才暴露。

### registry 双阶段注册机制

#### 接口约定

`cert.Register`（`registry.go:23-35`）是四个注册表中唯一带条件分支的：

```go
func Register(name string, factory ProviderFactory, config ProviderConfig) {
	providersMu.Lock()
	defer providersMu.Unlock()
	_, hadCfg := configs[name]
	if factory != nil {
		providers[name] = factory
	}
	// acme 包 init 会用空 ProviderConfig 仅补全工厂，避免覆盖 providers.go 中的名称/说明/表单字段
	if config.Type == "" && hadCfg {
		return
	}
	configs[name] = config
}
```

由此推出四种确定行为：

| 入参组合 | 工厂表 | 配置表 | 语义 |
| --- | --- | --- | --- |
| `factory != nil` + `Type` 非空 | 写入 | 整体覆盖 | 一步到位（`huoshan`、`ucloud`） |
| `factory != nil` + `Type` 为空 | 写入 | 保持不变 | 只补工厂（`tencent`、`aliyun_cert`、`google` 等） |
| `factory == nil` + `Type` 非空 | **不动** | 整体覆盖 | 只登记表单（`providers.go` 全部条目） |
| `factory == nil` + `Type` 为空 | 不动 | 覆盖为空配置 | 破坏性写法，禁止使用 |

与 DNS 侧的关键差异：`dns.Register`（`dns/registry.go:18-23`）无条件写两张 map，
允许把已有工厂覆盖成 `nil`；`cert` 侧的 `factory != nil` 判断使「表单后到」不会摧毁实现。

#### 注册写法

`providers.go` 的 5 条签发登记全部 `factory = nil`：`google`(:11)、`litessl`(:33)、
`tencent`(:51)、`aliyun_cert`(:65)、`customacme`(:81)；部署登记自 `:95` 起，
其中 `ucloud`(:549) 是 `IsDeploy: true` + `nil` 工厂。新渠道**不要**往 `providers.go`
加表单条目，除非同时确保某子包会补工厂；按 `huoshan` 风格在子包内一次写全是当前最安全的路径。

#### 调用与消费

视图切分完全靠 `IsDeploy`：`GetCertProviderConfigs`（`:71-81`）取 `!IsDeploy`、
`GetDeployProviderConfigs`（`:95-105`）取 `IsDeploy`、`GetAllProviderConfigs`
（`:60-68`）不过滤。部署视图还要经 `MergeDeployProviderConfigsForAPI`
（`merge_deploy_api.go:5`）合并，它在 `:40` 回查 `cert.GetProviderConfig(typ)`

### 云证书渠道与部署器的边界

#### 接口约定

证书扩展点有三个互不相同的抽象：`cert.Provider`（`cert/interface.go:52`，9 方法，
**签发**证书产出 PEM）、`base.DeployProvider`（`deploy/base/base.go:45`，仅

「云证书上传」在不同渠道落在不同抽象，这是新渠道最容易选错的位置：

| 需求 | 应实现 | 依据 |
| --- | --- | --- |
| 向上游 CA 申请一张新证书 | `cert.Provider.CreateOrder` + `FinalizeOrder` | `aliyun.go:122`/`:281` |
| 把已签发证书推到云厂商 CDN | `base.DeployProvider.Deploy` | `deploy/providers/*`，注册键如 `aliyun_cdn` |

### 与 ACME 渠道的分界

#### 接口约定与判定标准

`cert/acme/acme.go` 用一个 `ACMEClient` 结构体承接 5 个渠道（`letsencrypt`:46、
`zerossl`:57、`google`:70、`litessl`:73、`customacme`:76），差异全落在构造函数的
`directoryURL`、`email`、`eabKID`、`eabHMACKey` 四个字段（`:100-216`）。「何时该走 `acme/`」
的实测判据：

| 条件 | 归属 | 理由 |
| --- | --- | --- |
| 上游实现 RFC 8555（newAccount/newOrder/authorization/finalize） | `acme/` | 九步流程完全复用，只需新增构造函数 |
| 需要 EAB 凭证 | `acme/` | `createEAB`（`acme.go:541`）已实现，`google`/`litessl`/`zerossl` 共用 |
| 需要自定义 directory URL，或要支持 `http-01` | `acme/` | `customacme`(`:76`) 即为此存在；只有 `acme` 读 `PreferredChallenge` |
| 上游返回「工单 + 轮询 + 证书包」，甚至返回 zip/tar 而非 PEM 链 | 独立子包 | `aliyun`/`tencent`/`huoshan`/`ucloud` 全属此类；`tencent.go:421` 的解包逻辑是渠道专有 |
| 需要联系人姓名/手机号等实名字段 | 独立子包 | `providers.go:70-73` 的 `username`/`phone` 仅云证书用 |

判定为 ACME 渠道时最小改动是在 `acme.go` 加一个构造函数与一条 `Register`，**不需要新建子包**：

```go
func NewMyACMEProvider(config, ext map[string]interface{}) cert.Provider {
	client := &ACMEClient{
		directoryURL: "https://example-acme/dir",
		email:        getString(config, "email"),
		eabKID:       getString(config, "kid"),
		eabHMACKey:   getString(config, "key"),
		client:       &http.Client{Timeout: 30 * time.Second},
	}
	if ext != nil {
		if key, ok := ext["account_key"].(string); ok {
			client.accountKey = parsePrivateKey(key)
		}
		if url, ok := ext["account_url"].(string); ok {
			client.accountURL = url
		}
	}
	return client
}
```

`acme.go` 已实现 `Revoke`(:1032) 与 `Cancel`(:1050)，新渠道直接免费获得。

#### 调用与消费

ACME 的 DNS-01 落地不在 `acme` 包内，而在 handler：`CreateOrder` 返回
`map[string][]cert.DNSRecord` 后，由 `handler/cert.go:977` 调 `dns.EnsureChallengeRecord`
写入解析；`certPreVerifyDNS`（`:1401`）在触发 CA 校验前用公共 DNS 复查 TXT 是否生效，
注释明确「仅做等待确认，不做无效修复」。这条边界值得记住：**证书渠道包永远不要直接依赖
`internal/dns`**，写解析的职责在编排层，渠道包只负责返回「需要哪些记录」。

## 性能考虑

- **HTTP 超时统一 30s。** ACME 各构造函数都写 `&http.Client{Timeout: 30 * time.Second}`
  （`acme.go:106`/`:122`），新渠道请对齐该值。
- **ACME 有完整退避，云证书渠道普遍没有。** `acmeClampRetry`（`acme.go:252`）与
  `acmeComputeRetryWait`（`:265`）读 HTTP 头与响应体计算等待时长并夹紧上限；
  `aliyun`/`tencent`/`huoshan`/`ucloud` 的 `request` 内**没有** 429 或退避处理，限流直接以
  error 冒泡。上游配额严格需自行实现。
- **轮询型渠道要显式设上限。** `aliyun.go:210` 的 `waitTaskDone` 是任务轮询，
  `tencent.go:240` 的 `FinalizeOrder` 走下载解包；不加次数上限订单会长期停在中间态。
- **合并视图每请求重算。** `GetCertProviders`（`cert.go:1387`）每次调
  `GetCertProviderConfigs()` + `MergeDeployProviderConfigsForAPI(GetDeployProviderConfigs())`，
  两个视图函数各全表拷贝（`registry.go:74-80`/`:98-104`）。`registry.go:16` 的注释
  自己说明「提供商在 init 中注册完毕后不变」，`APIProvidersSnapshot`（`:108-114`）
  正是为此设计但无调用方；45 键量级下影响可忽略。
- **日志回调是订单日志唯一出口。** `SetLogger` 在九步之前调用，各包用 `p.log(...)` 包裹
  （`aliyun.go:83`、`tencent.go:91`、`huoshan.go:72`、`ucloud.go:73`、`acme.go:246`），
  新渠道必须实现并在关键分支打点，否则订单日志页对你是空白。

| DNS-01 写记录失败 | `dns.GetProvider` 报错 | 是 DNS 账户问题不是渠道问题，看 `cert.go:964-970` |
| `GetAuthStatus` 恒 false | 上游验证未过或轮询判错 | `aliyun.go:260`、`tencent.go:217`、`acme.go:827` |
| `FinalizeOrder` 无 PEM | 上游返回 zip 而非证书链 | `tencent.go:421` 的 `extractCertificate` 是这类渠道必写辅助 |

## 结论

本文给出的是「先判归属、再选注册风格、最后接前端」的落地路径。

- 第一步不是写代码，是判定归属：走 `acme/`（RFC 8555 兼容）还是独立子包（工单式云证书），
  核心区分是**协议形态**而非品牌。
- 第二步选注册风格。**新渠道一律推荐 `huoshan` 风格的子包一次写全**（`Type` 非空 +
  真实工厂），因为它不依赖包初始化顺序这条无测试守护的前提。
- 第三步补 `main.go:27-30` 的 blank import。`ucloud` 是最有力的反例：445 行完整实现
  因缺一行导入成为死包，注册表里只剩一条 `IsDeploy: true` + `nil` 工厂。
- 双阶段注册带来三种合法组合与一种破坏性写法，`registry.go:23-35` 的四个分支必须逐一理解，
  否则会写出「表单在宿主、工厂在子包、子包忘了链接」的静默残缺态。
- 前端只需登记 `CERT_CATEGORIES` 与 `providerStyles` 两处，`api.ts` 不用改；但注意
  `CertProvider`（`api.ts:1303`）声明了后端不存在的 `max_domains`/`wildcard`，
  这是已存在的契约漂移，不要在其上追加假设。已知缺陷本文只记录不修复：
  `CreateCertAccount` 缺白名单校验、`APIProvidersSnapshot` 是死代码、`ucloud` 未链接、
  `CERT_CATEGORIES` 含陈旧项、云证书渠道无限流退避、`cert.Provider` 无列表方法。
