## 简介

本文给出 DNSPlane 在**本机开发场景**下的完整搭建路径：前置依赖校验、双端依赖安装、
后端与前端各自启动、首次安装向导、配置注入、数据与日志目录初始化，以及本仓库实测过的环境坑。

DNSPlane 以「单一 Go 二进制」为交付形态：Next.js 静态导出产物在编译期被
`//go:embed all:web` 打进可执行文件，运行时由同一个 Gin 进程同时提供 `/api` 与页面。
这决定了开发环境存在**两种工作模式**，且可用能力不同，详见下文「前端启动」一节。

## 项目结构

仓库为「两个平级模块 + 脚本层」的组织方式，开发环境需要同时理解两侧：

```
dns/
├── main/                       # Go 后端（module main）
│   ├── main.go                 # 入口：flag -> config -> database -> cache -> router
│   ├── go.mod                  # go 1.26.2
│   ├── config.json             # 工作区实际配置（端口 8800、debug）
│   ├── data/                   # SQLite 数据目录（运行时创建）
│   ├── logs/                   # 文本日志目录（运行时创建）
│   ├── web/                    # 前端产物落地目录（被 embed）
│   └── internal/{api,cache,config,database,dns,cert,monitor,service,...}
├── web/                        # Next.js 16 前端
│   ├── app/ components/ lib/ contexts/
│   ├── next.config.ts          # output: 'export'
│   ├── bun.lock / package-lock.json
│   └── scripts/sync-main-web.cjs
└── scripts/                    # build.sh / docker-build.sh
```

| 目录 | 开发环境中的职责 | 是否需要手工创建 |
|------|------------------|------------------|
| `main/` | `go run .` 的工作目录，`-config` 相对路径以此为基准 | 否 |
| `main/data/` | 主库 `data.db`、`logs.db`、`request_logs.db` | 由 `database.Init` 自动创建 |
| `main/logs/` | 按日期切分的文本日志 `<YYYY-MM-DD>.log` | 由 `logger` 自动创建 |
| `main/web/` | 前端静态产物落地处，被 `embed` 编译进二进制 | 由 `build:ci` 生成 |
| `web/` | `next dev --turbopack` 的工作目录 | 否 |
| `web/out/` | `next build` 的静态导出结果 | 由构建生成 |
| `scripts/` | 一键构建与镜像构建 | 否 |

## 核心组件

开发环境由四组组件构成，任一组缺失都会导致启动失败或功能退化：

| 组件 | 最低要求 | 缺失后果 | 实测证据 |
|------|----------|----------|----------|
| Go 工具链 | 声明版本 `1.26.2`；本机 `1.27.2` 可用 | 无法编译；`-lang` 由 `go.mod` 决定而非工具链版本 | `devlog.md` 模块 8 兼容性审计：`go build ./...` = 0 |
| Node 或 Bun | 官方镜像 `node:22`；本机 `v24.19.0` / `bun 1.4.0` | 前端无法构建，二进制中没有新页面 | `Dockerfile`、本次 `node --version` |
| SQLite | 无需系统包（纯 Go 驱动） | 无 | `glebarez/sqlite`；`scripts/build.sh` 使用 `CGO_ENABLED=0` |
| Redis（可选） | `enable=false` 时可完全不用 | 自动回退内存缓存，功能不中断 | `cache.Init`：Ping 3s 超时后 `NewMemoryCache` |

关键判读：

- **Go 版本不需要与 `go.mod` 严格相等**。`devlog.md` 记录了一次最小复现：`go.mod` 写 `go 1.26.2`、
  本机 `go1.27.1`、不带 `-gcflags` 时，Go 1.27 的嵌入字段新写法 `Emb{Base.Name: "x"}` 直接编译失败，
  结论是「`-lang` 默认取 `go.mod` 声明值，本机不会比 CI 更宽松」。
- **Bun 与 npm 并存**。`web/` 下同时存在 `bun.lock` 与 `package-lock.json`；
  `scripts/build.sh` 的优先级是「`bun` 可执行且 `bun.lock` 存在 → `bun install --frozen-lockfile`」，
  否则 `npm ci`。开发机只装其中一个即可。
- **Redis 不是硬依赖**，但 `main/config.json` 当前写的是 `enable: true`，
  本机若无 Redis，会在启动日志看到回退警告（属预期行为，不是故障）。

## 详细组件分析

### 5.1 前置依赖校验

先把本机版本读出来，再与仓库要求对照，避免后面把「环境问题」误判为「代码问题」：

```bash
# 在项目根目录执行
go version                       # 期望 >= go1.26 工具链；本机实测 go1.27.2
node --version                   # 官方镜像为 node:22；本机实测 v24.19.0
bun --version 2>/dev/null || echo "bun 未安装，将使用 npm"
npm --version
git rev-parse --is-inside-work-tree

# SQLite 不需要系统包：驱动是纯 Go 实现
rg -n "glebarez/sqlite|CGO_ENABLED" main/go.mod scripts/build.sh
```

判定规则：

| 检查项 | 通过标准 | 不通过的处理 |
|--------|----------|--------------|
| Go 工具链 | `go version` 主版本 ≥ 1.26 | 升级 Go；无法升级时用 `-gcflags="-lang=go1.26"` 复现 CI 语义 |
| Node | ≥ 20（`README.md` 开发说明） | 用 `fnm`/`nvm` 切到 22 |
| 包管理器 | `bun` 或 `npm` 至少一个可用 | 二者皆无则前端无法构建 |
| Redis | 可无 | `config.json` 把 `redis.enable` 置 `false`，或接受内存回退 |

### 5.2 获取代码与安装依赖

```bash
# 1) 克隆
git clone <仓库地址> dnsplane && cd dnsplane

# 2) 后端依赖（首次建议显式下载，便于观察网络失败）
cd main
go mod download
go build ./...          # 验证依赖闭包完整

# 3) 前端依赖：Bun 优先（仓库存在 bun.lock）
cd ../web
bun install --frozen-lockfile

# 或者没有 Bun 时使用 npm
npm ci
```

依赖安装的三条实测约束：

- `README.md` 写的是 `go mod tidy`，而 `tidy` 会**改写** `go.mod`/`go.sum`。日常拉取建议 `go mod download`，
  只在确实增删依赖时才 `tidy`，避免无关 diff。`--frozen-lockfile` / `npm ci` 同样是**锁文件优先**，
  与 `scripts/build.sh` 一致并可复现 CI；`bun install` / `npm install` 允许解析漂移，仅适合主动升级。
- `devlog.md` 记录过 `go build -mod=vendor -o /tmp/testbuild .` 返回 `BUILD_EXIT=1`：
  仓库**没有 `vendor/` 目录**，不要照搬需要 vendor 的构建习惯。
- `devlog.md` 另有一条「`web/` 编译验证（`node_modules` 缺失）需 `npm ci`」，
  说明前端依赖缺失是历史验证中断的真实原因之一。

### 5.3 后端启动

后端只有一条命令，但 `-config` 的解析基准是**当前工作目录**，不是可执行文件所在目录：

```bash
cd main

# 方式 A：使用工作区已有配置（端口 8800、mode=debug、data/data.db）
go run .

# 方式 B：显式指定配置文件
go run . -config config.json

# 冒烟验证（另开终端）
curl -sS http://127.0.0.1:8800/api/install/status
curl -sS -o /dev/null -w "%{http_code} %{redirect_url}\n" http://127.0.0.1:8800/
```

实测要点：

| 项 | 结论 | 证据 |
|----|------|------|
| 入口参数 | `flag.String("config", "config.json", ...)` | `main/main.go` |
| 监听地址 | `fmt.Sprintf("%s:%d", cfg.Server.Host, cfg.Server.Port)` | `main/main.go` |
| 读超时 | `ReadHeaderTimeout: 30s`、`IdleTimeout: 120s` | `main/main.go` |
| Gin 模式 | 仅当 `server.mode == "release"` 才 `gin.SetMode(gin.ReleaseMode)` | `main/main.go` |
| 工作区端口 | `8800` | `main/config.json` |

`go run .` 与 `go build` 都会触发 `main/web/` 的 `embed`。若 `main/web/` 是旧产物，
后端会**成功启动但页面是旧的**，不会报错——这是最常见的「改了前端没生效」误判来源。

### 5.4 前端启动与「dev 代理」实测结论

```bash
cd web
bun run dev          # 等价于 next dev --turbopack
# 或
npm run dev
```

`next dev --turbopack` 会在 `http://localhost:3000` 提供开发服务器。但本仓库
**没有任何 dev 代理配置**，实测依据：

- `web/next.config.ts` 只设置 `output: 'export'`、`trailingSlash: true`、`images.unoptimized`，
  **没有 `rewrites`/`redirects`/`proxy` 字段**。
- `web/lib/api.ts` 第一行是 `const API_BASE = '/api'`，即所有请求走**同源相对路径**。
- 全仓库 `web/app`、`web/components`、`web/contexts` 内除一处 Tunnel 表单占位文案外，
  没有硬编码 `8080`/`8800` 的后端地址。

结论（已验证）：单独运行 `next dev` 时，浏览器向 `:3000/api/*` 发请求会得到 404，
前端页面能渲染但**任何接口调用都失败**。这不是 bug，而是「静态导出 + 单二进制」架构的固有约束——
`output: 'export'` 模式下 Next 没有服务端运行时，无法承担代理。

因此开发时应在两条路径中选择：

```mermaid
flowchart TD
Q{改的是什么} -->|只改后端 Go| P1["路径一：go run .<br/>只访问 :8800<br/>页面用 embed 的旧产物"]
Q -->|只改前端| P2{"需要调真实接口?"}
P2 -->|不需要，纯样式/静态| P3["路径二 A：next dev :3000<br/>接口必然 404，可接受"]
P2 -->|需要| P4["路径二 B：bun run build:ci<br/>同步到 main/web<br/>再 go run . 访问 :8800"]
P4 --> P5["迭代成本高，但唯一<br/>端到端真实链路"]
```

**图表来源**
- [web/next.config.ts](file://web/next.config.ts)
- [web/lib/api.ts](file://web/lib/api.ts)
- [web/package.json](file://web/package.json)

**建议（未执行，需自行验证）**：若希望 `:3000` 也能直通后端，可在
`next.config.ts` 增加 `rewrites` 把 `/api/:path*` 指向 `http://127.0.0.1:8800/api/:path*`。
但 `output: 'export'` 与 `rewrites` 互斥，添加后 `next build` 会失败，
因此这只能是**临时本地改动，禁止提交**。本文不推荐把它当作标准流程。

### 5.5 首次安装向导与管理员创建

后端启动后，安装状态由用户表行数决定，而非任何标志文件：

```bash
# 1) 查询安装状态
curl -sS http://127.0.0.1:8800/api/install/status
# 未安装：{"code":0,"data":{"installed":false}}

# 2) 创建管理员（口令须满足复杂度）
curl -sS -X POST http://127.0.0.1:8800/api/install \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"{至少8位含大小写与数字}"}'

# 3) 复查
curl -sS http://127.0.0.1:8800/api/install/status
# 已安装：{"code":0,"data":{"installed":true}}

# 4) 登录验证
curl -sS -X POST http://127.0.0.1:8800/api/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"{同上}"}'
```

规则与实现位置：

| 行为 | 实现要点 |
|------|----------|
| 幂等保护 | `Install` 先 `Count` 用户表，`count > 0` 直接返回 `{"code":-1,"msg":"系统已安装"}` |
| 绑定校验 | `Username`/`Password` 均 `binding:"required"`，密码另带 `min=8` |
| 复杂度 | `utils.ValidatePasswordStrength`：≥8 位且**必须同时含大写、小写、数字** |
| 落库字段 | `Level: 2`、`Status: 1`、`RegTime: time.Now()`，口令 `bcrypt` 哈希 |
| 安装判定 | `InstallStatus` 与 `Install` 使用同一个 `Count`，无独立开关 |

注意：安装向导**不创建配置目录**，也不写入任何「已安装」标记文件。
若需要重置开发库，直接删除 `data/` 下三个 SQLite 文件并重启（删除前请确认无需保留数据）。

必须知道的三条行为特征：

- 配置文件缺失时进程**不会失败**，而是自动生成随机密钥并回写文件；`jwt.secret` 每次重装都会变，
  旧 token 全部失效，属预期。回写目录权限 `0700`、文件权限 `0600`，防止同机其他用户读取密钥。
- `config.Load` 用 `sync.Once` 包裹：**同一进程内只加载一次**，运行期改文件无效，必须重启。
- 环境变量 `DNSPLANE_JWT_SECRET` / `DNSPLANE_MASTER_KEY` 的优先级高于文件内容，
  容器化部署应优先用它们而不是挂载 `config.json`。

### 5.7 数据目录与日志目录初始化

两个目录都由代码自动创建，但权限与失败语义不同：

```bash
cd main
# 启动前目录可以不存在
ls -ld data logs 2>/dev/null

go run . -config config.json &

# 启动后检查产物
ls -l data/
# data.db  logs.db  request_logs.db（以及 WAL/shm 伴生文件）
ls -l logs/
# 2026-10-12.log 之类按日期命名的文件
```

| 目录/文件 | 创建者 | 权限 | 失败行为 |
|-----------|--------|------|----------|
| `data/`（由 `database.file_path` 推导） | `database.Init` → `os.MkdirAll(dir, 0755)` | `0755` | `创建数据目录失败` → `os.Exit(1)` |
| `data/logs.db` | `cfg.LogDBPath()`（同目录） | 文件默认 | `连接日志数据库失败` → 退出 |
| `data/request_logs.db` | `cfg.RequestDBPath()`（同目录） | 文件默认 | `连接请求日志数据库失败` → 退出 |
| `logs/`（文本日志） | `logger` → `os.MkdirAll(l.logDir, 0755)` | `0755` | **仅打印错误并降级为 `os.Stdout`，不退出** |
| 配置目录（含密钥） | `saveConfig` → `os.MkdirAll(dir, 0700)` | `0700` | 返回错误 |

文本日志按 `logs/<日期>.log` 切分，保留天数由 `logger.MaxAge = 30` 控制。
开发机长期运行会积累三类 SQLite 文件与文本日志，磁盘占用需纳入
[故障排查指南](#故障排查指南) 的配额检查。

## 性能考虑

开发环境层面的性能主要花在「编译与同步」，不是运行时：

| 痛点 | 现象 | 处置 | 证据 |
|------|------|------|------|
| Go 构建缓存膨胀 | `$HOME/.cache/go-build` 增至 `40G` | `go clean -cache` 可回收，但会拖慢后续所有构建，需先评估 | `devlog.md` 环境事故段 |

## 故障排查指南

```bash
# 统一准备一个不受 /tmp 配额影响的构建工作目录
mkdir -p "$HOME/.cache/go-work"
export GOTMPDIR="$HOME/.cache/go-work"

# 完整验证链（与 devlog.md 记录的验收口径一致）
cd main
go build -gcflags="-lang=go1.26" ./...
go vet ./...
go test ./... -count=1
```

本次实测结果：`GOTMPDIR=$HOME/.cache/go-work go build -gcflags="-lang=go1.26" ./...` → 退出码 `0`。

| 症状 | 根因 | 定位命令 | 解法 |
|------|------|----------|------|
| `write $WORK/_pkg_.a: disk quota exceeded` | `/tmp` 是带 `usrquota` 的 tmpfs，**用户配额**已满而 `df` 显示仍有空间 | `mount \| grep tmp`；`du -sh /tmp/*` | `export GOTMPDIR=$HOME/.cache/go-work`，**不要**盲目清理他人目录 |
| `invalid field name Base.Name in struct literal` | 写了高于 `go.mod` 声明语言版本的新语法 | `rg -n "^go " main/go.mod` | 按 Go 1.26 语义改写；`-lang` 取 `go.mod` 而非工具链 |
| `go build -mod=vendor` 失败 | 仓库无 `vendor/` | `ls main/vendor` | 去掉 `-mod=vendor`，或先 `go mod vendor`（会大幅膨胀 diff） |
| `next: command not found` | 未安装前端依赖 | `ls web/node_modules` | `bun install` 或 `npm ci` |
| `bun run build` 报 `powershell` 不是可执行文件 | 该脚本为 Windows 专属（`set "ANALYZE=true"` + `powershell` 拷贝） | `rg -n "powershell" web/package.json` | Linux/macOS 用 `bun run build:ci` |
| `missing out/ — run next build first` | `build:ci` 前置 `next build` 未产出 | `ls web/out` | 先完整执行 `next build`，或整体跑 `scripts/build.sh` |
| 页面正常、接口全 404 | 在 `next dev :3000` 上访问相对 `/api` | `rg -n "API_BASE" web/lib/api.ts` | 改走 `:8800`（见 5.4） |
| 端口被占用 | 8800/3000 已有监听 | `ss -ltnp \| grep -E '8800\|3000'` | 换端口，**不要**盲杀进程 |
| 启动日志 `Redis 连接失败...回退到内存缓存` | `redis.enable=true` 但服务未起 | `redis-cli -u redis://127.0.0.1:6379 ping` | 起 Redis 或置 `enable: false` |
| 登录 401 反复出现 | 重启时 `config.json` 缺失，自动生成了新 `jwt.secret` | `rg -n "secret" main/config.json` | 固定配置文件，容器用 `DNSPLANE_JWT_SECRET` |
| 改配置不生效 | `config.Load` 由 `sync.Once` 包裹 | — | 重启进程 |

## 结论

- 搭建路径已收敛为「`go mod download` + `bun install --frozen-lockfile` + `go run .`」三步，
  前端只在需要端到端时才走 `build:ci` 同步进 `main/web`。
- 最重要的环境认知纠偏有两条：其一，本仓库**没有 dev 代理**，`next dev` 与后端接口天然隔离，
  端到端联调必须经 `:8800`；其二，`web/package.json` 的 `build` 脚本是 Windows 专属，
  Linux/macOS 必须用 `build:ci`。
- 下一步建议：若团队需要「改前端即时联调」，应补一个受版本控制的可逆方案
  （例如独立的 dev-only 配置加载或反向代理脚本），而不是临时改 `next.config.ts`。
