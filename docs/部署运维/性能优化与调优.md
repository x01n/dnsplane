## 简介

DNSPlane 的性能画像非常特殊：**单进程 Gin** 同时承担 API 与静态页面，业务核心是
**云厂商 API 编排**，持久化默认落在**单机 SQLite**。这意味着瓶颈通常不在 CPU，
而在三处：外部 API 往返、SQLite 写串行化、以及请求追踪自身的观测开销。

本文只讨论**可由代码事实支撑**的调优面，并明确区分证据等级：

| 等级 | 含义 | 本文范围举例 |
|------|------|--------------|
| 已验证 | 本次会话实测命令输出 | `go build` 退出码、基准测试 ns/op、`go tool pprof -top` |
| 代码事实 | 直接读取自源码常量与参数 | 连接池 8/4、`DefaultTTL=60s`、`maxDispatchPerTick=100` |
| 推断 / 未执行 | 结构导出的判断，或给出方法但未产出数据 | 串行云 API 时延放大、端到端压测 |

**关键实测事实：本仓库没有任何 pprof 端点。**
`rg -l pprof main/ web/` 仅命中 `main/go.sum`（传递依赖哈希），源码中不存在 `net/http/pprof` 导入，
`main.go` 的 `http.Server` 只挂了 `api.SetupRouter`。所有 CPU 剖析只能走离线基准测试路径。

## 核心组件

与性能直接相关的六个既定参数（均为代码事实，非配置项）：

| 组件 | 参数 | 值 | 位置 |
|------|------|----|------|
| SQLite 连接池 | `MaxOpen/MaxIdle` · `MaxIdleTime/MaxLifetime` | 8 / 4 · 5m / 0（不重建） | `database.go` `applySQLiteConnPool` |
| MySQL 连接池 | `MaxOpenConns` / `MaxIdleConns` | 100 / 25 | `applyMySQLConnPool` |
| SQLite DSN | `journal_mode` / `synchronous` / `busy_timeout` | WAL / NORMAL / 5000ms | `sqliteDSN` |
| SQLite DSN | `cache_size` / `temp_store` / `mmap_size` | -16000 KB / MEMORY / 64 MiB | 同上 |
| GORM | `SkipDefaultTransaction` | `true` | `Init` 的 `gormConfig` |
| dbcache | `DefaultTTL` | `60 * time.Second` | `dbcache.go` |
| cache | Redis Ping 超时 / 默认 `PoolSize` | 3s / 10 | `cache.go` `Init` |
| logstore | `maxLogSize` / `requestStatsCacheTTL` | 10000 / 2m | `store.go` |
| monitor | tick / `maxDispatchPerTick` | 1s / 100 | `monitor.go` |
| record_sync | `recordSyncBatchSize` / `maxPages` | 100 / 100 | `record_sync.go` |
| HTTP Server | `ReadHeaderTimeout` / `IdleTimeout` | 30s / 120s | `main.go` |

三个容易忽略的结构性事实：

- 进程内有**三个独立 SQLite 句柄**（`DB`/`LogDB`/`RequestDB`），后两者恒为 SQLite（主库切 MySQL 也是）。
  按上限 8 算峰值 `8×3 = 24`，而 SQLite 单文件写本质串行，超出只增 page cache 内存
  （该判断写在 `applySQLiteConnPool` 注释里）；
- `RegisterDBCallbacks` 只挂 `DB` 与 `LogDB`，不挂 `RequestDB`，避免写日志再被自己追踪；
- `ConnMaxLifetime = 0` 对 SQLite 正确（无网络断连），但不可照搬到 MySQL。

## 详细组件分析

### GORM 连接池调优

实测参数与语义判读：

| 驱动 | MaxOpen | MaxIdle | ConnMaxIdleTime | ConnMaxLifetime | 判读 |
|------|---------|---------|-----------------|-----------------|------|
| SQLite | 8 | 4 | 5m | 0 | 写串行，8 已超出实际并行收益；提高上限只增内存 |
| MySQL | 100 | 25 | 5m | 1h | 有网络断连风险，`lifetime=1h` 用于规避服务端 idle kill |

`sqliteDSN` 注释里有一条会决定调优成败的约束：`glebarez/go-sqlite` 只识别 `_pragma`、
`_time_format`、`_txlock` 三类 DSN 参数，且 `_pragma` 在**每个新连接建立时重新执行**。
因此调 PRAGMA 必须改 DSN，事后 `Exec("PRAGMA ...")` 只作用于当次连接；
`_busy_timeout` 不是该驱动参数名，正确写法是当前的 `_pragma=busy_timeout(5000)`。

`SkipDefaultTransaction = true` 的依据同样写在源码注释：本项目无显式事务、无多行批量插入、
库内无外键约束，隐式事务只增加 WAL fsync。**未来若引入多语句原子写，必须显式 `DB.Transaction(...)`。**

调优验证：

```bash
cd main

# 观察当前池参数
rg -n "SetMaxOpenConns|SetMaxIdleConns|SetConnMax|_pragma" internal/database/database.go

# 变更参数后的最小验证链
GOTMPDIR="$HOME/.cache/go-work" go build -gcflags="-lang=go1.26" ./...
GOTMPDIR="$HOME/.cache/go-work" go vet ./...
GOTMPDIR="$HOME/.cache/go-work" go test ./... -count=1
```

### dbcache 命中与失效半径

读穿逻辑只有一条分支树，`cache.C == nil` 时降级为「直接 load + 序列化往返」，
不会报错，只是没有缓存收益：

```mermaid
flowchart LR
A["GetOrSetJSON(ctx,key,ttl,load,dest)"] --> B{"ctx.Err()?"}
B -->|是| Z[返回 ctx 错误]
B -->|否| C{"cache.C == nil?"}
C -->|是| D["load() + Marshal + Unmarshal"]
C -->|否| E{"GetJSON 命中?"}
E -->|命中| F["直接 Unmarshal 返回（零 SQL）"]
E -->|未命中| G["load()"]
G --> H["Set(key, json, ttl)"]
H --> I["Unmarshal 到 dest"]
```

**图表来源**
- [main/internal/dbcache/dbcache.go](file://main/internal/dbcache/dbcache.go)

命中面（`GetOrSetJSON` 全部调用点，实测 `rg -n` 结果）：

| 调用点 | 键 | 失效函数 | 半径 |
|--------|----|----------|------|
| `handler/account.go:109` | `db:v1:accounts:admin` / `db:v1:accounts:user:<uid>` | `BustAccounts(uid)` | 2 个精确键 |
| `handler/user.go:64` | `db:v1:users:admin_full` | `BustUserList()` | 1 精确键 + 前缀扫描 |
| `handler/cert.go:79` | `db:v1:cert:accounts:list:d{0,1}:(admin|u<uid>)` | `BustCertAccountsList()` | 整前缀 SCAN |

两处键设计直接决定命中率与失效成本：

- `KeyUsersList(page, pageSize, keyword)` 把 `sha256(keyword)[:8]` 写进键名（空词固定 `_`），
  使分页键**基数随搜索词无限增长**，是低命中/高残留的来源；
- `BustUserList()` 与 `BustCertAccountsList()` 走 `DeletePrefix`，在 Redis 后端下是
  `SCAN(count=100)` + 每 500 个 key 一批 `DEL`，内存后端下遍历 map——
  一次用户列表写入的失效代价随缓存总量线性上升。

调优取向（推断）：搜索类键应设更短 TTL 或改显式失效；`BustUserList` 频繁时应收窄前缀而非加大池。

### Redis 用途与边界

`go_redis.go` 除 KV 外还实现 List 操作（`LPush`/`LLen`/`LRange`/`LTrim`），
只被 `logstore` 使用，把日志装成定长列表：

| Redis 用途 | 键 | 上限/生命周期 |
|------------|----|----------------|
| 请求日志 | `app:request_logs` | `maxLogSize=10000`，`LLen > 10500` 才 `LTrim(0, 9999)` |
| 请求统计缓存 | `requestStatsCacheKey` | TTL `2 * time.Minute` |
| 读穿数据缓存 | `db:v1:*` | TTL `60s`（`dbcache.DefaultTTL`） |

每写一条都调 `LLen`，但只在超出 500 条余量时才 `LTrim`，属**摊还裁剪**：
避免每写必裁剪的双倍 O(N)，代价是列表短暂超限。

降级路径（实测代码）：`cache.Init` 用 3 秒超时 Ping，失败即 `Warn` 并 `NewMemoryCache(prefix)`，
**进程不退出**。副作用是内存缓存按进程计、重启即清空，且 `logstore.Init` 的非 Redis 分支为空实现，
于是请求日志改走 `RequestDB`（SQLite）。`key_prefix` 由 `NormalizeKeyPrefix` 叠加在
`db:v1:` 版本段之前，多环境共用 Redis 时它决定 `DeletePrefix` 的误伤范围。

### 批量任务并发度

后台任务各有明确的并发闸门，这些是**代码事实**：

| 任务 | 节律 | 并发控制 | 位置 |
|------|------|----------|------|
| 容灾检测 | `1s` ticker | 单轮最多派发 `100` 个；`sync.Map` 去重防重入；单任务 `Timeout+10s` 上下文 | `monitor.go` |
| 证书/部署任务 | `5m` ticker | 逐单处理，退避表 `{300,600,1800,3600,7200}` / 部署 `{60,300,600,1800,3600}` | `task_runner.go` |
| 域名到期检查 | `24h` ticker | 全表扫描 | `task_runner.go` |
| 记录同步 | 每轮 | 每域名**串行翻页**，`100 × 100 = 10000` 条上限 | `record_sync.go` |

`monitor.go` 有两处正向设计：超出 `maxDispatchPerTick` 的任务**不排队，保持原
`check_next_time` 等下一 tick**，避免单轮无限起 goroutine；顺延用 `WHERE id IN (?)`
按 frequency **分组合并 UPDATE**，把 N 条写合成 1 条。
单任务内对多目标探测是**并行**的（每地址一 goroutine + `WaitGroup`/`Mutex`），
时延取决于最慢目标而非目标数之和。

相对地，`record_sync.go` 的 `fetchAllRecords` 是纯串行 `for page := 1..100`，
每页一次 `GetDomainRecords`；唯一的并行度是「每轮多个域名」，翻页本身 N 次 RTT 叠加。
它每页检查 `ctx.Err()`，注释说明否则关停时 `StopRecordSync` 的 `wg.Wait` 会被整轮拖住。

### 云 API 串行瓶颈

最密集的证据在 `handler/batch.go`，四组写操作全部是「逐条串行调用 provider」：

| 位置 | 循环 | 每轮外部调用 | 复杂度 |
|------|------|--------------|--------|
| `batch.go:136` → `:157` | `for _, line := range lines` | `provider.AddDomainRecord` | N × RTT |
| `batch.go:167` → `:180` | `for _, rec := range items` | `provider.AddDomainRecord` | N × RTT |
| `batch.go:301` → `:302` / `:315` | `for _, recordID := range recordIDs` | `GetDomainRecordInfo` **+** `UpdateDomainRecord` | 2N × RTT |
| `batch.go:404` → `:409/:412/:415` | `for _, recordID := range recordIDs` | `SetDomainRecordStatus` 或 `DeleteDomainRecord` | N × RTT |

判读：**批量编辑的往返数是批量新增的两倍**，因为改之前先逐条读回完整记录。
按云 API 单跳 80–200ms 量级，100 条记录的批量编辑会落在 16–40 秒（推断，未实测），
瓶颈与 SQLite、连接池无关，扩池不会改善。

同一模式出现在容灾切换：`monitor.go` 按
`GetDomainRecordInfo` → `AddDomainRecord`（逐个备用值，`:571`/`:587`）
→ `SetDomainRecordStatus` → `DeleteDomainRecord` 顺序执行，切换时延即故障期间的解析空窗。

优化方向（建议，未实施）：读阶段可并行，写阶段受账户级 QPS 约束；
引入并发必须复刻 `monitor.go` 的「上下文超时 + 每轮 `ctx.Err()` 检查」，否则关停被外部调用拖住；
并发上限应取常量而非 CPU 核数，因为约束来自对端限流。

| 7-10 | `acceleration.go` 1000 / `user.go` 743 / `plan.go` 672 / `oauth.go` 565 | — | 加速、用户、套餐、OAuth |

需要澄清一个误解：**文件行数本身不是运行时性能问题**，Go 的编译单元大小不影响单次请求耗时。
它的间接影响有三条：

- 同一文件承载差异极大的响应路径。`domain.go` 既有同步查询也有 `utils.SafeGo` 异步写
  （实测 9 处），「这个接口是否等待落库」难以一眼判定；
- `domain.go:172`/`:206` 是内存内组装，而 `:742`/`:1631`/`:1764` 对应不同外部依赖层级，
  混排会掩盖真正的串行 IO 段；
- `db_queries` 是一维数组，单个 handler 产生几十条 SQL 时 `json.Marshal(*q)`
  会推高请求日志行大小，放大 `RequestDB` 写与 Redis List 内存。

结论（推断）：拆分巨型 handler 的收益是**可判定性与可观测性**，不是直接 CPU 节省。

两层短路的作用完全不同：

- **第二层（`db_queries` 键）是高价值短路**。源码注释写明「仅在有请求追踪时记录，

- **第一层（`trace_inject_gin` Before hook）不受同一开关保护**。

  后者用 `runtime.Stack(buf[:128], false)` 解析 goroutine 编号，并对 `sync.Map` 做一次 Load。
  这是**每条 GORM 语句都执行**的自省操作，高频小查询会被固定开销放大（推断，未量化）。

请求体与响应体都过 `SanitizeBodyForLog`。

### 日志异步落库开销

`RequestTrace` 的落库分支是一个**二选一而非双写**的设计，实测代码：

```go
// 异步写入：Redis 开启时仅写 Redis，避免与 SQLite 双写；否则只写 RequestDB
go func(l models.RequestLog) {
    if logstore.Store != nil && logstore.Store.IsRedis() {
        logstore.Store.SaveRequestLog(l)
        return
    }
    _ = database.RequestDB.Create(&l).Error
}(log)
```

开销判读：

| 维度 | Redis 路径 | SQLite 路径 |
|------|------------|-------------|
| 阻塞请求的时间 | 不阻塞（新 goroutine） | 不阻塞（新 goroutine） |
| 峰值并发 | 受 Redis `pool_size` 约束 | 受 `RequestDB` 池 8 约束，且与业务写争抢同一文件 |
| 保留量 | 固定 `10000` 条环形 | 无上限，持续增长直到 `maintenance` 清理 |
| 主要风险 | 重启即丢失全部日志 | 高 QPS 时 SQLite 写成为全进程瓶颈 |
| 错误可见性 | `SaveRequestLog` 返回值被忽略 | `.Error` 被显式丢弃（`_ =`） |

`go func` 只把延迟挪出请求路径，不减少总工作量：SQLite 路径下每个请求最终都是一次
`RequestDB.Create`，与主库共享同一进程的写串行资源。若「接口 SQL 很快但整体变慢」，
先确认是否运行在无 Redis 的 SQLite 日志路径。

## 性能考虑

按「先做哪件最有效」排序的调优优先级：

| 优先级 | 动作 | 依据 | 风险 |
|--------|------|------|------|
| 1 | 保证 Redis 可用，把请求日志从 SQLite 挪走 | `request_trace.go` 二选一分支；`RequestDB` 池仅 8 | 重启丢日志（List 非持久语义） |
| 2 | 串行云 API 改并行（先读后写、限并发） | `batch.go:301` 是 `batch.go:136` 的两倍 RTT | 触发云厂商限流 |
| 3 | 消除 `trace_inject_gin` 的无条件 goroutine 反查 | `trace_gin.go` `runtime.Stack(128)` | 破坏 SQL 与请求的归因 |
| 4 | 优化 `isSensitiveKey` 为集合/前缀树 | 实测 `30ms/90ms` 累计占比 | 敏感字段漏脱敏 |
| 5 | 收紧 `KeyUsersList` 搜索键基数；SQLite 池上限维持 8 不动 | `keys.go` 全词入键 / 池注释「超出只增 page cache」 | 命中率下降 / 提高后吞吐不涨 |
| 6 | `VACUUM` 放在业务低谷窗口执行 | `maintenance.go` 默认 24h 间隔 | 执行期间写放大 |

数据库维护侧已有的自愈动作（`maintenance.go` `optimizeGormDB`）：
`PRAGMA wal_checkpoint(TRUNCATE)` → `ANALYZE` → `PRAGMA optimize` → `VACUUM` →
`PRAGMA journal_mode=WAL`（注释说明 `VACUUM` 可能重置 journal 模式，需显式恢复）。
调优时**不要手工再补 `PRAGMA journal_mode`**，会与后台维护竞争。

配置层与代码层的边界：`ReadHeaderTimeout`、`IdleTimeout`、两侧连接池、
`dbcache.DefaultTTL`、`maxDispatchPerTick`、`recordSyncBatchSize`、`logstore.maxLogSize`
**全部是代码常量**。唯一可从 `config.json` 调整的是 Redis 的 `pool_size` 与 `min_idle_conns`；
`VACUUM` 间隔可经系统配置键 `maint_vacuum_interval_h` 覆盖（`maintenance.go`）。

## 结论

- 本项目的性能天花板由三件事决定：**日志落库走哪条路、云 API 是否串行、SQLite 单文件写串行**。
  连接池参数不是主要变量，且大部分是代码常量。
- 实测热点来自 `sanitize_bench_test.go`：单次列表响应脱敏 **339 µs / 61.5 KB / 1880 allocs**，
  `isSensitiveKey` 累计占 33%，是当前唯一有真实数据支撑的优化点。
- 观测本身有成本：`db_queries` 开关只保护 Explain 一层，
  `trace_inject_gin` 的 goroutine 反查在每条 GORM 语句上无条件执行。
- 已验证的负面事实是**没有 pprof 端点**；端到端压测未执行，吞吐推断不应作为容量目标。
