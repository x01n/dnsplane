## 简介

本篇回答四件事：**备份什么、怎么备、留多久、怎么恢复**。

DNSPlane 是「单二进制 + 本地 SQLite」形态的控制面，业务状态几乎全部落在
`data/` 目录的三个库文件里，密钥落在 `config.json`。这带来一个必须先讲清楚的结论：

> **主库的一份完整备份 = 全站凭据的一次完整外泄。**
> 数据库里的凭据列虽然是 `enc:v1:` 密文，但解密主密钥 `security.master_key`
> 就明文存放在同机的 `config.json` 中；此外 `sys_configs.value` 整列明文、
> `users.api_key` 明文。两者一起进 tar，就等于把私钥和保险柜钥匙放进同一个盒子
> （口径来源：`analysis-deploy.md` D-4 条目，代码取证 `hooks.go:32-70`、
> `database.go` 三库初始化、`config.go:169` 文件权限）。

因此本篇的备份对象分为四类，且**每一类的保护手段不同**：

| 类别 | 对象 | 敏感级 | 保护手段 |
|:---|:---|:---:|:---|
| A | 主库 / 日志库 / 请求库 | 高 | 密文列 + 明文列混杂，需整体加密后落盘 |
| B | `config.json`（含 `master_key`、`jwt.secret`、DB 口令） | 极高 | 单独走密钥通道，不与 A 同介质、同目录 |
| C | 加密后的账户凭据与证书私钥（库内 `enc:v1:` 列） | 高 | 依赖 B；B 丢失即永久不可解 |
| D | 运行产物：日期日志、本地部署写出的证书/私钥文件 | 中 | 按需，私钥文件按 0600 保护 |

工作区实测口径：`main/data/` 目前只有三个库文件及其 WAL 伴生文件，
没有独立的「用户上传附件目录」——本项目的证书导出走 HTTP 响应流
（`handler/cert.go` 的 `Content-Disposition: attachment`），私钥不落应用自己的目录；
唯一会往文件系统写私钥的路径是「本地部署」目标（`servers/local.go:100-113`）。
这一条与很多系统的直觉不同，备份脚本不要按臆想的路径去 tar。

行号、路径、文件体积均为当前工作区实测；命令类示例凡未实际执行的都显式标注「未实机」。

### 路径由谁决定

库文件名不是硬编码在业务代码里，而是由 `config.json` 的 `database.file_path` 推导：

- 主库：直接用 `DatabaseConfig.FilePath`（工作区实配 `data/data.db`）
- 日志库：`LogDBPath()` = `filepath.Dir(FilePath)/logs.db`（`config.go:58-61`）
- 请求库：`RequestDBPath()` = `filepath.Dir(FilePath)/request_logs.db`（`config.go:63-67`）

注意代码里的默认值是 `data/dnsplane.db`（`config.go:95`），与工作区实配的
`data/data.db` 不同名——**改 `file_path` 会同时改变三库所在目录**，
备份脚本必须以「`file_path` 的所在目录」为单位，而不是写死文件名。

## 核心组件

### 三库分工与驱动能力边界

| 库 | 变量 | 承载模型 | SQLite | MySQL |
|:---|:---|:---|:---:|:---:|
| 主库 | `database.DB` | 用户、账户、域名、证书订单/部署、监控任务、系统配置、配额套餐 | 默认 | 可切换 |
| 日志库 | `database.LogDB` | `Log`、`CertLog`、`DMCheckLog` | 固定 | **不切换** |
| 请求库 | `database.RequestDB` | `RequestLog` | 固定 | **不切换** |

关键结论（`database.go:104-118` 无条件 `sqlite.Open`）：
**即使 `driver = mysql`，日志库与请求库仍然是本地 SQLite 文件。**
所以「我用了 MySQL，是不是只要 dump 数据库就行」这个直觉是错的——
必须同时备份两个 SQLite 文件，否则操作审计与请求追踪在恢复后归零。

### 静态加密列清单

`models/hooks.go` 通过 GORM 的 `BeforeSave`/`AfterFind` 做字段级 AES-256-GCM 加解密，
共 7 个模型 9 列。备份时无需单独处理（它们在库里就是密文），
但**恢复后的可用性完全依赖主密钥**：

| 模型 | 加密列 | 业务含义 |
|:---|:---|:---|
| `Account` | `Config` | DNS 服务商 AK/SK、面板账号口令 |
| `CertAccount` | `Config`、`Ext` | ACME 账户私钥、EAB `kid`/`hmac` |
| `CertOrder` | `PrivateKey`、`Info` | 证书私钥与订单信息 |
| `CertDeploy` | `Config`、`Info` | 部署目标凭据、SSH `host_key` |
| `DMTask` | `ProxyPassword` | 容灾探测代理口令 |
| `User` | `TOTPSecret` | 二步验证密钥 |
| `UserOAuth` | `AccessToken`、`RefreshToken` | OAuth 令牌 |

加密实现要点（`crypto/crypto.go`）：

- 密文前缀 `enc:v1:`，格式为 `base64(nonce ‖ ciphertext ‖ tag)`
- 密钥 = `sha256(security.master_key)`，`sync.Once` 派生后缓存，不落盘
- `MustDecrypt` 在解密失败时**静默返回原文**（`crypto.go:95-101`），
  因此主密钥不匹配不会报错，只会把 `enc:v1:...` 当明文交给业务解析

### 三件套密钥

| 密钥 | 位置 | 环境变量覆盖 | 丢失后果 |
|:---|:---|:---|:---|
| `security.master_key` | `config.json` | `DNSPLANE_MASTER_KEY` | 全部 `enc:v1:` 列永久不可解 |

## 详细组件分析

### 冷备流程（停机快照）

冷备是唯一能保证「三库 + WAL 全一致」的方式。DNSPlane 的关闭序列是确定的，
`main.go` 中 defer 的注册顺序决定了退出时的收尾动作：

- 收到 `SIGINT`/`SIGTERM` → `srv.Shutdown(10s)` 排空 HTTP 连接
- 之后依次 `StopRecordSync` → `StopOptimizeRunner` → `StopMaintenance`
  → `taskCancel` + `taskRunner.Stop` + `scheduleRunner.Stop` → `mon.Stop`
  → `cache.Close` → **`database.Close`**（三个 `sqlDB.Close()`）
- SQLite 在最后一个连接关闭时会把 WAL 回写主文件并删除 `-wal`，
  这就是「进程干净退出后可以直接 cp」的依据

```bash
# 1. 排空并停机（等待日志出现「HTTP服务已关闭」且进程退出）
systemctl stop dnsplane          # 或 kill -TERM <pid>
while pgrep -x dnsplane >/dev/null; do sleep 1; done

# 2. 确认 WAL 已经合并（-wal 应为 0 字节或不存在）
ls -la main/data/

# 3. 打包三库 + 配置文件分离归档
STAMP=$(date +%Y%m%dT%H%M%S)
tar czf /backup/dnsplane-db-$STAMP.tgz -C main data/*.db
tar czf /backup/dnsplane-cfg-$STAMP.tgz -C main config.json

# 4. 校验与最小权限
sha256sum /backup/dnsplane-db-$STAMP.tgz > /backup/dnsplane-db-$STAMP.sha256
chmod 600 /backup/dnsplane-*.tgz

# 5. 拉起服务
systemctl start dnsplane
```

预期输出：第 2 步中 `data.db-wal` 为 `0 B` 或已消失；若仍是非零长度，
说明进程未干净退出（被 `kill -9` 或崩溃），此时**必须改用热备方式**，
不要直接 tar 半截 WAL。

### 热备（不停机）

WAL 模式 + `synchronous(NORMAL)` 意味着任意时刻 `-wal` 里都可能有未合并的页，
**`cp` 主文件会得到一个缺最新事务的库**。SQLite 官方在线备份 API 才是一致性口径：

```bash
# 逐库热备（未实机：本机未执行完整还原演练，命令形态取自 sqlite3 CLI 文档口径）
sqlite3 main/data/data.db ".backup '/backup/hot/data-$STAMP.db'"
sqlite3 main/data/logs.db ".backup '/backup/hot/logs-$STAMP.db'"
sqlite3 main/data/request_logs.db ".backup '/backup/hot/request_logs-$STAMP.db'"

# 一致性核验（未实机）
for f in /backup/hot/*.db; do sqlite3 "$f" "PRAGMA integrity_check;"; done
```

若不希望依赖 `sqlite3` CLI 是否安装，可在业务低峰用**只读 checkpoint**手工合并再取文件：

```bash
# 未实机：仅合并 WAL，不压缩、不锁写超过必要时长
sqlite3 main/data/data.db "PRAGMA wal_checkpoint(FULL);"
```

MySQL 形态（仅主库可能为 MySQL，日志库/请求库仍是 SQLite）：

```bash
# 未实机：账号口令从环境变量注入，禁止写进脚本或命令行历史
mysqldump --single-transaction --routines --triggers \
  --databases "{db_name}" | gzip > /backup/mysql-$STAMP.sql.gz
```

`--single-transaction` 是 InnoDB 一致性快照的关键；若库为 MyISAM 则需
`--lock-tables` 并接受写入阻塞。数据库口令字段来自 `config.json` 的
`database.password`，**明文存放**，因此备份产物一旦外泄即等同凭据外泄。

| 方式 | 一致性 | 是否需要停机 | 覆盖 WAL | 适用场景 |
|:---|:---:|:---:|:---:|:---|
| 停机后 `tar` | 强 | 是 | 是 | 变更窗口、月度全量 |
| `sqlite3 .backup` | 强 | 否 | 是 | 日常自动备份（推荐） |
| `cp` + 手工 `cp` | 弱 | 否 | **否** | 禁止使用 |
| `wal_checkpoint(FULL)` 后取文件 | 中 | 否 | 是 | 无 CLI `.backup` 支持时 |
| `mysqldump --single-transaction` | 强 | 否 | 不适用 | 主库为 MySQL 时 |

### 保留策略与 cron

应用内建的日志保留由 `maintenance.go` 决定，可通过系统设置的 `maint_*` 键覆盖。
**备份保留期应不短于对应的日志保留期**，否则「备份还在、库里的日志早已被清」并
不代表日志可回溯；反过来，请求库只留 7 天，若合规要求留 90 天，必须靠备份归档承接。

| SysConfig 键 | 默认值 | 含义 | 建议备份保留期下限 |
|:---|---:|:---|---:|
| `maint_operation_log_days` | 90 | 操作日志（`logs.db`） | ≥ 90 天 |
| `maint_cert_log_days` | 60 | 证书日志（`logs.db`） | ≥ 60 天 |
| `maint_monitor_log_days` | 60 | 容灾切换日志（主库） | ≥ 60 天 |
| `maint_check_log_hours` | 72 | 监控检查日志（小时） | 3-7 天 |
| `maint_request_log_days` | 7 | 请求日志（`request_logs.db`） | ≥ 7 天 |
| `maint_request_success_keep` | 2000 | 成功请求日志条数上限 | — |
| `maint_request_error_keep` | 1000 | 错误请求日志条数上限 | — |
| `maint_vacuum_interval_h` | 24 | VACUUM 间隔（小时） | — |


### 恢复演练

恢复分两种情形，路径完全不同。

```mermaid
sequenceDiagram
  participant OP as 运维
  participant BK as 备份介质
  participant FS as data 目录
  participant SV as dnsplane 进程
  participant DB as SQLite/MySQL

  OP->>BK: 取当日热备与密钥归档
  BK-->>OP: db.tgz + cfg.tgz（分开存放）
  OP->>SV: 停止服务并等待进程退出
  OP->>FS: 清空/改名原目录，保留一份现场
  OP->>FS: 解包三个 .db（权限 600）
  OP->>FS: 解包 config.json（权限 600）
  OP->>SV: 启动服务
  SV->>DB: AutoMigrate 补齐列
  SV->>DB: MigratePlaintext 原地补加密
  SV->>DB: migrateOldData 搬迁旧日志表
```

### JWT Secret 丢失的后果

`jwt.secret` 同时承担两件事，这决定了它丢失后的表现不是「重新登录就行」：

- 作为 access/refresh token 的签名密钥
- 作为会话 cookie 的加密密钥：`_t`、`_rt` 都是
  `AES-GCM(key = sha256(JWT.Secret))` 后的十六进制串（`analysis-auth.md` 会话 cookie 加密条目）

因此一旦 `config.json` 中的 `jwt.secret` 变了（丢失后自动生成、或容器重建未挂载卷）：

| 影响面 | 表现 | 恢复动作 |
|:---|:---|:---|
| 所有在线会话 | 一律 401，`middleware/auth.go` 解密失败分支 | 全员重新登录，无兼容路径 |
| refresh 流程 | `_rt` 无法解密，静默续期失效 | 同上 |
| 已签发 API 调用 | `Authorization: Bearer` 校验失败 | 客户端重新换取 token |
| 密文列 | **不受影响**（走 `master_key`，不是 JWT） | 无需动作 |

首次启动找不到配置文件时，`config.Load` 会**同时**随机生成
`jwt.secret` 与 `security.master_key` 并回写（`config.go:105-113`）；
历史默认值 `dnsplane-secret-key-change-me` 也会被自动替换
（`config.go:130-143`）。这就是「容器重建后凭据全废」的根本成因——
两个随机密钥都被换掉了。

正确处置是把两个值改为**由部署方固定注入**：

```bash
# docker run 形态（README/Dockerfile 口径）：两个密钥都必须来自带外保管
docker run -d --name dnsplane -p 8080:8080 \
  -v /srv/dnsplane/data:/app/data \
  -v /srv/dnsplane/config.json:/app/config.json:ro \
  -e DNSPLANE_JWT_SECRET={jwt_secret} \
  -e DNSPLANE_MASTER_KEY={master_key} \
  dnsplane:{tag}

# 取证：确认当前实例到底用的是哪个来源
grep -c DNSPLANE_MASTER_KEY /proc/$(pgrep -x dnsplane)/environ
```

### 备份文件即敏感数据：安全存储

把「备份 = 敏感数据」这条原则落成可执行约束：

1. **库备份与密钥备份分离**：不同目录、不同介质、不同审批人；
   恢复时两步拼装，日常不放在一起
2. **备份产物再加密一层**：`age` 或 `gpg` 对称加密，口令不入库不入仓
3. **落地即收权限**：`chmod 600`，属主为服务账号而非 root
4. **禁止进入构建上下文与仓库**：`analysis-deploy.md` D-5 指出
   `.dockerignore` 仅 6 行且未排除 `main/config.json`，
   该文件会随 `COPY main/ ./` 进入 builder 层
5. **Redis 快照同等对待**：账户列表缓存以 `db:v1:accounts:*` 写入
   `cache.C`，Redis 形态下**解密后的明文凭据**会进入 `dump.rdb`（TTL 60s 不等于不存在）
6. **异地副本走加密通道**，禁止明文 scp；对象存储需私有读写 + 生命周期规则

```bash
# 未实机：二次加密与清单留痕
tar czf - -C main data/*.db | age -p -o /backup/dnsplane-db-$STAMP.tgz.age
sha256sum /backup/dnsplane-db-$STAMP.tgz.age | tee -a /backup/MANIFEST

# 取证：确认 config.json 未被 COPY 进镜像层
docker history --no-trunc {image} | grep -i config.json
git check-ignore -v main/config.json
```

## 性能考虑

- **备份窗口与 VACUUM 冲突**：`optimizeGormDB` 每小时判定一次，
  默认每 24 小时对三库依次执行 `wal_checkpoint(TRUNCATE)` → `ANALYZE`
  → `PRAGMA optimize` → `VACUUM` → 恢复 `journal_mode=WAL`。
  `VACUUM` 会整文件重写并需要约两倍磁盘空间。把备份定在紧接维护之后
  （`GetMaintenanceStats` 暴露 `last_vacuum`/`next_vacuum`）能让
  `-wal` 处于最干净状态，也能避免与重写争抢 IO
- **`.backup` 的代价**：在线备份为 page-by-page 复制且持读锁；请求库通常最大，建议降频或从保留策略上裁剪
- **连接池影响**：SQLite 侧 `MaxOpenConns(8)`、`busy_timeout(5000)`。
  备份进程若与业务争用同一文件，写侧最多等 5 秒后报 `database is locked`，
  因此备份脚本应使用只读方式，不要对生产库执行 `VACUUM`
- **mmap 与压缩收益**：DSN 里 `mmap_size=67108864`、`cache_size=-16000`、
  `temp_store=MEMORY`，大库上另起 `sqlite3` 进程校验会额外占页缓存，
  低配机器把校验放到备份机上跑；SQLite 页内存在空闲碎片，
  `gzip` 收益有限，真正的体积收益来自应用自己的 `VACUUM`

### BK-1 恢复后所有 DNS 账户显示异常、证书全部部署失败

| 段 | 内容 |
|:---|:---|
| 症状 | 库文件恢复成功、进程正常启动、页面可登录，但账户列表点开报配置解析错误，证书任务批量失败，且**没有任何解密失败的报错** |
| 原因 | `config.json` 与库文件不来自同一时点，`master_key` 变化；`MustDecrypt` 静默把 `enc:v1:` 原文当明文返回（`crypto.go:95-101`），故无错误信号 |
| 方案 | 用备份的原始 `config.json`（或固定的 `DNSPLANE_MASTER_KEY`）重启；若原密钥确已丢失，只能到服务商侧重新签发凭据并重建账户，旧密文永久不可恢复 |

```bash
# 定位：确认密文列前缀是否完好（前缀在但解不开 = 密钥不匹配）
sqlite3 main/data/data.db "SELECT id, substr(config,1,7) FROM accounts LIMIT 5;"
# 定位：确认当前生效的主密钥来源
grep -o 'master_key[^,]*' main/config.json | cut -c1-24
tr '\0' '\n' < /proc/$(pgrep -x dnsplane)/environ | grep -c DNSPLANE_MASTER_KEY
```

## 结论

DNSPlane 的备份难点不在「拷文件」，而在**它把业务状态、密文凭据与解密主密钥
放在同一台机器上，且解密失败是静默的**。据此收敛为四条硬约束：

1. **备份单元是目录而不是文件名**——三库同源于 `database.file_path`，
   日志库与请求库在 MySQL 形态下依然是文件
2. **密钥必须与库分离归档**——`master_key` 决定 9 个密文列能否复活，
   `jwt.secret` 决定会话是否需要全员重登
3. **一致性只有两条路**——干净停机后打包，或 `sqlite3 .backup`；
   直接 `cp` 主文件在 WAL 下不成立
4. **备份产物按凭据级保护**——`sys_configs.value`、`users.api_key` 明文，
   Redis 快照含解密后凭据，权限与加密缺一不可

恢复演练每季度至少做一次，验收标准以「账户可点开、证书可续期、二步验证可登录」
三项为准，而不是以「页面能打开」为准。

### 备份脚本参考实现

> **章节来源**：见本节末尾汇总的[附录](#附录)来源块（`maintenance.go`、`config.go` 口径）。

```bash
#!/usr/bin/env bash
# /usr/local/sbin/dnsplane-backup.sh
set -euo pipefail

MODE="${1:-daily}"
APP_DIR="/srv/dnsplane"                       # 部署根目录
DATA_DIR="$(basename "$(jq -r '.database.file_path' "$APP_DIR/config.json")")"
DATA_DIR="$APP_DIR/$(dirname "$DATA_DIR")"    # 以 file_path 所在目录为备份单元
BK_ROOT="/backup/dnsplane"
STAMP="$(date +%Y%m%dT%H%M%S)"

mkdir -p "$BK_ROOT/$MODE" "$BK_ROOT/hot"
chmod 700 "$BK_ROOT" "$BK_ROOT/$MODE"

# 1) 三库在线备份：主库每次，日志库每次，请求库仅 weekly
for db in data.db logs.db; do
  sqlite3 "$DATA_DIR/$db" ".backup '$BK_ROOT/hot/$db.$STAMP'"
done
[ "$MODE" = "weekly" ] && \
  sqlite3 "$DATA_DIR/request_logs.db" ".backup '$BK_ROOT/hot/request_logs.db.$STAMP'"

# 2) MySQL 形态时追加逻辑备份：driver 为 mysql 时改用
#    mysqldump --single-transaction --databases "{db_name}"（见热备小节，未实机）

# 3) 归档并二次加密（age 公钥由部署方保管）
tar czf - -C "$BK_ROOT/hot" ./*".$STAMP" \
  | age -R /etc/dnsplane/backup.pub -o "$BK_ROOT/$MODE/db-$STAMP.tgz.age"

# 4) 校验与留痕；密钥归档只在轮换时手工执行，不进本脚本
sha256sum "$BK_ROOT/$MODE/db-$STAMP.tgz.age" >> "$BK_ROOT/MANIFEST"
test -s "$BK_ROOT/$MODE/db-$STAMP.tgz.age"

# 5) 轮转
find "$BK_ROOT/daily"   -type f -mtime +14  -delete
find "$BK_ROOT/weekly"  -type f -mtime +56  -delete
find "$BK_ROOT/monthly" -type f -mtime +365 -delete
```
