## 简介

解析记录是 DNS 面板写入最频繁的能力族。本系统对记录不做权威存储，**云端服务商是唯一事实源**，本地只保留一份用于配额判定与对账的镜像副本（`dns_records` 表）：所有增删改直接落服务商 API，读列表也直接打云端。抽象是 11 字段的 `dns.Record`，向下映射到 22 家各不相同的 API，向上为控制台与对外 v1 提供同一套 CRUD、TTL、线路、启停、备注、权重操作。

| 能力 | 落地位置 | 当前状态 |
|------|----------|----------|
| 列表读取（分页加 7 个筛选维度） | `handler.GetRecords`，`main/internal/api/handler/domain.go:640` | 已实现 |
| 单条新增、修改、启停、删除 | `domain.go:875`、`:972`、`:1124`、`:1048` | 已实现，异步回「提交成功」 |
| 批量新增、编辑、动作 | `batch.go:47`、`:223`、`:327` | 已实现，异步 |
| 线路编目、权重、分组、厂商日志 | `domain.go:1215`；`domain_ext.go:171`、`:216`、`:357`、`:387`、`:329` | 已实现；权重仅 A 与 AAAA，分组仅阿里云与 DNSPod |
| 本地镜像与定时对账、对外 v1 同步写 | `service/record_sync.go:317`、`:378`；`apiv1/record_sync.go:121-368` | 已实现；对账默认 30 分钟一轮，v1 有 5 个同步接口 |
| 记录值搜索的统一语义 | `domain.go:749-775` 仅在子域受限分支生效 | 待实现 |

四条设计前提贯穿全模块：云端优先（`domain.go:817`）；异步写加即时回填（`domain.go:929-951`）；子域授权是二级门禁（`permission.go:335`、`:344`）；写路径与验证路径分成两条——记录接口回答「云端接受了吗」，公网是否生效由 DoH 与本机递归回答（`dns_check.go:100-196`）。

## 核心组件

### Record 抽象与 Provider 记录族

`dns.Record`（`main/internal/dns/interface.go:6-18`）是唯一的记录领域结构，11 个字段全部由各家适配器从厂商响应回填。

| 字段 | 类型 | 语义 | 关键约束 |
|------|------|------|----------|
| `ID` | string | 云端记录标识 | 3 家为合成串（AWS、PowerDNS、Spaceship），删除时反解 |
| `Name` | string | 主机记录 | 根域各家取值不一（`@`、空串、域名本身） |
| `Type` | string | 记录类型 | 枚举见附录 |
| `Value` | string | 记录值 | 部分厂商对 CNAME 与 MX 自动补尾点 |
| `TTL` | int | 生存时间 | 各家 `GetMinTTL()` 返回 0 到 3600 |
| `Line` | string | 线路编码 | Cloudflare 语义是代理开关，华为恒为空串 |
| `MX` / `Weight` | int | 优先级与权重 | 权重仅 7 家声明支持，`recordChanged` 不比对它 |
| `Status` | string | `enable` 或 `disable` | 2 家列表接口不返回该字段，留空 |
| `Remark` / `Updated` | string | 备注与更新时间 | `Remark` 三态；时间多数厂商未回填 |

`PageResult.Records` 声明为 `interface{}`（`interface.go:35-38`），消费侧一律要做 `result.Records.([]dns.Record)` 断言：`domain.go:788`、`:828`、`domain_ext.go:196`、`batch_authz.go:57`、`service/record_sync.go:498`、`acceleration.go:601`。失败行为不统一——`domain.go:828` 走 `if ok` 分支静默给出空列表，`record_sync.go:498-501` 显式返回「记录列表类型异常」。

抽象层结构如下：`Provider` 持有 15 个方法（`interface.go:41-86`），其中 8 个直接操作记录、2 个服务于记录读写前置（线路编目与最小 TTL）；`PageResult` 承载 `Total` 与 `Records`（`interface.go:34-38`），`Records` 到 `[]Record` 的还原靠消费侧断言；可选扩展接口 `RecordGrouper`（`interface.go:102-106`）由运行时类型断言接入（`domain.go:811`、`domain_ext.go:369`、`:407`），是这套抽象唯一的扩展点机制。

| 方法 | 声明 | 主要调用点 |
|------|------|------------|
| `GetDomainRecords` 9 参 | `interface.go:52` | `domain.go:784`、`:814`、`:817`、`batch_authz.go:53`、`record_sync.go:494`、`monitor.go:969` |
| `GetSubDomainRecords` 6 参 | `interface.go:55` | `domain_ext.go:191`、`acceleration.go:597` |
| `GetDomainRecordInfo` | `interface.go:58` | `batch.go:287`、`domain_ext.go:262`、`apiv1/record_sync.go:73`、`:203` |
| `AddDomainRecord` 返回 recordID | `interface.go:61` | `domain.go:932`、`batch.go:149`、`:167`、`apiv1/record_sync.go:148` |
| `UpdateDomainRecord` 全量覆盖 | `interface.go:64` | `domain.go:1020`、`batch.go:300`、`domain_ext.go:268`、`apiv1/record_sync.go:227` |

| `DeleteDomainRecord` | `interface.go:70` | `domain.go:1102`、`batch.go:400`、`apiv1/record_sync.go:275`、`acceleration.go:615` |

### 本地镜像副本

`models.DNSRecord`（`main/internal/models/quota.go:75-93`）是云端记录的本地镜像，`did` 与 `record_id` 上有联合唯一索引 `idx_dns_record_remote`（`:77-78`），所有写入统一走 `UpsertLocalRecord` 的冲突更新（`service/record_sync.go:589-601`）。表头注释把动机写得很直白：配额判定要在创建前知道「该域名现有多少条记录」，每次查云端会消耗服务商 API 配额（`models/quota.go:65-74`，与 `service/record_sync.go:23-35` 同口径）。`uid` 的语义是「本面板内创建者，0 表示云端直接创建」（`models/quota.go:89`），是区分记录来源的唯一线索。

| 写入通道 | 位置 | 触发时机 |
|----------|------|----------|
| 单条新增回填 | `domain.go:944-948`、`apiv1/record_sync.go:390` | 云端写成功之后 |
| 单条更新回填 | `domain.go:1025-1031`、`apiv1/record_sync.go:421-423` | 先读原行再改字段 |
| 启停回填 | `domain.go:1189-1191`、`apiv1/record_sync.go:332` | 状态经 `recordStatusValue` |
| 删除移除 | `domain.go:1107`、`apiv1/record_sync.go:283`、`batch.go:408` | 云端删成功之后 |
| 批量新增回填 | `batch.go:154`、`:172` 调 `upsertBatchLocalRecord`（`:188`） | 逐条成功逐条写 |
| 定时全量对账 | `service/record_sync.go:378-476` | 默认 30 分钟一轮 |

回写通道字段集合不齐：单条新增写全字段含 `weight` 与 `uid`；批量新增的助手签名里**没有权重项**（`batch.go:188`），落库时 Go 零值补 0；批量编辑只刷 `line` 与 `ttl`（`:304-306`）。`recordChanged`（`record_sync.go:513-518`）比对 Name、Type、Value、Line、TTL、MX、Status、Remark 共 8 项，**不含 Weight**——只有权重变化时走「仅刷新 `synced_at`」分支（`:426-431`），本地停在旧值；而对账更新分支的字段表里确实写了 `weight`（`:415`），只要有别的字段同时变化就被顺带纠正，这掩盖了缺口。

同步侧由 `RecordSyncer`（`record_sync.go:81-88`）承担：启动后延迟 1 分钟做首轮（`:57`、`:128`），之后以 1 分钟 tick 轮询「是否到期」（`:144`、`:153-159`），每轮重读配置，间隔改动下一个 tick 即生效。间隔由 `record_sync_interval_min` 控制，默认 30 分钟、下限 5 分钟、上限 30 天（`:38-50`、`:192-205`）：上界不是装饰，`time.Duration(n)*time.Minute` 在 int64 纳秒会回绕，注释给出两个实测回绕值并说明后果是「把同步变成每轮 tick 都跑」（`:41-48`、`:186-190`）；整数解析用 `strconv.Atoi` 而非 `fmt.Sscanf`，因为后者会把脏值解析出前缀数字且不报错（`:182-185`）；到期判定优先用进程内 `lastRun`，因为持久化时间戳只有秒精度（`:85-87`、`:207-224`）。

整轮结果落 `sys_configs` 的 5 个键（`:66-73`、`:294-307`），经 `RecordSyncStatus()`（`:277-285`）由仪表盘透出（`handler/dashboard.go:377`），前端契约在 `web/lib/api.ts:765-773`。三档计数为成功、失败、**不完整**：分页被截断的域名单列一档，注释明确「不能与整轮成功混为一谈」（`:71-72`、`:354-358`）；落盘在 `defer` 里执行，同步任务 panic 时计数仍写入（`:320-326`）。

## 架构总览

一次「新增记录」从点击到镜像落库，包含异步写与定时对账两条并行路径。

```mermaid
sequenceDiagram
    autonumber
    participant FE as 前端记录页
    participant GW as 权限中间件
    participant H as CreateRecord
    participant Q as 配额校验
    participant PV as dns.Provider
    participant CL as 服务商云端
    participant DB as dns_records 镜像
    participant SY as RecordSyncer

    FE->>GW: POST /domains/:id/records
    GW->>GW: 写 perm_read_only 与 perm_sub_domain
    GW->>H: 放行
    H->>H: 绑定密文体、子域校验、配额判定
    H->>Q: CheckQuota records
    Q->>DB: COUNT 并 JOIN domains 与 accounts
    DB-->>Q: 已用条数
    H-->>FE: 提交成功，不含云端结果
    H->>PV: SafeGo 内 AddDomainRecord
    PV->>CL: 参数映射与签名后下发
    CL-->>PV: recordID
    PV-->>H: recordID 或 error
    alt 写成功
        H->>DB: UpsertLocalRecord 冲突更新
        H->>H: 审计动作 add_record
    else 写失败
        H->>H: 审计动作 add_record_failed，镜像不动
    end
    Note over SY,DB: 默认 30 分钟一轮，逐域名串行
    SY->>PV: GetDomainRecords 分页拉全量
    PV->>CL: 逐页请求，最多 100 页每页 100 条
    SY->>DB: 建、改、删三段差异写入
    SY->>SY: 三档计数落 sys_configs
```

### 记录读取链路

`GetRecords`（`domain.go:640-835`）是唯一读列表入口，被 `router.go:136` 与 `apiv1/record.go:25` 共用。入参 `GetRecordsRequest`（`:622-633`）带 7 个筛选维度加 `group_id`。顺序：模块门禁（`:641`）→ 绑定（`:645`）→ 域名 ID 二选一兜底（`:650-656`）→ 域级权限（`:665`）→ 读 `perm_sub_domain` 拆 `allowedSubs`（`:685-698`）→ 线路名映射与状态归一（`:715-722`）→ 分支。

| 维度 | 子域受限分支 `:781-803` | 默认分支 `:804-832` |
|------|------------------------|---------------------|
| 厂商调用次数 | 每授权子域一次，`perSubLimit` 为 500 | 一次，page 与 pageSize 原样透传 |
| 单路失败 | `continue` 跳过该子域（`:785-787`） | 返回「获取记录失败」 |
| 本地精筛 `filterLocal` | 生效（`:792`） | 不生效 |
| total 来源 | `len(list)`（`:793`） | `result.Total`（`:831`） |
| 分页 | 本地切片（`:794-803`） | 由服务商分页 |
| 回写 `record_count` | 不回写 | `Total > 0` 时回写（`:824-826`） |

`filterLocal`（`:749-775`）对 SubDomain 用 `EqualFold`、对 Value 用小写包含（`:758-761`）、对 Line 精确、对 Status 经 `recordItemStatusWant`（`:838-856`）归一、对 Type 用 `EqualFold`；注释说明不再按 keyword 缩窄以避免与服务商语义重复（`:748`）。`RecordItem`（`:701-713`）是响应序列化视图而非领域模型，字段用 PascalCase 对齐前端契约；`LineName` 取不到时回落线路编码原值（`:729-732`）。

`perm_sub_domain` 由 `middleware.Permission()` 写入，该中间件挂在控制台 `auth` 组（`router.go:104`，其上方 `:99-103` 记录了补挂动机：此前从未挂载，导致只读拦截、子域过滤、审计域名三处依赖同时失效）。v1 的中间件链（`apiv1/router.go:27-34`）**不含** `Permission()`，因此 v1 侧 `perm_sub_domain` 恒不存在，子域受限用户会读到该域名全部记录；域级权限仍由 `domain.go:665` 兜住。

### 创建记录

`CreateRecord`（`domain.go:875-952`）的校验顺序固定：模块门禁（`:876-878`）→ `BindDecryptedData`（`:880`）→ 域名 ID 兜底与加载（`:885-897`，失败回「域名不存在」）→ `CheckSubDomainPermission`（`:900`，失败回「无权操作该子域名」）→ `CheckQuota(c, "records")`（`:906`）→ provider 装配（`:910`）→ 线路与 TTL 兜底（`:915-920`）→ 派发 `utils.SafeGo` 后立即回「提交成功」（`:929-951`）。

`CreateRecordRequest`（`domain.go:858-868`）里 `Name`、`Type`、`Value` 带 `binding:"required"`，`Weight` 是 `*int`。goroutine 内 30 秒超时与响应时间解耦（`:930`），失败写 `add_record_failed` 后 `return`（`:933-936`），成功写 `add_record` 再回填（`:937-948`），而 `UpsertLocalRecord` 无返回值，回填是否成功不可观测。

兜底与服务商能力无关：`domain.go:915-917` 把空线路填成字面量 `"default"`，`:918-920` 把 TTL 为 0 填成 600；`GetMinTTL()` 只在 `domain_ext.go:321` 回显给前端提示，**写路径从不校正**，因此返回 3600 的 NameSilo 会拒绝该默认值，返回 0 的 dynv6 与 Technitium 则被过于保守的 600 限制。v1 的 `CreateRecordSync`（`apiv1/record_sync.go:121-168`）把同一套规则改为同步：等云端返回（`:148`）、失败回原因与错误码并 `Abort`（`:150-154`）、成功回带 `record_id`（`:167`）；`:115-120` 说明为什么必须回传 ID——「列表是最终一致的，刚写入的记录未必立刻可见」。

`RecordExistsLocally`（`record_sync.go:554-563`）的注释承诺「供创建前的重名判定使用」，`CurrentRecordTTL`（`:636-646`）与 `CurrentRecordMeta`（`:653-663`）承诺「更新前取回原值防零值覆盖」，但四个导出函数（另含 `CountDomainRecords`，`:571-578`）在全仓无任何生产调用点——注释承诺的两项保护实际未生效。

### Cloudflare 特例

**线路语义不是线路。** `lines.go` 文件头注释说明 Cloudflare 不提供按运营商分线路的解析，其「线路」实际是代理开关——0 灰云直接回源、1 橙云流量经边缘（`lines.go:5-15`），因此编目不可能是动态列表，也不需要调 API：`Lines` 恒两条（`:17-20`），`GetRecordLine` 返回该表副本（`cloudflare.go:488-493`），`GetMinTTL` 恒返回 60（`:495-497`）。写侧把 `line == "1"` 译成 `proxied=true`、其余一律仅 DNS（`:379`、`:429`），读侧反向映射（`:273-276`、`:343-346`），灰云记录的线路恒为 `"0"`。`keyword` 与 `value` 在该家互相覆盖：两者都映射到 `search`，后写的 `value` 顶掉 `keyword`（`:224-229`）。备注走 `comment` 字段（`:283-286`、`:386`），因此单独改备注要整条重写（`:447-453`）；`weight` 形参不出现在载荷里（`:371-403`），传入被静默忽略。

**启停用改名模拟。** 暂停时子域记录加 `_pause`、根域改 `__root__`（`:468-471`），启用时反向还原（`:473-479`），读侧 `GetDomainRecords` 与 `GetDomainRecordInfo` 都做同样的还原并置 `disable`（`:264-271`、`:334-341`）。后果有二：v1 的子域回查依赖这个还原，否则会拿 `www_pause` 去比授权子域而误拒；被暂停的记录在 Cloudflare 控制台上看起来是「不存在的主机记录」。

**类型变更致 recordID 漂移。** `UpdateDomainRecord` 先回查，类型不同则删除再新建并返回 `nil`（`:406-420`，Cloudflare 已弃用 PATCH 改类型）。调用方无从得知 ID 已变，仍按旧 ID 回填镜像（`domain.go:1025-1031`、`apiv1/record_sync.go:237-247`），v1 还把旧 ID 当结果返回（`:248`）。另一处连带：回查返回的名称已被还原成不带 `_pause` 的形式，因此对已暂停记录做更新会**顺带把它启用**。

**origin 与 tunnel 绕过抽象层。** 自定义主机名的回退源与隧道 CNAME 由 `EnhanceService` 直连云端 API：`GetFallbackOrigin`（`cloudflare_enhance.go:329`）读 zone 回退源，handler 侧带 60 秒缓存（`cloudflare.go:1404-1425`）；`UpsertTunnelCnameRecord`（`:549-657`）建指向 `<tunnelID>.cfargotunnel.com` 的 CNAME（`:551`）并**强制 `proxied=true` 与 `ttl=1`**（`:630-636`、`:645-651`，隧道要求橙云），同内容且已代理时返回 `unchanged`（`:621-623`），同名非 CNAME 存在时拒绝写入并点名冲突类型（`:585-587`）；`DeleteTunnelCnameRecordIfMatch`（`:662`）只在内容匹配时才删。调用点在 `cloudflare.go:2203` 与 `:2268`。这条通道既不写 `add_record` 审计，也不回填镜像——隧道 CNAME 要等下一轮对账才进入配额计数。

### DoH 查询

`main/internal/dns/doh/doh.go`（163 行单文件包）不参与记录 CRUD，它回答「记录是否已在公网生效」。查询流程是四步：`QueryContext` 先把类型名过 `dohTypeNumbers` 映射表，未命中直接返回错误（`doh.go:76-80`）；随后从池里随机选一家发起 GET（`:82-83`）；只有响应体 JSON 解析失败（`errMalformed`）才剔除该家、从剩余池再随机一次（`:87-107`）；网络错误、空响应、状态码异常一律原样返回不重试（`:87-89`、`:137-139`）。

`dns_check.go` 接入有两个细节：回退后把服务器名标注为「原名加 (DoH回退)」并用 DoH 主机名覆盖 IP 字段（`:165-167`），让结果来源可见；`queryDNSViaDoH` 给 `2*doh.Timeout`（`:189`），注释说明 Cost 语义要求记录两段合计耗时，避免上下文提前取消掩盖真实耗时（`:183-187`）。`LookupRecord`（`monitor.go:923-980`）是另一条读路径，走服务商抽象：先做域级与子域级双重校验（`:946-954`），再调 `GetDomainRecords`——但该调用把 `req.SubDomain` 放进了 **keyword** 槽位（`:969`，签名见 `interface.go:52`），各家对 keyword 解释不一，跨厂商结果不可比，且使用 `context.Background()` 无超时约束。

## 性能考虑

| 操作 | 厂商 API 次数 | 证据 |
|------|---------------|------|
| 读列表（域主或管理员） | 2 次：线路编目 1 加记录 1 | `domain.go:716`、`:817` |
| 读列表（子域受限，n 个子域） | 1 加 n 次，每次 500 条 | `domain.go:783-784` |
| 单条写，或 v1 单条更新 | 1 次写加 1 次镜像写；v1 更新是 2 次读加 1 次写 | `domain.go:932`、`:944`；`apiv1/record_sync.go:73`、`:203`、`:227` |
| 批量编辑 N 条 | 索引 1 到 10 页加 N 乘（1 重建加 2 次调用） | `batch_authz.go:135`、`batch.go:287`、`:300` |
| 批量启停或删除 N 条 | 索引 1 到 10 页加 N 乘（1 重建加 1 次调用） | `batch_authz.go:77-84`、`:134-145` |
| 单域名对账 | ceil(记录数 / 100)，最多 100 页 | `record_sync.go:486`、`:494` |

**批量权限校验的索引重建**是最突出的一处。`fetchCloudRecordRR`（`batch_authz.go:77-84`）内部调用 `cloudRecordRRIndex`，后者逐页打厂商（`:52-53`），而它在 `checkBatchRecordSubDomain` 的循环体内被逐条调用（`:134-135`），于是**每个 record_id 都重建一次全量索引**：选中 200 条做批量删除时理论上限 2000 次调用，配额瞬间打满且必然超时。修法很小——`cloudRecordRRIndex` 已是完整的索引构造函数，只需在循环外调用一次、循环体查表（`:116-145` 结构不变）。属「实现正确但调用方式不对」。

**批量创建并发**刻意不做：`BatchAddRecords` 在**一个** `utils.SafeGo` 协程里串行遍历（`batch.go:117-175`），整批共用 120 秒超时（`:118`），编辑与动作同样各 120 秒（`:280`、`:383`）。隐性上限是：单条平均耗时超过「120 除以条目数」秒时，后续条目在已取消的上下文里全部失败，而失败只计入 `failCount`（`:151`），审计里只有「成功 x, 失败 y」（`:176`），看不出是云端拒绝还是超时截断。文本模式与结构模式都没有条目数上限（`:131-174`），跨请求也无账户级并发闸。`BatchActionRecords` 另有可观测性缺陷：`switch action` 缺 `default`（`:392-401`），未知 action 时 `opErr` 恒 nil，走成功路径 `successCount++`（`:406`），既不报错也不改数据。

`SyncAllDomainRecords` 逐域名**串行**（`record_sync.go:343-364`），理由写在注释里——服务商普遍按账户限流，并发会打满配额反而拖慢整体（`:309-316`）。多域名下一轮对账耗时线性增长，因此同步器自持可取消上下文（`:97-100`），`fetchAllRecords` 每页检查 `ctx.Err()`（`:491-493`），保证关停不拖住 `StopRecordSync` 的 `wg.Wait`（`:108-122`）。测试锚点是 `TestStopRecordSyncInterruptsInFlightSync`（`record_sync_test.go:90`）与 `TestFetchAllRecordsStopsWhenContextCanceled`（`:176`）。`recordChanged` 的另一层价值是让未变化记录只刷时间戳（`:426-431`），配合空状态豁免（`:531-533`）把一轮写事务压到「真实变化数」。

**分页处理实测**：`ProviderFeatures.Page` 为 true 的有 6 家，但真正忽略分页参数的只有 4 家——两者不能互推。AWS（`aws.go:599-652`）、百度（`baidu.go:267-364`）、NameSilo（`namesilo.go:144-232`）、PowerDNS（`powerdns.go:243-340`）的函数体内均无页切片，返回全量；HE DNS 本地切片（`henet.go:274-278`），Spaceship 透传 skip 与 take（`spaceship.go:108-109`），青云DNS 透传 offset 与 limit（`qingcloud.go:165`）。handler 默认分支不做本地二次分页（`domain.go:816-831`），`pageSize` 只兜下界不封上界（`:675-682`），因此前 4 家在千条记录域名下整表返回且分页控件失效，与 `client.tsx:725` 的空转发叠加。

### 专项一：SetRecordStatus 缺子域校验

`SetRecordStatus`（`domain.go:1124-1196`）在安全审计后补齐了域级权限与只读检查——`:1151-1152` 的注释写明「原实现遗漏权限校验，与 CreateRecord、UpdateRecord、DeleteRecord 不一致；拥有任意域名读权限的用户可对全站任何记录调启停 → DoS」。但**子域校验仍未补**：与 `CreateRecord`（`:900`）、`UpdateRecord`（`:1000`）不同，这里没有任何 `CheckSubDomainPermission` 调用，`DeleteRecord` 同样如此（`:1076` 只有域级）。

入参结构解释了原因：`SetRecordStatusRequest` 只有 `DomainID`、`RecordID`、`Enable`（`domain.go:1113-1117`），请求里没有主机记录，无法本地判子域；批量族已用云端反查补上此口（`batch_authz.go:132-145`），单条路径未复用。`batch_authz.go:18-21` 的文件头注释登记了这个不对称——「单条接口在建写之前一律走 `CheckSubDomainPermission`」对 add 与 edit 成立，对 delete 与 status 并不成立。

修复素材仓库里已有两份：`batch_authz.fetchCloudRecordRR`（`:77-84`）与 `apiv1/record_sync.go:70-82`。取舍要说明：前者每次调用重建全量索引，搬到单条路径会让「暂停一条记录」变成最多 10 页厂商查询；更合适的是复用 `GetDomainRecordInfo`（`apiv1/record_sync.go:73` 正是这么做的），成本恒定 1 次调用。另外 `CheckSubDomainPermission` 对空主机记录返回 true（`permission.go:355-358`），「不传就等于不限」，补校验时必须先确认能拿到非空判定依据，否则加了调用也是空转。

### 专项二：只读判定无类型断言保护

`domain.go:1081` 与 `domain.go:1159` 写法完全相同：

```go
if readOnly, exists := c.Get("perm_read_only"); exists && readOnly.(bool) {
```

三个可验证事实：`exists &&` 有短路保护，键不存在时不执行断言，不会因「未写入」而 panic；键是否存在取决于中间件是否走到写入分支——管理员在 `permission.go:138-141` 提前返回，无域名 ID 的请求在 `:144-148` 提前返回，只有 `:168`（自有账户写 `false`）与 `:201`（委派写 `perm.ReadOnly`）两处写入；断言本身无 comma-ok，当前两处写的都是布尔值故**不构成在线缺陷**，属健壮性问题——任何后续写入方（例如把权限对象整体塞进上下文）都会让这两行 panic，被 Recovery 转成 500，而非「拒绝写入」这一安全语义。

同仓库已有正确写法：`domain_ext.go:63-68` 的受检断言 `if ro, ok := readOnly.(bool); ok && ro`；`permission.go:387-393` 的 `UserModuleAllowed` 全程用带第二返回值的断言。更实质的问题是判定重复且口径不一：中间件已在 `permission.go:183-187` 按只读拦截过一次，handler 又各自判一次，v1 走 `requireWritable`（`scope.go:94-109`）直接查权限表——三处判同一件事、用两套数据源，这是「只读用户仍能写」难以一次修干净的结构原因。两处应改为受检断言或直接复用 `ensureDomainWrite`（`domain_ext.go:59-76`），后者一次完成「域级、只读、子域」三段检查，能同时解决专项一的缺口。

## 结论

本模块骨架清晰：`dns.Provider` 定义 8 个记录方法，22 家适配器落到厂商 API，handler 层做权限与配额，service 层维护一份以云端为准的镜像副本。KISS 与 YAGNI 的取舍在几处刻意设计上看得见——镜像不参与读链路、异步写加即时回填、v1 单独重写为同步而不改控制台行为。成立之处值得保留：本地镜像承担配额判定避免每次创建消耗上游配额（`record_sync.go:23-35`）；以云端为准的三段差异对账穷举两边差集（`:410-467`）；v1 同步让程序化调用方拿得到成败与 recordID（`apiv1/record_sync.go:19-28`）；批量族判定依据不取自请求，攻击者不能自证清白（`batch_authz.go:23-31`）；空状态豁免比较避免每轮空写（`record_sync.go:520-533`）；截断时跳过删除段而非贸然对齐（`:457-467`）。

|------|------|----------|
| A / AAAA | 主机名到 IPv4 / IPv6 | 权重仅 7 家声明支持，且只有这两类可改权重（`domain_ext.go:199`） |
| CNAME | 别名 | 与 A 或 AAAA 在同线路上冲突，见「记录冲突」 |
| MX | 邮件交换 | 使用 `MX` 优先级字段，部分厂商自动补尾点 |
| TXT | 文本 | ACME 挑战使用，同子域允许多条 |
| NS | 名称服务器 | 子域委派使用 |
| SRV / CAA | 服务定位 / 证书签发授权 | Technitium 与 DNSLA 支持 SRV；doh.pub 对 CAA 返回错误体，见「DoH 查询」 |
| PTR | 反向解析 | Technitium 支持，DNSLA 白名单里没有 |

三个类型在特定服务商处可用但前端表里没有，创建入口不可达：ALIAS（Spaceship，`spaceship.go:156-160`）、ANAME 与 DNAME（Technitium，`technitium.go:191-297`）、URL 转发（DNSLA 类型码 256，`dnsla.go:35-37`；能力位见 `interface.go:160` 的 Redirect）。DNSLA 白名单只有 9 项，未命中的类型反查表返回零值并原样下发，属静默错误而非显式拒绝。

批量文本模式不显式指定 `type` 时走 `detectRecordType`（`batch.go:146-148`、`:197-209`）：`net.ParseIP` 成功得 A 或 AAAA，含冒号得 AAAA，其余一律得 CNAME——因此一条 MX 或 TXT 在批量文本模式下会被误判成 CNAME，除非调用方显式带 `type`（`auto` 与空串等价）。`SmartParseRecord` 是另一套规则：可解析为 IP 得 A 或 AAAA，含点且不含空格斜杠反斜杠得 CNAME，**其余一律 TXT**（`domain_ext.go:276-299`）。另有 `IsIPValue`（`monitor.go:1218`）与 `isIPv4`（`acceleration.go:631-642`）两份独立 IP 判定实现，是剩余重复点。

### 各家最小 TTL 与特性位

`GetMinTTL()` 是接口里唯一不带上下文参数的方法（`interface.go:82`），返回 0 表示厂商未声明最小值。实测 22 家取值分档：0 为 dynv6（`dynv6.go:432`）与 Technitium（`technitium.go:644`）；1 为阿里云ESA（`aliyunesa.go:478`）、GoEdge（`goedge.go:696`）、华为云（`huawei.go:381`）；60 为 Cloudflare（`cloudflare.go:496`）、DNSmgr（`dnsmgr.go:462`）、百度（`baidu.go:499`）、PowerDNS（`powerdns.go:606`）、青云DNS（`qingcloud.go:516`）、Spaceship（`spaceship.go:286`）、AWS（`aws.go:868`）、DNSLA（`dnsla.go:401`）、腾讯云EO（`tencenteo.go:471`）；300 为 HE DNS（`henet.go:434`）与宝塔（`bt.go:384`）；600 为阿里云（`aliyun.go:339`）、DNSPod（`dnspod.go:331`）、京东云（`jdcloud.go:373`）、西部数码（`west.go:323`）、火山引擎（`huoshan.go:471`）；3600 为 NameSilo（`namesilo.go:313`），全仓最大。控制台创建记录的兜底 TTL 恒为 600（`domain.go:918-920`）且不做上界校正，`GetMinTTL()` 只在快速信息里回显（`domain_ext.go:321`）——对 NameSilo 域名该默认值低于厂商下限，对返回 1 的三家又过于保守。

`ProviderFeatures`（`interface.go:157-167`）里与记录直接相关的位取自各家 `Register` 的 `Features` 字面量（例如 `aliyun.go:25-27`、`dnspod.go:27-28`、`cloudflare.go:31-32`、`spaceship.go:30-39`）。汇总：`Status` 为真 14 家（为假的 8 家是阿里云ESA、AWS、百度云、dynv6、HE DNS、华为云、NameSilo、Spaceship）；`Weight` 为真 7 家（宝塔、DNSLA、DNSPod、GoEdge、火山引擎、青云DNS、腾讯云EO）；`Page` 为真 6 家（AWS、百度云、HE DNS、NameSilo、PowerDNS、Spaceship）；`Log` 为真仅阿里云与 DNSPod；`Remark` 为 1 的 4 家（阿里云、DNSmgr、DNSPod、青云DNS）、为 2 的 9 家（阿里云ESA、百度云、宝塔、Cloudflare、GoEdge、华为云、火山引擎、PowerDNS、Technitium）、其余 9 家为 0。

两类声明都**不能只信字面值**：`Page` 与「忽略分页」不能互推——声明为真的 6 家里 Spaceship 与 HE DNS 实际处理了分页，忽略参数的是另外 4 家（见「分页处理实测」）；`Log` 声明为真的 DNSPod，其 `GetDomainRecordLog` 实现整段被注释、返回错误（`dnspod.go:306` 附近）。以特性位驱动 UI 时应回到各家方法实现二次确认。
