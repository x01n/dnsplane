## 简介

本文档描述 DNSPlane 后端 HTTP 中间件层的完整装配关系与逐个组件的行为契约。系统存在**两条互不相交的中间件链**：

- 控制台链 `/api`：面向浏览器，依赖 HttpOnly Cookie 会话 + CSRF double-submit，鉴权走 JWT。
- 对外 API 链 `/api/v1`：面向 API Key 客户端，无 Cookie，鉴权走 HMAC-SHA256 签名，响应经 `AdaptResponse` 统一改写。

`main/internal/api/router.go:63` 显式把 `apiv1.Setup(r)` 挂在引擎根节点而非 `/api` 分组下，原因写在 `router.go:57-62` 的注释里：`/api` 分组的 CSRF 校验会让没有 Cookie 的 API Key 客户端所有写请求被拒，而签名本身即身份与完整性凭据。

本文重点回答三个问题：

1. 每个中间件的作用、输入输出、失败响应与精确挂载位置。
2. **双层 panic 恢复**为什么必须让 `Recovery` 紧跟 `RequestTrace`——顺序颠倒会让请求日志完全丢失。
3. `apikey.go` 与 `sign.go` 中的 `DecryptAndVerify` 为何成为零引用死代码。

## 详细组件分析

### SecurityHeaders 与 CORS

`SecurityHeaders`（`auth.go:483`）纯写响应头，不读上下文、不中断链。固定注入 `X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`、`Permissions-Policy` 与一条完整 CSP（`auth.go:490-501`）。CSP 中 `frame-src` 被单独列出，注释在 `auth.go:496` 说明原因：三家验证码 SDK 都把控件渲染进跨源 iframe，缺该指令会回落 `default-src 'self'` 而拦截。HTTPS 条件下追加 HSTS（`auth.go:503-505`），不带 `includeSubDomains`。

`CORS`（`auth.go:516`）输入是 `Origin` 请求头，输出是四个 `Access-Control-*` 头。放行判定在 `isAllowedOrigin`（`auth.go:542`）：优先匹配系统 `site_url`，未配置时只允许与当前请求 `Host` 一致的来源，`localhost`/`127.0.0.1` 作为开发豁免。`OPTIONS` 直接 `AbortWithStatus(204)`（`auth.go:527-530`），因此 `RequestTrace` 必须排在 CORS 之后，否则预检请求会污染请求日志——这条依赖写在 `router.go:46`。

失败响应：CORS 不回 403，仅省略 `Access-Control-Allow-Origin`，由浏览器拦截，因此服务端日志看不到显式拒绝，排障需看 `Origin` 落库字段。

`X-Error-ID`、`X-Request-ID`、`X-Token-Expiring` 通过 `Access-Control-Expose-Headers`（`auth.go:525`）显式暴露给跨源脚本，前端才能显示错误追踪号。

### RequestTrace

`request_trace.go:135`。作用：生成 `X-Request-ID`、包裹响应写入器、在 `c.Next()` 返回后把一条 `models.RequestLog` 异步落库。

输入与输出：

| 项目 | 来源 | 上限/处理 | 位置 |
| --- | --- | --- | --- |
| `X-Request-ID` | 自生成 `GenerateRequestID()` | 原子序列 + UnixNano，非加密随机 | `:47` |
| 请求体 | `io.LimitReader(MaxBodySize)` | 64KB，读完回填 `NopCloser` | `:151-154` |
| 请求头 | 多值合并 + `Host` 补记 | 交给 `SanitizeHeadersForLog` | `:157-172` |
| 响应体 | `respCaptureWriter` 缓冲 | 成功 16384B，失败 256KB | `:174-182`、`:240-246` |
| DB 查询 | `DBQueriesKey` | 累加耗时并 JSON 化 | `:251-261` |

关键常量集中在 `request_trace.go:24-32`：`RequestIDKey`、`ErrorIDKey`、`DBQueriesKey`、`ErrorStackKey`、`ExtraDataKey`、`MaxBodySize`、`MaxResponseSize`；正文截断另有 `maxRequestLogBodyLen = 8192`（`:57`）与 `maxSuccessResponseCapture = 16384`（`:60`）。

`X-Error-ID` 的送达依赖写入器重写：`respCaptureWriter` 在 `WriteHeader`（`:80`）、`WriteHeaderNow`（`:86`）、`Write`（`:91`）三处调用 `noteStatus`（`:73`），因为状态码一旦写出响应头即被快照，之后设的头不再送达（`request_trace.go:120-121` 注释）。`MarkErrorID`（`:122`）对 `< 400` 或已写出的响应直接返回，且已有 `ErrorID` 时复用同一值，保证响应头与落库记录一致。

落库分支（`:296-302`）：`logstore.Store` 处于 Redis 模式时只写 Redis，避免与 SQLite 双写；否则写 `database.RequestDB`。整个落库在 goroutine 内完成，主链路不等待。

请求体脱敏顺序值得注意：先取解密明文（`GetDecryptedData`），表单 URL 编码转 JSON，再统一 `SanitizeBodyForLog`，最后截断（`:211-231`）。响应侧同样脱敏，因为登录/刷新类接口可能回显 token（`:247-248`）。

```go
// request_trace.go:196-209 错误判定

if isError {
    errorID = c.GetString(ErrorIDKey)
```

这说明 `has_error` 与 HTTP 状态码是**两条独立的错误信号**：`SetError`（`:316`）置位 `has_error`，即便 handler 返回 200 + `code:-1`（控制台风格）也会记为错误请求。

### Recovery 内层

`recovery.go:21`，全文件仅 78 行，只做四件事：

1. 区分连接中断与真实 panic。`net.OpError` → `os.SyscallError` → 错误串含 `broken pipe` 或 `connection reset by peer` 判定为客户端断开（`:26-35`），仅 `logger.Warn` 后 `Abort`，不告警、不写 500 体。
2. 采集 `runtime.Stack` 到 8192 字节缓冲（`:44-46`）。
3. `SetError(c, "PANIC: ...")` 与 `c.Set(ErrorStackKey, stackTrace)`（`:62-63`），把错误信息交回 `RequestTrace` 落库。
4. 若响应已部分写出则只 `Abort`（`:64-67`），避免二次写 body；否则返回 500 且体为 `{"code":-1,"msg":"服务器内部错误"}`（`:70-73`）。

失败响应表：

| 场景 | 判定条件 | HTTP | 响应体 | 位置 |
| --- | --- | --- | --- | --- |
| 客户端断开 | brokenPipe | 无（Abort） | 无 | `:48-54` |
| panic 且响应已写出 | `c.Writer.Written()` | 保留原状态 | 原内容不追加 | `:64-67` |
| panic 且未写出 | 默认 | 500 | `{"code":-1,"msg":"服务器内部错误"}` | `:70-73` |

`**Recovery 与 Logger 的分工**`：`Logger` 只输出到控制台与日志文件，`Recovery` 只写数据库所需的错误上下文，两者无耦合，故 `Recovery` 不重复打印请求行。

### 双层 panic 恢复设计

这是本层最反直觉、也最容易被误改的一处。`router.go:34-43` 的块注释给出了完整理由，逐条对应实现：

```go
/*
 * panic 恢复分两层，内层必须紧跟 RequestTrace：
 *   - RequestTrace 的落库代码在 c.Next() 之后，panic 若穿透到链首，这段代码不会执行，
 *     请求日志将完全丢失（实测：仅外层 gin.Recovery 时 RequestLog 零记录）
 *   - 内层在此处被 RequestTrace 包裹，middleware.Recovery 先 SetError 并写 ErrorStackKey，
 *     再把 panic 挡在 RequestTrace 之内，使 c.Next() 正常返回后完成落库，保留 ErrorID 与堆栈
 *   - 外层 gin.Recovery 保留，兜住不经 RequestTrace 的静态资源、页面路由与 NoRoute 的 panic
 */
```

### DecryptAndVerify 与 apikey.go 的死代码成因

两个组件形态不同，但根因相同：**能力被迁移到新的挂载点，旧实现留在原包内未被删除**。

`sign.go:17` 的 `DecryptAndVerify` 实现的是"前端加密请求体"链路：解析 `{key, iv, data}` 三段信封（`:19-29`）→ `utils.HybridDecryptWithKey` 混合解密（`:37`）→ 从 `Authorization` + `X-Refresh-Token` + `X-Secret-Token` 派生签名密钥（`:49-58`）→ `utils.ParseSignedRequestWithKey` 校验签名（`:61`）→ 写 `aes_key` 与 `decrypted_data`。

它的失败响应全部是 **HTTP 200 + `code:-1`**，msg 分别为 `请求格式错误`、`请求解密失败`、以及签名校验的 `err.Error()` 原文（`:26`、`:40`、`:64`）。

关键事实：**全仓无任何挂载点**。`rg -n 'DecryptAndVerify'` 在 Go 源码中只命中定义处与三处注释（`sign.go:16`、`permission_route_test.go:57`、`handler/dashboard_proxy_test.go:70`），没有任何 `Use` 调用。它的存在被两处测试注释反过来证实为缺失：

- `permission_route_test.go:56-58`：写入 `decrypted_data` 的 `DecryptAndVerify` 中间件从未被挂载。
- `handler/dashboard_proxy_test.go:69-73`：`DecryptAndVerify` 与 `JSONBodyToDecryptedData` 两个会写 `decrypted_data` 的中间件"在本仓均无挂载点"，因此 `BindDecryptedData` 恒走 `ShouldBindJSON` 明文分支，请求在 `binding:"required"` 阶段就被拦下。

但 `sign.go` 的其余部分**并未失效**：`EncryptedResponse`（`:142`）被 `handler/dashboard.go:326` 实际调用，`GetDecryptedData`（`:84`）、`BindDecryptedData`（`:104`）、`GetOriginalResponse`（`:175`）被 handler 层与 `request_trace.go:213`、`:235` 广泛使用。这解释了为何死代码长期存活——文件本身是活的，只有入口中间件是空的，删除单个函数需要确认整条前端加密协议是否还对外承诺。

`middleware/apikey.go` 的成因更清晰：`APIKeyAuth`（`:44`）与 `JSONBodyToDecryptedData`（`:27`）在 `apiv1` 包内各有一份新实现（`apiv1/auth.go:44`、`:143`），且新实现改用 v1 错误码（`Fail`/`Failf`）而非裸 JSON。`apiv1/router.go:30-31` 因同包引用直接写成 `APIKeyAuth()`，`rg -n 'middleware\.APIKeyAuth|middleware\.JSONBodyToDecryptedData'` **零命中**，因此 `apikey.go` 全文件（含 `computeHMACSHA256` `:108`、`APIKeyTimestampTolerance` `:20`）都不再进入运行时链路。

| 死代码 | 行数 | 替代实现 | 未删除的可观测原因 |
| --- | --- | --- | --- |
| `sign.DecryptAndVerify` | `sign.go:17-72` | 无（前端加密链路整体停用） | 同文件的响应封装被大量引用 |
| `middleware.APIKeyAuth` | `apikey.go:44-105` | `apiv1.APIKeyAuth:44` | 错误码协议升级为 v1 枚举 |
| `middleware.JSONBodyToDecryptedData` | `apikey.go:27-37` | `apiv1.JSONBodyToDecryptedData:143` | 同上，同包名遮蔽需显式限定 |

风险说明：这三处都是 `exported`，编译器与 `go vet` 不会报警，静态检查也无法识别，只能靠引用扫描发现。若后续重启前端加密链路，直接挂 `middleware.DecryptAndVerify` 会与新式 `CORS` 放行头（`X-Secret-Token` 已在 `Allow-Headers` 内，`auth.go:524`）兼容，但会绕过 v1 错误码体系，需明确归属。

## 性能考虑

热路径上每请求都会执行的成本项，按量级排序：

| 开销点 | 实现 | 上限/缓解 | 位置 |
| --- | --- | --- | --- |
| 请求体读取 | `io.LimitReader` 全读入内存 | 64KB | `request_trace.go:152` |
| 响应体截取 | 缓冲复制 | 成功 16KB / 失败 256KB | `:60`、`:31` |
| body/响应脱敏 | JSON 递归解析 | 命中关键字即掩，`>8192` 截断 | `:228-231` |
| 请求头序列化 | map 合并 + JSON | 敏感头不落明文 | `:157-172` |
| DB 查询收集 | 每请求一个切片指针 | `AddDBQuery` 追加 | `:346` |
| 请求日志落库 | `go func` 异步 | Redis 模式仅写 Redis | `:296-302` |
| 审计落库 | `utils.SafeGo` 异步 | 截断 500/200 | `audit.go:74-88` |
| 用户查询 | 10 秒 TTL 缓存 | 权限变更延迟可接受 | `auth.go:166-170` |

三个具体取舍值得记录：

1. `GenerateRequestID`（`request_trace.go:47`）用**原子自增 + UnixNano**而非 `crypto/rand`，注释直言"避免每请求 crypto/rand 开销"；而 `GenerateErrorID`（`:53`）仍走 `crypto/rand`，因为错误路径低频且 ID 会暴露给用户。
2. 请求日志与审计都异步写，代价是**响应已返回但日志尚未落库**。测试为此专门实现了 `waitRequestLog` 轮询等待（`recovery_trace_test.go:38` 超时报错可见），文档层面须承认这个可见延迟。
3. `Logger` 不写正常快速请求到文件（`logger.go:243`），把文件 I/O 只留给 4xx/5xx/慢请求，是磁盘压力与可观测性的直接折中。

`CSRF` 与 `Auth` 都使用常量时间比较（`csrf.go:109`、`apikey.go:94` 与 `apiv1/auth.go:118`），这部分不追求速度而追求时序一致性，不应被"优化"为 `==`。

## 结论

本次梳理确认了四项事实：

1. **两条链彻底分离是有意的架构决策**，不是复制粘贴。`/api` 依赖 Cookie + CSRF，`/api/v1` 依赖签名 + 响应适配，共用点只有引擎级三件套与 `RequestTrace`/`Recovery`/`CORS`/`AuditLog` 四个可复用中间件。
2. **双层 panic 恢复的顺序不可调换**，`router.go:34-43` 的注释 + `recovery_trace_test.go` 三条测试构成"文档—实现—回归"三位一体的防护。内层负责保住请求日志与 `ErrorID`，外层负责兜住非 `/api` 路径。
3. **三处死代码已定位到具体行**：`sign.go:17` 的 `DecryptAndVerify` 无任何挂载点，`apikey.go` 的 `APIKeyAuth` 与 `JSONBodyToDecryptedData` 被 `apiv1` 包内新实现取代。它们都是 exported，静态检查无法发现，只能靠引用扫描维持认知。
4. **中间件依赖以顺序与上下文键表达**，因此"漏挂"不会报错只会静默失效——`Permission` 的历史事故（`router.go:97-103`）是最直接的证据。

遗留待观察：`apiv1/router.go:33` 注释提到"认证与限流之后"，但仓库内未见限流中间件实现，属注释与现状不一致（标记为待确认，不推断为已存在）。

**建议的后续动作**（未执行，属建议）：若确认前端加密协议不再对外承诺，删除 `DecryptAndVerify` 与其独占依赖分支；`apikey.go` 可整体删除，前提是 `apiv1` 新实现已通过等价测试覆盖（`apiv1/*_test.go` 中 6 处 `v1.Use(APIKeyAuth())` 表明覆盖存在）。
