### 链层：两条互不继承的链

控制台链与对外链刻意不共享分组。`main/internal/apiv1/router.go:12-15` 的注释给出了唯一理由：`/api` 分组带 CSRF double-submit 校验，API Key 客户端既没有 cookie 也无从取 token，继承那条链会让所有写请求在 CSRF 处被拒；签名本身就是身份与完整性凭据。

| 维度 | 控制台 `/api` | 对外 `/api/v1` |
| --- | --- | --- |
| 挂载点 | `api/router.go` 的 `r.Group("/api")` | `apiv1/router.go` 的 `engine.Group("/api/v1")` |
| 调用方 | `main.go:128` → `api.SetupRouter(staticFS)`；`api/router.go:63` → `apiv1.Setup(r)` | 同左（v1 由控制台路由文件反向装配） |
| 鉴权 | Cookie + JWT + `middleware.Auth` | HMAC-SHA256 签名 `APIKeyAuth` |
| CSRF | `middleware.CSRF()` | 不挂载 |
| 响应 | `{code, msg, data}`，可加密混淆 | `OK/Fail/Failf` + `request_id` |
| 路由量 | 快照 226 条 | 快照 145 条（全部 POST） |

### 业务层：handler 是唯一共享实现

`apiv1` 不复制业务逻辑，它直接复用 `handler` 包的同名函数，只替换认证与响应格式。唯一例外是内部使用 `utils.SafeGo` 异步执行的写接口——程序化调用需要真实成败与失败原因，所以 `apiv1/record_sync.go` 重写为同步实现（快照 444 行）。

`requireAdmin` 与 `requireUserModule` 定义在 `main/internal/api/handler/account.go:43` 与 `:67`，被同包各 handler 调用；`apiv1` 侧对应的是 `scope.go` 的 `requireModule` / `requireAdmin`。两套语义相同、入口不同，新增接口时不要混用。

#### GOTMPDIR 非 /tmp 的坑

现象是 `go build` 报 `write $WORK/_pkg_.a: disk quota exceeded`。`/tmp` 是带 `usrquota` 的 tmpfs，**用户配额**已满而 tmpfs 整体仍有 6.3G 可用，`df` 显示 `Used 73%` 看不出问题，只有实际写入才失败。仓库的既有处置是把 `GOTMPDIR` 指向非 `/tmp` 路径，全程构建与测试都在该路径完成：

```bash
# 一次性：为当前 shell 指定构建临时目录
export GOTMPDIR=/home/clfchen/.cache/go-work
mkdir -p "$GOTMPDIR"

# 三条准入门禁命令（工作目录必须是 main/）
cd main
GOTMPDIR="$GOTMPDIR" go build   -gcflags="-lang=go1.26" ./...
GOTMPDIR="$GOTMPDIR" go vet     ./...
GOTMPDIR="$GOTMPDIR" go test    ./... -count=1
```

`$HOME/.cache/go-build` 在 `devlog.md` 中已增至 40G。`go clean -cache` 能回收，但那是全局缓存、会拖慢后续所有构建，属于需先确认的操作，不要在迭代中顺手执行。同理，`/tmp` 下的大件占用（`/tmp/engperf` 5.9G 等）**未被删除**，因为归属未经逐个确认——排查配额时先确认归属，再谈清理。

### 构建流程

`scripts/build.sh` 是本地一键构建入口，做三件事：前端 → 后端交叉编译 → 校验和。


版本号优先级为：环境变量 `VERSION` > 仓库根 `VERSION` 文件 > `git describe --tags --always --dirty` > `dev`。产物落在 `dist/dnsplane-linux-<arch>`，并生成 `dist/SHA256SUMS`。

一个已验证的不一致点值得记录：`build.sh` 传入 `-ldflags="-s -w -X main.Version=${VERSION}"`，但 `main` 包内（仅 `main.go` 一个文件）检索不到 `Version` 标识符；CI 的构建命令是 `CGO_ENABLED=0 go build -buildvcs=false -trimpath -ldflags="-s -w"`，不含 `-X main.Version`。**推断**：Go 链接器对不存在符号的 `-X` 静默忽略，因此不影响构建成功，但版本号并未真正注入二进制。若需要版本可追溯，应先在 `main` 包补 `var Version = "dev"`，再依赖该 ldflags。

### 参数绑定与上下文约定

控制台 handler 一律经 `middleware.BindDecryptedData` 取参（`main/internal/api/middleware/sign.go:104`）。它的分支必须理解清楚，否则会写出只在加密链路下工作的代码：

```go
// 语义摘自 main/internal/api/middleware/sign.go
func BindDecryptedData(c *gin.Context, v interface{}) error {
    data := GetDecryptedData(c)
    if data == nil {
        // 明文链路：GET/HEAD 走 Query，其余走 JSON body
        if c.Request.Method == http.MethodGet || c.Request.Method == http.MethodHead {
            return c.ShouldBindQuery(v)
        }
        if err := c.ShouldBindJSON(v); err != nil {
            // POST 无 body（如 /accounts/:id/delete）时 ShouldBindJSON 报 EOF，
            // 路径参数由 handler 自行补全，这里按「无参」处理而非报错
            if errors.Is(err, io.EOF) { return nil }
            if strings.Contains(strings.ToLower(err.Error()), "unexpected end of json input") {
                return nil
            }
            return err
        }
        return nil
    }
    // 加密链路：decrypted_data 已在上下文，序列化后回填结构体
    b, err := json.Marshal(data)
    if err != nil { return err }
    return json.Unmarshal(b, v)
}
```

三条约定：

- 路径参数与 body 参数**分开取**。`c.Param("id")` 不能被 `BindDecryptedData` 替代；且路径参数为空时必须早退，因为 `First(&cat, "")` 会退化成不带主键条件的查询、静默命中全表第一条。`apiv1` 的路由表没有路径参数，`c.Param` 恒为空串，这条退化路径是**可达的**。
- 响应只走 `middleware.SuccessResponse` / `SuccessMsg` / `ErrorResponse` / `ErrorResponseWithCode`。`ErrorResponse` 会先 `SetError(c, msg)`，把错误上下文写入请求追踪，这是排错时能查到 ErrorID 的前提。
- 需要用户身份时读上下文键 `user_id`（**字符串**，不是 uint）、`username`、`level`。`level >= 2` 为管理员，这是 `handler/account.go:43` 与 `apiv1/scope.go:38` 共同的判定。

后端性能瓶颈集中在「出站上游调用」与「日志落库」两类，缓存层是唯一的横向缓解手段。

## 结论

本仓库的后端贡献体验可以压缩成三条命令、两条链、一份实现：

- **三条命令**：`go build -gcflags="-lang=go1.26" ./...`、`go vet ./...`、`go test ./... -count=1`，工作目录 `main/`，`GOTMPDIR` 必须落在非 `/tmp` 路径。验收写「全部含测试的包 ok、FAIL 包数 0」并附当次实测包数（当前 15 个）。
- **两条链**：控制台 `/api` 与对外 `/api/v1` 不共享分组，CSRF 是唯一分水岭；链顺序不是风格问题，`Recovery` 与 `RequestTrace` 的内外关系直接决定 panic 时能否留下请求日志。
- **一份实现**：`handler` 是唯一的业务实现，`apiv1` 只做鉴权、参数桥接与响应重编码。这条复用带来两个必须承认的代价——中文错误文案到错误码的**有损映射**，以及异步写接口在对外语义下必须重写为同步。

三个已定位、可低成本推进的改进项：`apiv1/util.go` 把测试辅助编入生产二进制；`main` 包缺 `Version` 变量导致 `build.sh` 的 `-X main.Version` 落空；`scope.go` 关于「`Permission` 从未挂载」的注释已与 `router.go:104` 的现状不一致。三者都不涉及行为重构，属于下一轮可直接落地的清理。
