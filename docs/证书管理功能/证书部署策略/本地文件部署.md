## 简介

`local` 是 DNSPlane 部署器体系中最直接的一个渠道：**把证书与私钥直接写到运行 DNSPlane 的那台
机器的文件系统上**，然后在本机执行管理员填写的重载命令。它没有网络跳数、没有传输凭据，
落地能力完全等价于 DNSPlane 进程自身的文件权限，典型用途是把 ACME 签出的证书同步到与面板
同机部署的 Nginx/Apache 证书目录，让 Web 服务器 reload 后立刻使用新链。

| 维度 | `local` 本机部署 | `ssh` 远程部署 | 云厂商部署器（`providers/`） |
|------|------------------|----------------|------------------------------|
| 目标机 | DNSPlane 所在机器 | 任意可达主机 | 厂商边缘节点 |
| 传输凭据 | 无（复用进程权限） | 口令/私钥（账户配置字段） | AK/SK 或 Token |
| 落地手段 | `os.WriteFile` + 本机 `sh -c` | SFTP 上传 + 远程会话 | API 调用 |
| 权限门槛 | 创建任务需管理员 | 任意用户 | 任意用户 |
| 容器可用性 | 受限（镜像无 shell、非 root） | 可用 | 可用 |

实现证据：文件写入见 `local.go:98-114`，重载执行见 `local.go:117-133`；管理员门槛见
`cert.go:1248-1264`（安全审计 H-3 注释）；表单归属见 `config_server.go:72-98`。
本文结论均可按行号回溯到工作区文件；无法从代码验证的部分（如 SELinux 行为）显式标注为通用指导。

## 核心组件

`local` 的组件粒度很小：一个 provider 类型 + 三个共享辅助函数 + 一套基类设施。
下表按「是否属于 `local` 专属」划分，避免把 `ssh`/`ftp` 复用的代码算作本实现。

| 组件 | 类型 | 职责 | 定义位置 | 是否 `local` 专属 |
|------|------|------|----------|:------------------:|
| `LocalProvider` | 结构体 | 承载配置与日志，实现部署接口 | `local.go:19-21` | 是 |
| `NewLocalProvider` | 工厂 | 注册中心构造入口 | `local.go:23-27` | 是 |
| `Check` | 方法 | 校验路径非空且目录已存在 | `local.go:29-51` | 是 |
| `Deploy` | 方法 | 写证书、写私钥、执行重载 | `local.go:53-137` | 是 |
| `sanitizeLocalPath` | 函数 | 拒 `..`、拒控制字符、强制绝对路径 | `path_guard.go:26-29` | 组内共享 |
| `splitExecLines` | 函数 | 按行拆分并跳过空行与 `#` 注释 | `exec_lines.go:5-19` | 组内共享 |
| `firstStringInMap` | 函数 | 多别名取首个非空字符串 | `task_fields.go:7-22` | 组内共享 |
| `BaseProvider` | 基类 | 配置存取、日志、默认 `Check` | `base.go:119-123`、`:241-244` | 全局共享 |
| `Register` / `ProviderDeployWithInfo` | 注册与调度 | 按键取工厂、可选接口降级 | `base.go:84-89`、`:142-150` | 全局共享 |

大纲中的「备份」一项必须如实说明：**`local` 没有实现任何备份逻辑**。
在 `servers/` 全目录检索 `bak`/`backup`/`.old`/`rename`/`Remove`/`Chmod`/`Chown`，
仅命中 `local.go:122`、`:124` 两行 `exec.CommandContext`（属于重载分支，不是备份）。
证书与私钥都是**就地覆写**，历史版本不留存；如需回滚，只能靠外部机制（文件系统快照、
配置管理工具、`cmd` 内自行 `cp`）。该结论与素材 `analysis-deploy.md` 第 429 行
「备份归目标服务管理，不在本应用职责内」一致。

## 架构总览

一次 `local` 部署从任务表扫描开始，经解析配置、构造 provider、逐域名写文件、
执行重载，最后把结果与日志落库。全程受一个 5 分钟上下文约束（`task_runner.go:345`）。

```mermaid
sequenceDiagram
  participant TR as TaskRunner
  participant DB as cert_deploys
  participant RG as deploy.GetProvider
  participant LP as LocalProvider
  participant PG as sanitizeLocalPath
  participant FS as 本机文件系统
  participant SH as sh -c

  TR->>DB: 扫描 active 且未锁定的任务
  TR->>DB: 条件更新 is_lock=true 抢占
  TR->>TR: 解析账户配置与任务配置 JSON
  TR->>RG: GetProvider("local", accConfig, deployConfig)
  RG-->>LP: NewLocalProvider(accConfig)
  LP-->>LP: SetLogger(闭包写入 logBuilder)
  TR->>LP: ProviderDeployWithInfo(ctx, fullchain, key, cfg)
  LP->>LP: format 守卫，拒绝 pfx 与 jks
  LP->>LP: 读取 cert_path / key_path / restart_cmd
  loop 每个域名
    LP->>LP: 替换路径中的 domain 占位符
    LP->>PG: 校验证书路径与私钥路径
    PG-->>LP: 通过或返回遍历错误
    LP->>FS: MkdirAll + WriteFile 证书 0644
    LP->>FS: MkdirAll + WriteFile 私钥 0600
  end
  loop 每条重载命令
    LP->>SH: exec.CommandContext(ctx, "sh", "-c", line)
    SH-->>LP: CombinedOutput
  end
  LP-->>TR: nil 或错误
  alt 失败
    TR->>DB: status=-1 或 3，写入 error 与日志
  else 成功
    TR->>DB: status=2，写入 log_content 与 issue_time
  end
```

## 详细组件分析

### 路径解析：三级取值与键别名

`Deploy` 对路径与命令都做了「任务配置优先、账户配置兜底」的多别名取值。证书路径依次尝试
`cert_path` → `pem_cert_file`（`local.go:58`），仍为空时回退 `GetStringFrom(config, "cert_path")`
（`:60`）；后者先查任务配置再查账户配置（`base.go:246-256`），并在账户配置层做大小写与
下划线/驼峰互转匹配（`base.go:198-228`）。私钥路径同构（`:62-65`）。重载命令的别名更长：
`restart_cmd` → `reload_cmd` → `cmd`（`:66`），之后回退 `restart_cmd`（`:68`）、`reload_cmd`
（`:71`）。注意**账户配置兜底不再尝试 `cmd`**，把 `cmd` 写在账户级不会生效 —— 这是键别名链
的不对称点。

| 语义项 | 任务配置别名（顺序即优先级） | 账户配置兜底键 | 代码位置 |
|--------|------------------------------|----------------|----------|
| 证书路径 | `cert_path`、`pem_cert_file` | `cert_path` | `local.go:58-61` |
| 私钥路径 | `key_path`、`pem_key_file` | `key_path` | `local.go:62-65` |
| 重载命令 | `restart_cmd`、`reload_cmd`、`cmd` | `restart_cmd`、`reload_cmd` | `local.go:66-72` |
| 格式 | `format` | 未兜底（仅任务配置） | `local.go:54` |
| 域名列表 | `domainList`、`domains`、`domain` | 由调度层注入 | `local.go:74`、`base.go:305-339` |

双注册表在这里留下了实际影响：`config_server.go:83-97` 的任务表单用 `pem_cert_file`/
`pem_key_file`/`cmd`，而 `cert/providers.go:308-312` 的账户表单用 `cert_path`/`key_path`/
`reload_cmd`。代码同时兼容两套键名，但 `merge_deploy_api.go:12` 的 `patchServer` 白名单包含
`local`，导致 **API 下发的账户表单以 `AllDeployConfigs` 为准**（只有 `name` 一个字段，
`config_server.go:80-82`），账户级路径在 UI 上已无处可填。

### {domain} 占位符与多域名展开

`base.GetConfigDomains` 从 `domainList`（支持 `[]string`、`[]interface{}`、逗号/换行字符串）或
`domains`、`domain` 取域名列表（`base.go:305-339`），逗号与换行由 `SplitDomains` 归一
（`base.go:287-303`）。列表为空时写入空串占位并只跑一轮（`local.go:75-77`），等价于
「按字面路径写一次」。调度层会在任务配置缺字段时补齐：`domainList` 来自 `cert_domains` 表
按 `sort ASC` 的查询（`task_runner.go:329-337`），`domains` 是其逗号拼接（`:338-340`），
手动链路同构（`cert_deploy.go:809-815`）。因此 `local` 天然支持「一张证书的多 SAN 各自落地到
不同目录」。

替换手段是简单字符串替换：`strings.ReplaceAll(targetCertPath, "{domain}", domain)`
（`local.go:83`），私钥同理（`:84`），且**替换发生在路径校验之前**（`:88-95`）。
这带来一条安全属性：若 `cert_domains` 中存在异常域名（如包含 `..`），污染后的路径
会被 `sanitizeLocalPath` 拦下而不是静默穿越。整体执行次序为：格式守卫（`:54-57`）→
键解析（`:58-72`）→ 域名展开（`:74-77`）→ 逐域名校验与写入（`:79-115`）→
拆分并串行执行重载（`:117-133`）→ 完成日志（`:135`）；任一环节出错立即返回。

### 权限与落盘语义

写入用 `os.MkdirAll(dir, 0755)` 建目录、`os.WriteFile` 落文件：证书 `0644`
（`local.go:100-105`），私钥 `0600`（`:109-114`）。五段语义必须分清：

| 关注点 | 实际行为 | 依据 |
|--------|----------|------|
| 属主 | 由 DNSPlane 进程 UID/GID 决定，代码不做 `Chown`（全目录无该调用） | `local.go:98-114` |
| 目录权限 | 仅目录**新建**时按 0755 申请且受 umask 影响；已存在目录不改权限 | `local.go:100`、`:109` |
| 文件权限 | `os.WriteFile` 的 perm 仅在**创建**新文件时生效；覆写已存在文件走截断，权限沿用原值 | `local.go:103`、`:112`（标准库语义，仓库无测试覆盖） |
| 写入原子性 | 无临时文件 + `rename`，是就地截断覆写 | `servers/` 检索无 `rename` 命中 |
| 落盘同步 | 无 `File.Sync()` 调用，异常断电不保证持久 | `local.go:103`、`:112` |

「文件权限沿用原值」这条对私钥尤其关键：若历史私钥曾以 0644 创建，本部署器**不会**把它收紧到
0600，修复只能靠人工 `chmod` 或在 `cmd` 里补一条 `chmod 600`。此为依标准库语义得出的行为描述，
仓库内无对应测试，实际影响面标记为「未在本地复现」。无备份的连带后果是**部分失败不可回滚**：
某域名证书写入成功而私钥失败（磁盘满、目录只读）时函数直接返回错误（`:112-114`），已写的
证书不会还原；多域名循环同理，前面留新链、后面留旧链。

### SELinux 与系统层上下文

代码层面**没有任何 SELinux 处理**：全仓检索 `selinux`（含 `*.go`、`*.md`、`*.yaml`）在后端与
配置中零命中，说明部署器不调用 `restorecon`、不写 `semanage`、也不感知 enforcing 模式。
下表属通用运维指导，不对应仓库代码：

| 场景 | 现象 | 处置方向 |
|------|------|----------|
| enforcing 下写 `/etc/pki/tls/certs` | 进程无域标签权限，报 `permission denied` | 为 DNSPlane 进程域授予 `cert_t` 写权限，或改写到无标签约束目录 |
| 新建私钥文件标签错误 | Nginx 读取被拒（`open() failed ... Permission denied`） | 对目标目录执行 `restorecon -R` |
| systemd 沙箱加固 | 写目录被 `ProtectSystem=strict` 拦下 | 用 `ReadWritePaths=` 显式放行 |

容器形态下的约束比 SELinux 更硬：官方镜像运行阶段是
`gcr.io/distroless/static-debian12:nonroot`（`Dockerfile:32`）并以 `USER nonroot:nonroot`
启动（`Dockerfile:35`），既没有 root 写系统目录的权限，也没有 `/bin/sh` 供 `local.go:124`
调用 —— 后者意味着**容器内 `local` 的重载分支必然失败**。素材 `analysis-deploy.md` 第 27 行与
第 499 行（问题 D-9）记录的正是同一事实。

## 性能考虑

| 问题 | 现状 | 影响 | 优化方向 |
|------|------|------|----------|
| 轮询粒度 | `certTaskInterval` 固定 5 分钟（`task_runner.go:41`、`:100`） | 新签发证书最迟 5 分钟后落地 | 用手动执行入口立即触发（`cert_deploy.go:837`） |
| 单任务串行 | 一次扫描内逐条 `executeSingleDeploy`（`task_runner.go:238`） | 任务多时尾部延迟明显 | 按账户类型分片（需先解决同机写冲突） |
| 多域名循环 | 顺序写文件（`local.go:79-115`） | 域名越多耗时越长，仍在 5 分钟预算内 | 控制单任务域名数量 |
| 重载等待 | `CombinedOutput` 同步阻塞（`local.go:126`） | reload 卡死会占满整个上下文 | 命令内加 `timeout 30s` 前缀 |
| 非原子覆写 | 截断写入，无 rename（`local.go:103`、`:112`） | reload 与写入交叠可能读到半写文件 | 由 `cmd` 做「写临时路径 + `mv` + reload」 |
| 失败放大 | 每次重试都重写文件并重载服务（`task_runner.go:244-279`） | 磁盘满等持久故障会反复触发 reload | 修根因后再启用，或调低 `max_retry` |

最实际的改进是把重载纳入写后校验：当前 `local` 不验证服务是否真的加载了新链（无握手探测），
`status=2` 只代表命令退出码为 0。需要业务级确认时，可把校验命令写进 `cmd`，
让非零退出码自然反映为部署失败。

### reload 失败排查顺序

1. 读 `cert_deploys.log_content`：失败时错误消息带了 `CombinedOutput` 全文
   （`local.go:126-128`），这是第一手证据。
2. 确认命令没被整段注释：`splitExecLines` 会丢掉 `#` 开头行与空行（`exec_lines.go:13-16`），
   全部注释等于「无命令」而静默跳过重载。
3. 确认命令存在于进程 PATH，且运行环境支持它（`systemctl` 在非 systemd 环境不可用）。
4. 先跑 `nginx -t`/`apachectl configtest`：reload 常因新证书与既有配置不匹配失败。
5. 记住退出码会传播（`local.go:127-129`）但**已写入的文件不回滚**，
   「reload 失败而证书已换」是正常形态。

## 结论

`local` 用 145 行代码完成了「本机写文件 + 本机执行重载」这一闭环，是 KISS 的正面样本：
无凭据管理、无网络重试、无厂商 SDK，仅靠 `os` 与 `os/exec` 两个标准库落地。它的价值在于把
DNSPlane 变成一台自托管证书分发器，让同机 Nginx/Apache 在续期后自动获得新链。

优势：零传输凭据，私钥不经网络外送；天然支持 `{domain}` 占位与多 SAN 展开；
权限模型清晰，创建与修改都要管理员（`cert.go:1226`、`:1276`），把 RCE 面收敛到可信角色；
路径守卫独立成文件，与 `ssh`/`ftp` 共享同一套遍历防御（`path_guard.go:31-63`）。

需要正视的短板（均可按行号复核）：**无备份、无回滚**，部分失败会留下新旧混合状态
（`local.go:79-115`）；**非原子写**，无临时文件 + `rename`；**权限不纠正**，覆写不重置已存在
文件的权限位；**无前置命令**（`ssh` 有 `cmd_pre`，对比 `ssh.go:153`）；**容器内不可用**
（`Dockerfile:32`、`:35`）；**双注册遗留**，`cert` 侧账户表单被 `patchServer` 覆盖而 `Check`
仍依赖账户级路径（`local.go:29-51`、`providers.go:308-312`、`merge_deploy_api.go:12`），
表现为测试恒失败；**格式声明与实现矛盾**，表单提供 `pfx`/`jks` 而实现只认 PEM
（`config_server.go:84-88` vs `local.go:54-57`）。

建议的最小改进方向（不含代码变更承诺）：写文件改为「临时文件 + `chmod` + `rename`」以获得
原子性并在覆写时显式设权限；循环前做一次可选的 `.bak` 复制以满足回滚；把 `Check` 的取值来源
统一到任务配置以消除测试误报。三者都不引入新依赖。
