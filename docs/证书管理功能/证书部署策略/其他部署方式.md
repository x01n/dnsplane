## 简介

本文覆盖证书部署器体系中**不属于**「云厂商 CDN/WAF 主流程」与「SSH/FTP/本地文件」
两大常见形态的剩余部署方式：`deploy/others/` 的 5 个注册名
（`west` 西部数码虚拟主机、`rainyun` 雨云、`unicloud` uniCloud 服务空间、
`kuocai` 括彩云、`uusec` 南墙 WAF，共 604 行）、对象存储形态
（`s3storage`、`aliyun_oss`、`huawei_obs`），以及自建边缘与脚本形态
（`goedge` 的 GoEdge 与 FlexCDN 双系统类型、`local` 与 `ssh` 内嵌的自定义命令）。

**能力边界澄清**：`base.Register` 全量检索（`deploy/**` 下 96 处注册）中**不存在**
`webhook` 与 `technitium` 两项。`technitium` 仅是 DNS 服务商
（`dns/providers/technitium/technitium.go`，实测 665 行），由 `main.go:50`
空导入注册；`webhook` 全部落在 `internal/notify/` 与 `internal/monitor/` 通知域。
详见「详细组件分析」末节。

本文所有结论均来自实际读取的代码，行号以当前工作区文件为准；
所有密钥、口令、令牌一律写作 `{占位}`。

### others 包的内部构成

`others` 是 `deploy/` 五个子包中最小的一个：5 个文件、5 个 `init()` 注册、
零单元测试，包内不存在共享工具文件。五个部署器的调用形态为：`kuocai` 登录换
token 后 `PUT /api/domain/{id}/ssl`；`rainyun` 用 `x-api-key` 直连，`id` 为空走
POST 新增、否则 PUT 更新；`unicloud` 登录后按域名循环
`POST /api/domain/bindssl`；`uusec` 用账户填写的控制台基址登录后 `PUT`；
`west` 用 MD5 时间戳签名加表单 POST。`kuocai`、`unicloud`、`uusec` 三者的
`login()` 结构几乎逐行相同，属明显 DRY 违规。

## 核心组件

### 接口实现矩阵

`base.DeployProvider` 要求三个方法（`base/base.go:45-54`）。下表统计各实现对
该契约及可选接口 `DeployWithInfoProvider`（`base/base.go:69-74`）的满足情况，
`✗` 表示未实现，此时 `ProviderDeployWithInfo`（`base/base.go:142-150`）
退化为普通 `Deploy`。

| 注册名 | 实现类型 | Check | Deploy | SetLogger | DeployWithInfo | 凭据键 | 任务键 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `west` | `WestProvider` | 签名试调用 | 自实现 | 转发基类 | ✗ | `username`、`api_password` | `sitename` |
| `rainyun` | `RainyunProvider` | GET user/info | 自实现 | 转发基类 | ✗ | `apikey` | `id` |
| `unicloud` | `UnicloudProvider` | `login()` | 自实现 | 转发基类 | ✗ | `username`、`password` | `spaceId`、`provider`、`domains` |
| `kuocai` | `KuocaiProvider` | `login()` | 自实现 | 转发基类 | ✗ | `username`、`password` | `id` |
| `uusec` | `UusecProvider` | `login()` | 自实现 | 转发基类 | ✗ | `url`、`username`、`password` | `id`、`name` |
| `goedge` | `GoEdgeProvider` | 校验并取 token | 自实现 | 转发基类 | ✗ | `url`、`accessKeyId`、`accessKey`、`usertype`、`systype` | 无 |
| `s3storage` | `S3Provider` | 校验并 GET `/` | 自实现 | 转发基类 | ✗ | `AccessKeyId`、`SecretAccessKey`、`endpoint`、`region` | `bucket`、`cert_path`、`key_path` |
| `aliyun_oss` | `AliyunOSSProvider` | 继承基类空实现 | 委托 `deploy()` | 转发基类 | **✓** | AK/SK（阿里云基类） | `oss_endpoint`、`oss_bucket` |
| `huawei_obs` | `HuaweiOBSProvider` | 键存在性校验 | 自实现 | 转发基类 | ✗ | AK/SK 加项目 ID | `obs_endpoint`、`obs_bucket` |
| `local` | `LocalProvider` | 目录存在性校验 | 自实现 | 转发基类 | ✗ | 无 | `format`、路径、`cmd` |

关键结论：`others/` 五个部署器**全部不实现** `DeployWithInfoProvider`，不会向
`cert_deploys.config` 与 `cert_deploys.info` 回写新生成的证书 ID，这与 `aliyun_oss`、
`aliyun_lb`、`tencent_update`、`axisnow`、`qzyun` 等「上传后回写 ID」的部署器存在
能力差——平台侧 ID 变化时必须人工改任务配置。

### BaseProvider 配置读取契约

`BaseProvider`（`base/base.go:120-135`）是这些部署器的唯一共享依赖，
其键匹配策略决定「表单字段名与代码里 `GetString("...")` 是否对得上」。

| 方法 | 位置 | 语义 | 对其他部署方式的影响 |
| --- | --- | --- | --- |
| `GetString` | `base.go:199-228` | 四级匹配：精确、忽略大小写、下划线转驼峰、驼峰转下划线 | `api_password` 可写成 `apiPassword` 命中 |
| `GetStringFrom` | `base.go:247-256` | 任务配置优先，空则回退账户配置 | `west.sitename`、`kuocai.id` 两处任填 |
| `Log` | `base.go:131-135` | `Logger` 为 nil 时静默丢弃 | 手动路径与调度路径日志行为不同 |
| `SplitDomains` | `base.go:288-303` | 逗号与换行统一切分 | `unicloud` 未使用，改用手写 `strings.Split` |
| `GetConfigDomains` | `base.go:306-339` | `domainList` → `domains` → `domain` | `goedge` 使用；`unicloud` 未使用 |
| `GetProvider` | `base.go:92-105` | 工厂查表，未命中返回 unknown 错误 | 每次调用都新建实例，token 无法跨任务复用 |

`unicloud.go:78` 用 `strings.Split(p.GetStringFrom(config, "domains"), ",")`，
仅支持英文逗号；而 `SplitDomains`（`base.go:292`）的 `strings.NewReplacer`
会把 `\r\n`、`\r`、`,` 全部归一为 `\n` 再切分，因此 uniCloud 任务用换行分隔域名
会得到「一整行」的错误结果。继承关系上，本文涉及的 10 个类型全部嵌入
`BaseProvider`，其中仅 `AliyunOSSProvider` 额外满足 `DeployWithInfoProvider`。

### 三条执行入口的差异

同一部署器实例可能被三条路径调用，context 约束与日志落库行为完全不同，这是排障最易混淆之处。

| 入口 | 位置 | Context | 是否执行 Check | 是否写 log_content | 是否走 DeployWithInfo |
| --- | --- | --- | --- | --- | --- |
| 自动调度 | `task_runner.go:322-350` | `WithTimeout(5m)`（`:345`） | ✗ | ✓（`:370`） | ✓ |
| 失败重试 | `task_runner.go:277` → 同一函数 | 同上 | ✗ | ✓ | ✓ |
| 手动部署 | `cert.go:1369-1376` | `context.Background()` | ✗ | ✗（仅更新 `updated_at`） | ✗ 直接 `provider.Deploy` |
| 账户连通性检测 | `cert_deploy.go:305-316` | `WithTimeout(30s)` | ✓ | ✗（只写进程日志） | 不涉及 |

手动路径调用 `provider.Deploy` 而非 `base.ProviderDeployWithInfo`
（`cert.go:1376`），因此这条路径上即便部署器实现了信息回写也不会落库；
它也没有超时约束，只能依赖各部署器内部 `http.Client{Timeout: ...}` 兜底。

## 详细组件分析

### 西部数码 west：MD5 时间戳签名与表单编码

`others/west.go`（118 行）是 `others` 中唯一不走 JSON 的部署器。
签名在 `west.go:64-68`：`md5(username + api_password + timestamp)` 再
`hex.EncodeToString`。`Check` 把 `act=getlist` 拼进 URL 查询串发起 GET
（`west.go:42-45`）；`Deploy` 改用 `client.PostForm`，把 `act=setssl`、
`sitename`、`cert`、`key` 与三要素签名放进
`application/x-www-form-urlencoded` 表单体（`west.go:87-96`）。
成功判定字段也与众不同：`west` 读 `result["result"]` 且要求等于 `200`
（`west.go:57`、`:108`），`kuocai`/`unicloud`/`uusec` 读 `result["code"]` 要求
等于 `0`，`rainyun` 读 `result["code"]` 却要求等于 `200`。

| 维度 | 取值 | 位置 |
| --- | --- | --- |
| API 基址 | `https://api.west.cn/api/v2/host/` | `west.go:42`、`:85` |
| 口令字段 | `api_password`（可驼峰回退） | `west.go:35`、`:76` |
| 目标粒度 | 单个 FTP 账号 `sitename` | `west.go:77` |
| 成功码 | `result == 200` | `west.go:57`、`:108` |
| HTTP 超时 | 60 秒（Check 与 Deploy 共用） | `west.go:70-72` |
| 幂等性 | 同一 `sitename` 覆盖写入 | 由 `act=setssl` 语义决定 |

### 雨云 rainyun：无状态 API Key 与新增更新双分支

`others/rainyun.go`（110 行）最简洁：不登录、不换 token，每次请求直接带
`x-api-key` 头（`rainyun.go:37`、`:86`）。`Deploy` 核心分支在
`rainyun.go:66-76`：任务配置的 `id` 为空时 `POST /ssl/cert` 新增，
非空时 `PUT /ssl/cert/{id}` 更新，表单据此标注「留空则为添加证书」
（`config_cloud.go:427`）。

可观察的运维后果：**留空 `id` 的部署任务每轮调度都会在平台侧新增一张证书**而非
覆盖旧的。调度器每 5 分钟一轮（`task_runner.go:41`），只要证书内容变化就再写一条；
又因不实现 `DeployWithInfoProvider`，新 ID 不回写，无法自动收敛为「更新」模式。
`Check` 复用 `GET /user/info`（`rainyun.go:36`），码非 `200` 时报「API错误」
并附带 `message` 字段（`rainyun.go:51-53`），错误键名与其他部署器不同。

### uniCloud：登录式 token 复用与多域名循环

`others/unicloud.go`（133 行）先登录 `unicloud.dcloud.net.cn/api/login`
（`unicloud.go:49`），把 `data.token` 存入实例字段 `p.token`（`:64-69`），
随后在 `Deploy` 内按域名循环 `POST /api/domain/bindssl`（`:88-125`）。

```mermaid
sequenceDiagram
    participant TR as 调度器
    participant PV as UnicloudProvider
    participant CA as uniCloud 控制台 API
    TR->>PV : Deploy 传入 fullchain 与 privateKey
    PV->>PV : 解析 spaceId 与 provider 与 domains
    PV->>CA : POST /api/login 账号口令
    CA-->>PV : code 为 0 且 data.token
    loop 每个域名
        PV->>CA : POST /api/domain/bindssl 携带 Bearer token
        CA-->>PV : code 与 message
    end
    PV-->>TR : 全部成功返回 nil
```

**图表来源**
- [unicloud.go](file://main/internal/cert/deploy/others/unicloud.go#L75-L129)

三点实现细节：其一，**域名切分不统一**，`unicloud.go:78` 用
`strings.Split(..., ",")`，表单提示也写「多个域名可使用,分隔」
（`config_cloud.go:447`），与全局 `SplitDomains` 支持的换行不一致。
其二，**失败即中断且不续跑**，循环内任一域名失败直接 `return`
（`unicloud.go:111`、`:119`、`:123`），后续域名不再尝试、已成功域名不回滚。
其三，**循环内响应体关闭**用「先 `ReadAll` 再显式 `Close`」而非 `defer`
（`:114-115`）。`provider` 字段（`aliyun` / `tencent`，`:441-445`）
只作为请求体一部分透传，部署器内部不对该值做任何分支。

### 括彩云 kuocai：登录换 token 与域名 ID 定位

### 南墙 WAF uusec：目录归属错位与自建基址风险

`uusec` 实现放在 `others/`，表单却登记在 `config_selfhosted.go:407-423`，
Class 为 `ClassSelfHosted`；`deploy/README.md:72` 把「南墙WAF」列在自建系统清单，

`strings.TrimRight(p.GetString("url"), "/")`（`uusec.go:38`、`:77`），不校验 scheme、

但 recover 位于**整批任务**层级而非单任务层级，一次 panic 会让本轮后续部署任务

超时与并发：

| 组件 | 超时来源 | 数值 | 位置 |

| `uusec` | 登录与部署各自构造 | 30 / 60 | `uusec.go:42`、`:87` |
| `goedge` | 单一 client 覆盖 list、update、create | 30 秒 | `goedge.go:53` |
| `s3storage` | 单一 client | 30 秒 | `s3storage.go:43` |

| 手动路径 | 无 | 无上限 | `cert.go:1376` |

结构性瓶颈有三点。其一 **全串行**：`unicloud.go:88` 的域名循环与 `goedge.go:106`
的证书列表循环都是顺序 HTTP、无并发，`unicloud` 若有 N 个域名最坏耗时约 N × 60 秒，
粗算 N 大于 5 即有撞上 5 分钟总超时的风险。其二 **每次部署重新登录**：
`kuocai.go:79`、`unicloud.go:82`、`uusec.go:83` 在 `Deploy` 内再调 `login()`，
`p.token` 只是实例内缓存且实例由 `GetProvider` 每次新建（`base.go:104`）。
其三 **`http.Client` 未复用**：`west.go:40`、`rainyun.go:34` 等在函数内现场构造，
每轮新建 Transport，TLS 握手无法跨任务复用。

写放大与重试：`logBuilder` 每次 `p.Log` 追加一行，最终整串写入
`cert_deploys.log_content`（`task_runner.go:341-344`、`:370`），长循环部署器会显著
放大单任务日志量，而手动路径完全不写该字段（`cert.go:1382` 仅更新 `updated_at`）。
退避表 `{60, 300, 600, 1800, 3600}` 秒（`task_runner.go:23`），`max_retry` 为 0 时
默认 5 次（`:251-254`），成功后 `retry` 归零（`:369`）；对「新增型」部署器
（`rainyun` 留空 `id`）而言每次重试都可能再插一张证书，重试语义在此**有害**。

## 结论

「其他部署方式」在架构上不是特殊路径，而是 `DeployProvider` 契约下的普通实现，
特殊性体现在四点：

1. **归属错位**。`others/` 目录与 `Class` 分类不一一对应：`uusec` 归
   `ClassSelfHosted`，其余四个归 `ClassCloudService`；`s3storage` 实现在
   `providers/` 却分类为 `ClassServer`。阅读代码应以 `base.Register` 的名字为唯一索引。
2. **凭据形态多样但都很薄**。`west` 用 MD5 时间戳签名、`rainyun` 用静态 API Key、
   其余三个用账号口令换 Bearer token；五者都没有 token 过期处理。
3. **普遍缺位的能力**：全部不实现 `DeployWithInfoProvider`，没有「新证书 ID
   自动回写」；错误处理普遍忽略 `json.Marshal` 与 `http.NewRequestWithContext`
   返回值；无任何单元测试。
4. **Webhook 与 Technitium 不是部署器**，`local` 与 `ssh` 的 `cmd` 字段是
   当前唯一的自定义脚本入口。

改进优先级（按成本从低到高）：把 `unicloud` 的 `strings.Split` 换成
`base.SplitDomains`；给 `rainyun` 增加 ID 回写以消除重复新增；把三个 `login()` 抽到
`others` 包内共享函数以消除 DRY 违规；为 `uusec.go:99` 补 `err` 判断以杜绝批次级
panic；最后把 `README.md` 的文件清单与现实对齐。

### 新增一个 others 风格部署器的最短步骤

1. 在 `deploy/others/` 新建文件，声明 `type XxxProvider struct { base.BaseProvider }`
   并实现 `Check` / `Deploy` / `SetLogger`（契约见 `base/base.go:45-54`）
2. 在 `init()` 内 `base.Register("xxx", NewXxxProvider)`（`base.go:85-89`）；
   `others` 包已被 `main.go:55` 空导入，**无需改动** `main.go`
3. 在对应 `config_*.go` 用 `registerDeployConfig` 登记 `Inputs` 与 `TaskInputs`
   （`config.go:47-49`）
4. 若希望新证书 ID 自动回写，额外实现 `DeployWithInfo` 并写入 `info.Config`，
   由 `base.InfoUpdates`（`base.go:156-183`）合并落库
5. 若类型名落在 `patchServer` 白名单（`merge_deploy_api.go:12`，当前为 `ssh`、
   `ftp`、`local`），cert 侧表单会被 `AllDeployConfigs` 覆盖
