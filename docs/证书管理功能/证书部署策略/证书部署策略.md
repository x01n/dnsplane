## 简介

证书部署策略对应 `main/internal/cert/deploy` 包：把一张已签发的证书推到「一个外部目标」，
目标可以是云厂商 CDN、对象存储、WAF、负载均衡、运维面板，也可以是一台 SSH/FTP 可达的服务器。
全包按目录切成 **5 组部署器**：

| 组 | 目录 | 定位 | 文件数 | 行数 | `base.Register` 数 |
|----|------|------|:------:|:----:|:------------------:|
| 契约层 | `deploy/base/` | 接口、实现注册中心、`BaseProvider`、配置工具 | 1 | 339 | 0 |
| 云与自建 | `deploy/providers/` | 云产品 + 自建 CDN/WAF + 面板 + 对象存储 + 容器 | 56 | 15727 | 77 |
| 服务器 | `deploy/servers/` | SSH / FTP / 本地文件系统 | 6 | 655 | 3 |
| 面板 | `deploy/panels/` | ACE Panel / AMH / 宝塔 Windows 极速版 | 3 | 356 | 3 |
| 其他 | `deploy/others/` | 西部数码 / 雨云 / uniCloud / 括彩云 / 南墙 WAF | 5 | 604 | 5 |

含 `deploy/` 根目录 6 个配置与合并文件（1317 行）在内，全包 **77 个 Go 文件、18998 行、零测试文件**；
`base.Register` 去重后是 **88 个实现键**，而面向前端的表单表 `AllDeployConfigs` 只有 **53 条**。
三条贯穿全文的事实：**两套注册中心并存**（实现表 `base/base.go:85`、表单表 `config.go:47`，
键集合互不相等，实测差集为表单有实现无 11 项、实现有表单无 46 项，对齐靠 `registry.go:27`
四段回落）；**目录分组 ≠ 业务分组**（`panels/` 只有 3 个文件，面板族实际 17 个实现且多在
`providers/`，而 `deploy/README.md:18-31` 描述的 `interface.go` / `executor.go` 在 `deploy/` 根
**并不存在**）；**失败可见性在调度层**（执行由 `task_runner.go:281` 统一驱动，退避与通知分别
在 `:23` 与 `:456`，88 个部署器没有一个引用数据库或 notify 包）。

## 核心组件

### DeployProvider 接口与回传契约

| 符号 | 位置 | 语义 |
|------|------|------|
| `DeployProvider` | `base/base.go:45` | `Check` / `Deploy` / `SetLogger`，任何部署器至少满足它 |
| `ProviderFactory` | `base/base.go:77` | `func(config map[string]interface{}) DeployProvider` |
| `DeployInfo` | `base/base.go:60` | `Config` 合并回任务配置，`Data` 存入任务 `info` 字段 |
| `DeployWithInfoProvider` | `base/base.go:69` | 独立接口，未实现则不参与回写 |
| `ProviderDeployWithInfo` | `base/base.go:142` | 运行期类型断言分派 |
| `InfoUpdates` | `base/base.go:156` | 回传信息转 `cert_deploys` 更新字段，无内容返回 `nil` |

拆两个接口的理由写在 `base.go:137-141`：`BaseProvider` 若提供 `DeployWithInfo`，
嵌入它的部署器会因**方法提升**被误判为「支持回传」，实际部署被默认实现吞掉。
实测实现该方法的文件共 11 个（`aliyun_*` 7 个 + `axisnow` `huawei_upload` `qzyun` `tencent_update`），
其中 `aliyun_upload.go:58` 用 `var _ base.DeployWithInfoProvider = (*AliyunUploadProvider)(nil)`
把契约固化到编译期。

## 详细组件分析

### 契约组 base

`base.go` 一个文件承载三类职责：接口定义（`:45-77`）、实现注册中心（`:79-117`）、配置工具
（`:199-339`）。339 行对 88 个实现而言是极简公共层——厂商差异全部压在实现文件里，公共层不感知
任何上游协议。对外视图合并在 `merge_deploy_api.go:5`，由 `GET /api/cert/providers`
（`router.go:245` → `cert.go:1387-1396`）触发，四条裁决：

| 情形 | 结果 | 位置 |
|------|------|------|
| 两表都有且键在 `patchServer`（仅 `ssh`/`ftp`/`local`） | 表单表的字段、名称、图标**覆盖** cert 表 | `merge_deploy_api.go:12`、`:16-36` |
| 两表都有但不在白名单 | 保留 cert 表定义 | `:37` |
| 仅表单表有，但 cert 表同名且 `IsDeploy=false` | 跳过（签发渠道优先） | `:40-43` |
| 仅表单表有 | 经 `deployConfigToAPIProviderConfig` 补入，`IsDeploy: true` | `:44`、`:49-64` |

白名单只放 3 键是刻意收窄：这 3 类的表单字段与实现严格一一对应，其余类型的 cert 侧定义
更贴合上游产品语义。

### 服务器组 servers

3 个实现，共同特征是**把 PEM 原文写到目标路径**，路径安全与格式边界全在这里。

| 部署方式 | 目标平台 | 认证方式 | 幂等性 | 关键位置 |
|----------|----------|----------|--------|----------|
| `ssh` | Linux/Windows OpenSSH | 密码或 PEM 私钥（可带 passphrase），可选 `host_key` | 覆写文件，命令逐行重复执行 | `ssh.go:42` `connect`、`:140` `Deploy`、`:222` `uploadFile`（`scp -t`，`:244`）、`:247` `runCommand` |

四条共性做法可直接当作服务器类部署器的编写范式：**多键名兼容**
（`cert_path` 与 `pem_cert_file` 同时接受，`ssh.go:145-152`）、**`{domain}` 占位符展开**
（`ssh.go:172-179`、`ftp.go:94-105`）、**路径安全网**（`path_guard.go:22`/`:27` 拒绝 `..` 段与
控制字符，远端强制 `/` 开头；文件头 `:9-19` 标明安全审计 H-1）、**多行命令拆分**

## 性能考虑

### 并发模型与超时

部署**不是并发执行**：`executeDeployTasks`（`task_runner.go:217`）与
`retryFailedDeployTasks`（`:244`）都是单重 `for` 循环逐个调 `executeSingleDeploy`（`:281`）。
并行度只体现在「多实例靠数据库行锁抢占」——`:284-291` 用 `WHERE is_lock = false` 做 CAS，
`RowsAffected == 0` 即放弃。

```mermaid
sequenceDiagram
    participant SCH as 调度器 每5分钟
    participant DB as cert_deploys
    participant PV as 部署器实例
    participant NM as notify 管理器

    SCH->>DB: 抢占 is_lock=false 且 status 为 0 或 2
    DB-->>SCH: RowsAffected 大于 0 继续
    SCH->>DB: 置 is_lock=true status=1 lock_time
    SCH->>PV: GetProvider 新建实例并 SetLogger
    SCH->>PV: ProviderDeployWithInfo 5 分钟超时
    PV-->>SCH: DeployInfo（外部目标写入由 PV 完成）
    alt 成功
        SCH->>DB: status=2 retry=0 log_content issue_time
        SCH->>NM: 成功通知（需显式开启）
    else 失败
        SCH->>DB: status=-1 retry+1 retry_time
        SCH->>NM: 仅末次失败时发通知
    end
```

**图表来源**

- [task_runner.go](file://main/internal/service/task_runner.go#L281-L392)

| 参数 | 取值 | 位置 |
|------|------|------|
| 调度器心跳 | 启动后 30 秒首跑，之后每 5 分钟 | `task_runner.go:41` |
| 单部署 ctx 超时 / 通知 ctx 超时 | 5 分钟 / 10 秒 | `task_runner.go:345` / `:477` |
| 部署锁强制释放 | 10 分钟，置 `status=-1` | `task_runner.go:422-433` |

5 分钟 < 10 分钟，正常情况下 `defer cancel()` 先取消 ctx、再由
`updateDeployFailedWithLog`（`:408`）落失败态，不留悬挂锁。真正吃满 5 分钟的往往是
「多域名循环 + 每步重新登录」的面板族（`cdnfly.go:51`/`:92`/`:122` 三处 `login`），
优化点在会话复用，不在调度层调参。

### 失败重试与通知时机

| 维度 | 取值 | 位置 |
|------|------|------|
| 重试触发条件 | `active = true AND status = -1 AND is_lock = false` | `task_runner.go:246-247` |
| 退避间隔 | 60 / 300 / 600 / 1800 / 3600 秒 | `task_runner.go:23` |
| 最大次数 | `cert_deploys.max_retry`，为 0 取默认 5 | `task_runner.go:251-254` |
| 计数递增 | 每次失败 `retry + 1` 并记 `retry_time` | `task_runner.go:401-402`、`:414-415` |
| 成功归零 | 成功路径显式 `retry: 0` | `task_runner.go:369` |

`issue_time`。`notify` 侧无渠道级重试与限流，失败通知本身是一次性投递——不能因为

## 结论

本文把证书部署策略拆成「5 组部署器 + 2 套注册表 + 1 条解析链 + 1 个调度层」，结论均来自实测：
88 个实现键与 53 条表单是**两份不相等的事实来源**，差集 11 / 46 可由 `grep` + `comm` 复现，
对齐依赖 `registry.go:27` 的四段回落，其中第四段（固定后缀猜测）最脆弱；
`DeployProvider` 与 `DeployWithInfoProvider` 分离是正确的依赖倒置——避免方法提升造成误判
（`base.go:137-141`），让 77 个无需回写的实现零成本满足契约，符合 KISS 与 YAGNI；
目录分组已失去分类语义，`panels/` 仅 3 文件而面板族实际 17 实现分散两处，
`deploy/README.md` 的结构描述与统计均过期；幂等性四种策略并存（回写 ID、ID 空则新增、
按域名匹配且冲突即拒绝、纯覆写），选型应按目标平台能否提供稳定 ID 决定；执行是
「单轮串行 + 行锁抢占」的多实例安全模型，重试由调度层统一退避（60→3600 秒、默认 5 次）。

**已知风险（只指出，未实施改动）**：手工部署路径 `cert.go:1376` 不写日志与状态，与自动路径
分叉；SSH/local 表单宣称的 `pfx`/`jks` 与实现矛盾；`host_key` 只在账户配置读取却无表单字段；
6 个部署器固定跳过 TLS 校验，与 `ssh.go` 已加固的主机密钥校验形成不一致基线；
`deploy/` 18998 行零测试，上述行为无法被回归拦截。
