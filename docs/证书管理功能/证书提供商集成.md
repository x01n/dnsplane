## 简介

`main/internal/cert` 是证书签发域唯一的厂商差异收敛点。它把「ACME 协议族」与「四家国内云厂商自有证书 OpenAPI」两套完全不同的业务模型压平成同一个 Go 接口 `cert.Provider`（`interface.go:52-79`，9 个方法），使 `handler/cert.go` 的签发流水线（`cert.go:656` → `:754` → `:769` → `:793`）看不到任何厂商 SDK 类型或签名细节。

本文聚焦**云证书渠道**与承载它们的注册表机制，口径以当前工作区实读为准：

## 项目结构

证书域按「接口与注册表在根包、每家厂商一个子包、部署器独立第二套注册中心」三层组织，本文涉及的结构如下（行数为 `wc -l` 实测）：

```text
main/internal/cert/
├── interface.go            115  接口 + 5 个跨渠道数据结构
├── registry.go             114  双 map 注册中心 + 双视图切分 + API 快照
├── providers.go            623  32 处 Register：5 处签发表单 + 27 处部署表单
├── acme/acme.go           1052  ACME v2 客户端，一个实现服务 5 个 CA key
├── aliyun/aliyun.go        512  CAS RPC + HMAC-SHA1 签名（手写，无 SDK），另含 279 行测试
├── tencent/tencent.go      495  SSL API + TC3-HMAC-SHA256（手写，无 SDK），另含 315 行测试
├── huoshan/huoshan.go      488  certificate_service + Sig v4 风格签名（零测试）
├── ucloud/ucloud.go        445  api.ucloud.cn + SHA1 签名（未接入装配、零测试）
└── deploy/                          ← 与签发接口完全隔离
    ├── base/base.go        339  DeployProvider + 独立注册表
    ├── config.go            49  DeployProviderConfig + AllDeployConfigs（表单见 config_cloud.go 515 行）
    ├── registry.go          73  四级回落解析 {type}_{product}
    └── merge_deploy_api.go  64  cert 表 + AllDeployConfigs 双源合并
```

| 层次 | 载体 | 职责边界 | 越界风险 |
|------|------|----------|----------|
| 契约层 | `cert/interface.go` | 只定义跨渠道可表达的最小公约字段 | 厂商专有字段（如 `instance_id`）只能借 `OrderInfo.OrderURL` 传递 |
| 装配层 | `cert/registry.go` + `cert/providers.go` | 工厂与表单双写、按 `IsDeploy` 切视图 | `init()` 顺序决定谁覆盖谁 |
| 适配层 | `acme`/`aliyun`/`tencent`/`huoshan`/`ucloud` | 签名、请求、响应解析 | 表单字段与实现读取的键名不一致 |
| 调用层 | `handler/cert.go` | 配额、鉴权、DNS 写入、轮询编排 | 未调用 `Revoke`/`Cancel`/`BuyCert` |
| 部署层 | `cert/deploy/*` | 把已签发的证书推到目标产品 | 与签发注册表同名不同义（`ucloud`） |

`OrderInfo.OrderURL` 被四家云渠道复用为「厂商侧订单/实例主键」，这是理解全部云适配代码的前提：`aliyun.go:203` 存 `InstanceId`、`tencent.go:143` 存 `CertificateId`、`huoshan.go:166` 存 `instanceID`、`ucloud.go:104` 存 `CertificateID`；而 ACME 存的是 CA 返回的订单 URL。字段名与语义不一致，导致模型侧的长度约束只对 ACME 路径有冲突风险。

### CertProvider 接口

### Registry 注册中心

`registry.go` 用两张全局 map 承载「工厂」与「表单」，由 `sync.RWMutex` 保护（`:12-14`）：

| 符号 | 位置 | 语义要点 |
|------|------|----------|
| `ProviderFactory` | `:9` | `func(config, ext map[string]interface{}) Provider`，`ext` 专供 ACME 复用账户密钥 |
| `Register` | `:23-35` | `factory != nil` 才覆盖工厂（`:27-29`）；`config.Type == "" && hadCfg` 时直接 `return`，只补工厂不覆盖表单（`:31-33`） |
| `GetProvider` | `:38-49` | 未注册报 `unknown cert provider`（`:43`）；注册了但工厂为 `nil` 报 `nil factory`（`:46`） |
| `GetProviderConfig` | `:52-57` | 只查 cert 表，不回退 `AllDeployConfigs` |
| `GetCertProviderConfigs` | `:71-81` | 按 `!IsDeploy` 切签发视图（`:76`） |
| `GetDeployProviderConfigs` | `:95-105` | 按 `IsDeploy` 切部署视图（`:100`） |
| `APIProvidersSnapshot` | `:108-114` | `sync.Once` 只构建一次，前提注释明确「init 注册完毕后不变」（`:16`） |

`Register` 的短路条件是理解本域装配的关键：它**只保护 `Type` 为空**的情形。若子包带非空 `Type` 重新注册，表单会被整体覆盖——`huoshan.go:27-42` 与 `ucloud.go:24-37` 就是自带完整表单的写法，而 `aliyun.go:37`、`tencent.go:42` 与 `acme.go:70/73/76` 传 `cert.ProviderConfig{}` 走短路，把表单留在 `providers.go`。`providers.go:45-50` 的注释记录了这一耦合约定，并警告删掉该处注册会让 `/api/cert/providers` 丢表单。

`tencent_test.go:205-223` 的 `TestRegistrationKeepsFormConfig` 专门锁定该语义：先断言 `cert.GetProvider("tencent", …)` 能拿到非 nil 实现，再断言 `cert.GetProviderConfig("tencent")` 的 `Name` 仍为「腾讯云免费SSL」且 `len(cfg.Config) != 0`。

### init() 注册与装配顺序

Go 的包初始化保证「被导入包先于导入包完成 `init()`」。`cert` 是 `acme`/`aliyun`/`tencent`/`huoshan`/`ucloud` 的被导入方，因此顺序恒为：`providers.go:3-6` 先登记全部表单（工厂传 `nil`），随后各子包 `init()` 补工厂。

### 阿里云免费 SSL（aliyun_cert）

**认证与签名**。凭据为 `access_key_id`/`access_key_secret`（`providers.go:71-72`），`NewProvider` 只读取这两项（`aliyun.go:54-61`），表单额外收集的「姓名/手机号码/邮箱地址」（`providers.go:73-75`）在该包内**无任何读取点**——联系人实际由云端 `ListContact` 提供（`aliyun.go:149-161`）。签名走阿里云 RPC 规范：`signedBody` 补齐 8 个公共参数（`aliyun.go:382-397`），`SignatureMethod` 固定 `HMAC-SHA1`、`SignatureVersion` 固定 `1.0`、版本号固定 `2020-04-07`（`:24`），`signForm` 以 `access_key_secret + "&"` 为密钥对 `POST&%2F&<规范化查询>` 求 HMAC 再 Base64（`:399-404`），`percentEncode` 把 `+` 还原为 `%20`（`:438-440`）。全部实现为手写，不依赖官方 SDK。

**认证与签名**。四个常量固定接入面：`open.volcengineapi.com`、`cn-north-1`、`certificate_service`、`2021-06-01`（`huoshan.go:20-23`）。凭据键名为**大驼峰** `AccessKeyId`/`SecretAccessKey`（`:32-33`），`NewProvider` 用包内 `getString` 精确匹配读取（`:52-59`、`:61-66`）——无大小写或驼峰回落，键名拼错会静默变成空凭据。签名是 SigV4 风格：规范化请求含方法、URI、查询串、头集合与正文 SHA256（`:400-407`），凭证范围 `日期/cn-north-1/certificate_service/request`（`:411`），密钥链 `secretAccessKey → date → region → service → request` 逐层 HMAC-SHA256（`:424-429`），`Authorization` 头拼 `Credential/SignedHeaders/Signature`（`:432-438`）。有正文时把 `content-type:application/json` 纳入签名头，无正文时只用 `host;x-date`（`:390-395`）。查询串把 `+` 替换成 `%20`（`:386`）。

## 性能考虑

| 项目 | 取值 | 位置 | 影响 |
|------|------|------|------|
| API 客户端超时（4 家云 + acme 各工厂） | 30 秒 | `aliyun.go:26`、`tencent.go:37`、`huoshan.go:56`、`ucloud.go:57` | 单请求上限，不含重试 |
| 证书 ZIP 下载超时 | 腾讯复用 30 秒客户端；UCloud 独立 60 秒 | `tencent.go:402`、`ucloud.go:284` | 大包下载在腾讯侧更易超时 |

| 火山信息模板重复查询 | `BuyCert` 与 `CreateOrder` 各一次 | `huoshan.go:89`、`:121` | 因 `OrderInfo` 无处存 org id（`:105-109` 注释） |

云渠道与 ACME 的成本结构差异明显：ACME 是**多轮短请求**（一次签发十余次 HTTP 往返，无固定 sleep），云渠道是**少轮长等待**（3 次左右往返 + 30 秒级轮询或 3 秒固定 sleep）。这决定了排障策略不同：前者看速率限制，后者看等待是否足够。

三条值得关注的工程代价：

- 云渠道 `CreateOrder` 内部自带等待（轮询或 sleep），意味着 handler 协程在整个 `CreateOrder` 期间不可中断，鉴权与配额逻辑无法在此期间介入。
- `getMainDomain` 只保留「倒数两段」（`aliyun.go:505-512`、`tencent.go:488-495`），对 `com.cn` 之类二级后缀会把主域算错；火山与 UCloud 不做该折算，改用申请域名原样分组（`huoshan.go:201`、`ucloud.go:220`），因此同一份代码库存在两套分组口径。部署侧 `tencent_cdn.go:147-148` 的 300 毫秒注释为「等待证书处理」，属经验值，批量部署同一账户时会线性叠加。

四类最容易踩的实现约束：

- **键名精确匹配陷阱**：`huoshan.go:54-55` 与 `ucloud.go:52-57` 用包内 `getString`（`:61-66`/`:62-67`）做精确匹配，没有部署侧 `base.GetString` 的四级回落（`base.go:199-227`）。火山表单是大驼峰 `AccessKeyId`/`SecretAccessKey`，UCloud 是小写 `public_key`/`private_key`——照搬部署表单写法去建签发账户会静默拿到空凭据。
- **被忽略的错误**：`huoshan.go:329` 的 `Cancel` 与 `ucloud.go:381` 的 `CancelCertificateOrder` 都丢弃返回值，取消失败时上层无法感知；`ucloud.go:315`、`:325` 的 ZIP 读取同样忽略 `io.ReadAll` 错误。
- **签名时间偏差**：阿里云用 UTC 秒级 `Timestamp`（`aliyun.go:391`），火山用 `x-date`（`:354`、`:448`），腾讯用 Unix 秒（`:298`、`:308`）。任一家对时钟偏差敏感时，主机时钟漂移会让三家同时报签名错误，排查应先比对 NTP。
- **测试基线现状**：`internal/cert` 下仅 `aliyun`（11 个测试函数）与 `tencent`（9 个）有单测，`huoshan`/`ucloud`/`acme` 无测试文件。实测 `go test ./internal/cert/aliyun/ ./internal/cert/tencent/ ./internal/cert/huoshan/ ./internal/cert/ucloud/ ./internal/cert/acme/`（工具链 `go1.27.2 linux/amd64`）结果为 `ok aliyun 2.017s`、`ok tencent 0.012s`、其余三包 `[no test files]`。`aliyun_test.go:89-229` 覆盖了签名自洽、错误透出与假服务端全流程；`tencent_test.go:205-223` 覆盖注册不覆盖表单、`:229` 起覆盖 `FinalizeOrder` 端到端。新增渠道时这两份测试可直接作为样板复用。

## 结论

1. **接口收敛是有效的**。四家云厂商与 ACME 的 9 方法接口（`interface.go:52-79`）让 `handler/cert.go:656-793` 的签发流水线保持厂商无关，任何新增渠道只需实现一个包并 `cert.Register`，无需改调用层——这是 OCP 的直接体现。
2. **「表单与工厂分离 + `Type` 空值短路」是 clever 但脆弱的约定**。`registry.go:31-33` 让子包能安全补工厂（`aliyun.go:37`、`tencent.go:42`），但该保护不覆盖 `Type` 非空的整表单重写；`providers.go:45-50` 的注释与 `tencent_test.go:205-223` 是这个隐式契约唯一的显式记录。
3. **`ucloud` 是「实现完成、装配缺失」的典型**。代码完整（`ucloud.go:110-364`）、签名最简（SHA1 串接，`:400-409`），但因缺少 blank import 而不可用，且注册表把它当纯部署项（`providers.go:549-562`）。要启用需两处协同：加 `main.go` 导入 + 处理与既有 `ucloud` 部署键的覆盖关系（`registry.go:26-34` 的短路对它无效，因为 `ucloud.go:24-37` 带非空 `Type`）。
4. **状态与有效期口径不统一**。阿里云与腾讯云用本地 x509 解析（`aliyun.go:486-502`、`tencent.go:469-485`），火山与 UCloud 采信云端字段（`huoshan.go:295-306`、`ucloud.go:345-355`）；终态判定各自私有（`normal`/`1`/`300+1`/`COMPLETED`）。跨渠道一致性校验若缺失，续期判断会出现「同一张证书不同到期时间」的观感差异。
5. **吊销/取消/购买是接口层预留、应用层未接线**的能力（`Revoke`/`Cancel`/`BuyCert` 无上层调用点，`ucloud.go:120` 是唯一自调用）。证书数量因此只增不减，额度型渠道（腾讯 50 张、阿里每年 20 张，`providers.go:55`/`:69`）存在耗尽风险。
6. **测试基线偏向阿里与腾讯**（合计 20 个测试函数，`huoshan`/`ucloud`/`acme` 为零），任何厂商响应结构变更只能靠生产暴露。下一步建议按优先级：补 `ucloud` 装配或明确移除该包 → 为四个云渠道补与 `aliyun_test.go` 同构的假服务端测试 → 在 `Provider` 与部署接口之间补一个统一的状态归一化函数，替代各包私有判定。
