## 简介

本文聚焦 DNSPlane 证书域中「一张证书从待申请到过期」的全生命周期实现，覆盖状态机、定时调度、
自动续期钩子、部署联动与到期通知五条主线。所有结论均来自当前工作区实际读取的代码与行号。

### 生命周期阶段与阅读前提

| 阶段 | 承载代码 | 触发方式 | 可观测状态 |
|------|----------|----------|------------|
| 待申请 | `CreateCertOrder` 建单 | 用户提交 | `status = 0` |
| 申请中 | `processCertOrderAsync` | 手动 process 或 `is_auto` | `status = 1` |
| 签发完成 | `FinalizeOrder` 回写 | ACME `finalize` 成功 | `status = 3` + `issue_time` + `expire_time` |
| 部署下发 | `executeDeployTasks` | 签发成功或证书更新检测 | 部署任务 `status` 1/2/-1 |
| 自动续期 | `checkCertRenewal` | 每 5 分钟心跳 | `status` 由 3 复位为 0 |
| 到期提醒 | `checkCertExpire` | 每 24 小时心跳 | `is_send` + `expire_notice_at` |
| 失败终态 | 六类负值状态 | 各阶段错误分支 | `status = -1 ~ -5` |

阅读前提有三条：其一，签发渠道与部署器实现清单见「证书部署策略」子文档，本文不重复枚举 88 个
部署器；其二，只有「签发—续期—到期」这条主线是全自动的，吊销与取消在当前工作区无任何入口，
属接口预留而非可用能力，证据见[吊销与取消](#吊销与取消能力存在但链路不可达)；其三，文中所有密钥、
令牌、口令一律以 `{占位}` 表示，不出现真实值。

协作原则有三点。**依赖倒置**：`service` 不 import `handler`，续期需要执行 ACME 时通过
`SetCertRenewProcessStarter(handler.TriggerCertOrderProcessing)`（`main.go:108`）把函数指针注入
`service` 的包级变量，反向依赖仅存在于装配期。**单一职责**：`task_runner.go` 只管「何时做」，
`cert.go` 只管「怎么做」，状态写入点集中在 `cert.go:509-820` 与 `task_runner.go:198-205`。
**开闭原则**：新增签发渠道不改动生命周期代码，只需实现 `cert.Provider` 九方法
（`interface.go:52-79`）并在自身 `init()` 注册。

|:----:|-----------------------------|-----------------------------------|------------------|

| 1 | validating | 未映射 | 处理中；`runAutoAuth` 为假时也停在 1 等待人工验证 |
| 2 | validated | 未映射 | **无赋值点**，属幻影状态 |

## 详细组件分析

### 申请：建单与自动占位

`CreateCertOrder`（`cert.go:354`）在写库前完成四道校验，任一失败即返回且不产生订单：
配额 `CheckQuota(c, "certs")`（`:356`）、属主 `requireCertAccountOwner`（`:366`，实现
`cert_authz.go:32`）、标识合法性 `validateCertOrderDomains`（`:374` 调用，定义 `:265`）、
校验方式约束 `validateChallengeChoice`（`:391` 调用，定义 `:321`，纯 IP 禁 `dns-01`、
通配符禁 `http-01`）。

订单以 `Status: 0` 落库（`:403`），随后按用户提交顺序写入 `cert_domains`（`:411-418`，`sort` 递增）。
若 `is_auto` 为真且能取到签发渠道，建单请求**就地占位**：`order.Status = 1`（`:443`）→ `Save`（`:444`）
→ `go processCertOrderAsync(...)`（`:446`），首张证书无需再调 process 接口。

加密边界由 GORM 钩子固定：`CertOrder.BeforeSave` 只加密 `PrivateKey` 与 `Info`（`hooks.go:38-39`），
`FullChain` 与 `DNS` 为明文列（`models.go:239-240`）；续期与部署比对依赖的
`expire_time`/`issue_time` 均为明码时间列（`models.go:225-226`）。

### 部署：签发结果驱动的自动下发

部署任务不在证书状态机内，而是通过 `issue_time` 与订单建立因果关系。`executeDeployTasks`
（`task_runner.go:217`）每轮拉取 `active = true AND is_lock = false AND status IN (0, 2)`（`:219-220`），
过滤条件为：订单必须 `status = 3` 且 `fullchain`、`private_key` 均非空（`:227`）；
已部署过的任务仅当 `order.IssueTime` **严格晚于** `deployTask.IssueTime` 时才重下发（`:230-239`）。

`executeSingleDeploy`（`task_runner.go:281`）用一条带 `is_lock = false` 条件的 UPDATE 完成加锁
（`:284-291`，`RowsAffected == 0` 即让位），部署上下文带 5 分钟硬超时（`:345`），成功回写
`status = 2`、`retry = 0`、`log_content`、`last_time`、`issue_time`（`:364-377`），并把部署器回传的
配置增量合并进任务配置（`:374`）。失败经 `updateDeployFailed`/`updateDeployFailedWithLog` 写
`status = -1` 与 `retry + 1`（`:395-419`）。

手动入口只有 `ProcessCertDeploy`（`cert.go:1315`）一条：同步执行 `provider.Deploy`（`:1376`），
**只更新 `updated_at`**（`:1382`），既不写 `status`、也不写 `log_content`，更不参与重试与通知。

| 部署触发路径 | 加锁 | 写 `log_content` | 更新 `status` | 通知 |

| `executeSingleDeploy` | 是 | 是 | 2 / -1 | 失败时 |
| `retryFailedDeployTasks` | 是 | 是 | 2 / -1 | 达上限时 |

### 续期：扫描、退避与复位

`checkCertRenewal`（`task_runner.go:153`）是自动续期唯一入口。

```mermaid

    HOOK -->|"是"| RUN["回调 TriggerCertOrderProcessing 起协程"]
    RUN --> CAS{"CAS 占位成功"}
    CAS -->|"否"| DROP["记录并发抢占告警并返回"]
```

### 到期提醒

`checkCertExpire`（`task_runner.go:893`）由 24 小时心跳驱动（`runExpireNotice` 首跑 60 秒，
`:115-139`）。进入函数先执行一条补偿 UPDATE：把 `status = 3 AND is_send = true AND expire_notice_at IS NULL`

|:--------:|----------|----------|
| ≤ 0 | 【证书已过期】 | 已于 `{expire_time}` 过期，请立即续期或检查自动续期任务 |
| 1 至 7 | 【证书即将过期】 | 将在 N 天后过期，请及时续期 |
| 8 至提前窗口 | 【证书到期提醒】 | 将在 `{expire_time}` 过期（剩余 N 天） |

### 失败重试与锁兜底

证书侧与部署侧的重试是两套互不相干的策略。

| 维度 | 证书续期重试 | 部署任务重试 |
|------|--------------|--------------|
| 候选条件 | `is_auto = 1 AND status = 3` 且进入续期窗口 | `active = 1 AND status = -1 AND is_lock = 0`（`:246-247`） |
| 上限 | 固定 5（`:172`） | `MaxRetry`，为 0 时取 5（`:251-253`） |
| 退避序列 | 300/600/1800/3600/7200 秒（`:185`） | 60/300/600/1800/3600 秒（`:23`） |
| 成功归零 | **否** | 是（`:369`） |
| 上限后通知 | 是，24 小时冷却（`:173-179`） | 是，最后一次失败时（`:358-360`） |

锁兜底 `releaseExpiredLocks`（`task_runner.go:421`）每轮最后执行：部署锁 10 分钟超时释放并置
`status = -1`（`:422-433`）；订单锁 15 分钟超时释放并置 `status = -6`，随后逐个补发签发失败通知
（`:435-453`）。但订单分支的条件是 `is_lock = true AND status = 1`（`:442`），而全仓没有任何代码把
`cert_orders.is_lock` 置为 `true`（两条 CAS 只更新 `status`），因此 **-6 实际不可达**，
`checkCertRenewal` 里的 `order.IsLock` 跳过（`:167`）也永远不成立。协程泄漏时订单只能靠 5 分钟
`updated_at` 陈旧判定由人工重处理解锁（`cert.go:535-542`）。

（`database.go:147`、`:152-157`），使重启后的续期可被重新调度。

## 性能考虑

### 续期并发

单个心跳周期内 `checkCertRenewal` 对候选列表**串行遍历并同步触发协程**
（`task_runner.go:166-214`、`cert.go:623`），没有任何并发上限。若重启或配置变更后同时有 N 张证书
进入续期窗口，会一次性拉起 N 个 ACME 协程，每个协程内部又包含 `time.Sleep(10s)` 加最多 10 轮轮询
（`cert.go:767-790`），单协程最短存活约 110 秒。叠加放大因素如下：

| 因素 | 实测取值 | 后果 |
|------|----------|------|
| ACME 限流退避 | 最多 12 次（`acme.go:39`、`:344`） | 单请求可等待至小时级 |
| 协程上下文 | `context.Background()`（`cert.go:647`） | 优雅关闭无法取消，`taskCancel()` 只作用于调度器 |
| ACME 账户复用 | 未持久化（`cert.go:726-733`） | 每单每轮都 `newAccount`，易撞 newAccount 速率限制 |
| 挑战记录清理 | 签发成功后无删除逻辑（`cert.go:977` 单向写入） | 同域名多次续期后 TXT 记录堆积 |

改进方向按投入产出排序为：给续期协程加 `context.WithTimeout`、限制并发协程个位数、
把账户密钥与 `account_url` 以 `{占位}` 形式回写 `cert_accounts.ext`、签发成功后清理 `_acme-challenge`。

### 通知未达

通知链路有四个独立门闩，任一不满足即静默返回：

1. **总开关**：`cert_expire_notice_enabled`（`task_runner.go:894`）、`cert_issue_notice_enabled`（`:661`）、
   `cert_renew_fail_notice_enabled`（`:682`）为默认开启；`cert_issue_success_notice_enabled`（`:634`）
   与 `cert_deploy_success_notice_enabled`（`:458`）为**显式开启**语义（`sysconfigBoolExplicitOn`，`:746`）。
2. **提前窗口与去重**：剩余天数需进入 `cert_expire_notice_days` 窗口，且距 `expire_notice_at`
   不少于 `cert_expire_notice_interval_days`（`:898-920`）。
3. **冷却**：续期失败通知 24 小时冷却（`:729-734`，时间戳存 `renew_fail_notice_at`，
   `models.go:241`）。
4. **渠道配置**：`sendCertNotification` 每次新建 `notify.Manager` 并按 `sys_configs` 重新装载渠道
   （`:617-625`），渠道未配置时只在日志留下「发送证书通知失败」。

另有一项与数据库方言相关的风险：`cert_issue_success_notice_enabled`（33 字符）与
`cert_deploy_success_notice_enabled`（34 字符）超过 `SysConfig.Key` 声明的 `size:32`（`models.go:315`）。
SQLite 不强制变长上限，默认部署无异常；MySQL 下写入可能截断，截断后的键名与读取键不一致，
表现为设置页勾选成功但通知永远不发。此项属**推断**，本环境未实测 MySQL 行为。

此外 `MaybeNotifyCertAutoRenewACMEFailure`（`task_runner.go:701`）在 `cert_renew_fail_notice_enabled`
判定之后便无任何调用方，属死代码，不应作为排障线索。

## 结论

### 成果、缺口与原则评价

证书生命周期在本项目中已是**闭环可用**的：建单、DNS-01/HTTP-01 自动写入、CA 验证轮询、本地生成
私钥签发、`issue_time` 驱动的部署联动、5 分钟心跳的自动续期与 24 小时心跳的到期提醒共同构成完整
链路；核心并发风险由 CAS 状态占位（`cert.go:535-542`）与部署锁（`task_runner.go:284-291`）覆盖。

需要正视的缺口有五项：状态语义三处不一致，`2`/`4`/`-6`/`-7` 无实际赋值路径且通知文案与真实失败阶段
错位；续期计数永不归零，约 15 个月后自动续期停摆并产生误报；订单锁形同虚设，`is_lock` 无置位点使
`-6` 分支与 `IsLock` 跳过均为死逻辑；吊销能力不可达，接口与 ACME 实现均就绪但无路由与调用方；
手动部署不写状态，`ProcessCertDeploy` 与调度器行为不对称，观测面缺失。

原则视角的结论是：按 KISS，生命周期本身足够简洁，单一 `status` 整型列加单一心跳协程即驱动全部行为；
按 YAGNI，`Revoke`/`Cancel`/`BuyCert` 与 `status` 2/4 属预留而未收敛的设计，建议要么补齐入口、
要么从接口与注释中删除以免误导排障；按 SRP 与 DIP，钩子注入（`cert_renew_hook.go`）让调度层与
HTTP 层互不 import，是本域最干净的一处解耦。
