## 简介

证书管理功能域覆盖一张 TLS 证书从「无」到「线上生效」再到「过期前被替换」的闭环，四段串成一条可自动运转的流水线：**申请**（向 ACME CA 或云厂商下单取得验证挑战）、**部署**（把 `fullchain + privateKey` 推送到 CDN/WAF/负载均衡/面板/容器/远程主机）、**续期**（调度器按剩余天数复位订单重签并联动重部署）、**吊销**（接口层已声明，应用层无入口）。

实测规模界定本域边界：

| 维度 | 规模 | 说明 |
| --- | --- | --- |
| 签发渠道实现包 | 5 个 | `acme`、`aliyun`、`tencent`、`huoshan`、`ucloud`；`ucloud` 未被链接，实际生效 4 个 |
| ACME 品牌键 | 5 个 | `letsencrypt`、`zerossl`、`google`、`litessl`、`customacme`（`acme.go:46/:57/:70/:73/:76`） |
| 部署器分组与实现 | 5 组 / 88 个 | `base`/`providers`/`servers`/`panels`/`others`；`main.go:55-58` blank import 4 组（`base` 无实现）；`base.Register` 去重实测 providers 77、servers 3、panels 3、others 5 |
| 部署表单条目 | 53 条 | `AllDeployConfigs`：cloud 23、selfhosted 26、server 4 |
| 域内非测试代码 | 22842 行 | `internal/cert`（含测试 23436）；`deploy/` 子树 18998 行且零测试文件 |

设计取向一句话：**签发侧走统一抽象，部署侧走「注册表 + 表单」双轨**。签发侧用 9 方法接口（`cert/interface.go:52-79`）把 ACME 与云厂商压成同一条状态流；部署侧因 88 个目标平台在认证方式、幂等语义与返回信息上没有公约数，退化为每文件自成实现，靠 `base` 层薄契约粘住。逐部署器的字段级说明与重试参数全表归属《证书部署策略》。

## 详细组件分析

### 证书账户与部署账户

`cert_accounts` 一张表承载两类账户，靠 `is_deploy` 区分（`models.go:202`）。这不是泛化设计，而是两侧表单结构高度重合的结果——都是「一个 `type` + 一份 JSON 凭据」。

| 属性 | 证书账户（`is_deploy=false`） | 部署账户（`is_deploy=true`） |
| --- | --- | --- |
| 类型键来源 | `cert.GetCertProviderConfigs()`（`registry.go:71`） | `MergeDeployProviderConfigsForAPI` 的 deploy 视图 |
| `config` / `ext` 列 | AES-256-GCM 密文（`hooks.go:35`）；`ext` 写 `order_info` | 密文；`ext` 当前无写入方 |
| 属主判定 | `requireCertAccountOwner`（`cert_authz.go:32`） | 同函数逐条 `uid` 比对 |
| 创建端点 | `POST /api/cert/accounts`（`cert.go:152`） | `/api/v1/cert/deploy-accounts/create`（`cert_deploy.go:62`） |
| 删除副作用 | 仅软删，不检查关联订单（`cert.go:206-214`） | 控制台无检查；对外按 `aid` 计数拒绝（`cert_deploy.go:187-193`） |

凭据键一律脱敏描述，真实值不落文档：`AccessKeyId={占位}`、`SecretKey={占位}`、`password={占位}`。`CreateCertAccount`（`cert.go:152`）把请求体 `type` 透传入库而不校验其是否存在于注册表，后果是写入未知 `type` 后账户在界面显示为未知类型，直到取 provider 才报 `provider not found`。

### 申请与签发

`CreateCertOrder`（`cert.go:354`）是纯落库阶段，不做任何出站调用。三段前置校验各有明确边界：

| 校验 | 函数 | 位置 | 规则 |
| --- | --- | --- | --- |
| 域名标识 | `validateCertOrderDomains` | `cert.go:265` | 长度 ≤ 253、禁空白；纯 IP 放行 |
| 订单类型 | `detectCertOrderKind` | `cert.go:287` | 返回 `dns` / `ip` / `mixed` |
| 验证方式 | `validateChallengeChoice` | `cert.go:321` | 纯 IP 禁 `dns-01`；通配符禁 `http-01` |

真正出站的是 `processCertOrderAsync`（`cert.go:646`），按 ACME 四段式驱动，每段失败独立映射到一个负状态并触发失败通知：

| 阶段 | 调用点 | 失败状态 | 通知点 |
| --- | --- | --- | --- |
| 取 provider | `cert.GetProvider` `cert.go:506` | `-1`（`:509`/`:518`） | `cert.go:596` 同类分支 |
| 创建订单 | `provider.CreateOrder` `cert.go:656` | `-2`（`:659`） | `cert.go:662` |
| 触发验证 | `provider.AuthOrder` `cert.go:754` | `-3`（`:756`） | `cert.go:759` |
| 轮询状态 | `provider.GetAuthStatus` `cert.go:769` | `-4`（`:782`） | `cert.go:785` |
| 完成签发 | `provider.FinalizeOrder` `cert.go:793` | `-5`（`:796`） | `cert.go:799` |

`FinalizeOrder`（`acme.go:887`）内私钥与 CSR 全部本地生成（`acme.go:891-906`、`:979`），**私钥从不出站**——这是整条链路最重要的安全性质；支持 `RSA 2048/4096` 与 `EC P-256/P-384`。

一处关键缺陷：`CreateOrder` 在 `accountURL` 为空时自调 `Register`（`acme.go:582-586`），但返回值被丢弃（`if _, err := c.Register(ctx)`），handler 也不写回 `cert_accounts.ext`（`cert.go:726-733` 只写 `order_info`）。后果是每单新建一个 CA 账户，撞上 Let's Encrypt `newAccount` 限流（每 IP 3 小时 5 个）后被 429 卡住。

实现要点：

- **记录名冲突规避**：`acme.go:678-682` 用 `auth_%d_%s` 与 `wildcard_%s` 作 challengeKey，避免同主域多标识符互相覆盖
- **TTL 策略**：`dns.DefaultDNSLine(account.Type)` 取线路，TTL 默认 600，`namesilo` 强制 3600（`cert.go:971-975`）
- **TXT 语义**：`ensure_challenge.go:89-95` 对 TXT 走「同值跳过、异值追加」，非 TXT 走「删旧建新」（`:97-107`）
- **华为云合并**：`mergeHuaweiTXTRecordsForCert`（`cert.go:825`）把同主机名多值合成 `"a","b"` 一条
- **公共 DNS 预检**：`certCheckTXTRecord`（`cert.go:1467`）并行查 `8.8.8.8`/`1.1.1.1`/`223.5.5.5`，全失败回退 DoH
- **自动触发条件**：`runAutoAuth = addedRecords > 0 || (纯 http-01 且 is_auto)`（`cert.go:735`）

## 性能考虑

### 并发签发

签发是全域唯一的长耗时出站操作集合，实现选择了「每单一个协程、串行等待 CA」：

| 行为 | 位置 | 代价 |
| --- | --- | --- |
| 每单起独立协程 | `cert.go:546`（另有 `:446`、`:623`） | 无并发上限，批量下单同时挂 N 个协程 |
| 无 context 超时 | `cert.go:647` `context.Background()` | 无法随优雅关闭取消 |
| 固定 10 秒写入等待 + 10 轮 × 10 秒轮询 + 三轮 DNS 预检 | `cert.go:741`、`:765-790`、`:1401-1460` | 每单最短约 20 秒，最长数百秒纯等待 |
| ACME 退避上限 | `acme.go:39` 12 次、`:252-261` 钳制 10 秒~2 小时 | 单订单协程可存活数小时 |

`context.Background()` 与 `main.go:111-120` 的 `taskCancel()` 是两个不同的 ctx 根：后者只覆盖调度器协程树，签发协程不在其作用域。这解释了停止服务时已下单的签发流程会跑完，而重启后 `resetStuckOrders`（`database.go:152`）把它们复位成 0。日志成本同样计入：`appendOrderLog`（`cert.go:626-633`）每次把整条 `info` 重写并重新 AES-GCM 加密，长流程是 O(n²) 写放大，且用 `fmt.Printf` 直写 stdout（`cert.go:629-632`）绕过 logger 的级别、轮转与脱敏，因此日志文件里查不到证书流程记录。

| 云证书渠道 | 各包自行重试或不重试 | `aliyun`/`tencent`/`huoshan`/`ucloud` | 无统一策略，细节未知 |
| 部署器 | 单次失败即返回 | `base/base.go` 无重试层 | 由 `retryFailedDeployTasks` 补偿 |

真正的容量约束来自 CA 而非本系统：账户密钥未持久化（`acme.go:583` 丢弃 `Register` 返回值）使每单都打 `newAccount`，而 LE 的账户创建速率远低于证书签发速率。修复这一处（把 `account_url` 写入 `cert_accounts.ext` 并复用 KID）可把续期成本从「随单量线性上升」降回常数。

部署侧策略是「失败退避而非事前节流」：`task_runner.go:23` 的 60/300/600/1800/3600 秒序列加 `MaxRetry` 上限（默认 5）。同一账户的多个部署任务在同一轮 `executeDeployTasks` 中顺序执行（`task_runner.go:217-242`），不会并发打同一个云 API——这是当前实现的一处隐性保护，但没有显式声明。

### 证书签发失败

先读订单日志再看状态码。日志入口 `GetCertOrderLog`（`cert.go:1001`），前端在 `status === 1` 时 5 秒轮询（`cert/page.tsx:163-175`）。

| 状态 | 真实含义（赋值点） | 通知里的名字 | 首要排查动作 |
| --- | --- | --- | --- |
| -1 | 取 provider 失败（`cert.go:509`/`:596`） | 购买证书失败 | 核对 `cert_accounts.type` 是否在注册表；`ucloud` 账户必然失败 |
| -2 | `CreateOrder` 失败（`cert.go:659`） | 创建订单失败 ✓ | 看 CA 报错；429 说明新建账户撞限流 |
| -3 | 触发 CA 验证失败（`cert.go:756`） | 添加 DNS 失败 ✗ | 实为 `AuthOrder` 报错，不是 DNS 写入问题 |
| -4 | 验证轮询超时（`cert.go:782`） | 验证 DNS 失败 ≈ | 由 `certPreVerifyDNS` 日志区分传播延迟与值不匹配 |
| -5 | `FinalizeOrder` 失败（`cert.go:796`） | 验证订单失败 ✗ | 订单已 valid，问题在 CSR 或下载阶段 |
| -6 | 订单锁超时被释放（`task_runner.go:445`） | 订单验证未通过 ✗ | 实际几乎不出现，见下文锁说明 |

模型注释、通知映射、实际赋值三处互相错位会直接把排障引向错误方向：用户收到「添加 DNS 失败」时 DNS 记录其实早已写入成功。排障以本表状态码为准。

订单锁形同虚设：`ProcessCertOrder` 与 `TriggerCertOrderProcessing` 只做 `status` 的 CAS（`cert.go:536-543`、`:615-622`），从不置 `is_lock`/`lock_time`；而 `releaseExpiredLocks` 的订单分支要求 `is_lock = true AND status = 1`（`task_runner.go:439-441`）。协程泄漏时订单会一直停在 `status=1`，只能等 `updated_at` 超 5 分钟后由人工重触发覆盖。

### 续期未触发

按扫描条件逐字段核对（顺序即 SQL WHERE 顺序，`task_runner.go:163-165`）：`is_auto = true` → `status = 3` → `expire_time` 非空且早于阈值 → `IsLock == false`（`:167`）→ `Retry < 5`（`:172`，累计值且永不归零）→ 距 `retry_time` 超过退避间隔（`:185`）。

六项全过仍不续期时，检查 `CertRenewProcessStarter` 是否被注入——`task_runner.go:210` 未注入只打一条 `logger.Error` 且不重试，日志文案含「请在 main 中注册 handler.TriggerCertOrderProcessing」。

部署不联动的排查点：`executeDeployTasks` 仅在 `order.IssueTime` 严格晚于 `deploy.IssueTime` 时重部署（`task_runner.go:230-239`），两者任一为 `nil` 即走 `continue`（`:236`），表现为续期成功但线上证书不更新；该字段只在部署成功路径回填（`:384`）。此外 `MaybeNotifyCertAutoRenewACMEFailure`（`:701`）无任何调用方，因此「ACME 续期失败」这一类通知目前不会发出。

## 结论

证书域实现了「签发 + 部署 + 续期」三段闭环，缺「吊销」一段。

做得扎实的部分：ACME 客户端的限流退避与 nonce 复用（`acme.go:265`、`:334`）已达到可直接投产的成熟度；私钥本地生成、从不出站（`acme.go:891-920`）是正确的核心不变式；三类账户与订单的敏感列走 AES-256-GCM（`hooks.go:35-52`）；属主链把 `CertDeploy.uid` 与 `CertOrder → CertAccount.uid` 显式区分（`cert_authz.go:88-91`）；`local` 部署单独设卡；钩子注入让 handler 不反向依赖通知实现。

| 优先级 | 待改进项 | 证据 |
| --- | --- | --- |
| P0 | 私钥经 PEM 下载落入 `request_logs` | `cert.go:1098-1104` + `request_trace.go:244` + `sanitize.go:109` |
| P0 | 订单与账户列表内联下发全部私钥 | `cert.go:219-253`、`models.go:239-240` |
| P0 | 6 个部署器固定跳过 TLS 校验 | `synology.go:42` 等 6 处 |
| P1 | ACME 账户密钥未持久化；续期 `retry` 永不归零 | `acme.go:583`、`cert.go:726-733`、`task_runner.go:203` |
| P1 | 吊销、取消、购买全链路不可达 | `interface.go:57/72/75` |
| P1 | 约 700 行部署 handler 未路由 | `cert_deploy.go:331-1032` |
| P2 | 状态语义三处不一致，`2`/`4`/`-7` 为幻影 | `models.go:228` vs `task_runner.go:543-563` vs 赋值点 |
| P2 | 订单锁从未被置位；`process_id` 列 32 字符装不下订单 URL | `cert.go:536-543`、`task_runner.go:439-441`、`models.go:224` vs `cert.go:670` |
| P2 | 挑战 TXT 签发后不清理 | `cert.go:718`、`ensure_challenge.go:89-95` |
| P3 | `ucloud` 未链接、表单与实现矛盾、日志 O(n²)、测试近乎空白 | `main.go:27-30`、`config_server.go:29-40`、`cert.go:626-633` |

结构层面最值得优先做的一件事是**把三个部署入口收敛成一个**：`ProcessCertDeploy`（手动、无锁、无回写）与 `executeSingleDeploy`（调度、有锁、全回写）语义不一致，而设计更完整的 `DeployProcess` 却未路由。三者收敛后状态机与日志才有单一事实源。
