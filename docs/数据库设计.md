## 简介

dnsplane（版本 `1.0.11`）的持久层是「**三库分离 + GORM AutoMigrate + 无外键 + 无显式事务**」的组合：

| 设计点 | 落地方式 | 证据 |
|--------|----------|------|
| 逻辑库拆分 | 主库 `database.DB`、日志库 `LogDB`、请求日志库 `RequestDB` | `database.go:21-25` |
| 建表能力 | 完全由 `AutoMigrate` 生成，仓库内无 `*.sql` 迁移文件与版本表 | `database.go:241-277`、`:299-311` |
| 双驱动 | SQLite（默认，纯 Go 驱动 `glebarez/sqlite v1.11.0`）与 MySQL（`gorm.io/driver/mysql v1.6.0`）；日志库与请求库**硬编码 SQLite**，不随 `database.driver` 变化 | `database.go:15-16`、`:90-118`、`go.mod:9`、`:26-27` |
| 事务与完整性 | `SkipDefaultTransaction: true`；全库零外键声明，关联由业务层手工级联 | `database.go:76-79`、`models/` 无 `constraint:FK` 标签 |
| 敏感字段 | `BeforeSave`/`AfterFind` 做字段级 AES-256-GCM，密文前缀 `enc:v1:` | `hooks.go:32-70`、`crypto.go:17`、`:42-62` |
| 读穿缓存与 SQL 追踪 | `dbcache` 对热点列表做 60 秒 JSON 缓存（DB 为权威源）；GORM 回调按请求收集 `DBQuery` 写入 `request_logs.db_queries` | `dbcache.go:12`、`:14-44`、`database.go:347-352`、`:427-496` |

结论分两层次：**已验证**＝模型标签逐字段实读，表名/DDL/索引来自运行时三库 `sqlite_master` 实查；**推断**＝`dns_records`、`user_quotas` 在本地运行时库中不存在（该库陈旧），结构按 `models/quota.go` 标签推导并在文中明确标注。脱敏约定：口令、令牌、密钥、连接串一律写作 `{占位}`。

SQLite 的并发上限来自 DSN 内的 PRAGMA 而非连接数。`sqliteDSN`（`database.go:39-46`）串起 `journal_mode(WAL)`、`synchronous(NORMAL)`、`busy_timeout(5000)`、`cache_size(-16000)`、`temp_store(MEMORY)`、`mmap_size(67108864)`；`:34-38` 注释记录一条硬约束——`glebarez/go-sqlite` 只识别 `_pragma`/`_time_format`/`_txlock` 三类参数，且每个新连接重建时重新执行 `_pragma`，因此 **PRAGMA 必须写进 DSN**。MySQL 侧 DSN 形如 `username:{占位}@tcp(host:port)/database?charset=utf8mb4&parseTime=True&loc=Local`（`database.go:83-84`）。

### 迁移策略

`migrate()`（`database.go:241-277`）注册 26 个模型、`migrateLogDB()`（`:299-305`）注册 3 个、`migrateRequestDB()`（`:307-311`）注册 1 个。因无外键，顺序**不是硬依赖**，实际按「用户与权限 → DNS 资源 → 证书 → 任务 → Cloudflare → 配额」的认知顺序排列。`AutoMigrate` 只新增表/列/索引，**不删除、不重命名、不缩窄类型**，项目在其上叠加 7 类手工兼容：

| 类型 | 机制 | 位置 |
|------|------|------|
| 数据搬迁 | `migrateOldData()`：主库若仍有 `logs`/`cert_logs`/`request_logs`，按 500 条批量搬入 LogDB/RequestDB，随后 `DELETE` + `DROP TABLE` + `VACUUM` | `database.go:160-239`，批次 `:171-172` |
| 数据搬迁 | `migrateGitHubIDToOAuth()`：`github_id > 0` 写入 `user_o_auths`，已存在则跳过（幂等） | `database.go:280-297`，调用点 `:275` |
| 数据搬迁 | `crypto.MigratePlaintext(DB)`：按 `DefaultMigrateSpecs` 白名单把不以 `enc:v1:` 开头的明文列原地加密 | `migrate.go:14-22`、`:24-41`，调用点 `database.go:137` |
| 状态修复 | `resetStuckOrders()` 把 `CertOrder.status = 1` 重置为 `0`；`cleanInvalidTasks()` 把 `did = 0` 或 `record_id` 为空的 `DMTask` 置 `active = false` | `database.go:152-157`、`maintenance.go:134-152` |
| 默认值兜底 | `initAdmin()` 不硬编码默认凭据，用户表为空时仅提示走 `POST /api/install` | `database.go:313-325` |
| 默认值规避 | `Plan.Status`/`UserSubscription.Status` 故意不加 `gorm:"default"`，避免值为 0 时被跳过而写入库默认 1 | `quota.go:25-31`、`:49` |

### 维护任务

`MaintenanceService`（`maintenance.go:101-106`）为单例协程：`maintService != nil` 时直接返回以保证幂等（`:111-114`），启动后延迟 30 秒执行首轮，此后每小时 `runCleanup()`，`VACUUM` 按 `VacuumInterval` 判定（`:168-195`）。阈值来自 `sys_configs` 的 `maint_%` 键，每轮开头重新装载（`:200`），故改动下一小时生效。

| 清理目标 | 所在库 | 判据 | 默认保留 | 位置 |
|----------|--------|------|----------|------|
| `Log` / `CertLog` | LogDB | `created_at < now-Nd` | 90 天 / 60 天 | `:204-207`、`:212-215` |
| `DMCheckLog` | LogDB | `created_at < now-72h`（按小时） | 72 小时 | `:220-223` |
| `DMLog` | **主库** | `created_at < now-60d` | 60 天 | `:228-231` |
| `RequestLog` | RequestDB | 按天 `now-7d`；另按 `is_error` 分流，`Offset(keep)` 取最小保留 ID 后删 `id <=` | 7 天；成功 2000 / 错误 1000 条 | `:237-245`、`:250-268` |

压缩阶段对三库各执行五条 SQLite 专用语句：`wal_checkpoint(TRUNCATE)` → `ANALYZE` → `PRAGMA optimize` → `VACUUM` → 恢复 `journal_mode=WAL`（`:284-320`）。`GetMaintenanceStats()`（`:336-353`）是双检锁 + 25 秒 TTL 的进程内快照，行数估算读 `sqlite_stat1` 而非逐表 `COUNT(*)`，并置 `tables_approx = true`（`:406-422`）。

覆盖 `users`、`user_o_auths`、`permissions`。本域不是 RBAC 三表（`roles`/`user_role` 未实现），而是 **Level 整数 + Permissions JSON 模块点 + 域名级委派行**的混合形态。

五条调度扫描都精确命中复合索引前缀，这是当前设计里最扎实的部分：

| 热路径 | 查询条件 | 命中索引 | 位置 |
|--------|----------|----------|------|
| 监控到期扫描 | `active = ? AND check_next_time <= ? ORDER BY check_next_time asc` | `idx_dm_tasks_active_next` | `monitor/monitor.go:150-151` |
| 证书到期续期 | `is_auto = ? AND status = ? AND expire_time < ?` | `idx_cert_orders_auto_scan` | `task_runner.go:163-164` |
| 部署任务取活 / 失败重试 | `active = ? AND is_lock = ? AND (status = ? OR status = ?)`、`active = ? AND status = ? AND is_lock = ?` | `idx_cert_deploys_scan` | `task_runner.go:219-220`、`:246` |
| 定时切换取活 | `next_time > 0 AND next_time <= ? AND active = ?` | `idx_schedule_tasks_active_next` | `service/schedule.go:98` |

关键词搜索一律写成 `%kw%`，会废掉 `idx_domains_name` 等所有 B 树索引，随表规模线性劣化：`handler/domain.go:112`、`handler/monitor.go:118`（三列）、`handler/schedule.go:65`（5 列串接）、`handler/user.go:439`、`handler/logs.go:76`、`handler/request_log.go:74`（五列）、`handler/optimizeip.go:161-163`。建议改前缀 `LIKE 'kw%'` 以复用索引；确需全文则对 `domains.name`、`request_logs.path` 引入 SQLite FTS5 或 MySQL `FULLTEXT`。

四处「循环内逐行查库」构成 N+1：`task_runner.go:174-175`（续期循环内每单 `Pluck("domain")` 查 `cert_domains`）、`:207`（每单插一条 `cert_logs`）、`:224-226` 与 `:268`（部署/重试循环内每条任务 `First(&order)`）、`record_sync.go:209-227`（差异同步对每行分别 `Updates`/`Update`/`Create`/`Delete`，批量 100）。`SkipDefaultTransaction: true`（`database.go:78`）使逐条操作各自独立提交，单条开销小但总次数不减；建议把 `First(&order)` 提为一次 `WHERE id IN (...)` 预取，`cert_domains` 用 `oid IN (...)` 分组装载。

|------------|-----|--------|----------|
| `db:v1:accounts:admin`、`db:v1:accounts:user:{uid}` | 60s | `account.go:103-109` | `BustAccounts`：`account.go:246`、`:298`、`:352` |

三条相关细节：`GetOrSetJSON` 的回填写入失败被显式吞掉（`dbcache.go:40-42`），缓存不可用时退化为「每次回源」而不报错；`sysconfig` 不探测 DB 变更，绕过它直接写库的入口必须自行失效（`handler/user.go:712` 写入后 `:715` 立即 `Invalidate`）；缓存实例为 nil 时直接回源（`dbcache.go:19-28`）。

## 故障排查指南

### SQLite 锁、MySQL 兼容与字段迁移冲突

三库均为独立 SQLite 文件，路径由主库路径派生（`config.go:58-68`，默认 `file_path = data/dnsplane.db`，`:95`）。

| 现象 | 判据 | 处置 |
|------|------|------|
| `database is locked` | DSN 内已含 `busy_timeout(5000)`（`database.go:42`） | 确认 DSN 未被自改覆盖；PRAGMA 必须写在 DSN 里才作用于每条新连接（`:34-38`） |
| 主库旁 `-wal`/`-shm` 常驻 | WAL 生效（`journal_mode(WAL)`，`:40`） | 正常；`wal_checkpoint(TRUNCATE)` 由维护任务执行（`maintenance.go:297`） |
| 体积不降但空闲页多 / VACUUM 后并发退化 | `PRAGMA freelist_count`（`maintenance.go:401-404`）；`VACUUM` 可能重置 journal 模式 | 等或缩短 `maint_vacuum_interval_h`；代码在 `:311` 恢复 `WAL`，手工执行需自行恢复 |
| 主库切 MySQL 后日志看不到 / MySQL 下维护静默失效 | `LogDB`/`RequestDB` 硬编码 `sqlite.Open`（`database.go:106`、`:114`）；`optimizeGormDB` 五条全为 SQLite 专用（`maintenance.go:297-311`），仅 `VACUUM` 检查错误 | 多副本部署下各副本日志互不可见，需外部汇聚；`PRAGMA page_count` 失败使 `size` 归 0，应加 `IsSQLite()` 分支（`database.go:27-32`） |
| `sys_configs` 新键在 MySQL 报错 | `Key` 声明 `size:32`（`models.go:315`），实测最长键 `cert_expire_notice_interval_days` 恰 32 字符 | 先扩列到 64 再新增键 |
| `driver` 填错却不报错 | `case "sqlite": fallthrough` → `default`（`database.go:91-92`） | 静默落 SQLite 分支；排查先核 `IsSQLite()` |

`AutoMigrate` 只加不减，导致「旧库正常、新库静默失效」的分叉：

| 症状 | 根因 | 证据与影响 |

## 结论

三库分离 + 单文件 SQLite + 无外键，对「单机自托管面板」这一目标是合适的：零部署成本、备份即拷文件、`SkipDefaultTransaction` 与 WAL 把单条写代价压到最低。五条调度扫描与复合索引严格对齐，说明索引被真实消费；字段级加密（7 表 10 列）把云端凭据从明文风险中摘出，`enc:v1:` 前缀为换密钥留了余地。

必须优先修复的三项：

| 优先级 | 问题 | 最小修复方向 |
|--------|------|--------------|
| 1 | `DMTask` 缺列导致全新安装监控整体失效 | 在 `models.go:134-176` 补声明四字段，或改 `monitor.go:334` 只写模型已知列并检查 `Error` |
| 2 | `Updates(map)` 绕过加密钩子 | 敏感列改走 `Save(&struct)`，或写入前显式 `crypto.Encrypt` |
| 3 | `migrate.go:21` 表名 `user_oauths` 与真实 `user_o_auths` 不符 | 修正常量，并用显式 `TableName()` 切断 GORM 缩略语拆分 |

结构性建议：引入显式 `TableName()`（`user_o_auths`、`cloudflare_c_id_r_routes` 是命名策略的副产品，长期制造匹配成本）；引入最小版本化迁移（一张 `schema_version` 表 + 少量 `UP` 脚本即可，`AutoMigrate` 不删列不删索引，遗留项只增不减）；补齐删除路径的级联清单（`dns_records`、`cloudflare_hostnames`、`domain_aliases`、账户删除路径下的 `cert_orders`/`cert_deploys` 目前无人负责）；让搜索路径与索引和解（前缀匹配或 FTS 二选一）。
