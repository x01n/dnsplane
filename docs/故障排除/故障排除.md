## 简介

本篇是 DNSPlane 故障排除域的总览文档，目标是把"出现异常"这一模糊输入收敛为**可执行的七类分诊**，
并为每一类给出：症状表、可复制的定位命令、以及指向子文档的下钻入口。

七类分诊口径（与代码域一一对应，不引入新分类）：

- 登录与会话：验证码、令牌签发与吊销、Cookie 与 Bearer 双通道、权限判定
- DNS 操作：记录增删改查、批量路径、服务商能力与配额
- 证书签发与部署：ACME 订单状态机、续期计数、部署器落地
- 通知：渠道可达性、告警风暴、同步发送阻塞
- 性能：厂商调用放大、分页失效、慢连接与超时缺配
- 崩溃与重启：panic 恢复层级、请求日志丢失、优雅关闭
- 数据与迁移：主密钥、密文列、缺列静默失败、日志清理与保留

**反幻觉声明**：本文所有源码结论均给出文件与行号锚点。标注"实测"的条目来自
`docs/问题检测报告.md` 与 `.wiki-context/analysis-*.md` 的取证记录；标注"推断"的条目为源码路径
推演，未做运行期复现。命令块中的输出为**预期输出**，不代表本次已执行。

本域的四篇子文档按取证手段划分，交叉链接见 [日志分析](file://docs/故障排除/日志分析.md)、

[安全事件响应](file://docs/故障排除/安全事件响应.md)。

## 项目结构

排障时需要知道的不是源码树，而是**证据树**：一次故障的可观测面分散在五处产物中。

| 证据位置 | 内容 | 写入者 | 可信度 |
|:---|:---|:---|:---|
| `main/logs/<日期>.log*` | 结构化运行日志、panic 堆栈 | `logger.NewWithOptions` | 受轮转与级别过滤影响 |
| `main/data/logs.db` | 控制台"操作日志" | `middleware/audit.go` | Redis 开启时改落 Redis |

| `main/config.json` | `master_key` 与运行配置 | `config.go` | 缺失时会被随机重建 |

## 核心组件

排障视角下需要重点理解的组件只有五个。

### 认证双通道与会话缓存

`middleware/auth.go` 的 `Auth` 采用 **Cookie `_t` + Authorization Bearer 双写一致性校验**：先从
`_t` cookie 取密文并 `DecryptCookie`，再提取 Bearer token 比对，两者不一致直接
`401 {"code":401,"msg":"Token不一致"}`。这是"能登录但接口全 401"最常见的第一因。

Cookie 属性（`:308-309`）：`_t` 的 path 为 `/`，`_rt` 的 path 为 `/api/auth/refresh`，两者均 HttpOnly，
`secure` 取决于运行期配置。前端把 access token 另存 `localStorage`，因此任何"清 cookie 但不清
localStorage"或"反向代理吞掉 `Authorization` 头"的变更都会命中上述不一致分支。

第二处易踩点：`getCachedAuthUser` 命中即返回，`authUserCacheTTL = 30 * time.Second`，且
`InvalidateAuthUserCache` 无调用点（实测 `rg` 零命中），因此禁用账户、降级 `level`、改权限 JSON
都要等缓存过期才生效，30 秒窗口内的"改权限没反应"属预期行为。

### 权限中间件的放行与回落

`Permission()` 有两处与直觉相反的行为，必须同时记住：

- `permission.go:143-148`：请求中解析不到 `domain_id` 时**直接 `c.Next()` 放行**，把判定责任交给
  handler。若某条写路径 handler 自身未做域校验，就构成越权面。
- `permission.go:229-231` → `:152`：`domainID` 最终回落到 `c.Param("id")`，随后无条件按 `domains.id`
  查库，查不到即 `200 {"code":-1,"msg":"域名不存在"}`。这污染约 40 条带 `:id` 但语义非域名的路由
  （`/monitor/tasks/:id/*`、`/cert/accounts/:id/*`、`/accounts/:id/*`、`/logs/:id` 等）。
  `level >= 2` 在 `:138` 直通，故**该误拒只在普通用户身上显现**。

### 请求追踪与双层 Recovery

`RequestTrace` 的落库代码位于 `c.Next()` **之后**。若只有链首的 `gin.Recovery()`，panic 会穿透到
链首而跳过落库，请求日志完全丢失（analysis-auth 记录为实测：仅外层 Recovery 时 RequestLog 零记录）。
因此 `applyAPIMiddleware` 在 `RequestTrace` 之后内联挂载 `middleware.Recovery()`，先 `SetError`
并写 `ErrorStackKey`，把 panic 挡在 RequestTrace 之内。链首的 `gin.Recovery()` 保留，用于兜住
不经 RequestTrace 的静态资源、页面路由与 `NoRoute`。

### 证书订单状态机与调度器

`cert_orders.status` 的语义在三处不一致：模型注释、通知名映射、实际赋值互相错位；`-7` 无赋值点，
`2`/`4` 从未使用。后果是**用户看到的错误名不等于失败环节**：所谓"添加 DNS 失败"实为 CA 验证触发
失败。自动续期的 `retry` 只在 `task_runner.go:203` 每轮 +1，成功路径 `cert.go:810` 不重置，累计到 5
即永久停摆并误报"已连续尝试5次仍未成功"。

### 主密钥与密文列

`crypto.MustDecrypt` 在解密失败时**静默返回原串**，不报错。叠加 `config.go:105-111` 在
`config.json` 缺失时生成随机 `master_key` 并回写，形成最危险的静默故障：容器重建或未持久化该文件
→ 新密钥读不到旧密文 → 所有 `enc:v1:` 列（账户凭据、证书私钥、TOTP、OAuth token）表现为"值变成
一长串乱码字符"而不是"解密失败"。

## 详细组件分析

### 通用处置流程：复现→采集→定位→修复→回归

任何一类分诊都走同一条五步流程，且**每一步都有可验证的产物**，不允许跳步。

| 步骤 | 动作 | 产物 | 判定标准 |
|:---|:---|:---|:---|
| 复现 | 固定账号、固定输入、一次只改一个变量 | 可重放请求（含 `X-Request-ID`） | 三次中至少两次一致 |
| 采集 | 同时取运行日志、请求日志、库内状态 | `logs/*.log` 切片 + `request_logs` 行 + SQL 结果 | 时间轴可对齐 |
| 定位 | 按决策树收敛到单一组件，比对源码锚点 | 文件+行号+触发条件 | 能解释全部观测 |
| 修复 | 最小范围改动，不夹带重构 | diff | 公共 API 与返回结构不破坏 |
| 回归 | 先确认回归测试失败，再实施修复 | `go test` 结果 | 包数与全绿口径一致 |

回归阶段的可验证口径来自 `devlog.md` 的真实执行记录。本仓库 `go.mod` 声明 `go 1.26.2`，
本机工具链更高，不带语言级别参数直接构建会失败；同时默认 `TMPDIR` 不可写，需显式指定 `GOTMPDIR`：

```bash
# 预期输出：构建与静态检查均无输出、退出码 0
GOTMPDIR=/home/clfchen/.cache/go-work go build -gcflags="-lang=go1.26" ./...   # LANG126=0
GOTMPDIR=/home/clfchen/.cache/go-work go vet ./...                             # VET=0
```

```bash
# 预期输出：每包一行 ok，FAIL 包数 0；当前基线口径为 15/15 包全绿
GOTMPDIR=/home/clfchen/.cache/go-work go test ./... -count=1                   # TEST=0
```

`devlog.md` 中该口径随测试补全从 8 包、9 包、13 包、14 包推进到 **15/15 包全绿**（`devlog.md:2494`）。
回归验收以"包数不减、FAIL 包数为 0"为准，而不是只看退出码。

分诊类之间的依赖不是平行的：**数据与迁移是根因层**，它一旦异常，会伪装成登录、DNS、证书、监控四类
的独立故障。

```mermaid
flowchart TD
  KM["master_key 与库结构<br/>数据与迁移"] --> AUTH["登录与会话<br/>TOTP/OAuth/APIKey"]
  KM --> ACC["账户凭据"]
  ACC --> DNS["DNS 操作<br/>provider 装配"]
  DNS --> CERT["证书签发<br/>DNS-01 挑战"]
  DNS --> MON["监控故障切换"]
  CERT --> NOTIFY["通知<br/>续期失败告警"]
  MON --> NOTIFY
  RT["RequestTrace 与双层 Recovery<br/>崩溃与重启"] --> OBS["可观测性"]
  AUTH --> OBS
  DNS --> OBS
  CERT --> OBS
  OBS --> PERF["性能分诊的判据"]
  KM -.->|"静默返回密文<br/>不报错"| CERT
  KM -.->|"静默返回密文<br/>不报错"| DNS
```

中间件挂载顺序本身构成一条硬依赖，任何"改了顺序看看"的尝试都会破坏可观测性：
`CORS` → `RequestTrace` → 内层 `Recovery` → `CSRF` → `Auth` → `Permission`。
`RequestTrace` 必须在 CORS 之后（OPTIONS 不记日志）、在内层 Recovery 之前（否则 panic 穿透丢日志），
`Permission` 必须在 `Auth` 之后（依赖 `user_id` 与 `level` 上下文键）。

对外 API（`apiv1`）与控制台共用 handler 但**不共用权限链**：控制台走 `Permission()`，
`apiv1` 走 HMAC 签名 + `scope.go`。同一动作在两条路径上表现不一致时，先确认走的是哪条链。

## 性能考虑

排障中的性能结论必须区分"放大调用次数"与"延长单次延迟"两类，二者的证据来源不同。

| 类型 | 现象 | 度量入口 | 首选缓解 |
|:---|:---|:---|:---|
| 调用放大 | 配额瞬间打满 | 厂商控制台配额曲线 | 循环外构建索引、结果缓存 |
| 全量返回 | 整表渲染、分页失效 | 响应记录条数 | handler 层统一本地分页 |
| 连接不复用 | 首字节延迟高 | TLS 握手计数 | 按 `aid+type` 缓存实例 |
| 同步阻塞 | 单周期耗时叠加 | 发送点前后时间戳 | 异步扇出与渠道节流 |
| 无超时 | 慢连接堆积、fd 增长 | goroutine/fd 曲线 | 读写超时与 ctx 传播 |
| 写放大 | 磁盘 IO 持续高 | 加密调用次数 | 追加写而非整串重写 |

三点必须在排障中明确排除的"假指标"：

- `data_db_size`/`logs_db_size`/`request_db_size`：来自硬编码相对路径 `data/*.db`，改过数据目录后
  恒为 0，不能据此判断"库没长大"。
- `version`：硬编码 `"1.0.0"`，不能用于版本核对。
- 监控"运行状态"：判定阈值（10 秒/15 秒）与心跳周期（60 秒）矛盾，约 75-83% 时间显示未运行，
  不能据此判断调度器停了。

延迟类故障优先看 `request_logs.db` 的单请求耗时分布，而不是文件日志；命令与索引用法见
[性能诊断](file://docs/故障排除/性能诊断.md)。

## 结论

七类分诊并非并列关系，而是**分层关系**：数据与迁移（主密钥、库结构）位于最底层，它的失败模式是
"静默返回错误值"而非"报错"，因此会向上伪装成登录、DNS、证书、监控四类故障；可观测性层
（`RequestTrace` 与双层 `Recovery` 的顺序）决定"你能不能看到证据"，其重要性仅次于根因层。

三条硬结论：

- 排障前必须先确认三个"假指标"不可用：`version` 硬编码、库体积路径硬编码、监控运行状态阈值矛盾。
  否则会把观测缺陷误判为业务故障。
- 大量"看起来是权限 bug"的症状源于 `Permission()` 的两处设计（缺 `domain_id` 放行、回落 `c.Param("id")`），
  单点修复即可覆盖约 40 条路由的误拒面。
- 任何修复都必须走 `GOTMPDIR` + `-gcflags="-lang=go1.26"` 的构建与 `go test ./... -count=1` 回归，
  以"15/15 包全绿、FAIL 包数为 0"为验收口径；包数只减不增视为回归。

本域后续四篇子文档承担具体操作细节：症状到修法映射见[常见问题解决](file://docs/故障排除/常见问题解决.md)，
取证与日志结构见[日志分析](file://docs/故障排除/日志分析.md)，指标与压测口径见
[性能诊断](file://docs/故障排除/性能诊断.md)，凭据泄露与越权的处置见
[安全事件响应](file://docs/故障排除/安全事件响应.md)。
