## 简介

本篇解决的是**"慢在哪里、由什么驱动"**，即诊断方法；**"改哪个参数"**属于
[性能优化与调优](file://docs/部署运维/性能优化与调优.md)，两篇严格分工、互为交叉链接。

DNSPlane 的可观测面比一般服务窄，诊断前必须先接受三条实测事实：

- **没有 pprof 端点**：全仓检索 `net/http/pprof`、`pprof.` 零命中（实测于
  [router.go](file://main/internal/api/router.go) 与 `main/` 全目录），任何
  "访问 `/debug/pprof/`" 的写法在本项目不可用。CPU/内存剖析只有**离线 bench** 一条路。
- **没有 `/metrics`、`/health`**：进程内指标只有一个管理员接口
  `GET /api/dashboard/system/info`（[router.go:248](file://main/internal/api/router.go#L248)）。
- **每个请求自带一份微剖析**：`RequestTrace` 把 `duration`、`db_query_time`、
  `db_queries[]` 逐条落库，这就是本项目的事实上的 per-request profile。

因此本文的五维（CPU / 内存 / 磁盘 IO / 网络与云 API / GC 与慢查询）不是五套工具，
而是**同一批已有数据源的五种切法**。


## 架构总览

### 请求生命周期与采样点

一次 `/api` 请求在链上产生的可观测数据，就是五维诊断的全部原料。理解"谁在什么时候写下哪个数字"，
才能解释数字为什么会失真。

```mermaid
sequenceDiagram
  participant C as 客户端
  participant CT as RequestTrace
  participant H as handler
  participant P as 云 API Provider
  participant G as GORM 回调
  participant W as Logger 中间件
  participant RB as request_logs / Redis

  C->>CT : HTTP 请求
  CT->>CT : 生成 request_id，写 X-Request-ID
  CT->>CT : 读 body（上限 64 KB）并挂 db_queries 切片
  CT->>H : c.Next()
  H->>G : SELECT/INSERT（仅 DB 与 LogDB）
  G->>CT : append {sql, duration_ms, rows}
  H->>P : 串行外呼（单次最坏 30 s / SDK 120 s）
  P-->>H : 响应
  H-->>CT : 状态码与响应体（截取上限 256 KB）
  CT->>W : 链返回，W 判定 SLOW（阈值 3 s）
  W->>W : FileWarn 写 logs/日期.log
  CT->>CT : duration = time.Since(start)
  CT-->>C : 响应（4xx/5xx 前补 X-Error-ID）
  CT->>RB : 异步 goroutine 落库（Redis 或 SQLite 二选一）
```

## 详细组件分析

### CPU 维度：症状 → 采样 → 判据

**症状**：单请求 `duration` 偏高但 `db_queries` 总耗时极低；批量或整点窗口 CPU 打满；
GC 变密（表现为耗时呈周期性尖峰）。

**采样**：本项目没有常驻 pprof，唯一可用路径是在 `sanitize_bench_test.go` 上做离线剖析。
先取基准数（本机实测，go1.27.2 / linux-amd64 / i5-10200H）：

```bash
cd main && go test -run '^$' \
  -bench 'BenchmarkSanitizeBodyForLog|BenchmarkIsSensitiveKey' \
  -benchtime=2000x -benchmem ./internal/api/middleware/
```

预期输出（本机实采）：

```

BenchmarkIsSensitiveKey-8       	    2000	       826.6 ns/op	      64 B/op	       8 allocs/op
BenchmarkSanitizeBodyForLog-8   	    2000	    339090 ns/op	  16.84 MB/s	   61408 B/op	    1879 allocs/op
PASS
ok  	main/internal/api/middleware	0.691s
```

再取 CPU profile（`-o` 与 profile 都用绝对路径，避免把 26 MB 测试二进制和 `cpu.out`
落在包目录里——本机实测包目录未生成 `internal/api/middleware/cpu.out`）：

```bash
mkdir -p /tmp/dnsperf && cd main && go test -run '^$' \

  -cpuprofile /tmp/dnsperf/cpu.out -o /tmp/dnsperf/middleware.test \
  ./internal/api/middleware/
go tool pprof -top -nodecount=8 /tmp/dnsperf/cpu.out
```

预期输出（本机实采，节选）：

```

Duration: 9.27s, Total samples = 9940ms (107.21%)
Showing top 8 nodes out of 195
      flat  flat%   sum%        cum   cum%
     350ms  3.52%  3.52%      350ms  3.52%  internal/runtime/maps.memHashAES
     310ms  3.12%  6.64%      460ms  4.63%  internal/runtime/maps.(*Map).getWithoutKeySmallFastStr

     200ms  2.01% 15.19%      670ms  6.74%  strings.ToLower
```

**判据**：

| 观测 | 结论 | 下一步 |
|---|---|---|
| flat 首位是 `maps.*` / `mallocgc*` | CPU 花在哈希与分配，不在算法 | 走内存维与 GC 维 |
| `strings.ToLower` cum 占比高 | 脱敏与过滤做大小写归一的热路径 | 见调优文档的脱敏章节 |
| `ns/op` 高但 `allocs/op` 低 | 真 CPU 密集 | 剖析调用方，非分配问题 |
| `duration` 高、`db_queries` 空、CPU 不高 | 不在 CPU 维 | 走网络维 |

**边界**：离线 bench 只覆盖请求/响应脱敏链路，**不能**外推为线上整机 CPU 结论（推断）；
线上 CPU 归因仍需 `duration` + `db_queries` 的分段法。

### 内存维：症状 → 采样 → 判据

**症状**：RSS 单调上涨、容器被 OOMKilled、长驻后接口整体变慢。

**采样一：进程内唯一指标源**。`GetSystemInfo` 直接返回 `runtime.ReadMemStats` 的两个字段与
协程数（`dashboard.go:491-511`），路由为 `GET /api/dashboard/system/info`，**仅管理员**：

```bash
curl -s -H "Authorization: Bearer <token>" \
  http://127.0.0.1:8080/api/dashboard/system/info | jq '.data | {goroutines, memory_alloc, memory_sys, num_cpu}'
```

预期输出（形态，键名与 `dashboard.go:499-512` 一致；本机服务未运行故未实采）：

```json
{"goroutines": 24, "memory_alloc": 18874368, "memory_sys": 73400320, "num_cpu": 8}
```

注意：控制台会话下响应体可能被载荷加密，`jq` 只能看到信封。`sign.go:152-156` 的分支表明
**`auth_type=apikey` 时返回明文**，因此诊断脚本优先走 `/api/v1/system/*` 族（API Key 通道）。

**采样二：SQLite 页缓存的算术上界**。当前 DSN 与连接池为实测值：

| 参数 | 值 | 出处 |
|---|---|---|
| `cache_size` | `-16000`（每连接 16 MB） | `database.go:39-46` |
| `mmap_size` | `67108864`（每连接 64 MB 映射） | `database.go:45` |
| `MaxOpenConns` | `8`（三个库各一套） | `database.go:48-58` |
| 页缓存上界 | 8 × 16 MB = 128 MB/库，三库约 384 MB | 上述两行相乘（推断自参数值） |

`devlog.md:36` 记录了历史形态：连接池 64 配 `cache_size=-64000` 时最坏约 4 GB，属已修复口径，
见到旧部署包要按旧值核算。

**采样三：单请求缓冲上限**。`request_trace.go` 的常量决定每个在途请求最多占用多少内存：
`MaxBodySize = 64 KB`（读请求体）、`maxRequestLogBodyLen = 8192`、
`maxSuccessResponseCapture = 16384`（响应截取）、`MaxResponseSize = 256 KB`（落库响应上限）。
在途请求数 × 上述量级是内存突增的第一解释项。

```bash
cd main/data && du -sh data/* 2>/dev/null; vmstat 1 2
```

预期输出（本机实采，容器外开发机）：

```
428K	data/data.db
32K	data/data.db-shm
0	data/data.db-wal
180K	data/logs.db
32K	data/logs.db-shm
0	data/logs.db-wal
40K	data/request_logs.db
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st gu
 2  0 4175776 3150416 4682924 21526556 6 112  920  4858 19705  58 37  8 55  1  0  0
```

**判据**：`memory_alloc` 是存活堆，`memory_sys` 是运行时向系统拿的总量；两者同步抬升且不回落
→ 真实增长；`memory_alloc` 锯齿回落但 RSS 抬升 → 还给了 OS 的延迟或页缓存/mmap 贡献（推断）。

**通用手段（本项目未使用，标注为推断）**：`GODEBUG=madvdontneed=1` 用于让运行时更早归还页面。
全仓检索 `GODEBUG` 零命中（`main/` 目录实测），故它只能作为外部验证手段，不能当作现成能力描述。

**协程现场**：`main.go:146` 只注册了 `SIGINT`/`SIGTERM`，`SIGQUIT` 未被接管，因此 Go 运行时的默认
行为仍在——向进程发 `SIGQUIT` 会 dump 全部协程栈**并终止进程**。这是破坏性动作，
仅在愿意接受服务中断时使用，且优先用 `system/info` 的 `goroutines` 数值做趋势判断。

### 磁盘 IO 维：症状 → 采样 → 判据

**症状**：长尾与整点对齐（维护任务窗口）；`-wal` 文件膨胀；写入报忙或延迟；日志文件突然归零。

**采样**：三个库都跑在 WAL 模式，参数为实测：

```go
// database.go:39-46 —— PRAGMA 必须写进 DSN，才对连接池每条连接生效
path + "?_pragma=journal_mode(WAL)&_pragma=synchronous(NORMAL)&_pragma=busy_timeout(5000)" +
     "&_pragma=cache_size(-16000)&_pragma=temp_store(MEMORY)&_pragma=mmap_size(67108864)"
```

```bash
ls -la main/data
timeout 20 iostat -x 1 2 | tail -3
timeout 20 lsof +D main/data
```

预期输出（本机实采）：`ls` 显示 `-wal` 为 0 字节、`-shm` 各 32 K，且三个 `.db` 权限为 `0755`
（`logs/*.log` 为 `0644`）；`iostat` 末行为设备级 `%util`/`await` 序列；`lsof +D` 本次**无命中行**
（进程未运行），运行期预期每个库出现 `.db`、`-wal`、`-shm` 句柄（推断）。

**判据**：`%util` 逼近 100 且 `await` 同步抬升 → 设备饱和；`bo`（块写出）尖峰与
`VACUUM` 窗口对齐 → 维护任务驱动，而非业务流量。

**三个体积口径的坑**（务必在结论里排除）：

- `dashboard.go:495-497` 用**硬编码相对路径** `data/data.db`、`data/logs.db`、
  `data/request_logs.db` 取体积，只算 `.db`，**不含 `-wal`/`-shm`**；本机这两类伴生文件共 64 KB，
  相对总量约 9% 的低估。
- 同一段代码依赖进程 cwd。容器内 cwd 为 `/app` 时口径正确；
  从仓库根启动 `go run main/main.go` 时三个 size 会同时为 0（`getFileSize` 吞掉错误返回 0，
  `dashboard.go:515-521`），此时"体积为 0"不代表没有数据。
- `database.file_path` 可配置，但 `GetSystemInfo` 不读该配置，改目录后指标固定失真。

**维护任务对 IO 的形状**：`maintenance.go` 每小时执行清理，`VACUUM` 间隔默认 24 小时
（`:24`、`:37`），压缩序列为五步（`:283-311`）：
`wal_checkpoint(TRUNCATE)` → `ANALYZE` → `PRAGMA optimize` → `VACUUM` → `journal_mode=WAL` 恢复。
`VACUUM` 需要重写整库，是三库中唯一的独占型 IO 尖峰；`GetMaintenanceStats` 的行数取自
`sqlite_stat1`（`:406`），**未跑过 `ANALYZE` 时该数字陈旧**，不得当作实时行数用。

**交叉链接**：文本日志"当日 10 MB 超限即删除重建"的语义与后果由
[日志分析](file://docs/故障排除/日志分析.md) 承担；本篇只关心它带来的写放大与丢失窗口。

### 网络与云 API 维：症状 → 采样 → 判据

**症状**：`duration` 很高、`db_query_time` 接近 0、状态码 200、日志无 `ERROR`。

**串行外呼点（取证清单）**：本项目的云 API 调用绝大多数是**请求路径内串行**，
耗时随目标数量线性放大，这是最长尾问题的第一因。

| 位置 | 形态 | 串行次数 | 后果 |
|---|---|---|---|
| `domain.go:783-789` | 多子域列表合并，`for _, sub := range allowedSubs` 内 `GetDomainRecords(1,500)` | N 次（每子域 1 次） | 列表页耗时 ≈ N × 单呼 |
| `domain.go:716` | 同一请求前置 `GetRecordLine` | 1 次 | N+1 形态 |
| `domain.go:1709-1717` | 子域托管校验轮询，`for i:=0;i<4` + `Sleep(3s)` | 4 次外呼 + 最多 9 s 睡眠 | 单请求可稳定挂 12 s 以上 |
| `domain.go:1738-1743` | `for _, ns := range nameServers` 调 `ensureNSRecord` | 每个 NS 2 次（查询+新增） | NS 越多越慢 |
| `domain.go:381-383` | 30 s `context.WithTimeout` 包住 `GetDomainList` | 1 次 | 上限被显式钉死 |
| `logs.go:69-84` | 域名操作日志优先服务商，失败降级本地 | 1 次 + 降级查询 | 响应带 `source` 字段可判 |
| `batch.go:157`、`:180`、`:302-315`、`:415` | 批量增改删，逐条串行，`utils.SafeGo` 异步 | 每条 1–2 次，ctx 120 s | **请求日志 duration 不反映真实耗时** |

**超时口径不一致（实测计数）**：`http.Client{Timeout: 30 * time.Second}` 在
`main/internal/dns/providers/` 下命中 19 个文件；而 `timeout_test.go:15-25` 记录了三个 SDK 系
provider 的默认值：**aliyun 10 s、dnspod 60 s、huawei 120 s**，且"三者都不接收 ctx"，

### GC 与慢查询维：症状 → 采样 → 判据

**症状**：日志页统计接口长尾、带关键词的查询慢、周期性整体变慢。

**机制（先弄清样本从哪来）**：`database.go:373-426` 给 `DB` 与 `LogDB` 的六类操作
（Query/Create/Update/Delete/Row/Raw）各注册 before+after 回调，after 回调
`recordQueryCallback`（`:428-497`）做三件事：取 gin 上下文、算 `time.Since(start)`、
把 `{sql, duration_ms, rows, error}` 追加进 `db_queries`。四个约束直接决定样本可信度：

- **`RequestDB` 不注册回调**（`:373-377` 注释：避免写请求日志本身再被追踪）。
- **无请求上下文则不记录**（`:441-444`）：定时任务、monitor 协程、启动迁移都没有样本。
- **SQL 截断 2000 字符**（`:477-479`），长 `IN` 列表看不到尾部。
- **没有阈值**：本项目不存在"慢查询阈值"常量，`duration_ms` 是全量样本，
  判定完全依赖读取端排序（实测 `database.go` 与 `trace_gin.go` 无阈值分支）。

`trace_gin.go` 用 `runtime.Stack` 解析 goroutine id 建立 `goroutine → *gin.Context` 映射
（`:16-L38`），再由 `injectGinIntoDBStatement` 注入语句上下文——这是"哪条 SQL 属于哪个请求"
能被还原的原因，也解释了并发协程为何会丢样本（协程切换后 id 不同）。

**采样一：单请求 SQL 明细**。详情的 `db_queries` 是 JSON 文本，取回后排序：

```bash
curl -s -X POST http://127.0.0.1:8080/api/v1/system/request-logs/detail \
  -H "X-API-Key: <key>" -H 'Content-Type: application/json' \
  -d '{"request_id":"req_1759..._12"}' \
  | jq -r '.data.db_queries | fromjson | sort_by(-.duration_ms) | .[0:5][] | [.duration_ms,.rows,.sql[0:60]] | @tsv'
```

预期输出（形态，字段名取自 `database.DBQuery` 的 json 标签 `sql/duration_ms/rows/error`；
本机服务未运行，数值为示意）：

```
412	1840	SELECT * FROM "request_logs" WHERE (request_id LIKE '%www%'...
96	20	SELECT "id","request_id","error_id","user_id","username","...
12	1	SELECT count(*) FROM "logs" WHERE uid = 7
```

**采样二：确认是"全表扫"还是"排队"**。SQLite 侧没有服务端慢日志，只能从查询构造反推：

| 查询点 | 构造 | 成本形态 |
|---|---|---|
| `request_log.go:72-100` | `keyword` 对 5 列 `LIKE '%..%'` | 无法走索引，整表扫 |
| `request_log.go:104-145` | `Count` 与 `Find` 双 goroutine 并发 | 连接池 8 下互相排队 |
| `request_log.go:270-300` | `GetRequestStats` 单条聚合全表 `SUM(CASE)` | 每次缓存过期即全表扫 |
| `store.go:77-120` | Redis 侧带筛选时 `LRange(0, total-1)` | O(N) 拉取 + 内存过滤 |
| `store.go:186-243` | Redis 统计：500 条一批全扫 + 2 min 缓存 + 互斥合并 | 冷缓存时首个请求承担全扫 |
| `models.go:353-377` | 索引仅 `request_id`/`error_id`/`user_id`/`is_error`/`created_at` | `path`/`body`/`response` 无索引 |

**GC 侧**：没有 `runtime/metrics` 暴露、没有 pprof 端点，因此 GC 只能间接观测。
可用组合是：CPU profile 的 `alloc_objects`（本机实采）+ `bench` 的 `allocs/op`（实测 1879
allocs/op 对应约 16 KB body）+ `memory_alloc` 趋势。

### 中间件链对诊断的影响

诊断数据的产生顺序被链顺序钉死（`router.go:26-58`）：链首是
`SecurityHeaders → gin.Recovery → Logger`，`/api` 组内是
`CORS → RequestTrace → Recovery → CSRF → AuditLog`。

- `Logger` 在链首，位于 `RequestTrace` **之外**：它的 `latency` 与 RequestTrace 的 `duration`
  统计区间不同（前者不含 CORS 之前的排队），两者对不上不是 Bug。
- `RequestTrace` 之后的 panic 才会被内层 `Recovery` 标记 `has_error` 并保留堆栈；
  顺序一旦被改，`db_queries` 与请求日志同时归零（见
  [日志分析](file://docs/故障排除/日志分析.md) 的实证结论）。
- `auth_type=apikey` 由 `apiv1/auth.go:109` 写入，决定响应是否明文，从而影响
  `jq` 类诊断脚本能否直接解析。

## 性能考虑

本篇不给调参结论，只给**归因顺序**，具体动作见
[性能优化与调优](file://docs/部署运维/性能优化与调优.md)。

- **先分段再深挖**：`duration` − `db_query_time` 是外部等待与自代码时间之和，
  未做这一步就剖析 CPU，通常白干。
- **串行外呼是本项目的主瓶颈形状**：耗时随目标数线性放大，任何"偶发很慢"应先数外呼次数。
- **观测本身有成本**：`RequestTrace` 会为每个 `/api` 请求截取 body/response 并序列化
  `db_queries`；`sanitize_bench_test.go` 的实测显示一条 16 KB 响应要 1879 次分配。
  关掉追踪能降低开销，但同时失去唯一的 per-request 剖析源。
- **Redis 与 SQLite 的查询成本不对称**：Redis 侧带筛选查询是 O(N) 全量拉取，
  SQLite 侧是 `LIKE '%..%'` 全表扫；两者都不随数据量给出优雅退化。
- **维护窗口是可预测的 IO 尖峰源**：每小时清理、默认 24 小时 `VACUUM`，
  长尾若集中在同一时刻，先看维护配置而不是业务代码。
- **无 pprof 是硬约束**：所有 CPU/内存结论只能来自离线剖析或进程内瞬时指标，
  跨时间窗的趋势需要外部采集器自建（本仓未提供）。

## 结论

- **五维共享一套数据源**：`duration` / `db_query_time` / `db_queries` / `SLOW` 行 /
  `system/info` / 离线 bench profile。诊断能力的上限由这六项决定，不是由工具数量决定。
- **两条硬事实约束了方法**：无 pprof 端点（全仓检索零命中），无慢查询阈值常量（回调全量记录）。
  任何"打开 /debug/pprof"或"设置慢查询日志"的方案在本项目都不成立。
- **主要瓶颈形状已知**：请求路径内的串行云 API 扇出（`domain.go` 多处）与
  SDK provider 的超时不一致（10/60/120 s 且不接 ctx），足以解释绝大多数长尾。
- **观测自身有成本**：脱敏与截取的分配量已被 bench 量化（约 16 KB 响应 1879 allocs/op）。
- **口径陷阱要背下来**：三库体积不含 `-wal`/`-shm` 且依赖 cwd；`db_queries` 在后台任务里恒空；
  批量动作的真实耗时不在请求日志里；行数统计取自 `sqlite_stat1` 可能陈旧。
- 下一步：把本篇的分段判据固化成采集脚本，与
  [性能优化与调优](file://docs/部署运维/性能优化与调优.md) 的动作表逐条对齐。
