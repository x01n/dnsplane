## 概述

DNSPlane 是一个把「多服务商 DNS 管理 + 证书自动化 + 容灾监控 + 部署编排」收敛进**单一 Go 进程**
的控制台系统。它刻意不引入消息队列、独立缓存服务或微服务拆分：前端以 Next.js 静态导出产物
`go:embed all:web` 内嵌进二进制（`main/main.go:63-64`），持久化落到三个 SQLite 文件（可切 MySQL 主库），
横向扩展完全靠**注册表 + 工厂**的模式适配层——22 家 DNS 服务商、9 个证书签发渠道、
多个部署目标分组与 13 个通知渠道各自 `init()` 注册到全局表，装载函数无需随渠道增减而修改。

| 维度 | 内容 |
| --- | --- |
| 交付形态 | 单 Go 二进制，前端静态产物 `go:embed` 编入，容器镜像基于 distroless nonroot |
| 并发模型 | 一进程内 1 个 HTTP Server + 6 类后台协程组，共享 `cache.C` 与三个 `*gorm.DB` |
| 对外接口 | 控制台 `/api`（约 226 条）+ 对外 `/api/v1`（145 条，全 POST） |
| 规模重心 | `cert` 与 `api` 两线约占非测试代码 63% |

架构上有三个不可回避的张力，本文围绕它们展开：

- **一套 handler、两条链路**：控制台 `/api`（会话 Cookie + CSRF + JWT）与对外 `/api/v1`
  （API Key HMAC 签名 + 响应重编码）共享 `api/handler` 的 244 个 `gin.Context` 导出函数。
- **双层 panic 恢复**：`RequestTrace` 的落库代码在 `c.Next()` 之后，必须被一层 `middleware.Recovery`
  包裹，否则任何穿透到链首的 panic 都会让请求日志完全丢失（`api/router.go:34-43` 注释实测结论）。
- **进程内后台调度**：监控、证书续签、部署重试、日志清理、优选 IP、记录同步六类常驻协程
  与 HTTP 服务同生命周期，靠 `context.WithCancel` 与 `defer` 逆序优雅收尾。

进程边界的三个关键约束：

- **Redis 是可选项**。`cache.Init` 在 Redis 启用且地址非空时 `PING`（3 秒超时），失败即降级为
  进程内存缓存并告警，不阻断启动（`main/internal/cache/cache.go:69-76`，`main.go:83-92`）。
- **日志库不受 driver 配置影响**。即便主库选 MySQL，`LogDB`/`RequestDB` 仍硬编码 SQLite 驱动
  （`database.go:106,114`），容器化多副本下日志互不可见。
- **注册靠 blank import**。`main.go:27-58` 以匿名导入拉起证书渠道、22 家 DNS provider、
  部署器分组，各包 `init()` 把工厂写进全局表；删除任一 import 即注销该能力。

链路中两处「顺序即正确性」的设计不可调换：

- **内层 Recovery 必须紧跟 RequestTrace**。若只保留外层 `gin.Recovery`，`RequestTrace` 在

  生成一条无意义的请求日志（`api/router.go:46` 注释）。

### 中间件双链对照

控制台链与对外 `/api/v1` 链共用引擎级三段，但组级顺序不同，且 V1 有意**不继承 CSRF**。
下表按 `.Use` 实参顺序列出两条链。

| 序 | 控制台 `/api` 链（注册位置） | 对外 `/api/v1` 链（注册位置） | 说明 |
| --- | --- | --- | --- |
| 1 | `SecurityHeaders`（引擎级 `router.go:28`） | `SecurityHeaders`（引擎级） | CSP 含三家验证码域名、HTTPS 下 HSTS |
| 2 | `gin.Recovery`（引擎级 `router.go:29`） | `gin.Recovery`（引擎级） | 兜静态/页面/NoRoute 的 panic |
| 3 | `middleware.Logger`（引擎级 `router.go:30`） | `middleware.Logger`（引擎级） | 彩色 stdout + 分级落文件 |
| 4 | `CORS`（组级 `router.go:45`） | `RequestTrace`（`apiv1/router.go:27`） | V1 先 Trace 后 CORS 与其注释顺序一致 |
| 5 | `RequestTrace`（`router.go:47`） | `Recovery`（`apiv1/router.go:28`） | 内层恢复挡在 Trace 之内 |
| 6 | `Recovery` 内层（`router.go:48`） | `CORS`（`apiv1/router.go:29`） | OPTIONS 预检不被认证拦 |
| 7 | `CSRF`（`router.go:50`） | `APIKeyAuth`（`apiv1/router.go:30`） | V1 无 CSRF：签名即身份与完整性凭据 |
| 8 | `AuditLog`（`router.go:52`） | `JSONBodyToDecryptedData`（`apiv1/router.go:31`） | 读 body 后立即还原，否则下游 EOF |
| 9 | `Auth`（`router.go:96`） | `AuditLog`（`apiv1/router.go:32`） | 审计读 `user_id`，须在认证之后 |
| 10 | `Permission`（`router.go:104`） | `AdaptResponse`（`apiv1/router.go:34`） | 链末包裹后续所有写出，重编码为 V1 契约 |
| — | handler 内 `requireAdmin`/`CheckQuota` | 路由级 `requireModuleMW`/`adminOnly` | 细粒度校验下沉 |

V1 挂在引擎根而非 `/api` 组内（`api/router.go:63` 早于 `router.go:64`）：API Key 客户端没有
`_csrf` cookie，继承 CSRF 链会让所有写请求被拒，而签名本身即身份与完整性凭据
（`apiv1/router.go:9-23` 注释）。

### 认证流

登录成功后签发双 token：Access 15 分钟、Refresh 7 天，均为硬编码常量
（`middleware/auth.go:91-92`，与 `config` 的 `expire_hour` 无关）。会话载体是三枚 Cookie：
`_t`（Access，AES-GCM 加密，key = `sha256(JWT.Secret)`）、`_rt`（Refresh，path 限定 `/api/auth/refresh`）、

完全一致（`middleware/auth.go:125`），Refresh 走 JTI 轮转 + 重用检测（`:382`）。对外 V1 走另一条身份路线：
HMAC-SHA256 签名串 `uid + "\n" + timestamp + "\n" + METHOD + "\n" + PATH`，±5 分钟窗口，
`hmac.Equal` 常量时间比较（`apiv1/auth.go:44,93,96`）。

## 部署拓扑

### 交付形态与 Docker 多阶段

交付物是「前端静态导出产物 embed 进单一 Go 二进制」。Dockerfile 为三阶段，
最终镜像是 `distroless/static-debian12:nonroot`（uid 65532），只含一个二进制。

```mermaid

        N1["npm ci"] --> N2["next build --webpack<br/>output:export"]
        N2 --> N3["sync-main-web.cjs<br/>out -> main/web"]
    end
    subgraph Builder["stage builder : golang:1.26.2-bookworm"]
        G1["go mod download"] --> G2["COPY --from=web main/web"]
        G2 --> G3["go build CGO_ENABLED=0<br/>-trimpath -ldflags -s -w"]
    end
    subgraph Run["runtime : distroless nonroot"]
        R1["COPY /dnsplane -> /app"] --> R2["USER nonroot:nonroot"]
        R2 --> R3["EXPOSE 8080<br/>ENTRYPOINT /app/dnsplane"]
    end
    N3 --> G2
    G3 --> R1
```

| 阶段 | 基础镜像 | 关键命令 | 产物 |
| --- | --- | --- | --- |
| web | `node:22-bookworm-slim`（`Dockerfile:4`） | `npm ci` → `next build --webpack` → `sync-main-web.cjs` | `main/web`（embed 源） |
| builder | `golang:1.26.2-bookworm`（`Dockerfile:12`） | `go mod download` → `COPY --from=web` → `go build -trimpath`（`CGO_ENABLED=0`） | `/dnsplane` 静态二进制 |
| runtime | `distroless/static-debian12:nonroot`（`Dockerfile:32`） | `COPY /dnsplane /app` → `USER nonroot` → `EXPOSE 8080` | 仅含一个二进制的最终镜像 |

关键约束与风险：

- `go:embed all:web` 是硬前置：`main/web/` 不入库，干净仓库直接 `go build` 会因缺目录失败，
  必须先跑 `build:ci` 同步产物（`web/package.json`）。
- 交叉编译靠 `GOOS/GOARCH/GOARM`（`linux/arm/v7` 可产）；前端只在 `BUILDPLATFORM` 构建一次，
  避免多架构并行 `npm ci` 拖垮网络。
- 运行阶段 `/app` 由 root 拥有而进程以 nonroot 运行，`config.Load` 与 `database.Init` 默认写相对
  cwd 路径——**不挂载可写卷或不显式指定 `-config` 路径时，容器可能在配置写入阶段退出**（推断，
  未实机验证）。部署配方：挂可写卷到 `/app` 或用 `-config /data/config.json`。
- CI 四 job（`release-init`/`frontend`/`binaries`/`docker`）互不跑测试：`build.yml` 全程无
  `go test`/`npm test`/lint，而仓库有 78 个 `*_test.go`。质量门禁仅覆盖前端类型与镜像构建。

### 运行时拓扑

单容器可水平多副本，但需知晓两处「进程本地状态」：日志库硬编码 SQLite（多副本日志互不可见），

## 架构决策

下表汇总关键取舍：决策、被否决的备选、选择原因与付出的代价。

| 决策 | 备选 | 选择原因 | 代价 |
| --- | --- | --- | --- |
| 单二进制 embed 前端 | 前后端分离双服务 | 部署只需一个进程/镜像，无跨域与独立编排 | 前端改动必须整体重构建；`build` 脚本 Windows-only |
| SQLite 优先三库分离 | 统一 MySQL | 零外部依赖即可跑，日志/请求库与业务库隔离 IO | MySQL 主库下日志仍写本地 SQLite；`VACUUM` 等维护仅 SQLite 可用 |
| 无外键 + 无显式事务 + AutoMigrate | 版本化 SQL 迁移 | 无 DBA 也能升级，`SkipDefaultTransaction` 降开销 | 只加列不减列，遗留死列/冗余索引长期驻留；无法回滚 |
| 注册表 + 工厂适配多服务商 | if/else 分派 | 新增渠道不改装载函数（开闭原则） | blank import 与包 `init()` 的装载顺序耦合 |
| 一套 handler、两条链路 | 控制台与 V1 各写一套 | 消除 244 个接口的重复实现 | `apiv1 → handler` 侧向耦合；参数读取差异靠 bridge 回填 |
| 双层 panic 恢复 | 仅外层 gin.Recovery | 保住 RequestTrace 在 `c.Next()` 后的落库 | 链更复杂，顺序被改坏即失去报警能力 |
| 钩子注入解耦 handler↔service | service 直接 import handler | 打破签发↔通知循环依赖（`main.go:108,110`） | 依赖注入分散在 main，可读性下降 |
| Access 15m / Refresh 7d 硬编码 | 复用 `config.expire_hour` | 常量清晰、避免配置歧义 | `expire_hour` 成为无读取点的死配置 |
| distroless nonroot 运行 | 完整 base 镜像 | 攻击面与体积最小 | 无可写 cwd，需显式挂卷；无 shell 调试 |
| V1 不继承 CSRF | 复用 `/api` 组链 | 签名即身份与完整性凭据，无 cookie 无法 double-submit | V1 与控制台鉴权语义分叉，需各自维护 |
