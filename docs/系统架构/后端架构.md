## 简介

DNSPlane 后端是一个 **单进程、单二进制、单体（Monolith）Go 服务**：同一进程同时承担 HTTP API 网关、业务编排、外部云厂商协议适配、后台定时调度与前端静态资源服务五种角色。没有消息队列、没有独立网关进程，所有边界以 Go 包划分而非进程划分。

### 架构基调与规模重心

最重要的结构性事实是 **入口分裂、业务复用**：控制台链路 `/api`（会话 Cookie + CSRF + JWT）与对外链路 `/api/v1`（API Key HMAC 签名 + 响应格式改写）共享同一批 `func X(c *gin.Context)` 处理函数。V1 只通过参数桥接补齐路径参数读取差异，并把 5 个解析记录写接口重写为同步实现。收益是业务逻辑零重复，代价是对外契约受控制台实现牵制。

按工作区当前实测（`rg --files -g '*.go'` 后 `cat | wc -l`，含 `main.go`）：非测试 71937 行、含测试 88829 行，分布在 22 个 `internal` 一级子包。规模重心不在 HTTP 层而在协议适配层：`internal/cert`（22842 行非测试，其中 `cert/deploy/` 占 18998 行）与 `internal/api`（20705 行）合计约占 60.5%。

### 装配入口与内嵌静态资源

## 核心组件

### Router：两条链路一个引擎

`api.SetupRouter(staticFS embed.FS) *gin.Engine`（`router.go:18`）是唯一引擎构造入口，内部拆为三段以便测试复刻生产链路：`newBaseEngine`（`:24-32`，`gin.New()` + 关闭尾斜杠重定向 + 链首三件）、`applyAPIMiddleware`（`:44-53`，`/api` 组级五件）、`setupRouter`（`:55-464`，226 条控制台路由 + 静态服务 + `NoRoute`）。

关键装配事实：`apiv1.Setup(r)` 在 `router.go:63` 调用，**早于** `router.go:64` 的 `r.Group("/api")`。V1 因此挂在引擎根而非 `/api` 组内，不继承 CSRF 校验——API Key 客户端没有 cookie，也无从取得 token。

后端用 **注册表 + blank import + `init()` 自注册** 承载全部可扩展点，四套机制彼此独立：

## 详细组件分析

### 中间件链顺序与双层 Recovery 设计

控制台链的实际顺序必须按 `.Use` 书写顺序理解，不能按直觉排序：`SecurityHeaders` → `gin.Recovery` → `Logger`（以上引擎级，`router.go:28-30`）→ `CORS` → `RequestTrace` → `Recovery` → `CSRF` → `AuditLog`（以上 `/api` 组级，`router.go:45-52`）→ `Auth` → `Permission`（以上 `auth` 子组级，`router.go:96` 与 `:104`）→ handler；响应写出后回穿 `AuditLog`（落 `LogDB`）与 `RequestTrace`（落 `RequestDB` 或 Redis）。

双层 Recovery 不是冗余，而是 `router.go:34-43` 注释块记录的设计约束：

| 层次 | 位置 | 覆盖范围 | 存在理由 |
| --- | --- | --- | --- |
| 外层 `gin.Recovery()` | `router.go:29` | 静态资源、页面路由、`NoRoute` | 兜住不经 `RequestTrace` 的 panic |
| 内层 `middleware.Recovery()` | `router.go:48` | `/api` 组，**必须紧跟 `RequestTrace`** | `RequestTrace` 落库在 `c.Next()` 之后，panic 穿透到链首会让请求日志完全丢失 |

内层实现（`recovery.go:21-78`）区分两类异常：`net.OpError` + `os.SyscallError` 命中 broken pipe 或 connection reset 时只记 Warn 并 `c.Abort()`（`:26-35`、`:48-54`），避免客户端断开被当成服务端故障；真实 panic 记 8192 字节堆栈、调用 `SetError` 生成 `X-Error-ID` 并写 `ErrorStackKey`（`:56-67`），未写出响应时回 500。V1 链顺序不同（`apiv1/router.go:27-34`）：Trace、Recovery、CORS、`APIKeyAuth`、`JSONBodyToDecryptedData`、AuditLog、`AdaptResponse` 链末——`AdaptResponse` 必须最后注册，因为它包裹后续所有写出。

### Provider 注册机制的实现细节

四套注册表结构相近但各有取舍：

1. **证书注册表的「只补工厂」短路。** `cert.Register` 仅在 `factory != nil` 时覆盖工厂，在 `config.Type == "" && hadCfg` 时直接返回不覆盖表单（`registry.go:26-34`）。这让「`providers.go` 维护表单、子包 `init()` 只补实现」成为可能，代价是两处注册点必须同时存在。
2. **通知渠道重复注册即 panic。** `RegisterChannel` 对同一 `Type()` 二次注册直接 panic（`channel_registry.go:59-65`），把配置错误暴露在启动期；`Channels()` 按标识排序返回副本（`:76-85`），使装载顺序与注册顺序解耦；`ChannelConfigKeys()`（`:108-129`）由注册表推导而非手工维护。
3. **DNS 工厂没有 error 通道。** `ProviderFactory` 返回具体类型而非 `(Provider, error)`（`registry.go:9`），构造失败只能塞进实例的 `lastErr`，而 `registry.go:36` 仍返回 `err == nil`，后续方法调用即空指针 panic；唯一取错出口 `GetError()` 无生产调用方。
4. **部署器有两套名称空间。** `base.Register` 的键与 `cert` 表按 `IsDeploy` 切出的部署视图彼此独立，靠 `MergeDeployProviderConfigsForAPI` 合并、`deploy/registry.go:27` 做「原名 → `{type}_{product}`（任务）→ `{type}_{product}`（账户）→ `{type}_{cdn|acm|cloudfront}`」四级回落。

接口本身的规模差异也影响扩展成本：`dns.Provider` 是 15 方法单一大接口（`interface.go:41-86`），Go 编译期要求 22 家全部完整实现；`cert.Provider` 是 9 方法（`interface.go:52-79`）。扩展能力则靠类型断言（`RecordGrouper`、`DomainAliaser`、`SubdomainDelegator`）叠加，与 `ProviderFeatures` 布尔位是两套并行且不同步的口径来源。

### GORM 事务与 dbcache 读穿缓存

GORM 层没有一处显式 `Transaction`，这是配置声明而非遗漏：`SkipDefaultTransaction: true`（`database.go:76-79`）的注释给出三条前提——无显式事务、无多行批量插入、库内无外键约束。收益是单条写只产生一次 WAL fsync；代价是跨行操作的原子性完全由业务顺序保证，中途崩溃会留下部分写入，`resetStuckOrders()`（`:152`）把 `CertOrder.status = 1` 重置为 0 正是对此的补偿。

### 外部云 API 串行化与并发上限

记录全量对账刻意不并发：`record_sync.go（服务）:122-127` 的注释写明「逐个域名处理而非并发拉取：DNS 服务商普遍按账户限流，并发会把配额瞬间打满，反而拖慢整体进度」，单域名失败只记日志并继续。抽象层与通知层则 **完全没有节流**：`internal/dns` 与 `internal/notify` 检索 `rate`/`limiter`/`throttle`/`backoff` 除签名函数外零命中；`NotifyManager.SendAll`（`notify.go:688-696`）串行遍历渠道并共享单一 deadline，靠后渠道可能被饿死，`Send` 只回传第一个错误（`:698-704`）。

### JWT 校验失败

`Auth` 中间件（`auth.go（中间件）:125-202`）要求 **`_t` cookie 解密结果与 `Authorization: Bearer` 完全一致**。排查顺序：缺 cookie 或空值直接 401「未登录」；解密失败 401「会话已过期」（根因见下一小节）；双值不一致常见于前端只带 Bearer 未带 cookie；剩余有效期不足 5 分钟回写 `X-Token-Expiring: true`，前端据此触发 `POST /api/auth/refresh`；刷新失败先查 `rtjti:<uid>` 条目——`validateAndRevokeRefreshJTI`（`:353`）在「缓存就绪但条目缺失」时一律拒绝，这是 JTI 轮转与重用检测的预期行为；算法混淆面已由 `ParseToken`（`:423`）强制断言 `*jwt.SigningMethodHMAC` 收口。令牌实际有效期是硬编码常量 `AccessTokenExpire = 15m`、`RefreshTokenExpire = 7d`（`:91-92`），与 `config.json` 的 `jwt.expire_hour` **无关**，后者无任何读取点。

### Cookie 解密失败与字段解密静默降级

`_t` cookie 不是 JWT，而是 `hex(nonce + ciphertext)` 的 AES-256-GCM 密文，密钥为 `sha256(JWT.Secret)`（`deriveKey` `:35`）。因此更换 `jwt.secret` 会立即让所有既有会话失效，表现为「全员掉线」。`config.Load` 在检测到历史默认 secret 或空值时会自动生成随机串并回写文件（`config.go:130-143`），若部署把 `config.json` 当模板反复覆盖就会出现偶发全量掉线；多副本必须固定 `jwt.secret` 或用 `DNSPLANE_JWT_SECRET` 注入。cookie 的 `Secure` 标志取决于 `isSecureRequest`（`:324`），它信任 `X-Forwarded-Proto`，反代未透传该头会使 HTTPS 下行为异常。CORS 侧 `isAllowedOrigin`（`:542`）按 `site_url` → 同 Host → localhost 三级判定；`_csrf` 刻意不设 `HttpOnly`（`csrf.go:62-66`），校验用 `subtle.ConstantTimeCompare`。

与 cookie 解密不同，模型层字段加密 **失败不报错**：`crypto.MustDecrypt`（`crypto.go:95-101`）解密失败时原样返回密文，`hooks.go` 的 `AfterFind`（`:23-51`）因此把 `enc:v1:...` 当明文交给上层。若服务商配置看起来是一串 `enc:v1:` 前缀文本，根因几乎必然是 `security.master_key` 变更或与库不匹配，而非厂商侧异常；密钥为空时 `deriveKey` 直接 panic（`crypto.go:26-36`），属启动期显式失败。

### GORM AutoMigrate 冲突与遗留列

`AutoMigrate` 只新增表/列/索引，**不删除、不重命名、不缩窄类型**（`database.go:241-297`），因此存量库会长期带有：模型未声明的旧列（重命名或删除字段后残留）；同列双索引（字段改名后旧索引名仍在）；无对应模型的孤儿表；因未进入 `migrate()` 列表而始终不创建的新表；以及 MySQL 下 `SysConfig.Key` 声明 `size:32` 顶到上限导致的写入报错（SQLite 不校验长度，MySQL 会）。

## 结论

后端是 **边界清晰但体量不均衡的单体**：以 Gin 引擎为唯一入口、以包为模块边界、以注册表承载全部可扩展点（22 家 DNS、19 个证书渠道、88 个部署目标、13 个通知渠道），用 71937 行非测试代码换来单二进制交付与零外部编排依赖。

按四条尺子衡量：**做得好的部分**是中间件顺序用注释与测试锁死而非依赖直觉、`newBaseEngine` 让测试能复刻生产链路、四套注册表统一遵循「启动期写 / 运行期读 / 读写锁 / 返回副本」、`service` 与 `handler` 之间用钩子注入实现依赖倒置、SQLite 池参数与 PRAGMA 有明确理由。**违背单一职责**的是 `middleware` 同时负责鉴权、审计落库与配置读取，以及 2509 行的 `cloudflare.go` 与 1748 行的 `domain.go` 把四件事写进一个文件。**违背开闭原则**的是 V-01 的具体服务商类型 import 使「新增服务商不改现有代码」的承诺失效。**违背 DRY** 的是 V-07 的五份装配实现与 V-05 的死代码分叉。**YAGNI 层面的冗余**包括无读取点的配置项、12 个无路由指向的导出 handler、4 个无人调用的 `service` 导出函数。

下一轮优先级最高的三项改进是：把 provider 装配收敛为单一工厂（消除 V-07）、在 V1 链补入口限流并修正 `apiv1/router.go:33` 的注释与实现矛盾、把 `apiv1/util.go` 的测试辅助迁出非测试文件（消除 V-04）。三者都不改动公共 API，可用现有测试与 `go build ./...` 验证。
