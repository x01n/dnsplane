## 简介

DNSPlane 的部署模型可以压缩成一句话：**前端静态导出产物被 `go:embed` 编进一个 Go 二进制，该二进制再被塞进 distroless 非 root 镜像，最终同时以"容器镜像"与"多平台裸二进制"两条通道交付。**

三个设计动机：

- **零依赖落地**：运行阶段基础镜像为 `gcr.io/distroless/static-debian12:nonroot`（[Dockerfile:32](file://Dockerfile#L32)），除二进制与 CA 证书外没有任何发行版内容，目标机器无需安装 Node、Go 或额外系统库。
- **单进程交付**：`//go:embed all:web` 与 `staticFS`（[main.go:63-64](file://main/main.go#L63-L64)）让控制台页面与 API 由同一进程、同一端口提供（默认 `0.0.0.0:8080`，[config.go:89-90](file://main/internal/config/config.go#L89-L90)），不存在静态服务器与跨域配置。
- **交叉编译友好**：`CGO_ENABLED=0`（[Dockerfile:24](file://Dockerfile#L24)、[build.yml:140](file://.github/workflows/build.yml#L140)）使一次宿主机构建即可产出 12 个 GOOS/GOARCH 组合。

关于"双流水线"必须澄清口径：**当前仓库只有 GitHub Actions 一条在用流水线**。CNB 的 `.cnb.yml` 已在提交 `66f4799` 中整体删除（`git show --stat` 实测 `.cnb.yml -360` 行、`build.yml +208` 行），`git cat-file -e HEAD:.cnb.yml` 报"路径不在 HEAD 中"，其演进序列（`6f89682` 新增、`119c9cd`/`f668f88`/`42f3a23`/`20f3865`/`156e21c`/`be8bab4`/`b374fcf` 迭代）全部失效。CNB 唯一残留是 `scripts/docker-build.sh:13` 的默认镜像仓库名与 `:47` 的 OCI source label，见第 5.7 节。

### 忽略规则与构建上下文卫生

`.dockerignore` 只有 6 条：`.git`(1)、`.github`(2)、`web/node_modules`(3)、`web/.next`(4)、`web/out`(5)、`**/*.md`(6)。它挡住了体积最大的垃圾，却没挡住最敏感的东西：`.gitignore` 挡住了 `main/config.json`(28)、`main/data/`(31)、`main/logs/`(30)、`main/web/`(33)、`main/main`(34) 与 `.cnb-token.local`(36)，但 `COPY main/ ./`（[Dockerfile:21](file://Dockerfile#L21)）读的是文件系统而不是 git 索引，两个边界彼此独立。

| 未被排除的路径 | 性质 | 进入构建上下文的后果 |
| --- | --- | --- |
| `main/config.json` | 本地配置，含 `jwt.secret` 与 `security.master_key` 实值（本文一律记为 `{JWT_SECRET_占位}` / `{MASTER_KEY_占位}`） | 进入 builder 层与 buildkit/Actions 缓存层；最终镜像只 `COPY /dnsplane`（[Dockerfile:34](file://Dockerfile#L34)），密钥不入产物但入缓存 |
| `main/main` | 上一轮编译的陈旧二进制 | 无谓放大上下文与层体积 |
| `main/data/`、`main/logs/` | 运行期 SQLite 与应用日志 | 真实业务数据与访问 IP 进入缓存层 |
| `main/web/` | 上一轮嵌入产物（454 文件 / 6.7 MB） | 与 [Dockerfile:22](file://Dockerfile#L22) 的覆盖写入冗余；`web` 阶段失败时可能静默残留旧前端 |

建议（属运维口径，非现状）：`.dockerignore` 追加 `main/config.json`、`main/data/`、`main/logs/`、`main/main`、`main/dist/`，把"密钥与运行数据永不进构建层"变成机制而非约定。

两个易被误读的细节：

- `web` 阶段产物在容器里的绝对路径是 `/build/main/web`，而非 `/build/web/main/web`。`sync-main-web.cjs:5` 用 `path.join(__dirname, "..", "..", "main", "web")` 上跳两级，容器内 `__dirname` 为 `/build/web/scripts`，最终落到 `/build/main/web`，与 [Dockerfile:22](file://Dockerfile#L22) 的取值路径对齐。
- `main/web` 被写入两次：`COPY main/ ./`(21) 带进宿主机残留产物，随后 `COPY --from=web ... ./web`(22) 覆盖。**生效的是第 22 行**，第 21 行那份只是缓存污染。

## 架构总览

从源码到可运行制品的完整数据流，六个节点分别对应"源码 → 前端构建 → 静态文件同步 → Go 交叉编译 → 镜像分层 → 推送"：

```mermaid
flowchart LR
  SRC["源码<br/>web/ 与 main/"] --> FE["前端构建<br/>npm ci + next build --webpack"]
  FE --> SYNC["静态文件同步<br/>web/out → main/web<br/>454 文件 / 6.7 MB"]
  SYNC --> EMBED["go:embed all:web<br/>编译期嵌入"]
  EMBED --> GO["Go 交叉编译<br/>CGO_ENABLED=0 -trimpath<br/>-ldflags=-s -w"]
  GO --> IMG["镜像分层<br/>distroless nonroot<br/>单层二进制"]
  GO --> BIN["12 平台裸二进制<br/>dnsplane-os-arch"]
  IMG --> GHCR["推送 GHCR<br/>amd64 / arm64 / arm-v7"]
  BIN --> REL["上传 GitHub Release<br/>仅 tag 触发"]
```

## 详细组件分析

### 阶段一 web：前端构建单元

`web` 阶段是整条流水线里唯一被"平台"刻意绕开的阶段。[Dockerfile:2](file://Dockerfile#L2) 的注释写明动机：**前端只在 `BUILDPLATFORM` 上构建一次，避免多架构并行 `npm ci` 拖垮网络导致超时**。因此三架构镜像共享同一份前端产物，只有 Go 编译与运行阶段跟随 `TARGETPLATFORM`。

依赖层与源码层在第 6 行与第 9 行之间切开：先拷 `package.json` 与 `package-lock.json`，再 `npm ci`，最后才 `COPY web/ ./`。清单不变则改业务代码不触发重装依赖。第 7 行把 npm 的 HTTP 重试次数设为 5、最小重试间隔 20 秒、最大重试超时 120 秒，是对"到 registry 链路抖动"的直接补偿。

构建命令来自 [package.json:8](file://web/package.json#L8) 的 `build:ci`：`next build --webpack && node scripts/sync-main-web.cjs`。两点值得注意：显式 `--webpack`（不使用 `dev` 脚本里的 Turbopack）；同文件的 `build` 脚本（第 7 行）是 **Windows-only**，命令含 `set "ANALYZE=true"` 与 `powershell -NoProfile -Command ...`，而 [README.md:58](file://README.md#L58) 与 [README.md:151](file://README.md#L151) 恰恰引导 `bun run build` 并声称产物在 `../main/web/out`——实际产物落在 `main/web`（无 `out` 子目录）。

静态导出能力由 [next.config.ts:4-8](file://web/next.config.ts#L4-L8) 决定：`output: 'export'`、`trailingSlash: true`、`images.unoptimized: true`。`trailingSlash` 与后端 `NoRoute` 的逐级回退（[router.go:411-456](file://main/internal/api/router.go#L411-L456)）是配套设计，否则嵌入 FS 里的 `xxx/index.html` 无法被路径拼中。

### 阶段二 builder：Go 交叉编译单元

第 19-20 行是模块模式的核心：先只拷 `main/go.mod` 与 `main/go.sum`，再 `go mod download`，[Dockerfile:18](file://Dockerfile#L18) 的注释解释意图为"依赖不变即可复用 download 层"。仓库内**不存在 `main/vendor` 目录**（实测），故构建必然需要访问模块代理，[build.yml:3-4](file://.github/workflows/build.yml#L3-L4) 的注释同样写明这一点。

交叉编译参数逐行看：

- 第 23 行 `set -eux`：任何一步失败立刻中断，并把命令回显到日志，便于 CI 排障。
- 第 24 行导出 `CGO_ENABLED=0`、`GOOS=${TARGETOS}`、`GOARCH=${TARGETARCH}`。本阶段跑在 `BUILDPLATFORM`，`TARGET*` 可与宿主架构不同，这正是"一台 runner 出三架构"的前提。
- 第 25-27 行处理 ARM 变体：仅当 `TARGETARCH=arm` 且 `TARGETVARIANT` 非空时，用 `${TARGETVARIANT#v}` 去前缀赋给 `GOARM`，于是 Buildx 的 `linux/arm/v7` 翻译成 `GOARM=7`，与矩阵里的 `goarm: "7"`（[build.yml:82](file://.github/workflows/build.yml#L82)）口径一致。

```bash
docker run -d --name dnsplane \
  -p 127.0.0.1:8080:8080 -v $HOME/dnsplane-data:/data -w /data \
  -e DNSPLANE_JWT_SECRET='{JWT_SECRET_占位}' \
  -e DNSPLANE_MASTER_KEY='{MASTER_KEY_占位}' \
```

### 构建性能：缓存边界与重复工作

### distroless 缺工具与非 root 权限

`distroless/static` 是刻意"什么都没有"的镜像：没有 shell、没有包管理器。由此产生三类必然故障：

- `docker exec -it <c> sh` 直接失败。调试只能靠 `docker logs`，或用同基础镜像另起一个带 shell 的调试容器挂载同一卷。
- **证书"本地服务器"渠道在容器内必然失败**：[local.go:122-124](file://main/internal/cert/deploy/servers/local.go#L122-L124) 按平台拼 `exec.CommandContext(ctx, "cmd", "/c", line)` 或 `("sh", "-c", line)`，而 `nonroot` 镜像两者皆无，命令以"文件不存在"结束。应改用 SSH 渠道，或把私钥目录以可写卷暴露给外部进程处理。
- 网络能力受限：`nonroot` 无 `CAP_NET_RAW`，原始套接字失败后代码内建降级——`icmp.ListenPacket("ip4:icmp", ...)`（[check.go:68](file://main/internal/monitor/check.go#L68)）失败即调用 `checkTCPFallback` 拨 `host:80`（[check.go:151-160](file://main/internal/monitor/check.go#L151-L160)），错误串为 `icmp unavailable, tcp80 failed`，看到它不代表源站故障。

权限与写盘是最常见的"起不来"：

## 结论

部署面的取舍非常清晰：**用 `go:embed` 把前端折叠进二进制，用 `CGO_ENABLED=0` 把平台差异折叠进交叉编译，用 distroless 把运行时折叠进一个文件**。叠加之后交付物只剩 GHCR 多架构镜像与 Release 上的 12 个裸二进制，部署方无需理解 Node、Go 或反向代理的组装关系；GitHub Actions 是唯一在用流水线，历史 CNB 流水线已在 `66f4799` 整体删除，仅剩 `docker-build.sh` 的默认仓库名与 OCI label 需要订正。

已验证的优点：层缓存边界切得准确（清单与源码分两次 `COPY`）、交叉编译避免在 QEMU 里跑 `npm ci`、矩阵 `fail-fast: false`、Release 创建幂等、跨 job 用 Actions 缓存规避 artifact 配额、Redis 不可达时降级不阻断启动。

需要正视的短板（均有正文证据）：流水线无测试与 lint 门禁；`-X main.Version` 空操作导致版本三处分裂；distroless `nonroot` 与写盘需求硬冲突，官方镜像开箱不可用；无 `HEALTHCHECK` 与健康端点，叠加"监听失败不退出"使编排层难以区分"活着"与"能服务"；`.dockerignore` 过薄使密钥与运行数据进入缓存层；一次运行构建前端两遍且无 `concurrency`/`timeout-minutes`。

优先级建议：补齐 `.dockerignore` → 运行阶段预留可写目录或 `--chown=nonroot` → 增加 `HEALTHCHECK` 与真正的健康端点 → `main` 包补 `Version` 符号并让 CI 传 `build-args` → `docker` job 复用 `main/web` 并加 `concurrency` 组 → CI 增加 `go test ./...` 与静态检查。前四项均为纯部署面收敛，不改业务逻辑。
