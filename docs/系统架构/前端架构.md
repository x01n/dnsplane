## 简介

`web/` 是 DNSPlane 的唯一前端应用：Next.js 16.2.4（App Router）+ React 19.2.4 + Tailwind CSS 4 + Radix UI，UI 约定为 shadcn `new-york` 风格。它不是常规的前后端分离站点，而是**纯静态导出的单二进制内嵌控制台**：`output: 'export'`（`web/next.config.ts:4`）让产物成为一份纯 HTML/JS/CSS 目录树，由 `web/scripts/sync-main-web.cjs:4-13` 同步进 `main/web`，再由 `main/main.go:63-64` 的 `//go:embed all:web` 编译进 Go 可执行文件，运行时同一个 Gin 进程既发页面又发 `/api` 网关。

这决定了本文全部技术判断的基线：**前端没有服务端运行时**。没有 Server Action、没有 ISR、没有 middleware 重写、没有流式 SSR，鉴权、权限过滤、数据获取都在浏览器完成。

### 三条关键设计取舍

- **静态导出换单二进制分发**：代价是动态段必须由客户端自行解析，收益是零依赖运行与 `distroless` 终态镜像（`Dockerfile:32-37`）。
- **客户端鉴权换同域简化**：凭据由 `SetAuthCookies` 写入 HttpOnly Cookie（`main/internal/api/middleware/auth.go:296-311`），前端只持有 access token，`Auth` 中间件再做双值比对（`auth.go:143-150`）；代价是权限可见性必须在前端复刻（`app/(dashboard)/layout.tsx:232-250`）。
- **无表单库换可控性**：`web/package.json:12-53` 未引入 zod / yup / react-hook-form，校验为手写条件加 `toast.error`，配合 `lib/email.ts:2-6`、`lib/site-key.ts:7-9` 这类最小校验器。

## 架构总览

浏览器与后端同 Origin，页面由 Go 的 `NoRoute` 回落到内嵌 `index.html`，随后数据面完全由客户端 React 接管。

### 请求主链与网关侧顺序

前端发出 `/api/*` 后，服务端在 `main/internal/api/router.go:44-53` 依次挂载 `CORS → RequestTrace → Recovery → CSRF → AuditLog`，`Auth` 与 `Permission` 再叠加到受保护子组（`router.go:95-104`），链首另有 `SecurityHeaders + gin.Recovery + Logger`（`router.go:24-32`）。静态资源不经这条链，缓存由 `tryServeFile`（`router.go:384-405`）单独决定：HTML 与 txt 为 `no-cache`，其余 `public, max-age=31536000`，并以内容 SHA-256 作 `ETag` 处理 `If-None-Match` → 304（`:396-402`）。

### 请求瀑布与并发合并

静态壳无法在服务端预取数据，首屏必然出现「壳加载 → 取用户 → 取业务数据」的串行瀑布。项目用三种手段压缩：

- **并发合并**：`csrfInFlight`（`api.ts:29,44`）与 `refreshInFlight`（`:27,128-130`）把首屏并发触发的 CSRF 引导与令牌刷新各合并为一次往返，避免 JTI 轮转被多次刷新互相踩掉。
- **页面内并发**：概览页并发拉统计与系统信息并设 30 秒自动刷新（`app/(dashboard)/dashboard/page.tsx:31-50`），证书页与部署页的 `loadData` 为四路并发。
- **本地持久化减少往返**：`usePageSize`（`lib/hooks.ts:12-26`）以 `page_size_<key>` 记忆每页条数并在无 window 时回落默认值，`PageTabs` 以 `dnsplane_page_tabs`（`components/page-tabs.tsx:13`）恢复页签、上限 `MAX_TABS = 15`（`:14`）。

尚未利用的一项：服务端在 access token 剩余不足 5 分钟时回写 `X-Token-Expiring`（`main/internal/api/middleware/auth.go:190-196`）并显式 `Expose`（`:525`），但本次检索未在 `web/` 找到任何读取该响应头的代码，即前端目前只在 401 之后被动刷新（`api.ts:216-237`），过期窗口内第一个请求必然多一次往返。这属可优化点而非缺陷。

### Hydration 不匹配

本项目对 hydration 的处理是「一处豁免加一处避免」。豁免点唯一：`app/layout.tsx:21` 的 `suppressHydrationWarning`，因为 `next-themes` 会在客户端给 `<html>` 写 class，服务端产物没有该属性值；该属性只容忍元素属性差异，不掩盖子节点结构差异。避免点为 `components/theme-toggle.tsx:27` 用 `useSyncExternalStore` 而非 effect 内 `setState` 做挂载判定，且 `app/(dashboard)/layout.tsx:143`、`lib/hooks.ts:15`、`components/page-tabs.tsx:44` 均以 `typeof window === 'undefined'` 守卫本地存储访问。

若新组件出现 `Hydration failed`，先自查是否在 render 阶段直接读 `window`、`localStorage` 或 `Date.now()`，不要通过扩大 `suppressHydrationWarning` 范围来掩盖——它只应存在于根 `<html>`。

### Cookie 域、SameSite 与代理协议

`SetAuthCookies`（`main/internal/api/middleware/auth.go:296-311`）写两个 Cookie：`_t`（path `/`，Max-Age 为 access 有效期 15 分钟，见 `:91`）与 `_rt`（path `/api/auth/refresh`，7 天，见 `:92`），均为 HttpOnly 加 `SameSite=Strict`。三个易踩点：

- 未指定 `Domain`，因此是 host-only Cookie。用 `localhost:8080` 登录后再以 `127.0.0.1:8080` 打开即视为另一站点，表现为登录后立刻回到登录页。
- `Secure` 随协议：`isSecureRequest`（`:320-329`）先查 `c.Request.TLS`，再回落 `X-Forwarded-Proto: https`。代理若未转发该头，HTTPS 站点会得到非 Secure Cookie 并被浏览器在后续 HTTPS 请求中拒发。
- `SameSite=Strict` 意味着站外链接首次进入可能不带 Cookie。项目把这类场景改造为前端中转页：`app/(auth)/magic-login/page.tsx:36-41` 读 `token` 后 `window.location.assign('/api/quicklogin?token=')`，由同域跳转完成会话建立。

### CORS 与预检

同域内嵌部署下 CORS 不生效，但中间件仍执行。`CORS()`（`auth.go:516-534`）的行为是：`Origin` 命中 `isAllowedOrigin` 才回显 `Access-Control-Allow-Origin` 并附 `Allow-Credentials: true`（`:519-522`），`Allow-Headers` 固定含 `Authorization`、`X-CSRF-Token`、`X-Refresh-Token`、`X-Secret-Token`（`:524`），`OPTIONS` 一律 204 中止（`:527-530`）。

`isAllowedOrigin`（`:542-571`）三级判定需按顺序理解：`localhost` 与 `127.0.0.1` 直接放行；否则若配置了 `site_url`，只允许与其 scheme 加 host 完全相等的 Origin；两者皆无时退化为「Origin 主机与本请求 Host 一致」。因此跨域前端接入**必须**把 `site_url` 配成前端实际访问的地址并逐字一致。另需注意 `Allow-Methods` 未列 `PUT` 与 `DELETE`（`:523`），而前端 `api.ts:286-292` 会发这两种方法：同域无碍，改为需预检的跨域调用则可能被拒。

### `_t` 与 Authorization 不一致

这是本项目特有且最易误判的一类故障。服务端 `Auth` 要求 `_t` 解密出的 access token 与 `Authorization: Bearer` **逐字相等**（`auth.go:143-150`），任一缺失或不等均返回 401 且 `msg` 为 `Token不一致`。前端令牌有两个来源：构造时读 localStorage（`api.ts:31-35`）与请求前 `syncTokenFromStorage`（`:107-114`），二者只保证「内存与本地存储对齐」，不保证「与 Cookie 对齐」。触发路径三条：

1. **多标签页**：A 页刷新成功换发新 `_t`，B 页仍持旧 localStorage 令牌，B 的下一个请求即不一致。前端仅有同页的 `refreshInFlight` 合并，无跨页同步机制。
2. **OAuth 回调**：`exchange` 后走 `refreshSession({ persist: false })`，令牌只存内存不落盘（`api.ts:99-105,169-172`），此时刷新页面会丢掉内存令牌，需重新登录。
3. **手动清 localStorage 而未退出**：`_t` 仍在但请求无 `Authorization`，命中 `headerToken == ""` 分支。

排查顺序：先在 DevTools 复制请求的 `Authorization`，再按 401 的 `msg` 精确区分 `未登录`、`会话已过期`、`Token不一致`、`Token无效或已过期`、`无效的Token类型`、`用户不存在`、`账户已被禁用` 七种（`auth.go:127-181`）。恢复手段统一为清本地令牌后重登（`app/(dashboard)/layout.tsx:163,178`、`api.ts:232`），因为服务端 `Logout` 只清 Cookie（`auth.go:313-318`），不会反向清理浏览器存储。

## 结论

- **形态**：`web/` 是 33 页、110 个源文件、约 3 万行的 Next.js 16 纯静态控制台。页面主体是客户端组件，服务端组件只剩根布局与五个转发薄壳，数据面完全经 `lib/api.ts:24-293` 的单例走同域 `/api/*`。
- **模块边界**：`app` 负责路由与守卫，`components/ui` 是无业务依赖的可替换层，`components` 根级与 `auth/` 分别是业务复用层与视觉层，`lib` 是传输与契约层，`contexts` 仅一个 24 行下发件。除 `oauth-callback-view` 引视觉层样式外未见跨层反向依赖与环。
- **静态导出的三条约束**都有明确对应物：占位 `generateStaticParams` 加客户端解析、薄壳加 `client.tsx`、`useSearchParams` 的 `Suspense` 边界；回落链在服务端 `router.go:411-461` 与前端目录之间构成隐式契约，改一侧必须同步另一侧。
- **质量口径已收紧**：`strict` 且移除 `ignoreBuildErrors`、`refresh_token` 不落 localStorage、URL 不再承载凭据。
- **需处理的最小集合**（按优先级）：补声明 `@radix-ui/react-visually-hidden`；删除 708 行死代码并合并两个验证码弹窗实现；把 `QUOTA_DIMENSIONS` 与 `CERT_STATUS_MAP` 收敛到 `lib` 单一来源；为 `monitor/page.tsx:153` 与 `cert/page.tsx:119` 的顶层 `useSearchParams` 补 `Suspense`；拆分 6 个超千行页面；把 `web/README.md` 从 `create-next-app` 模板改写为真实的 `build:ci` 口径。
- **本次未验证**：未执行 `npm run build:ci`、`npm run lint` 与 `tsc --noEmit`，因此「零告警」「类型全通过」为**未知**，现有 `web/out` 与 `main/web` 属历史产物，不构成本次结论。
