## 简介

本文覆盖 dnsplane 的横向安全能力——与具体 DNS 业务无关、跨所有请求生效的防护机制。回答三个问题：某类攻击由哪个文件拦、拦不住的原因在哪、密钥从哪来且存在哪里。

| 攻击面 | 主防线 | 实现位置 | 生效范围 | 已知未覆盖 |
|:---|:---|:---|:---|:---|
| CSRF | double-submit cookie + SameSite=Strict | `middleware/csrf.go:70` | `/api` 组写请求 | `/api/v1` 整组、18 条白名单 |
| XSS | CSP + 安全响应头 + React 默认转义 | `middleware/auth.go:483` | 全部响应 | CSP 含 `unsafe-inline`/`unsafe-eval` |
| SQL 注入 | GORM `?` 占位符 + 排序白名单 | `handler/domain.go:89`、`handler/optimizeip.go:177` | 全部查询 | 用户输入不可达表名/列名 |
| SSRF | 协议白名单 + 私网拦截（探测另有 dial 二次校验） | `monitor/ssrf.go:31`、`notify/safe_url.go:15` | 探测 CheckType 2/3、出站通知 | Ping/TCP 探测无拦截；通知链无 dial 回调 |
| 邮件头注入 | 控制字符拒绝 | `notify/safe_url.go:79` | 三套邮件后端 12 处 | — |
| 暴力破解 | 子网 + 用户名双维锁定 + 时序抖动 | `handler/auth.go:87`、`:107`、`:128`、`:41` | `POST /api/login` | 用户名喷洒可绕过 |
| 凭据入日志 | 39 键 + 正则的 body/header 掩码 | `middleware/sanitize.go:17`、`:71` | 请求日志 body 与 header | `Query` 字段完全未脱敏 |

两个必须先纠正的认知偏差：

- `middleware/sanitize.go` 容易被读成「HTML 净化器」，但它的全部职责是**请求日志脱敏**——把命中敏感关键字的值替换为固定掩码 `***REDACTED***`（`sanitize.go:13`）。代码库中不存在 HTML sanitizer，XSS 防御完全依赖响应头与 React 默认转义。
- 设计层面的「请求体加密 + 报文签名 + 响应混淆」链路在当前工作区**没有任何生产调用点**（`sign.go:17` 未挂载、`web/lib/crypto.ts` 零引用），因此不计入防护层，本文单列小节给出证据。

## 详细组件分析

### CSRF：双链差异与白名单

double-submit cookie 的核心是「无服务端状态」：token 不存储，仅比对 cookie 与 header 是否同值。

| 要素 | 实现 | 位置 |
|:---|:---|:---|
| cookie / header 名 | `_csrf` / `X-CSRF-Token` | `csrf.go:23-24` |
| token 强度 | 32 字节 `crypto/rand` → 64 位 hex | `csrf.go:55-59` |
| cookie 属性 | 非 HttpOnly、`SameSite=Strict`、`Path=/`、TTL 7 天、`Secure` 随协议 | `csrf.go:62-67` |
| 安全方法处理 | GET/HEAD/OPTIONS 不校验；缺 cookie 时补发 | `csrf.go:84-90` |
| 比对方式 | `subtle.ConstantTimeCompare` | `csrf.go:109` |
| 跳过集合 | 前缀 2 项 + 精确 16 项 = 18 | `csrf.go:30-33`、`:36-53` |
| 发放端点 | `GET /api/csrf` → `{code:0,data:{token}}` | `router.go:68` → `csrf.go:119` |
| 前端取 token | 优先读 cookie，缺失则 bootstrap 并合并并发 | `web/lib/api.ts:41-64`、`:196-200` |

非 HttpOnly 是模式要求而非缺陷：前端必须能读出 cookie 值并回显到 header。代价是 XSS 一旦发生即可直接读取 token，因此该模式的安全性完全依赖「XSS 不可能发生」这一前提。

```mermaid
sequenceDiagram
    participant FE as ApiClient
    participant MW as CSRF 中间件
    participant H as 业务 handler
    FE->>MW: GET /api/csrf，回 Set-Cookie _csrf 与 body token
    FE->>MW: POST /api/domains 携带 X-CSRF-Token
    MW->>MW: 路径是否命中 18 条白名单
    alt 命中白名单
        MW->>H: 直接放行
    else 需要校验
        MW->>MW: ConstantTimeCompare(cookie, header)
        alt 不匹配或缺失
            MW->>FE: 403 token 缺失 或 不匹配
        else 匹配
            MW->>H: c.Next()
        end
    end
```

| 维度 | 控制台链 `/api` | 对外链 `/api/v1` |

| 挂载位置 | `api := r.Group("/api")` + `applyAPIMiddleware` | `v1 := engine.Group("/api/v1")`（引擎根） |
| CSRF | 校验（白名单除外） | 完全不经 CSRF |
| 身份凭据 | JWT（cookie `_t` + `Authorization`） | `X-API-UID`/`X-API-Timestamp`/`X-API-Sign` |

值得记录的薄弱点：V1 签名不覆盖请求体与查询串，也没有 nonce 去重（对照：已死掉的控制台签名链是覆盖的，`utils/sign.go:196`）。同一条签名在 5 分钟窗口内可被原样重放，也可在保持签名有效的前提下替换请求体参数。

### XSS：响应头与前端渲染约束

代码库不含 HTML sanitizer，XSS 防御由响应头与前端约束两层构成。

| 层 | 具体值 | 位置 | 缺口 |
|:---|:---|:---|:---|
| CSP `script-src` / `style-src` | 均含 `'unsafe-inline'`，前者另含 `'unsafe-eval'` + 三家验证码域名 | `middleware/auth.go:492-493` | `unsafe-*` 使白名单机制基本失效 |
| CSP `frame-src` | `'self'` + 三家验证码域名 | `middleware/auth.go:497` | 缺该指令会回落 `default-src 'self'` 拦死 SDK（注释 `:496`） |
| 点击劫持 / MIME 嗅探 | `X-Frame-Options: SAMEORIGIN`、`frame-ancestors 'self'`、`X-Content-Type-Options: nosniff` | `middleware/auth.go:485-486`、`:501` | — |
| HSTS | `max-age=31536000`，仅 HTTPS 时写 | `middleware/auth.go:503-505` | 不含 `includeSubDomains`（避免误伤兄弟域） |
| 前端渲染 | React JSX 默认转义 | 本次 `web/` 全量检索 `dangerouslySetInnerHTML` 零命中 | — |
| 第三方 siteKey | `^[A-Za-z0-9_-]+$`，长度 1-128 | `web/lib/site-key.ts:7-9` | — |
| 重定向目标 | 仅允许 `/` 开头且非 `//` 起始的站内相对路径 | `web/app/(auth)/magic-login/totp/page.tsx:95` | — |

CSP 里 `unsafe-eval` 的存在说明该策略不是按最小权限设计的，而是「加一层但不影响现有前端」的产物。因此不能把 CSP 当作可信边界来评估 CSRF token 与 localStorage 中 access token 的安全性。

### SSRF：两条出站链路的覆盖差异

系统有两类由用户配置驱动的出站请求：容灾探测与通知外发。两者各有一份拦截实现，能力不对等。探测链（`monitor/ssrf.go`）的构成：

| 校验 | 位置 | 规则 |
|:---|:---|:---|
| `validateCheckURL` | `ssrf.go:31-59` | 协议仅 `http`/`https`（`:16-19`）；host 非空；拒 `localhost`/`.localhost`/`.internal`/`.local`（`:49-52`）；IP 字面量走私网判定（`:53-57`） |

推理链条很短：`aes_key` 只由 `DecryptAndVerify` 在 `sign.go:45` 写入 context；该中间件无调用点，故 `GetAESKey` 恒返回 `nil`（`:94-101`）；于是 `EncryptedResponse` 在 `:161-164` 必然走 `c.JSON(http.StatusOK, data)` 明文分支，响应混淆同样不可达。它还引出一个命名陷阱：`web/lib/api.ts:298-303` 的 `encryptedPost` 只是 `api.post` 的别名，但找回密码与重置 TOTP 页面仍用它提交请求，容易误判该链路存在加密。

### 日志脱敏与其覆盖边界

`sanitize.go` 是凭据在日志侧的最后一道掩码，但作用域有明确边界。

| 输入位置 | 是否脱敏 | 依据 |
|:---|:---|:---|
| 请求 body（JSON / 表单） | 是 | `request_trace.go:228` → `SanitizeBodyForLog` `sanitize.go:101`；表单分支 `:120-129` |

## 性能考虑

防护开销按「每请求常数」与「随载荷线性」两类分看。

| 环节 | 复杂度 | 热路径位置 | 说明 |
|:---|:---|:---|:---|
| CSRF 比对 | O(64) 字符 | `csrf.go:109` | 常量时间是刻意的耗时不裁剪，代价可忽略 |
| CSRF / 审计白名单 | O(1) map + 定长切片 | `csrf.go:93-102`、`audit.go:128-146` | 精确匹配走 map 并先于前后缀扫描 |
| header 脱敏 | O(header 数) | `sanitize.go:155-169` | 纯 map 查找 |
| body 脱敏 | O(JSON 节点数) + 一次解析一次序列化 | `sanitize.go:101-132` | 全链最贵的一步 |
| `isSensitiveKey` | O(1) 查表 + 1 次正则 | `sanitize.go:92-97` | 归一化表避免 O(表大小) 重算 |
| cookie AES-GCM | O(len(token)) | `middleware/auth.go:45-64` | 每请求一次解密 |
| JWT / V1 HMAC 验签 | 各一次 HMAC | `middleware/auth.go:423-445`、`apiv1/auth.go:94-96` | 微秒级；V1 少一次 cookie 解密与一次 JWT 解析 |
| bcrypt 比对 | 2^12 轮 | `handler/auth.go:333` | 单次数百毫秒量级，**仅口令复核路径触发** |

**bcrypt 不属于签名校验开销。** 依赖 `users.password` 的路径只有 `Login`、`ChangePassword`（`handler/auth.go:487`）、`DisableTOTP`（`:688`）这类口令复核入口；`middleware.Auth` 只做一次 HMAC 与一次 AES-GCM 解密，并命中 30 秒用户缓存（`authUserCacheTTL`，`middleware/auth.go:99`），因此常规请求的密码学成本恒定极低。真正需要担心的是登录洪峰——锁定阈值（5 次/15 分钟）本身就是对 bcrypt 成本的容量保护。

**请求日志脱敏会随响应体积放大。** `SanitizeBodyForLog` 对 JSON 走「解析 + 递归 + 再序列化」（`sanitize.go:109-117`），CPU 与分配双密集。项目为此留了基准入口：`sanitize_bench_test.go:12`（`BenchmarkIsSensitiveKey`，覆盖每 key 成本）与 `:26`（`BenchmarkSanitizeBodyForLog`，样本为 50 条记录的标准列表响应）。复现命令：

```bash
cd main && go test ./internal/api/middleware/ -run '^$' -bench 'Sanitize' -benchmem
```

需提醒的是这两个基准**未覆盖** Query 路径，因为该路径根本没有脱敏逻辑（`request_trace.go:278`）。

## 结论

**已达成**：CSRF 用无服务端状态的 double-submit cookie，token 为 32 字节随机值、常量时间比对并配 SameSite=Strict（`csrf.go:55-67`、`:109`），且控制台与对外 API 的链差异有代码级解释与两处同步注释；SQL 注入面上不存在用户可控的 SQL 片段（`domain.go:89-94`、`optimizeip.go:177-190`、`migrate.go:14-22`）；密码学选型符合当前基线——JWT 强制 HMAC 系算法拒 `alg=none`（`middleware/auth.go:429`）、会话 cookie 与字段级各用独立密钥、TOTP secret 密文入库（`hooks.go:56`）、口令统一走 `bcryptCost`（`handler/auth.go:36`）；限流与失败计数统一到 `cache.Incr` 单一原子原语并对失败分支加抖动（`handler/auth.go:128-131`、`:41-47`）；探测链的出站防护做到「URL 校验 + dial 阶段二次拦截」双层结构，私网段覆盖含 CGNAT 与 IMDS（`ssrf.go:31`、`:99`）；请求加密与报文签名链路已被证实未挂载，不计入防护层。

**未达成（按优先级）**：

1. 行为验证码存在类型混淆绕过（`captcha.go:265-284` 采信请求体类型）与「一次性删除导致无重试」。
2. `Query` 字段未脱敏（`request_trace.go:278`），一次性登录令牌与 OAuth 授权码明文入请求日志库。
3. V1 签名不覆盖请求体与查询串、无 nonce（`apiv1/auth.go:93`、`:69`），存在窗口内重放与参数替换。
4. SSRF 覆盖不完整：Ping/TCP 型探测不经 `validateCheckURL`；通知链无 dial 回调。
5. CSP 含 `unsafe-inline`/`unsafe-eval`（`middleware/auth.go:492-493`），不能当作 XSS 可信边界。
6. CORS 对 `localhost`/`127.0.0.1` 无条件放行且允许携带凭据（`middleware/auth.go:546-549`），无环境判断。
7. 内存与 Redis 的 `Incr` 窗口语义不一致（滑动 vs 固定），同一阈值表现不同。
8. `isPrivateOrReservedIP` 两处重复、`middleware/apikey.go` 与 `apiv1/auth.go` 重复且语义分叉。

上述第 1、2、3 项已在分析素材中登记为待修复项，本文只做定位与成因说明，不改动代码。
