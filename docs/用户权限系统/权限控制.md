## 简介

dnsplane 的授权体系由「一个中间件 + 六类权限点 + 一层兜底」构成：控制台 `auth` 路由组（201 条路由）在 `Auth` 认证之后统一挂载 `middleware.Permission()`（注册位置 `main/internal/api/router.go:104`，函数定义 `main/internal/api/middleware/permission.go:132`），由它完成域名、子域、只读三个维度的判定；其余更细的权限点（管理员、功能模块、资源属主、配额、特性开关）分布在 handler 函数主体内逐条生效。

按路由所指向 handler 的函数主体扫描（口径见 `.wiki-context/scan-backend.md` §5 与 §8.4），201 条已登录路由的权限点分布如下：

- `admin`（`requireAdmin` / `isAdmin`）：64 条
- `module`（`requireUserModule` / `UserModuleAllowed`）：47 条
- `domain`（`CheckDomainPermission` 等）：16 条
- `certOwner`（`requireCert*Owner`）：13 条
- `quota`（`CheckQuota`）：8 条
- `subdomain`（`CheckSubDomainPermission` / `checkBatchRecordSubDomain`）：3 条
- `feature`（`CheckFeature`）：3 条
- **无任何细粒度标签**：90 条，仅依赖 `Auth` + `Permission`（多标签路由按每个标签各计一次）

本文聚焦「权限如何被判定」这条主线：`Permission` 中间件的判定树、七类权限点各自的数据源与判定函数、`CheckDomainPermission` 与 `CheckSubDomainPermission` 的差异，以及「缺 `domain_id` 直接放行」与「`:id` 路径参数回落污染」两个已知风险点。认证与会话管理（JWT、Cookie、刷新链）不在本文范围，参见同目录《安全防护》与《认证系统》。

证据口径说明：本文全部 `文件:行号` 均在当前工作区实读校验（2026-10-11 快照）；路由权限点计数沿用扫描产物实测结果；工作区为非干净基线，行号以当前文件为准。

## 核心组件

### Role（角色层级 Level）

角色不是独立表，而是 `users.level` 整型列（`main/internal/models/models.go:10-19`，注释口径「0: 自助注册, 1: 第三方登录自动创建, >=2: 管理员」）。授予点：安装时写入 level=2，自助注册写 level=0，第三方登录自动建号写 level=1（行号沿用分析产物 `.wiki-context/analysis-auth.md` §3.1，本次未逐行复核，标记为「素材已验证」口径）。

`level >= 2` 是整条权限链路的**总短路**，出现在三处：

- `Permission` 中间件入口：`permission.go:138`，管理员直接 `c.Next()`，不做任何域名判定
- `CheckDomainPermission` / `CheckSubDomainPermission`：`permission.go:336-338`、`:345-347`，管理员恒为 `true`
- `UserModuleAllowed`：`permission.go:384-386`，管理员恒可访问任意模块

handler 级判定函数集中在 `account.go`：`checkAdmin`:24（兼容 `int`/`float64` 两种上下文取值形态）、`requireAdmin`:43（失败时写「权限不足，仅管理员可操作」响应并返回 false，安全审计 C-1 的兜底）、`isAdmin`:52（无副作用的谓词版本，供 `cert_authz.go` 与查询收窄使用）。

### Permission（委派权限表）

委派权限是唯一独立的权限实体表 `permissions`（模型 `main/internal/models/models.go:105-114`）：

| 列 | 模型字段 | 语义 |
| --- | --- | --- |
| `uid` | `Permission.UserID`:107 | 被授权用户 |
| `did` | `Permission.DomainID`:108 | 域名 ID（索引列） |
| `domain` | `Permission.Domain`:109 | 域名快照，判定按名称匹配 |
| `sub` | `Permission.SubDomain`:110 | 子域限制，空表示所有 |
| `read_only` | `Permission.ReadOnly`:111 | 只读授权标志 |
| `expire_time` | `Permission.ExpireTime`:112 | 过期时间，`*time.Time` |

读取入口 `activeDelegatedPermissionsByUID`（`permission.go:19`）按 `uid + domain` 查询并剔除 `expire_time` 已过期的行；同一用户对同一域名可能有多行（不同子域段），由 `mergePermissionRows`（`:52`）把子域列表并集、`read_only` 取「全部只读才是只读」的语义合并；`pickDelegatedPermission`（`:93`）再按请求携带的 `rr` 挑选精确匹配行或返回合并行。

### Owner（账户归属）

「域主」判定不需要 `permissions` 表：`domains.aid → accounts.id → accounts.uid`，若账户的 `uid` 等于当前用户即为属主（`Permission` 内联判定 `permission.go:159-164`；`getDomainPermission` 同构逻辑 `:310-314`）。属主获得完全开放：`perm_read_only=false`、`perm_sub_domain="*"`（`permission.go:168-170`）。

证书资产的属主判定是独立一族（`cert_authz.go`），因为资产链不同：`CertOrder.aid → CertAccount.uid` 两级传递（`requireCertOrderOwner`:46-65），而 `CertDeploy` 自带 `uid` 列且其 `aid` 指向**部署账户**而非证书账户，刻意不复用订单链（`:96` 函数头注释明确说明该区别）。

### Subdomain（子域粒度）

子域授权复用 `permissions.sub` 列，判定函数 `subGrantCoversRR`（`permission.go:34`）：授权值为空或 `*` 时全覆盖，否则按逗号分隔列表对 `rr` 精确匹配。运行期两处消费：`Permission` 的写请求二次校验（`:190-198`）与 `CheckSubDomainPermission`（`:344`）；批量族另有逐条判定（见详细分析）。

### Module（功能模块权限）

模块权限存储在 `users.permissions` 文本列（`models.go:19`，JSON 字符串数组），无独立权限点表。注入与判定分离：

- `ApplyUserPermissionModules`（`permission.go:367-380`）：空串或 JSON 解析失败 → `perm_modules_configured=false`；解析成功（含空数组 `[]`）→ 写入 `perm_modules` 数组
- `UserModuleAllowed`（`permission.go:383-399`）：`level>=2` 直通；**未配置直通**（兼容旧库，即老用户全放行）；已配置时仅允许列表内 key

模块 key 全集由前端导航声明：`domain`、`monitor`、`cert`、`deploy`（`web/app/(dashboard)/layout.tsx` 的 `navigation` 常量，素材记录为 `:55-93` 区间）。消费点：handler 内 `requireUserModule(c, "...")`（`account.go:67`）与 V1 路由级 `requireModule`（`apiv1/scope.go:28`）；V1 的 `APIKeyAuth` 同样调用 `ApplyUserPermissionModules`（`apiv1/auth.go:111`），保证两侧判定同源。

### Quota 与 Feature（配额/特性）

配额不是「能不能访问」而是「还能建几个」：`quotaForUser`（`quota.go:84`）按「个体覆盖（`user_quotas`）→ 套餐（`user_subscriptions`+`plans`）→ 系统默认（`sys_configs`）」三层取值，`level>=2` 直接无限。上限语义见 `models/quota.go:12-16` 注释：`-1` 不限、`0` 禁止、`>0` 上限。创建前校验 `CheckQuota`（`quota.go:120-140`）覆盖 8 个资源维度；`CheckFeature`（`quota.go:294`）做套餐特性开关，未订阅或键缺失一律放行。

### 判定树设计要点

- **短路优先**：`level>=2`（`:138`）与「无 domain_id」（`:144`）两条放行路径排在最前，保证管理员与非域名接口零额外查询
- **属主优先于委派**：先查账户归属（`:162`）命中即完全开放，不再读 `permissions` 表，普通高频路径只花两次查库
- **拒绝统一为 200 + `code:-1`**：`Permission` 的四种拒绝（`:153`、`:177`、`:184`、`:194`）都走 HTTP 200 的业务错误码而非 4xx，前端按 `code` 字段分派提示，避免与 401 会话失效混淆

## 详细组件分析

### 权限点分布：201 条路由的逐类拆解

计数口径（记录于 `.wiki-context/scan-backend.md` §5 引言）：权限点列取自路由所指向 handler 的**函数主体**扫描，跨函数委托的校验不计入；多标签路由按每个标签各计一次。因此「90 条无标签」的含义是「handler 主体内未检出下列任何函数」，**不等于无授权**——它们仍受 `Auth` + `Permission` 约束，只要请求带得出 domain_id。

### Permission 中间件主体

`Permission()`（`permission.go:132`）返回闭包，逐行对应架构总览的判定树。两个辅助提取器决定「哪些请求会进入判定」：

- `getDomainIDFromRequest`（`:210-234`）三级回落：① `decrypted_data` 上下文里的 `domain_id` / `did`（`:212-221`）→ ② `?domain_id=` 查询参数（`:224-226`）→ ③ `c.Param("id")` 路径参数（`:229-231`）。由于签名链中间件 `DecryptAndVerify` 实际从未挂载（`middleware/sign.go:17`，全仓零调用点），第①级对控制台请求不生效，域名 ID 实际靠②③两级取得
- `getSubDomainFromRequest`（`:237`）：同构逻辑，读 `name` / `rr` 字段

写请求识别 `isDomainScopedWriteRequest`（`:265`）把 POST 视为写，但对 `/whois` 后缀例外（`:272` 附近逻辑）——WHOIS 查询挂在 POST 下但本质是读，不应被只读授权拦截。

`pickDelegatedPermission`（`:93-129`）处理「同域名多条委派行」的选行：单行直接返回；多行时按请求携带的 `rr` 匹配包含它的行，纯列表请求（只有 domain_id）则返回 `mergePermissionRows` 的合并行供下游过滤。

### CheckDomainPermission 与 CheckSubDomainPermission 的差异

两者都走 `getDomainPermission`（`:304-322`，域名存在性 → 账户归属 → 委派合并三段），差异只在子域维度：

| 对比项 | `CheckDomainPermission`:335 | `CheckSubDomainPermission`:344 |
| --- | --- | --- |
| 签名 | `(userID, userLevel, domainID)` | `(userID, userLevel, domainID, subDomain)` |
| 管理员 | `userLevel>=2` 恒 true（:336-338） | 同（:345-347） |
| 判定粒度 | 仅域级 allowed | 域级 + 子域覆盖 |
| 属主 | 计入 allowed | `isOwner` 单独短路（:352-354），不受子域限制 |
| subDomain 为空串 | 不适用 | 视为不针对具体子域，放行（:356-358） |
| 只读维度 | 不判 | 不判（两者都只答「能不能碰」，只读拦截靠 `DomainPermissionOf`:330 取明细或 `Permission` 中间件本体） |

V1 侧判只读用 `DomainPermissionOf`（`:330-332`，即 `getDomainPermission` 的导出包装），因为 `Check*` 系列把 `perm`/`isOwner` 细节折叠成了布尔值，调用方拿不到 `read_only` 与 `sub`。

### certOwner：证书资产属主族

`cert_authz.go` 头注释（`:13-28`）记录了设立动机：安全审计 R-1 发现 cert 整套接口此前完全无鉴权，任意已登录普通用户可列出全站订单并用 `GET /api/cert/orders/:id/download?type=key` 拖走他人证书私钥、用 `POST /process` 强行触发别人的 ACME 续签烧上游配额。修复即本文件：

- `requireCertAccountOwner`（`:32-43`）：`cert_accounts.uid` 直比，非属主且非 `isAdmin` 拒绝
- `requireCertOrderOwner`（`:46-65`）：订单本身无 uid 列，经 `order.AccountID → CertAccount.UserID` 两级传递判定；关联账户已失效时单独报「订单关联的证书账户已失效」（`:57`）
- `requireCertDeployOwner`（`:96-107`）：`cert_deploys.uid` 直属判定；`:86-95` 注释解释了为何不能复用订单链——部署任务的 `aid` 指向部署账户，且 config 含外送目标地址，越权修改等于把他人私钥改送到自己机器
- 三个 `scope*Query`（`:68`/:76/:110）：列表查询的读侧收窄，管理员看全量，普通用户强制 `uid` 过滤；订单用子查询 `aid IN (SELECT id FROM cert_accounts WHERE uid=?)`（`:80-83`）

该族的设计取向是「失败即写响应」：`require*` 返回 `(资源, bool)`，false 时响应已落，handler 直接 return，避免每个调用点重复写错误分支（`:30-31` 注释明确该约定）。

### batch_authz：批量操作逐条子域判定

`checkBatchRecordSubDomain`（`batch_authz.go:87`）解决一个 `Permission` 中间件覆盖不到的问题：批量请求一次携带多条记录，各自的 `rr` 不同，中间件的单值 `getSubDomainFromRequest` 无法逐条把关。流程（`:87-110` 起）：

1. 先经 `middleware.DomainPermissionOf` 判域级 allowed，未通过写「无权限操作该域名」返回（`:98-101`）
2. `isOwner || level >= 2` 短路放行，省掉一次云端查询（`:102-104`）
3. 请求已给出 `rr` 的（新建类）本地直接判，刻意放在建 provider 之前——越权请求不消耗上游配额（`:106-110` 注释）
4. 仅有云端记录 ID 的（编辑/动作类）经 `cloudRecordRRIndex`（`:48`）或 `fetchCloudRecordRR`（`:77`）回查真实 `rr` 再判

三个调用点：`batch.go:95`（批量新增）、`:259`（批量编辑）、`:363`（批量动作），对应「subdomain 3」权限点。

### auth_control：权限体系的准入开关

`auth_control.go` 本身不是判定器，而是「谁能用什么方式进门」的管理面，全部经 `requireAdmin` 限定。安全边界是**可写键白名单**：固定键由 `authControlFixedKeys`（`:37-53`）枚举（`auth_password_login`、`auth_password_register`、`auth_magic_link_login`、`auth_email_verify`、`auth_email_whitelist*` 等），动态键 `auth_oauth_<provider>_login` 与 `auth_oauth_<provider>_register` 按前后缀放行（`isWritableAuthControlKey`:62-77，provider 取自 `oauth.GetEnabledProviders()`，避免固定清单在新增 provider 时漏放）。`UpdateAuthControl`（`:124`）写入后立即 `InvalidateSysConfigCache`（`:154`），使 60 秒配置缓存即时失效，权限开关变更不需要等待 TTL。

## 性能考虑

### 判定路径的每请求查库成本

非管理员 + 带 domain_id 的请求每笔至少两次查库：按 ID 取 `domains`（`permission.go:151-152`）、按 `aid` 取 `accounts`（`:159-162`）；非属主再追加 `permissions` 表查询（`:175` → `activeDelegatedPermissionsByUID:19`）。`permissions.did` 与 `uid` 均有索引（`models.go:107-108`），`uid + domain` 组合过滤走 uid 索引。管理员路径（`:138`）与无 domain_id 路径（`:144`）零额外查询，热点列表接口因此实际只受 `Auth` 层 30 秒用户缓存（`middleware/auth.go:99` `authUserCacheTTL = 30 * time.Second`，缓存键 `auth_user:<uid>`）影响。

一点可改进但未构成缺陷的冗余：属主判定时域名和账户各查一次，可在 SQL 层合并为一次 JOIN；当前逐条两次查库在 SQLite 单文件场景下成本仍在毫秒级，属「知晓即可」的量级。

### 缺 domain_id 直接放行的风险面

`permission.go:144-148`：取不到域名 ID 时中间件直接 `c.Next()`，把授权完全下压给 handler。这是性能与正确性的有意取舍（绝大多数接口与域名无关，不能全部拦下），但它决定了安全边界的位置：

- 受影响范围即「90 条无细粒度标签」路由中不带 domain_id 的部分。典型路径：`/api/domains/sync`、`/api/logs`、`/api/request-logs/*`、通知渠道测试 11 条（计数与路径清单口径来自 `.wiki-context/scan-backend.md` §8.4/:696-698）
- 其中用户管理与系统配置类靠 handler 内 `requireAdmin`（`account.go:43`）兜底；**标为「仅 Auth」者未检出该校验，应视为待核查而非已授权**——扫描产物原文（§8.4:699-700）即为该结论
- 具体风险样例：任何已登录用户能触达的 handler 若主体内既无 admin/module 也无 owner 校验，则同批用户间横向可达（例如用自己的凭证读全局列表）。cert 族历史上正是这种形态（`cert_authz.go:16-18` 头注释记录的 R-1 事故），后以独立属主族修复

对新增接口的工程要求（从判定树推导）：handler 若涉及域名资源，必须让请求携带 `domain_id`（query 或 body）或把资源 ID 放在**非 `:id`** 的语义化路径参数上并显式调用 `Check*Permission`；若不涉及域名，必须自行携带 admin/module/owner 三类标签之一，不能指望中间件兜底。

### c.Param("id") 回落的误拒成本

三级回落的最后一级（`:229-231`）把**一切**名为 `id` 的路径参数都当域名 ID 用。40 余条 `:id` 语义不是域名的路由（`/monitor/tasks/:id/*`、`/cert/orders/:id/*`、`/logs/:id` 等）因此被波及：level<2 用户访问时先按 `domains.id` 查库（`:152`），查不到即回「域名不存在」（`:153`）——报错文案与真实资源类别无关，用户与前端都无法从响应理解失败原因；若该数字偶然命中一个不属于自己的域名，还会得到误导性的「无权限操作该域名」（`:177`）。分析产物将其列为 P0 之一（`.wiki-context/analysis-auth.md` 问题 3，标注「已验证代码 + 推断行为」，本次未做运行期复现）。管理员因 `:138` 短路不受影响，所以问题只在普通用户身上显现。

建议的修复方向（同为分析产物 §9 第 5 条）：去掉 `c.Param("id")` 无条件回落，改为路由级显式声明域名参数名；在修复落地前，文档与排障应把「非域名路由返回域名不存在」识别为该机制的固有症状。

### 权限变更的 30 秒生效窗口

`Auth` 的用户缓存 TTL 30 秒（`middleware/auth.go:99`），level 变更、模块权限 JSON 修改、账户禁用都要等缓存过期才影响 `Permission` 与 `UserModuleAllowed` 的输入。`InvalidateAuthUserCache`（`middleware/auth.go` 内定义）目前无调用点（口径：`.wiki-context/analysis-auth.md` 问题 12，rg 实测零引用），因此不存在主动失效通道。评估影响时注意：缓存只影响判定**输入**的新鲜度，委派权限表 `permissions` 每请求实时查库，新增/删除委派行是即时生效的。

### 路径参数类：「域名不存在」误报

排障顺序（对应 `getDomainIDFromRequest` 的回落链）：

1. 确认响应文案是否为 `域名不存在`（`permission.go:153`）且接口本身与域名无关（如监控任务、证书订单）→ 即 `:id` 回落污染场景，level<2 用户专属；验证方法是同请求换管理员账号应直通
2. 域名接口取不到 ID → 检查请求是否带 `?domain_id=`（`:224`）或 body 中 `domain_id`/`did` 字段；注意 body 分支只对 V1 的 `JSONBodyToDecryptedData`（`apiv1/auth.go:143`）写入的 `decrypted_data` 生效，控制台请求的 body 取值靠 handler 绑定，中间件只认 query 与 `:id`（`middleware/sign.go:17` 未挂载的连带后果，口径 `.wiki-context/scan-backend.md` §8.1/:670-673）
3. 子域判定不符预期 → `getSubDomainFromRequest`（`:237`）读的是 `name`/`rr`，字段名不在其一则子域校验被跳过（`:192` 空串放行）

### 审计与观测

被 `Permission` 拒绝的请求响应是 HTTP 200 + `code:-1`，网关与监控面板**看不到 4xx**，排查越权问题要按 msg 文案（四种：`域名不存在`/`无权限操作该域名`/`该域名为只读权限，无法执行写操作`/`无权限操作该子域名`）检索而非按状态码。`AuditLog`（`middleware/audit.go:21`）只记 POST/PUT/DELETE/PATCH 且 `user_id` 为空整条不记；其 `perm_domain` 维度即消费 `Permission` 写入的上下文键，这也解释了挂载缺陷时代「审计日志 domain 恒为空」的现象（`router.go:97-103` 注释）。

## 结论

dnsplane 的权限控制是一个「中间件粗筛 + handler 精判」的双层结构：`Permission`（`permission.go:132`，挂载 `router.go:104`）以零配置方式兜住所有能取到 domain_id 的流量，产出 `perm_read_only` / `perm_domain` / `perm_sub_domain` 三个上下文键；细粒度维度由七类权限点在 handler 主体各自实现，201 条路由中 admin 64、module 47、domain 16、certOwner 13、quota 8、subdomain 3、feature 3，另有 90 条仅依赖前两层。

设计上的三个可取之处：判定函数以导出函数形式沉淀在 middleware 包（`Check*Permission`、`DomainPermissionOf`、`UserModuleAllowed`），控制台与 V1 两面复用同一实现，符合 DRY；属主优先短路于委派查询，热路径成本可控；拒绝文案与判定分支一一对应，排障可从 msg 直接反查行号。

三个必须正视的结构性弱点：其一，「缺 domain_id 放行」（`:144-148`）把 90 条无标签路由的安全责任完全转移给 handler，其中未检出 admin/module/owner 校验者应持续标记为待核查；其二，`c.Param("id")` 无条件回落（`:229-231`）污染 40 余条非域名路由，普通用户遭受语义错位的误拒；其三，模块权限「未配置直通」的兼容语义（`:387-391`）意味着存量库升级后权限收紧不会自动发生。三者都有明确修复路径（路由级显式声明域名参数、无标签路由补细粒度校验、迁移时回填权限 JSON），属于「已知且可还」的技术债而非隐性缺陷。
