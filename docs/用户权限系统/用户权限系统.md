## 简介

用户权限系统是 dnsplane 的控制面准入层，把「谁、用什么凭据、能操作哪些资源、能做哪些动作」收口在同一套链路上。控制台是长驻浏览器会话的 Web 应用，对外 API 是无浏览器上下文的机器对机器通道，两者的凭据形态、重放风险与吊销语义完全不同，因此系统在同一条链上承载两条互不相交的鉴权通路。

### 目标与落地手段

| 目标 | 落地手段 | 证据位置 |
| --- | --- | --- |
| 多认证方式并存 | 口令 / TOTP / 魔法链接 / OAuth / API Key 五条入口共用会话层 | `handler/auth.go:239`、`quicklogin.go:124`、`oauth.go:71`、`apiv1/auth.go:44` |
| 角色与功能权限分离 | `level` 决定管理员直通，`permissions` JSON 决定模块可见性 | `models/models.go:17`、`:19`、`permission.go:383` |
| 资源所有者隔离 | 域名归属 + 委派授权 + 子域覆盖 + 只读位四维判定 | `permission.go:132`、`:304` |
| 凭据不落地明文 | 会话 Cookie AES-GCM 封装、字段级 `enc:v1:` 加密 | `middleware/auth.go:45`、`crypto/crypto.go:17` |
| 全链路可追溯 | 请求追踪 + 审计日志 + 分级文件日志 | `request_trace.go:135`、`audit.go:21`、`logger.go:170` |

### 核心价值与阅读路径

权限判定收敛在「一个中间件 + 三个可复用函数」的极小面积上：`Permission()` 处理绝大多数请求，`DomainPermissionOf`、`CheckDomainPermission`、`CheckSubDomainPermission` 供 handler 与对外 API 直调（`permission.go:330`、`:335`、`:344`）。对外 V1 另建一层可枚举的范围声明，把控制台散落在 handler 内部的三类校验整理为「模块 / 域名 / 子域 / 只读」四个正交维度，动机是避免新增接口漏掉某一维度（`apiv1/scope.go:11-26`）。接入方式看核心组件与依赖关系分析，实现细节看详细组件分析，线上误拒看故障排查指南；同域《安全防护》一文聚焦攻击面，本文聚焦机制本身。

### 中间件链与组件清单

控制台链的实际 `.Use` 顺序如下，顺序本身是安全设计的一部分。

| # | 中间件 | 挂载点 | 成功输出 | 失败响应 |
| --- | --- | --- | --- | --- |
| 1 | `SecurityHeaders`（`middleware/auth.go:483`） | `router.go:28` | 六项安全头 + HTTPS 时 HSTS | 不会失败 |
| 2、3 | `gin.Recovery`、`Logger`（`logger.go:170`） | `router.go:29`、`:30` | 控制台彩色行；5xx→`FileError`（`:231`）、≥3s→`SLOW`（`:240`） | panic → 500；不拦 |
| 4 | `CORS`（`middleware/auth.go:516`） | `router.go:45` | 命中白名单才回显 Origin + `ACAC: true` | 不回显 Origin |
| 5 | `RequestTrace`（`request_trace.go:135`） | `router.go:47` | `X-Request-ID`；`c.Next()` 后异步落库 | 不拦；非 `/api` 直通（`:138`） |
| 6 | `Recovery` 内层（`recovery.go:21`） | `router.go:48` | `X-Error-ID` | 未写出时 `500 {code:-1}` |
| 7 | `CSRF`（`csrf.go:70`） | `router.go:50` | 安全方法补发 cookie | `403 {code:403}`（`:106`、`:110`） |
| 8 | `AuditLog`（`audit.go:21`） | `router.go:52` | `SafeGo` 异步写 `logs`（`:74`） | 不拦；`user_id` 空则不记（`:45`） |
| 9 | `Auth`（`middleware/auth.go:125`） | `router.go:96` | 注入 `user_id`/`level`/`perm_modules*` | `401`，7 种原因 |
| 10 | `Permission`（`permission.go:132`） | `router.go:104` | 注入 `perm_read_only` 等三键 | `200 {code:-1}`，4 种原因 |

内层 `Recovery` 必须紧跟 `RequestTrace`，否则 panic 穿透会让 `c.Next()` 之后的落库代码不执行，请求日志完全丢失（`router.go:34-43` 注释）。对外 V1 组挂在引擎根，仅复用追踪、恢复、CORS、审计四层，认证改为 `apiv1.APIKeyAuth`（`apiv1/auth.go:44`），并显式不挂 CSRF（`apiv1/router.go:11-15` 注释）。

`Auth` 每次请求都要确认用户存在且 `status=1`。为削减 SQLite 往返，`getCachedAuthUser` 以 `auth_user:<uid>` 缓存整份用户模型，TTL 30 秒（`middleware/auth.go:99`、`:456`）；审计与追踪均在 `c.Next()` 之后异步落库（`audit.go:74`、`request_trace.go:296-302`），主请求线程不等待，读动作由后缀白名单跳过（`audit.go:103`）以避免写满日志库。

| 问题 | 现状 | 效果与代价 |
| --- | --- | --- |
| 每请求一次 `users` 查询 | 30 秒读穿缓存 | 高频接口下 DB 查询量与 QPS 解耦；禁用、降级、改权限最多延迟 30 秒生效 |
| 缓存失效函数未被调用 | `InvalidateAuthUserCache:473` 定义后零调用点 | 管理员改权限无法即时生效，只能等 TTL |
| 缓存就绪但条目缺失 | `middleware/auth.go:359-363` 对 refresh JTI 直接拒绝 | 收紧重放窗口；`cache.C` 未初始化时降级放行（`:355`） |
| 注释与常量不一致 | `middleware/auth.go:166-169` 写「10 秒」，实际 30 秒 | 影响排障判断，以代码为准 |
| `DecryptCookie` + `ParseToken` + 逐字比对 | 每认证请求各 1 次（`:136`、`:146`、`:152`） | 均为 CPU 成本，相对数据库查询可忽略；密钥经 `deriveKey` 复用无派生开销 |
| 静态与页面路由 | `Auth` 与 `Permission` 只在 `auth` 子组挂载 | 不付认证开销；`RequestTrace` 对非 `/api` 直通 |

### cookie 与 Bearer 不一致的定位

`Auth` 采用「密文 cookie + 明文 Bearer 逐字比对」的双重校验（`middleware/auth.go:143-150`），任一通道单独失效都表现为 401。

### refresh JTI 轮转与吊销缺口

刷新链判定为「缓存中的 jti 是否等于提交的 jti」（`middleware/auth.go:353`），每用户同一时刻仅一个有效 refresh（`:335`）。命中即轮转（`:370-372`），不匹配即删除该用户记录并拒绝（`:364-369`），构成重用检测。

| 场景 | 预期 | 实际行为 | 影响 |
| --- | --- | --- | --- |
| 正常刷新 | 旧 refresh 作废，新对下发 | 一致 | 无 |
| 旧 refresh 被重放 | 判定失败 | 该用户 refresh 记录被清除 | 强制重新登录，属预期收紧 |
| 用户注销 | 所有会话失效 | `Logout:406` 仅清 cookie，不删 `rtjti` | 持旧令牌者在 7 天内仍可换新会话 |
| 改密或重置 | 既有会话失效 | 只 `Updates(map)`，不吊销 JTI 也不失效用户缓存 | 被盗会话不因改密被踢除 |
| 多标签页并发刷新 | 都成功 | 后刷新者胜出，另一页触发重用检测 | 表现为随机登出 |

### 权限误拒、验证码与死链路

`getDomainIDFromRequest` 的第三级回落是 `c.Param("id")`（`permission.go:229`）。对 `:id` 并非域名 ID 的路由（如 `/users/:id/permissions`、`/accounts/:id/*`，见 `router.go:115-212`），`level` 小于 2 的用户可能因该数字未命中 `domains` 表而被误报「域名不存在」。代码路径已验证，运行期复现未知（本次未获得覆盖该场景的夹具）。

| 症状 | 根因 | 处理 |
| --- | --- | --- |
| 行为验证码答错后必须重取 | `Verify` 在校验前即删缓存键（`captcha.go:272`） | 一次性设计，前端重新 GET |
| 多实例部署验证码永远失败 | 图形验证码用进程内 `DefaultMemStore`（`handler/auth.go:32`） | 单实例部署，或迁至共享缓存 |
| 换 IP 后仍被锁定 / 限流完全不生效 | 按 /24 或 /64 子网分桶（`handler/auth.go:87`）；`cache.Incr` 出错时一律放行 | 同子网共享计数，等 15 分钟窗口；检查 Redis 连接与降级状态 |
| 关闭邮箱验证后注册无频控 | `Register:1420` 未挂限流与人机验证 | 保持 `auth_email_verify` 开启 |
| 前端把未注册路径当鉴权失败 | `NoRoute` 返回 200 的 HTML（`router.go:411`） | 核对后端路由是否存在 |

`ParseToken` 强制签名方法为 HMAC 系（`middleware/auth.go:429`），`alg=none` 或 RS256 混淆都会在验签前失败，属预期行为，排障时不要放宽该判断。另有两处死代码容易误导：`DecryptAndVerify`（`sign.go:17`）、`GetAESKey`（`:94`）、`EncryptedResponse`（`:142`）组成的 RSA 混合加密链路全仓无生产调用点，`EncryptedResponse` 恒走明文分支；`middleware/apikey.go`（112 行）与 `apiv1/auth.go` 是同功能重复实现，前者零调用点且未写 `auth_type`。

## 结论

系统形成三层结构：横切层用十个中间件收口身份、范围与可追溯性；业务层用五个认证入口覆盖人与机器两类客户端；基础设施层把算法与凭据形态隔离在五个包内。角色、模块、资源三维彼此正交，新增接口只需声明组合。

| 优势 | 具体表现 | 待改进 |
| --- | --- | --- |
| 凭据不可混淆 | cookie 密文与 Bearer 明文逐字比对，强制 HMAC 算法族 | — |
| 令牌不留痕 | 会话 cookie 无 JWT 特征；OAuth 回调响应体不含令牌 | access token 仍落 `localStorage`（`api.ts:70`） |
| 吊销语义明确 | refresh JTI 一次性且用户维度唯一，重用即清 | 注销与改密不吊销 JTI |
| 判定面积小 | 资源隔离集中在 `Permission` 与三个导出函数 | `c.Param("id")` 回落污染非域名路由 |
| 开关可控 | 五种方式各有 `sys_configs` 开关并即时失效缓存 | 注册在关闭邮箱验证后无频控 |
| 观测完整 | 追踪、审计、分级日志、慢请求标记四路并存 | 口令登录不进操作日志 |

### 改进优先级

1. 会话吊销统一：`Logout`、改密、重置口令与重置 TOTP 均删除 `rtjti:<uid>` 并调用 `InvalidateAuthUserCache`，同时消除 30 秒权限窗口。
2. `domain_id` 去掉 `c.Param("id")` 无条件回落，改为路由级显式声明域名参数；行为验证码类型以缓存值为准，请求侧类型仅作一致性校验。
3. V1 待签串纳入请求体摘要与 nonce；追踪日志的 `Query` 字段接入敏感键脱敏。
4. 存量口令在登录成功后检测 bcrypt cost 并透明重哈希；清理死链路与重复实现（`middleware/apikey.go`、签名链、前端未引用的加密模块）。
