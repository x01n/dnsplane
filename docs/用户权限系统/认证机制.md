## 简介

dnsplane 提供五种互不替换的认证方式，分别服务「人」「人 + 设备」与「程序」三类调用方：

| 方式 | 定位 | 后端入口 | 凭据落地形态 |
| --- | --- | --- | --- |
| 口令登录 | 控制台主路径 | `handler.Login` | `_t` / `_rt` 双 HttpOnly Cookie + 响应体令牌 |
| TOTP | 口令之上的第二因子，非独立入口 | `Login` 内联分支、`MagicLinkVerifyTotp` | `users.totp_secret` 密文列 |
| Magic Link | 无密码登录，邮件一次性链接 | `RequestMagicLink` → `QuickLogin` | 缓存一次性令牌 + 兑换后的完整会话 |
| OAuth | 第三方身份委托 | `OAuthLogin` → `OAuthExchange` | 仅 HttpOnly Cookie，响应体不含令牌 |
| API Key | 对外 V1 的程序身份 | `apiv1.APIKeyAuth` | `users.api_key`，兼作 HMAC 密钥 |

三条设计事实定义了整套体系的取向：

- **会话凭据无明文特征。** cookie 值是 AES-256-GCM 密文的 hex 表示，看不到 JWT 三段式结构（`middleware/auth.go:41-60`）。
- **双通道一致性。** `Auth` 要求 cookie 解密出的 access token 与 `Authorization: Bearer` 逐字相等（`middleware/auth.go:143-150`），单凭一方无法构造合法请求。
- **刷新令牌一次性轮转。** 每次刷新删旧 JTI 登记新 JTI，不匹配即吊销该用户全部 refresh 记录（`middleware/auth.go:343-373`）。

权限模型（角色、模块权限、域名委派）与频控全貌分别见《权限模型》与《安全防护》。

## 项目结构

认证代码按「入口 handler / 会话中间件 / 能力包」三层分布，协议细节不落入 handler：

```text
main/internal/api/handler/     auth.go（口令、刷新、注销、改密、找回、注册、TOTP 生命周期）
                               auth_control.go（开关读写） quicklogin.go（一次性令牌）
                               behavioral_captcha.go captcha.go（人机验证准入） oauth.go
main/internal/api/middleware/  auth.go（JWT + Cookie 加密 + Auth 链 + 安全头 + CORS） csrf.go
main/internal/                 oauth/（Provider 接口与五种实现） captcha/（三型行为码）
                               verify/（邮箱码与频次） utils/totp.go crypto/（字段级 AES-GCM）
web/app/(auth)/  11 个页面：登录、注册、找回密码、找回 TOTP、两个 reset 落地页、
                 magic-link 申请、magic-login 中转、magic-login/totp 补验、
                 oauth-callback、github-callback（旧书签兼容）
```

| 模块 | 职责 | 关键导出 | 依赖方向 |
| --- | --- | --- | --- |
| `handler` | 入参绑定、业务分支、响应码 | `Login`、`RefreshToken`、`RequestMagicLink`、`OAuthExchange` | → `middleware`、`oauth`、`captcha`、`verify`、`utils` |
| `middleware` | 会话建立、校验、吊销、安全头 | `GenerateTokenPair`、`SetAuthCookies`、`DecryptCookie`、`Auth` | → `config`、`cache`、`database` |
| `internal/oauth` | OAuth2 协议差异封装 | `Provider`、`GetProvider`、`GetEnabledProviders` | → `database`、`models` |
| `internal/captcha` | 行为码答案存储与比对 | `Generate`、`Verify` | → `cache` |
| `internal/verify` | 邮箱码与发信频次 | `Generate`、`Verify`、`AllowPublicEmailRequest` | → `cache` |
| `internal/apiv1` | 对外接口签名认证 | `APIKeyAuth`、`JSONBodyToDecryptedData` | → `middleware`、`database` |

挂载位置是结构上的关键事实：公开认证路由直挂 `/api` 组（经 CSRF 与审计层、不经 `Auth`），受保护路由挂 `auth` 子组；`GET /api/quicklogin` 刻意留在 `auth` 组之外（`main/internal/api/router.go:69-92`、`:337`），靠一次性令牌自身鉴权。V1 链挂引擎根节点，不继承 `/api` 组的 CSRF（`main/internal/apiv1/router.go:24-34`）。

## 核心组件

### 会话凭据与 Cookie 加密层

`middleware` 同时签发 JWT 与把 JWT 再加密成 cookie 值，两者密钥同源：cookie 的 AES-256 密钥就是 JWT secret 的 SHA-256 摘要（`middleware/auth.go:34-39`）。

### 令牌参数与 Cookie 属性

生命周期参数全是代码常量而非配置项：`AccessTokenExpire = 15m`、`RefreshTokenExpire = 7d`、`authUserCacheTTL = 30s`（`middleware/auth.go:90-99`）。`config/config.go:69-72` 定义了 `jwt.expire_hour`，但本次未见读取点，令牌有效期不受配置文件影响（推断：基于定义位置与消费缺口，未做全仓复核）。

`GenerateTokenPair` 一次产出两个 HS256 令牌，仅靠 `token_type` 区分用途（`middleware/auth.go:228-283`），每个都带 16 字节随机 hex 的 `jti`（`:446-450`）。

| Cookie | 内容 | Path | Max-Age | HttpOnly | SameSite |
| --- | --- | --- | --- | --- | --- |
| `_t` | AES-GCM(access) 的 hex | `/` | 900 | 是 | Strict |
| `_rt` | AES-GCM(refresh) 的 hex | `/api/auth/refresh` | 604800 | 是 | Strict |
| `_csrf` | 32 字节随机 hex | `/` | 7 天 | 否 | Strict |

`Secure` 由 `isSecureRequest` 决定：`c.Request.TLS != nil` 或 `X-Forwarded-Proto: https`（`middleware/auth.go:320-329`）。`_csrf` 不能是 HttpOnly，因为 double-submit 要求前端把 cookie 值回填到请求头（`middleware/csrf.go:22-24`）。secret 可被环境变量 `DNSPLANE_JWT_SECRET` 覆盖，空值或历史默认值会在首启被 32 字节随机数替换并以 0600 回写（`config/config.go:122-143`、`:156-170`）；本文一律以 `{JWT_SECRET}` 占位。

### TOTP 组件

`utils/totp.go` 是纯函数集合，不依赖数据库与缓存：密钥为 20 字节随机 Base32 无填充（`:25-33`），URI 为 `otpauth://totp/{Issuer}:{Account}?secret=...&period=30&digits=6&algorithm=SHA1`（`:35-62`），校验遍历 `[-30, 0, +30]` 三个偏移（`:70-82`）。落库侧 `users.totp_secret` 经 GORM `BeforeSave` 做字段级 AES-GCM（`models/hooks.go:56-62`），前缀 `enc:v1:`，主密钥为 `sha256(security.master_key)`（`crypto/crypto.go:16-36`），环境变量 `DNSPLANE_MASTER_KEY` 可覆盖。

登录分支额外做计数器防重放：键 `totp_used:<sha256(secret) 前 8 字节 hex>:<counter>`，TTL 90 秒（`handler/auth.go:49-70`）。

## 详细组件分析

### 口令登录的准入顺序

登录的判定顺序不是随意的，代码注释锁定了三条理由：开关检查置于锁定计数之前（关闭时不存在凭据校验，不应累加失败次数）、人机验证置于口令比对之前、禁用账户分支也计入失败计数（避免用计数差异探测账户状态）。

```mermaid
flowchart TD
    A["POST /api/login"] --> B{"auth_password_login 开启"}
    B -- "否" --> Z1["拒绝：管理员已关闭密码登录"]
    B -- "是" --> C{"loginBlocked 已锁定"}
    C -- "是" --> Z2["429：15 分钟后再试"]
    C -- "否" --> D{"needCaptcha"}
    D -- "是" --> E{"captcha_type 分派"}
    E -- "behavioral 或 go-captcha" --> F["消费 captcha_verify 令牌"]
    E -- "turnstile" --> G["requireTurnstile"]
    E -- "第三方类型或 image" --> H["requireCaptcha 或图形码校验"]
    D -- "否" --> J["查询用户"]
    F --> J
    G --> J
    H --> J
    J --> K{"用户存在且 status 为 1"}
    K -- "否" --> Z3["计入失败并抖动延迟"]
    K -- "是" --> L["bcrypt 比对口令"]
    L -- "失败" --> Z3
    L -- "成功" --> M{"totp_open 且密钥非空"}
    M -- "是且无码" --> Z4["返回 code 2"]
    M -- "是且有码" --> N["校验动态码与计数器"]
    N -- "失败" --> Z3
    N -- "成功" --> O["签发 TokenPair 并登记 JTI"]
    M -- "否" --> O
```

## 性能考虑

每个经过 `Auth` 的请求都执行一次完整 AES-GCM 解密路径：`hex.DecodeString` → `sha256(Secret)` → `aes.NewCipher` → `cipher.NewGCM` → `gcm.Open`（`middleware/auth.go:66-88`），其中密钥派生与两个构造函数都没有缓存，而 `crypto` 包对同样操作做了 `sync.Once` 复用（`crypto/crypto.go:21-36`）。

| 环节 | 频次 | 可否复用 | 口径 |
| --- | --- | --- | --- |
| `deriveKey` 的 SHA-256 | 每次解密 1 次 | 可，密钥在配置加载后固定 | 结构性观察，未压测 |
| `aes.NewCipher` 与 `NewGCM` | 每次解密各 1 次 | 可，与明文无关 | 结构性观察，未压测 |
| `gcm.Open` 与 `hex.DecodeString` | 各 1 次 | 不可 | 输入约为令牌长度的 2 倍 |
| 用户查询 | 命中缓存则跳过 | 已由 30 秒缓存覆盖 | `middleware/auth.go:452-467` |

绝对耗时都不大，真实成本在于每请求固定分配的 `cipher.Block` 与 `cipher.AEAD` 对象带来的 GC 压力。请求量上升时最划算的改动是把派生密钥与构造函数一并收进 `sync.Once`，与 `crypto` 包既有做法同构，属去重而非新增抽象。本文未做基准测试，不给出百分比。

另两处取舍与性能直接相关：所有登录失败固定 sleep 50–150 ms（`handler/auth.go:38-47`），暴力破解场景会放大协程占用，换取账号存在性不可观测；四组公开邮件接口共用容量 32 的 `mailSendSem`，超额在 goroutine 内阻塞排队（`:818-837`），SMTP 抖动不会耗尽 FD，但队列堆积对用户不可见。

## 故障排查指南

| 症状 | 首要怀疑点 | 证据位置 | 处置 |
| --- | --- | --- | --- |
| 登录后立即 401「未登录」 | `_t` 未回传，或 Cookie 域与请求域不同 | `middleware/auth.go:308`（domain 传空串即 host-only） | 确认前后端同源；跨子域需改造 Cookie 作用域 |
| 401「Token不一致」 | 未带 `Authorization` 头，或本地令牌与 cookie 内令牌不同源 | `middleware/auth.go:143-150` | 让前端走一次 `POST /api/auth/refresh` 重新对齐 |
| 401「会话已过期」 | cookie 解密失败，通常是 secret 变更后旧 cookie 全失效 | `middleware/auth.go:66-88`、`config/config.go:122-143` | 清 cookie 重登；容器重建时固定 `DNSPLANE_JWT_SECRET` |
| 刷新总失败 | `rtjti:<uid>` 条目缺失（TTL 到期或 Redis 丢数据），用 refresh 令牌访问业务接口也归此类 | `middleware/auth.go:159-164`、`:353-373` | 属预期收紧策略，需重新登录 |
| TOTP 恒判错误 | 服务器与手机时钟偏差超过 30 秒；同一码二次提交属防重放命中 | `utils/totp.go:70-82`、`handler/auth.go:49-70` | 校准服务器 NTP，等下一个 30 秒窗口，勿改终端时间 |

### 时区与时间

TOTP 与 JWT 都用 Unix 秒，与时区无关，故障只有「时钟偏移」一种原因；偏移表在 `utils/totp.go:75` 写死为 `[-30, 0, 30]`，不可配置放宽。重置链接有效期由服务器写入时刻计算（`handler/auth.go:875`、`:980`、`:1075`），比对用 `user.ResetExpire.Before(time.Now())`（`:911`、`:1020`）：时区设置错但 UTC 时刻正确时不影响判定，UTC 时刻本身偏移则用户立刻看到「已过期」。认证用户缓存 30 秒（`middleware/auth.go:98-99`）意味着禁用、降级、改权限最长 30 秒后才生效；`InvalidateAuthUserCache` 已定义（`:469-477`）但本次未见调用点，目前只能等 TTL。同函数上方注释写「10 秒 TTL」与实际常量不一致（`:166-169`），排障以常量为准。

### 反向代理下的 Cookie

`Secure` 取决于 `isSecureRequest`（`middleware/auth.go:320-329`）。代理未透传 `X-Forwarded-Proto` 时，HTTPS 站点会拿到 `Secure=false` 的 cookie；反之该头可被伪造时，会写出 `Secure=true` 却实际明文传输。同一判定决定 HSTS 是否写出（`:502-505`）。排查顺序建议固定：先看响应 `Set-Cookie` 是否含 `Secure`，再确认 `Path=/api/auth/refresh` 是否让 `_rt` 只在刷新端点出现（`handler/auth.go:423-430` 的回落读取正依赖这一点），最后才怀疑 secret。

## 结论

五种方式在实现上收敛到同一条签发链：无论入口是 `Login`、`QuickLogin`、`MagicLinkVerifyTotp` 还是 `establishSession`，最终都调 `GenerateTokenPair` + `SetAuthCookies` + `StoreRefreshJTI`（分别见 `handler/auth.go:369-384`、`:1313-1326`、`handler/quicklogin.go:175-191`、`handler/oauth.go:396-420`）。这是当前体系最可取的一点——令牌语义、Cookie 形态与 JTI 登记规则只有一份定义，新增登录方式只需接上这三个函数。

差异被有意留在**准入层**而非会话层：各方式自行决定开关、人机验证、频控与第二因子，`Auth` 对来源无感（V1 的 API Key 是唯一例外，它写 `auth_type` 但不参与 cookie 校验）。

明确记录的不足有三类：吊销链不完整（注销与改密均不吊销 refresh、不清认证缓存）；行为验证码存在类型混淆（`internal/captcha/captcha.go:265` 起）；`Updates(map)` 与字段加密钩子组合导致同列明文密文混杂。三者都是实现缺陷而非架构选择，修法收敛在少数调用点，优先级表见《安全防护》。

### 凭据结构

```text
_t  = hex( nonce || ciphertext || tag )
      nonce 长度由 gcm.NonceSize() 决定；gcm.Seal(nonce, nonce, ...) 使 nonce 前置于密文
      ciphertext = AES-256-GCM( key = sha256(JWT_SECRET), plaintext = access JWT )
      Max-Age 900，Path /，HttpOnly，SameSite=Strict        （middleware/auth.go:45-60、:296-311）
_rt = 同结构，明文为 refresh JWT；Max-Age 604800，Path /api/auth/refresh
```

JWT 的 `Claims` 由 `user_id`、`username`、`level`、`token_type` 加注册声明组成（`middleware/auth.go:101-107`），access 与 refresh 除 `token_type` 与 `exp` 外无差别：

```json
{
  "user_id": "1",
  "username": "{username}",
  "level": 2,
  "token_type": "access",
  "exp": 1700000900,
  "iat": 1700000000,
  "jti": "32 位 hex（16 字节随机）"
}
```

算法固定 HS256，`ParseToken` 显式要求 `*jwt.SigningMethodHMAC`，其它 alg 一律拒绝（`:423-444`）。cookie 解密失败两种原因（hex 非法与认证标签不匹配）都折叠成同一个 false，`Auth` 因此无法区分管线被篡改与 secret 已轮换（`:66-88`）。
