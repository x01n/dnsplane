## 简介

DNSPlane 的配置分四层，越靠后加载的层优先级越高。四层不是并列可选，而是同一份运行参数在不同阶段的四种来源：

| 层 | 载体 | 读取入口 | 生效时机 | 可写入方 |
|----|------|----------|----------|----------|
| 内置默认 | `config.Load` 内的结构体字面量 | `main/internal/config/config.go:87-101` | 进程启动，仅一次 | 无（编译期固定） |
| 配置文件 | `config.json`（`-config` 可改路径） | `main/internal/config/config.go:103-120`、`main/main.go:67-70` | 进程启动，仅一次 | 运维（文件权限 0600） |
| 环境变量 | `DNSPLANE_JWT_SECRET` 与 `DNSPLANE_MASTER_KEY` | `main/internal/config/config.go:122-128` | 进程启动，覆盖配置文件 | 容器编排或 shell |
| 系统运行时 | `sys_configs` 表（键值对） | `main/internal/sysconfig/sysconfig.go:17-26` | 每次读取，带 60 秒缓存 | 管理员经系统设置页 |

第四层是本项目特有的设计：它不是「配置文件的补充」，而是一组**独立配置域**，承载开关、凭据与阈值，读写全走数据库。分工判据是变更代价而非重要性——监听地址、数据库连接、加密主密钥必须早于数据库存在，只能落在前三层；通知凭据、注册开关、日志保留天数需要即时生效，必须落在第四层。`sync.Once` 则决定了前三层的不可变性（`main/internal/config/config.go:79-86`）：一个进程内 `Load` 只真正执行一次，因此修改 `config.json` 必须重启进程。

## 项目结构

配置能力集中在三个包，职责边界互不重叠：

```text
main/internal/
├── config/
│   └── config.go          186 行  结构定义、加载、合并、随机密钥、落盘（全包唯一文件）
├── sysconfig/
│   └── sysconfig.go        43 行  sys_configs 表读写与 60 秒缓存（全包唯一文件）
└── dbcache/
    ├── dbcache.go          68 行  读穿缓存原语 GetOrSetJSON / Delete / DeletePrefix
    └── keys.go             50 行  缓存 key 命名与失效点
```

| 包 | 唯一职责 | 依赖 | 明确不做的事 |
|----|----------|------|--------------|
| `internal/config` | 启动期参数：解析、合并、补齐密钥、落盘 | 仅标准库 | 不读数据库，不感知请求上下文 |
| `internal/sysconfig` | 运行期键值配置的读写与缓存 | `cache`、`database`、`models` | 不做类型转换，不做值校验 |
| `internal/dbcache` | 热点列表的读穿缓存与失效 | `cache` | 不碰 `sys_configs` 表，与配置层无关 |

边界由依赖方向保证：`config` 是最底层，被 `database`、`crypto`、`api/middleware` 反向依赖（`main/internal/database/database.go:6`、`main/internal/crypto/crypto.go:13`、`main/internal/api/middleware/auth.go:36`）；`sysconfig` 位于业务层之上，不能被 `config` 反向引用——这正是「配置文件里读不到数据库覆盖值」的结构性原因。`dbcache` 与 `sysconfig` 都建在同一套 `cache.C` 抽象上（`main/internal/cache/cache.go:16-33`），但前者缓存**查询结果**、后者缓存**配置值**，混在一个包里会让「缓存穿透」与「配置未生效」两类问题难以区分。

## 核心组件

### Config 结构体

`Config` 是六个子配置的聚合根，字段即 `config.json` 的顶层键（`main/internal/config/config.go:16-23`）：

| 子配置 | 结构位置 | 字段数 | 消费方 |
|--------|----------|--------|--------|
| `Server` | `config.go:40-45` | 4 | `main.go:102-104`、`main.go:130`、`handler/auth.go:815` |
| `Database` | `config.go:47-55` | 7 | `database.Init`（`database.go:71`） |
| `JWT` | `config.go:69-72` | 2 | `middleware/auth.go:36`、`:249`、`:268`、`:424` |
| `Redis` | `config.go:30-38` | 7 | `cache.Init`（`main.go:83-91`） |
| `Security` | `config.go:26-28` | 1 | `crypto.deriveKey`（`crypto.go:26-33`） |
| `Proxy` | `config.go:74-77` | 2 | 无消费方 |

`LogDBPath` 与 `RequestDBPath` 不是配置项而是**派生函数**：日志库与请求库路径恒等于主库同目录下的 `logs.db` 与 `request_logs.db`（`config.go:57-67`），因此无法单独配置，改主库目录即同时改三库位置。

三个字段没有任何消费方（全库检索实测无读取点），属死配置，在[附录](#附录)逐条标注：`ServerConfig.BaseURL`（`config.go:44`）、`JWTConfig.ExpireHour`（`config.go:71`）、`ProxyConfig` 整节（`config.go:20`、`config.go:74-77`）。

### SysConfig 表

运行期配置只有一张表，模型极简（`main/internal/models/models.go:313-317`）：

| 列 | 类型约束 | 说明 |
|----|----------|------|
| `key` | `primaryKey;size:32` | 键名上限 32 字符，超长键无法落库 |
| `value` | `type:text` | 一律字符串，布尔与数字由消费方各自解析 |

`value` 只有字符串这一种类型是本项目最重要的一次取舍：写入端把前端 JSON 值统一转成字符串（`main/internal/api/handler/user.go:642-671`，布尔转 `true`/`false` 字面串，整数走 `strconv.FormatInt`，数组与对象转成 JSON 串），读取端各自决定「未配置」的默认语义。于是同一个空值在不同判据下结果并不一致：

| 判据函数 | 位置 | 未配置（空串）时 | 视为真的取值 |
|----------|------|------------------|--------------|
| `sysconfig.ExplicitOn` | `main/internal/sysconfig/sysconfig.go:39-43` | 关 | `true`/`1`/`yes`/`on` |
| `notify.ChannelEnabled` | `main/internal/notify/channel.go:22-25` | **开** | 除 `0`/`false`/`no`/`off` 外全部 |
| `sysconfigBoolDefaultTrue` | `main/internal/service/task_runner.go:736-743` | 开 | 同上 |
| `sysconfigBoolExplicitOn` | `main/internal/service/task_runner.go:745-748` | 关 | 同 `ExplicitOn` |

另有两处**绕过 sysconfig 包**、手写 `First` 查询的读取点（`main/internal/api/handler/auth.go:174-184`、`auth.go:629`），它们不吃缓存，没有 60 秒延迟，但也意味着同一次保存后不同入口看到的值可能不一致。

### 缓存层

`sysconfig` 的缓存极薄，两个常量加一次读写（`main/internal/sysconfig/sysconfig.go:12-37`）：

| 项 | 值 | 定义位置 |
|----|-----|----------|
| 逻辑前缀 | `syscfg:` | `sysconfig.go:13` |
| TTL | 60 秒 | `sysconfig.go:14` |
| 回源语句 | `Pluck("value", &value)` | `sysconfig.go:23` |
| 写穿策略 | 先 upsert 再 `Set`（不是删除） | `sysconfig.go:34-37` |

两个必须知道的性质：`GetValue` 不接 `Pluck` 返回的错误（`sysconfig.go:23`），键不存在与查询失败都表现为空串且空串照样写缓存 60 秒；`SetValue` 只写穿本进程（`sysconfig.go:36`），其他副本最长 60 秒后各自回源收敛，多副本部署下这是可观察行为。

`dbcache` 是另一套面向列表查询的读穿缓存：默认 TTL 60 秒（`main/internal/dbcache/dbcache.go:12`），`cache.C` 为 nil 时直接透传而不缓存（`dbcache.go:18-28`），key 命名与失效点集中定义（`keys.go:10-49`），关键字查询用 SHA-256 前 8 字节做摘要避免 key 过长（`keys.go:16-23`）。

覆盖关系是**后写胜**：环境变量高于 `config.json`（`config.go:122-128`），`config.json` 高于内置默认（`config.go:116` 的 `Unmarshal` 直接覆写同一 `cfg` 指针）。第四层 `sys_configs` 不参与这里，它由消费方在使用点自行覆盖，典型是 `LoadMaintenanceConfig`（`main/internal/database/maintenance.go:62-98`）与 `cert_expire_days`（`main/internal/service/task_runner.go:153-159`）。

历史默认密钥的强制轮换是启动期最有价值的行为：`legacyDefaultJWTSecret` 常量（`config.go:14`）命中即重建（`config.go:130-143`）。由于 `jwt.secret` 既是 HS256 签名密钥（`middleware/auth.go:249-262`）又是 cookie 会话 AES-GCM 密钥的派生源（`auth.go:35-39`），换密钥等于全端登出，属预期行为。

## 详细组件分析

### server 配置

| 键 | 类型 | 内置默认 | 消费位置 | 生效方式 |
|----|------|----------|----------|----------|
| `server.port` | int | `8080` | `main/main.go:130`、`main/internal/api/handler/auth.go:815` | 重启 |
| `server.host` | string | `0.0.0.0` | `main/main.go:130` | 重启 |
| `server.mode` | string | `release` | `main/main.go:102-104` | 重启 |
| `server.base_url` | string | 未初始化（空串） | 无消费方 | 不生效 |

`server.mode` 只做一件事：等于 `release` 时切 Gin 到 ReleaseMode。当前工作区的 `main/config.json:5` 写的是 `debug`，本地因此跑调试模式；生产镜像不含 `config.json`（`Dockerfile:32-37` 只拷贝二进制到 `/app`），走内置默认 `release`。

`server.port` 有两个消费点，第二个常被忽略：未配置 `site_url` 时 magic link 与找回密码链接回退成 `http://localhost:<server.port>`（`main/internal/api/handler/auth.go:805-816`）。这个回退是刻意的——注释说明 OAuth 的 `redirect_uri` 要求逐字一致，恒定端口会让链路整体失效。`server.base_url` 是死字段，跨域来源判定走 `sys_configs` 的 `site_url`（`main/internal/api/middleware/auth.go:551`）。

## 结论

四层配置的职责边界是这套设计最值得复述的结论：**前三层只解决「进程启动前必须知道的事」**，合并点唯一（`config.Load`）、覆盖方向单调，代价是不可变；**第四层解决「管理员要即时看到效果的事」**，代价是类型丢失（整表只有字符串）与语义分裂（同一空值在不同判据下分别是开、关、未配置）。

实测确认的三个缺陷均属可直接删除或补齐的低成本项：`jwt.expire_hour`、`server.base_url`、`proxy` 整节是死配置，无消费方却出现在结构体与 `README.md:78-94` 的示例里，会持续误导运维；`cron_*` 三键是假通路，读写端点齐备但调度器不消费；`config.Save`（`main/internal/config/config.go:179-186`）无任何调用方，`config.Load` 的唯一生产调用点是 `main/main.go:70`。`SysConfig` 无加密钩子是最需要使用者知情的一项：配置表的可读性等同于数据库文件的可读性。
