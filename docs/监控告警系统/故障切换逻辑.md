## 简介

故障切换是容灾监控的写入侧：探测发现主源连续失败达到阈值后改写云端 DNS 记录，把解析指向备用源；主源恢复且任务开启自动回切时再还原。整条链路由常驻协程驱动，无需人工介入即可闭环。

本文只讲**切换与回切的决策与执行**，即 `main/internal/monitor/monitor.go` 中从阈值判定到记录落地的代码路径。探测手段本身属于监控探测文档，本文仅在影响切换结论时引用其判定口径。

## 核心组件

### 状态机：status 与 err_count 的二元组

切换状态没有独立状态列，而是由 `dm_tasks.status` 与 `dm_tasks.err_count` 拼出的隐式状态机：

| 逻辑态 | status | err_count | 进入条件 | 退出条件 |
| --- | --- | --- | --- | --- |
| 正常 | 0 | 0 | 初始或回切成功 | 探测失败累计 |
| 疑似故障 | 0 | 1..Cycle-1 | 有失败但未达阈值 | 主源恢复清零；达阈值切换 |
| 切换中 | 0 | ≥ Cycle | `smartSwitch(task, true)` 期间 | 成功置 1，失败保持 0 |
| 已切换 | 1 | 0 | 切换成功 | 主源恢复且开启回切 |
| 回切中 | 1 | 0 | `restoreRecord` 期间 | 成功置 0，失败保持 1 |
| 故障且切换失败 | 0 | ≥ Cycle | `switchErr != nil` | 下一轮阈值条件重新成立 |

最后一行是全局行为的关键：**切换失败不推进状态**（`monitor.go:319-330`），下一轮 `errCount >= Cycle && Status == 0`（`:311`）再次成立。这既是"最终会切过去"的自愈保证，也是重复写接口与重复告警的风暴来源。

### 阈值与冷却

判定式一行：`errCount >= task.Cycle && task.Status == 0`（`monitor.go:311`），其中 `errCount = task.ErrCount + 1`（`:308`）。默认 `Cycle=3`、`Frequency=60` 时，从首次真实故障到切换落地约需 3 个周期。

两处边界无守卫：`Cycle` 为 0 时首次失败即切换；`Frequency` 为 0 时派发器把下次检查时间算成 `now + 0`（`:177`），下一秒立即重跑。创建路径有零值兜底、更新路径没有，差异见故障排查。

冷却方面，`monitor.go` 全文通读可确认不存在任何冷却、退避、静默期或告警合并判定。与"距离上次切换多久"相关的只有 `switch_time`（`models.go:158`），它在切换成功（`:321`）与回切成功（`:297`）时被写入，但**没有任何一处读取它做时间窗比较**。因此主源在阈值上下抖动时，切换与回切可在相邻两周期内来回发生。`TaskState` 与 `DMTask` 都未预留冷却字段，加冷却需同时改表结构与判定式，属契约变更。

| `OriginalValue` | 切换前主源值，回切时还原 | `:557`、`:495`、`:456` | `:538-541`、`:691-694` |
| `DeletedRecord` | 被删记录的 type/line/ttl/mx/remark，重建时逐字段复用 | `:496-500`、`:608-612`、`:635-639` | `:526-543` |

## 详细组件分析

### 主源判定：任一失败即故障

主源值按逗号拆成列表（`parseValues`，`monitor.go:952-965`），每个地址起一个 goroutine 并行探测，任一地址失败就把 `mainHealthy` 置 false（`:210-212`）。没有比例阈值也没有仲裁：3 个主源挂 1 个与挂 3 个，在切换决策上完全等价。多 IP 轮询场景下，单点抖动即可触发整条记录切到备用值。

`errMsg` 只取 map 中第一个失败项（`:244-250`）。Go 的 map 遍历顺序随机，因此同一批故障在不同轮次可能给出不同错误文本，告警内容不稳定。所有主源探测共用一个 `WaitGroup`，任务级 ctx 超时为 `Timeout + 10` 秒（`:192`）。

### 备用值选取与健康位默认值

备用值优先取 `BackupValues`（逗号分隔），回退 `BackupValue`（`getBackupValues`，`:967-976`）。每个备用值先经 `resolveToAddrs` 解析成可探测地址（`:978-989`）：已是 IP 直接用，否则 `resolveCNAME` 取 IPv4，解析失败则回退用原值探测。

健康位写 `backupHealthMap[val] = result.Success`（`:232`）。同一备用值解析出多个地址时后写覆盖前写，因此一个备用域名多 IP 场景下健康位取决于 goroutine 完成顺序。切换时选第一个健康备用值（`:569-576`），而 `isBackupHealthy` 在内存快照缺失时返回 `true`（`:939-949`）。

快照 `resolveStatuses` 只在 `processTaskAsync` 写入（`:274`），进程重启即为空。因此**重启后第一轮故障切换会在没有任何备用探测数据的情况下，直接选用列表第一个备用值**，即使它已不可用。备用列表为空时 `switchToBackup` 返回 `无备用值`（`:564-567`），进入切换失败分支。

### 切换策略分派与记录改写矩阵

`smartSwitch` 按 `task.Type` 分派（`:445-476`，值域注释见 `models.go:141`），三条路径的可逆性代价完全不同：

| Type | 名称 | 切到备用时 | 回切时 | `record_id` 是否变更 | 破坏性 |
| --- | --- | --- | --- | --- | --- |
| 0 | 暂停/恢复 | `disableRecord`：优先暂停，不支持或失败则删除并存原值 | `enableRecord`：`WasDeleted` 为真转重建，否则启用 | 删除路径会变 | 中 |
| 1 | 删除/重建 | 先存原值与元数据，再删除记录 | `recreateRecord` | 一定会变（新 ID） | 高 |
| 2 | 切换备用值 | `switchToBackup` | `switchToMain` | 视类型是否一致 | 低到高 |

分派前有两道空值守卫：`DomainID == 0` 与 `RecordID == ""` 直接返回错误（`:412-417`），这是唯一一处对任务配置完整性的显式校验；`Type` 之外的值返回 `unknown task type`（`:476`）不做任何写操作。

Type 2 的改写动作由"备用值类型"与"主记录类型"是否一致决定（`:622-657`），类型判定用 `GetRecordType`（`check.go:363-372`：IP 得 A/AAAA，其余得 CNAME）：

| 主记录 | 备用值 | 判定 | 改写动作 |
| --- | --- | --- | --- |
| A | IPv4 | 一致 | `UpdateDomainRecord` 原地改值 |
| AAAA | IPv6 | 一致 | `UpdateDomainRecord` 原地改值 |
| A | IPv6 或域名 | 不一致 | 暂停或删除主记录 + 新增对应类型记录 |
| CNAME | IPv4/IPv6 | 不一致 | 暂停或删除主记录 + 新增 A 记录 |
| CNAME | 域名 | 走 CNAME 备用分支 | 解析为 IPv4 后逐条加 A 记录 + 禁用主记录 |

最后一行（`:578-619`）的设计意图是避开"CNAME 与 A 不能共存"，代价是把弹性域名固化成若干静态 IP——备用方换 IP 后已切换的记录不会自动跟进，只能靠回切再重切刷新。新增 A 记录时错误被忽略（`:587-590` 仅在 `addErr == nil` 时追加 ID），部分 IP 添加失败既无告警，回切时也不会去删。

### 回切条件与四级回退

回切唯一入口在健康分支的 `if task.Status == 1 && task.AutoRestore`（`monitor.go:292`）。成功后一次性写 `status=0`、`switch_time`、`recover_time`、`err_count=0`，记一条 `action=2` 事件日志并发 `recover` 通知（`:296-301`）；失败只打一条 error 日志，状态保持已切换（`:302-304`），下一轮主源仍健康时再次尝试——这是回切方向唯一的隐式重试。

`restoreRecord` 即 `smartSwitch(task, false)`（`:705-708`），三分支各自的回退顺序：

| 分支 | 第一选择 | 失败后回退 | 最终回退 |
| --- | --- | --- | --- |
| Type 0 | 启用记录；若 `WasDeleted` 直接转重建 | 无 | 无 |
| Type 1 | `recreateRecord`，元数据缺省补 `default`/600/`A`/`MainValue` | 无 | 无 |
| Type 2 | 删全部备用记录 → 曾删除则重建 → 否则启用主记录 | 启用失败转读记录再改值回 `OriginalValue` | 读记录失败即返回错误 |

`switchToMain` 清理备用记录时逐条删除并把失败降级为 warn（`:666-670`），不中断回切，随后 `BackupRecordIDs` 置 nil（`:671`）——删除失败的备用记录会成为云端孤儿，且此后没有任何结构记得它存在。`recreateRecord` 在 `!state.WasDeleted` 时直接返回 nil（`:522-524`），若暂停实际成功但 `record_info` 写入失败，回切会误判为无需处理，主记录停留在暂停态。

### 并发切换保护与手动路径

保护分两个层级，粒度与失败后果不同：

| 机制 | 载体 | 容量 | 目的 | 生命周期 |
| --- | --- | --- | --- | --- |
| 任务重入锁 | `processing sync.Map` | 无上限 | 同一任务不被两个 goroutine 并发处理 | `LoadOrStore` 于 `:165`，`Delete` 于 `:185` |
| 探测信号量 | `checkSem chan struct{}` | 64（`:29`） | 限制同时持有的 socket 数 | 获取与释放都在 `checkAddress` 内（`:342-344`） |

任务锁是切换幂等的关键：派发器每 tick 都会命中同一到期任务，靠 `processing.LoadOrStore` 拦重入；`processTaskAsync` 用 defer 释放（`:185`）并在同一函数 `recover` panic（`:186-190`），因此协程崩溃不会导致锁永久泄漏。但即便任务因重入被跳过，派发器仍会顺延它的下次检查时间（`:164-167` 的 `continue` 在 ID 收集之后），实际探测间隔被拉长而非并发执行。

信号量层面的误判风险更严重：等待槽位期间 ctx 到期就返回失败结果 `"探测并发已满且等待超时"`（`:342-347`），这条结果与真实探测失败在 `:210-212` 处完全等价，会把主源判为不健康并累计 `err_count`。任务数一多就会出现与目标健康度无关的批量误切换。跨进程维度没有任何保护——`processing` 是实例字段（`:63`），多副本部署时两个副本可同时对同一条记录发起切换。

`ManualSwitch`（`:710-740`）是唯一绕开阈值直接执行切换的路径，它自己重查任务（`:713`）、不复用内存快照，与自动路径的差异：

| 维度 | 自动路径 | 手动路径 |
| --- | --- | --- |
| 触发 | 阈值判定（`:311`） | 端点调用（`handler/monitor.go:517`） |
| 备用健康位 | 读 `resolveStatuses`，缺失即视为健康 | 同样读快照，重启后为空 |
| 是否发通知 | 是 | 否 |
| 是否记 `dm_logs` | 是 | 是（`:730`、`:736`） |
| 权限校验 | 无（协程内部） | 模块 + 域名 + 只读位 + 子域（`handler/monitor.go:505`） |

手动切换不发通知但写审计日志（`handler/monitor.go:526`），这解释了"运维手动切过去之后告警渠道里没有记录"的常见疑问。

## 性能考虑

### 派发与并发预算

| 常量 | 值 | 定义位置 | 超限时行为 |
| --- | --- | --- | --- |
| `maxDispatchPerTick` | 100 | `monitor.go:24` | 未派发任务保持原 `check_next_time`，下轮按升序优先 |
| `maxConcurrentChecks` | 64 | `monitor.go:29` | 排队等待，等待期间 ctx 超时即判探测失败 |
| 任务 ctx 超时 | `Timeout + 10` 秒 | `monitor.go:192` | `WaitGroup` 内探测被 ctx 取消 |

按 `check_next_time` 升序取前 N 个（`:150-153`）让积压任务优先，配合 100 的上限形成公平调度。但 64 个探测槽被所有任务共享，单任务占用的槽位数等于主源地址数加上备用值解析出的地址数之和：一个配 5 主源 + 5 备用域名的任务可占 10 个以上槽位并持续数十秒，10 个这样的任务就打满信号量。

结论：容量估算应按"并发地址总数 / 64"而不是"任务数"，这是配置监控规模时最容易忽略的一点。

### 状态列写不进去

这是最需要优先排除的一条。`processTaskAsync` 的 `updates` map 含 4 个列名：`last_error`（`monitor.go:278`）、`backup_health`（`:282`）、`recover_time`（`:298`）、`fault_time`（`:316`），而 `DMTask` 结构体（`models.go:133-176`）经通读确认没有对应字段声明。

| 库状态 | `updates` 执行结果 | 表现 |
| --- | --- | --- |
| 旧库（历史版本遗留了这些列） | 成功 | 一切正常 |
| 新库（按当前结构体建表） | 整条 UPDATE 失败，错误被 `:334` 丢弃 | `err_count` 恒为 0 |

`err_count` 恒为 0 时 `errCount = 0 + 1 = 1`，默认 `Cycle=3` 下 `1 >= 3` 恒假，于是永不切换、永不告警、永不回切；`status` 同样写不进去，回切条件恒不成立。判定方法：主源持续故障时直接读 `err_count`，始终为 0 基本可锁定本条；若按 1、2、3 递增则跳过本条。

上游分析素材记录了对旧库 DDL 的实测（这些列存在于 `main/data/data.db` 而不在当前结构体）以及在按当前结构体新建的库上复现 UPDATE 失败、影响 0 行。本次未重跑该验证，引用时以此为准。

### 探测恒成功与假健康

主源被判健康、`err_count` 不涨，用户以为"该切没切"。三个可由代码直接验证的成因：

| 成因 | 机制 | 证据 |
| --- | --- | --- |
| ICMP 不可用降级 TCP:80 | `icmp.ListenPacket` 需特权，失败即回退探测固定 80 端口 | `check.go:68-71`、`:149-161` |
| 80 通而业务端口挂 | 上一行的直接后果，降级探测成功即判主源健康 | `check.go:151-161` |
| HTTP 判定过宽 | 正文仅取前 8192 字节匹配关键词，状态码白名单可放过异常 | `check.go:21`、`:24-42` |

同类问题还有 SSRF 守卫的类型不对称：`validateCheckURL` 只对 `CheckType` 2/3 生效（`monitor.go:363`、`:377`），协议白名单仅 `http`/`https`（`ssrf.go:15-18`），并在 dial 阶段由 `ssrfDialControl` 二次拦截解析后指向私网的地址以对抗 DNS rebinding（`ssrf.go:29-30` 注释）；`CheckType` 0/1 与 `resolveToAddrs` 的解析（`monitor.go:979-989`）都不做私网判定。结果是同一私网目标用 HTTP 监控会被判失败并切换，改用 ping 或 tcp 则不会——配置时必须统一探测类型口径。

建议：把 `CheckType` 显式设为与业务真实端口一致的 TCP（`monitor.go:352-357`），不要依赖 ping 的降级路径；`TCPPort` 为 0 时代码回退 80（`:354-356`）。

### 回切抖动与告警风暴

抖动表现为解析在主备之间来回切换，告警渠道短时间收到多条【容灾告警】与【容灾恢复】交替。成因组合均可由代码验证：回切无二次确认（`monitor.go:292`）、回切无驻留时间（`switch_time` 写了但无消费方）、主源判定过严（`:210-212`，反之任一时刻成功即算健康，无去抖）、切换失败反复重试（`:311` 与 `:325-330`）、告警无节流（`:767-822`）。

临时缓解首选**拉长 `Frequency`**，它同时降低切换与回切的频率上限；调大 `Cycle` 可延长判定窗口；关闭 `AutoRestore`（`models.go:174`）可彻底消除来回，代价是故障恢复后需人工回切。根治需要新增冷却字段与冷却判定，属表结构、决策式、API 三处联动改动。

### 记录残留、状态显示与前端缺口

三类记录残留：

| 现象 | 触发条件 | 代码依据 |
| --- | --- | --- |
| 备用记录成孤儿 | 回切时删除备用记录失败，仅记 warn 后继续 | `monitor.go:666-671` |
| 主/备重复解析 | `switchToBackup` 中 `WasDeleted` 已置真，紧随的删除不检查错误 | `:603-604`、`:613-614`、`:640-648` 配 `:617`、`:659` |
| CNAME 备用切换后不再跟进 | 切换时把备用域名固化为若干 A 记录 | `:586-591` |

第二行是顺序问题的核心：`state.WasDeleted = true` 之后紧跟的 `DeleteDomainRecord` 一律不检查返回值，而 `saveTaskState` 无条件执行，因此删除失败也会落库为"已删除"，回切据此走 `recreateRecord` 新增一条，与云端仍在的原记录构成同名重复解析。

运行状态显示类：`updateRunStatus` 由 60 秒 statusTicker 驱动（`:114`、`:130-141`），而 `/api/monitor/status` 只在 10 秒内视为运行（`handler/monitor.go:803`），两者相差 6 倍，绝大多数时刻前端都显示未启动——这不是切换故障，但会误导排查，排查前先确认 `run_time` 是否按 60 秒推进。另有一处 MySQL 专属问题：`handler/monitor.go:798` 写作 `Where("key = ?", "run_time")`，未加反引号，而 `key` 是 MySQL 保留字；同文件其他位置（`:132`、`:641`）与 `monitor.go:132` 一律带反引号。

前端可见性类：监控台的故障时间线依赖 `task.backup_health`、`last_error`、`fault_time`、`recover_time` 四个键（`page.tsx:992`、`:1000-1001`、`:1237-1256`），列表接口以 `dm_tasks.*` 扫描进 `models.DMTask` 再序列化，结构体没有这 4 个字段，因此这些键不会出现在 JSON 中，对应分支恒不渲染。渠道白名单同样有缺口：创建向导有通知渠道多选（`page.tsx:2001-2006`），编辑表单没有该字段，任务创建后无法通过界面调整白名单。

## 结论

### 决策逻辑完整，风险集中在契约与旁路

从阈值判定到记录改写再到回切，`monitor.go` 的决策路径清晰且自洽：`Cycle` 与 `err_count` 构成触发条件（`:308-311`），`smartSwitch` 按 `Type` 三分派（`:445-476`），能力表决定暂停还是删除（`:481`），`TaskState` 承载可逆性（`:42-53`），回切条件明确（`:292`）。按证据强度把问题分三档：

| 档位 | 问题 | 证据强度 |
| --- | --- | --- |
| 代码即证据 | 7 处写库不检查错误；`switch_time` 无消费方导致零冷却；`smartSwitch` 不继承任务超时；能力表仅 15 家且 `Delete`/`Mixed` 无消费方；`isBackupHealthy` 缺快照时默认真；信号量等待超时计入主源失败；删除备用记录失败仍继续；告警文案用阈值而非实际次数；重启后时间线四个键不渲染 | 高（均为本文实读行号） |
| 上游素材实测、本次未重跑 | 新库缺列导致 UPDATE 失败、`err_count` 恒 0 从而永不切换；旧库因残留列表现正常 | 中 |
| 依赖部署形态 | 容器内 ICMP 是否可用；MySQL 下 `/monitor/status` 是否报错 | 中 |

主备切换语义在"单副本、旧库、服务商登记齐全"三个前提下可用；三条前提任一不成立，都会退化为静默失效或破坏性路径。

### 改进顺序建议

1. 补齐 `DMTask` 缺失的 4 个字段、或把这 4 个键从 `updates` map 移除（二选一），并给 `:334`、`:548`、`:926`、`:931` 加错误检查——这是让其余修复可验证的前提
2. 给 `smartSwitch` 传入任务 ctx，使服务商调用受超时约束
3. 加最小切换驻留时间与回切连续轮次确认，冷却判定接在 `:311` 与 `:292`

5. 能力表与 provider 实现做一致性校验，或让 `Pause` 由 provider 自报，消除两份清单的分叉

前三项不涉及功能扩展，属补齐已有契约；第 4、5 项才是行为新增。按 KISS/YAGNI 口径，第 1 项未完成前不应推进后续各项。
