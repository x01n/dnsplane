## 简介

通知系统是 DNSPlane 唯一的出站消息投递层，落在 `main/internal/notify` 一个包内，把 13 个互不兼容的第三方协议压平成同一句 `Notifier.Send(ctx, title, content)`，供容灾监控、证书签发与部署、域名到期、认证类邮件、控制台测试端点、QQ 回调绑定六类业务共用。与解析链路「22 家服务商一个 `dns.Provider`」同构，本域的核心矛盾同样是厂商差异收敛，只是方向相反。

题面列举的「邮件/Webhook/Telegram/钉钉/飞书/QQBot/Discord」是主干渠道，注册表实际暴露 13 个标识，另有 Bark、企业微信群机器人、企业微信应用、公众号模板消息、WxPusher、自定义 Webhook 六个。以 `Channel` 接口为唯一事实源逐渠道累加 `ConfigKeys` + `EnabledKey` + `NoticeKey`（`channel_registry.go:108-129`），得到 **71 个配置键**（含 6 个不隶属任何渠道的 `notice_*` 开关），全部以 key-value 散落在 `sys_configs`（`models.go:314-317`），不存在独立的渠道配置表或发送记录表。

| 维度 | 实测值 | 取证位置 |
|------|:------:|----------|
| 已注册渠道 | 13 | `channel_adapters.go:330-344` 的 `init()` |
| 聚合配置键 | 71（含 6 个 `notice_*`） | `channel_registry.go:108-129` 求和去重 |
| 通知包规模 | 38 个 `.go`、7202 行（生产 3558） | 目录 `wc -l`，最大 `notify.go` 914 行 |
| HTTP 渠道超时 | 固定 30s（14 处） | `notify.go:322,416,720,777,819` 等 |
| SMTP 超时 | 拨号 12s、单阶段 15s | `notify.go:173-174`、`setSMTPDeadline:176` |
| 调用方 deadline | 容灾/证书/到期 10s，测试端点 30s | `monitor.go:814`、`task_runner.go:477,620,880,948` |
| 渠道内限流 / 重试 | 均不存在 | 生产文件 `rate.`/`limiter`/`retry` 零命中 |

一处口径要先说清：**「渠道可用性」与「渠道启用」是两层判定**。前者由 `Channel.Build` 的凭据守卫决定（缺键即不装载），后者由 `ChannelEnabled`（`channel.go:22-25`）决定，语义反直觉——未配置视为启用，仅显式 `0`/`false`/`no`/`off` 才关闭。注释给出的理由是这些 `*_enabled` 键引入前从未被后端消费，按「未配置即关」会让全部存量实例的通知在一次升级后静默失效（`channel.go:8-11`）。

### Channel 接口六法契约

| 方法 | 契约 | 违规后果 | 位置 |
|------|------|----------|------|
| `Type()` | 渠道唯一标识，白名单与前端选单取值依据 | 重复注册直接 panic | `channel_registry.go:22`、`:62-64` |

## 详细组件分析

### 邮件渠道：SMTP、Sendcloud 与 DirectMail

`buildMailNotifier`（`channel_adapters.go:364-400`）按 `mail_type` 三路分发：`1` → Sendcloud（`:374-380`），`2` → DirectMail（`:381-387`），`0` 或空 → SMTP（`:388-397`）。三路守卫**统一使用回退后的 `mailTo`**：`mail_recv` 为空回退 `mail_from`（`:365-368`），注释写明用 `mail_recv` 会让回退不可达而静默失效（`:354-356`）。端口经 `mailPortOrDefault`（`:454-460`）非法即回 25，加密由 `MailSecureFromConfig`（`:416-429`）解析——`mail_secure` 显式 `none` 不被历史键 `mail_tls` 改写，鉴权由 `MailAuthFromConfig`（`:442-451`）给出 `plain`/`login`/`crammd5`。

`EmailNotifier.Send`（`notify.go:113-170`）依次做头部注入防御（`:115-131`）、拼 `名称 <地址>` 与 `Content-Type: text/html; charset=UTF-8` 报文（`:134-141`）、选鉴权（`:146-154`，`login` 走自实现 `LoginAuth:282`）、选加密分支（`:157-169`），最终由 `sendViaClient`（`:255-275`）统一 Auth/Mail/Rcpt/Data。SMTP 无连接池，每次新建 TCP：拨号 12s、单阶段 15s（`:173-174`）；SSL 与 STARTTLS 均 `InsecureSkipVerify: true`（`:202`、`:243`），不校验证书链——账号口令存在中间人风险。

|----|-----------|-------------------|
| 端点 | `http://api.sendcloud.net/apiv2/mail/send`（`mail_sendcloud.go:14`，**明文**） | `https://dm.aliyuncs.com/`（`mail_aliyun.go:20`） |
| 正文字段 | `html`（`:79`） | `HtmlBody`（`:85`） |
| 签名 | 无 | RPC HMAC-SHA1（`aliyunRPCSignature:148`、`sha1.New` 在 `:151`） |
| 头部防御 | `:53-70` 四次 `SanitizeMailHeader` | `:58-75` 同样四次 |

## 性能考虑

**问题一：串行扇出共享单一 deadline。** `SendAll` 顺序遍历（`notify.go:688-696`），调用方给单个 10s ctx（`monitor.go:814`、`task_runner.go:477,620,694,880,948`），而每渠道 `http.Client.Timeout` 是 30s。首渠道慢（SMTP 最坏 27s）即吃满 10s，其后渠道在 ctx 已超时下必然失败；`Send` 只回传 `errors[0]`（`:698-704`），后续渠道的失败原因被丢弃。**优化**：并发扇出 + 每渠道独立超时，全部错误逐条落日志。**效果**：靠后渠道不再被首个慢渠道饿死，日志可定位「到底哪个渠道没发出去」；失败比例未在真实环境测量，判定为推断。

**问题二：容灾告警每次直查 71 键。** `buildNotifyManager` 每次告警执行一次 `WHERE key IN (…)` 直查主库（`monitor.go:832`），不走 `sysconfig` 的 60s 缓存（`sysconfig.go:14`）；`task_runner` 侧却走 `GetValue`（`task_runner.go:86`）。按 `maxConcurrentChecks = 64`、`maxDispatchPerTick = 100`（`monitor.go:24`、`:29`）的派发规模，批量域名同时抖动时每次切换/恢复新增一次配置查询——恰在最需要告警时给主库加压。**优化**：读取改走缓存或引入带失效通知的进程内快照。**效果**：读放大与告警次数解耦，放大倍数为推断。

**问题三：常驻 manager 不重载。** `r.notifyManager` 只在 `Start` 装载一次（`task_runner.go:56` → `:84-87`），`ReloadNotifyConfig`（`:976-977`）全仓零调用方，`UpdateSystemConfig` 只写库并 `sysconfig.Invalidate`（`user.go:673`）。改凭据后到期与部署链继续用旧值直到重启，而签发与续期链（每次新建）立即用新值。**优化**：`UpdateSystemConfig` 命中 `notify.NotifyConfigKeys()` 时触发重载，或常驻路径改按需构造。**效果**：四条链生效时点一致。

**问题四：令牌缓存粒度不一致。**

| 缓存点 | 层级 | TTL 口径 | 多实例一致 | 位置 |
|--------|------|----------|:----------:|------|
| 企微 / 公众号 access_token | 进程内 | `expires_in - 300` | 否 | `wxwork_app.go:33-65`、`wxtpl.go:35-67` |
| QQBot access_token | 进程内 + 共享 | `max(60, expires_in-120)`（命中后本地按 1h） | 是 | `qqbot.go:134-209` |
| 系统配置读取 | 共享缓存 | 固定 60s | 是 | `sysconfig.go:12-26` |
| 容灾告警配置读取 | **无缓存** | — | 是（每次直查） | `monitor.go:832` |

多实例下企微/公众号各自刷新令牌，厂商侧「同 corpid 重复取 token 互相挤掉」的行为本环境未实测，标注为未知。

### SSRF via Webhook

`ValidateOutboundURL`（`safe_url.go:15-43`）做四件事：scheme 白名单 `http`/`https`（`:10-13`、`:24-27`）、host 非空（`:28-31`）、保留域名拒绝（`localhost`/`.localhost`/`.internal`/`.local`，`:32-36`）、**仅当 host 是 IP 字面量**时判私网（`:37-41` → `isPrivateOrReservedIP:45-77`，覆盖回环、链路本地、组播、`IsPrivate`、`100.64.0.0/10` CGNAT、`169.254.169.254`、`240.0.0.0/4`）。

### Bark 与 Telegram 的报文陷阱

`GetSystemConfig`（`user.go:625-640`）把 `sys_configs` 全表原样返回，含 `mail_password`、`tgbot_token`、`discord_webhook` 等，有 `requireAdmin` 门禁（`:629`）但**无掩码**；同仓已有 `******` 掩码 + 哨兵回写保护的先例，通知侧未采用。表本身不加密（`models.go:315-316`，`Value` 为 `text`）。`UpdateSystemConfig`（`:673` 起）对任意 key 一律 upsert，仅 `proxy_type`/`proxy_port` 有校验（`proxyConfigRejectReason:725`），无通知键白名单。

另有方言相关隐患：`cert_issue_success_notice_enabled`（33 字符）与 `cert_deploy_success_notice_enabled`（34 字符）超出 `models.go:315` 的 `size:32`。SQLite 不强制变长上限，默认部署无异常；MySQL 下 AutoMigrate 建 `varchar(32)`，写入触发 1406 或被静默截断（取决于 `sql_mode`），截断后键名不再等于读取键 → 两个「成功通知」开关勾选无效果。该结论为**推断**：键长度与模型声明已实测，MySQL 行为未在本环境验证。

## 结论

**成果**：13 个渠道的键集合、构造守卫、报文格式、成功判据逐项落到行号；4 条装载路径与 3 类 manager 生命周期厘清；QQBot 的 Ed25519 体系与回调绑定链还原；邮件双装配点的口径统一程度确认。键总数 71 由注册表逐渠道累加自证，未依赖外部清单。

**原则映射**：**DRY** —— 注册表 + `ChannelConfigKeys()` 聚合（`channel_registry.go:108-129`）+ `MailSecureFromConfig`/`MailAuthFromConfig` 双装配点共用，已消除「三处装载各维护一份渠道清单」的分叉，剩余分叉是 `auth.go:751` 的第二套邮件装配。**OCP** —— 后端新增渠道确实只需注册（`channel_adapters.go:330-344`），但测试端点、前端卡片、任务白名单三处仍需手工改动，开闭只在后端成立。**KISS** —— `SendAll` 串行 + 单 ctx + 只回传首个错误，是最简单但不可靠的实现。**SRP** —— `notify.go` 914 行同时承载 7 个通知器 + `NotifyManager` + 正文适配 + 群机器人报文构造，属可拆分的巨石文件，按渠道拆独立文件是既有正确方向。

**已验证事实**：无渠道级限流与重试；Sendcloud 端点为明文 HTTP；`textcard.url` 硬编码无效域名；`LoadMailNotifier`、`NewMailContentAdapter`、`ReloadNotifyConfig` 生产零调用；设置页缺 `mail_enabled`/`qqbot_*`/`wechat_app*`；任务白名单缺 4 渠道。**未验证**：MySQL 下 33/34 字符键的落库行为、Bark 与 Telegram 在真实上游的失败率、飞书卡片配色命中关系、多实例令牌互斥行为。

**建议优先级**：渠道可达性（白名单补 4 项 + 两渠道补配置入口与测试路由）→ manager 重载 → 扇出并发化与错误逐条落日志 → 凭据掩码与回调鉴权 → 连接期 SSRF 拦截 → MySQL 键长 → 投递记录表。
