## 简介

监控告警域的数据落地由四类载体组成，它们的**生命周期、写入频率、可靠性契约完全不同**，用同一套排查方法必然失效：

| 数据类别 | 物理载体 | Go 类型 | 写入点 | 生命周期 |
|----------|----------|---------|--------|----------|
| 结果快照 | 主库 `dm_tasks` 状态列 | `models.DMTask` | `monitor.go:334` | 与任务同生命周期，不清理 |
| 探测历史 | 日志库 `dm_check_logs` | `models.DMCheckLog` | `monitor.go:253-265` | 默认保留 72 小时 |
| 切换日志 | 主库 `dm_logs` | `models.DMLog` | `monitor.go:930-937` | 默认保留 60 天 |
| 实时解析快照 | 进程内存 `sync.Map` | `monitor.ResolveStatus` | `monitor.go:274` | 进程生命周期，重启即空 |

先澄清命名口径：本域不存在名为 `MonitorResult` 或 `SwitchLog` 的 Go 类型，大纲所指的"结果快照 / 历史 / 切换日志"在代码中分别对应 `DMTask` 状态列、`DMCheckLog`、`DMLog`，加上一份只存在于内存的 `ResolveStatus`，后文统一使用代码里的真实标识符。存储侧的关键设计是**写入量由调度器节流，而非由保留策略兜底**：

| 节流参数 | 值 | 定义位置 | 作用 |
|----------|:--:|----------|------|
| tick 间隔 | 1 秒 | `monitor.go:110` | 到期判定粒度 |
| `maxDispatchPerTick` | 100 | `monitor.go:24` | 单轮最多派发任务数 |
| `maxConcurrentChecks` | 64 | `monitor.go:29` | 地址级探测并发上限 |
| 任务级 ctx 超时 | `Timeout + 10` 秒 | `monitor.go:192` | 单任务探测硬上限 |
| 历史查询点数上限 | 4000 | `handler/monitor.go:27`、`:852` | 单次读的最大行数 |

后四列是本文记录的首要结构性风险。`monitor.go:275-283`、`:298`、`:316` 通过 `Updates(map[string]interface{})` 写它们，而 `DMTask`（`models.go:134-176`）没有对应字段；`Updates` 按 map 键拼 SET 子句，列不存在即报错，`monitor.go:334` 未接收返回值，错误被静默丢弃。

对存量库做只读 DDL 导出（`main/data/data.db`）可见这四列确实存在，并额外残留 `uid`：

```sql
-- 来源：sqlite3 "file:main/data/data.db?mode=ro" ".schema dm_tasks"（节选）
`main_health` numeric DEFAULT true, `backup_health` text, `last_error` text,
`fault_time` datetime, `recover_time` datetime, `uid` text,
```

旧库因历史版本残留列而表现正常；以当前结构体 AutoMigrate 的新库不会创建这些列，而 AutoMigrate 只加列不减列，分叉无法靠重启自愈。另有一处类型口径冲突：`fault_time` / `recover_time` 在 `monitor.go:316`、`:298` 写入 `*time.Time`（实测列类型 `datetime`），前端却按秒级时间戳渲染 —— `monitor/page.tsx:1244`、`:1250` 直接对字段做 `* 1000`，即便列存在，展示的故障时间也会落在 1970 年附近。

### 写入频率：一轮探测的四次落库

```mermaid
sequenceDiagram

    participant D as dispatchTasks
    participant P as processTaskAsync
    participant L as LogDB
    participant M as 主库 DB

    T->>D: 每 1000ms
    D->>M: SELECT active=1 AND check_next_time<=now LIMIT 100
    D->>M: UPDATE check_next_time = now + Frequency
    D->>P: SafeGoWithName 起协程
    P-->>L: go LogDB.Create(DMCheckLog) 裸协程，错误未检查
    P->>M: resolveStatuses.Store 加 Updates(map) 状态列
    Note over T,M: 每 60 秒 statusTicker 额外写 run_time 与 run_count
```

**图表来源**
- [monitor.go:107-179](file://main/internal/monitor/monitor.go#L107-L179)

写入量的解析式（由 `dispatchTasks` 与"一行/轮"事实推导，非压测结果）：稳态行数速率约等于 Σ(1 / Frequency_i) 行/秒，与主源地址数、备用值数无关；72 小时窗口行数上界约 Σ(259200 / Frequency_i)，以 1000 个 60 秒任务推算约 432 万行 —— 该数为**推算**，仅用于说明容量级差。实测样本（`main/data/logs.db` 只读查询）为另一侧对照：`dm_check_logs` 514 行，`created_at` 跨度 2026-10-07 12:52:42 至 2026-10-08 20:45:33（约 31.9 小时），`logs` 153 行，`cert_logs` 5 行，整库 184320 字节，`error + backup_healths` 平均 16.88 字节 —— 小规模单实例样本，不能外推为生产基线。

各写入路径的错误处理现状（均无返回值检查）：

| 写入 | 位置 | 是否异步 | 错误处理 |
|------|------|----------|----------|
| `LogDB.Create(DMCheckLog)` | `monitor.go:253-265` | 裸 `go func` | 返回值丢弃 |
| `DB.Updates(updates)` | `monitor.go:334` | 同步 | 返回值丢弃 |
| `DB.Update(check_next_time)` | `monitor.go:175-177` | 同步 | 返回值丢弃 |

## 性能考虑

### 大表清理：DELETE 不缩文件，VACUUM 才缩

SQLite 的 `DELETE` 只把页放回 freelist，库文件不会变小。`optimizeGormDB`（`maintenance.go:283-320`）因此采用固定五步：`wal_checkpoint(TRUNCATE)` → `ANALYZE` → `PRAGMA optimize` → `VACUUM` → 恢复 `journal_mode=WAL`。

| 关注点 | 现状 | 位置 | 代价 |
|--------|------|------|------|
| 清理频率 | 每小时 | `:178` | 单轮全表 `DELETE` 扫描 |
| VACUUM 频率 | 每 24 小时（可配） | `:187-193` | 重写整个库文件 |
| VACUUM 时机 | 与清理同一 goroutine | `:191-192` | 阻塞同轮其他库优化 |
| 空间回收可观测 | `freelist_count * page_size` | `:399-404` | 仅统计，不提前触发 |
| 大事务 | `DELETE` 不带 `LIMIT` | `:221`、`:229` | 长写锁，WAL fsync 峰值 |

`dm_check_logs` 是唯一的高频大表，而 VACUUM 三库串行（`:274-276`）。WAL 下 `VACUUM` 需独占写权限，与探测写入的 `LogDB.Create`（`monitor.go:254`）竞争；连接池上限 8（`database.go:54`）、`busy_timeout(5000)`（`:42`）意味着写侧最多等 5 秒后报错，而该错误正好落在未检查返回值的路径上 —— 表现为"历史曲线出现空洞"而非日志报错。此外 `database.go:39-46` 的注释指出 `glebarez/go-sqlite` 只在每个新连接建立时应用 DSN 里的 `_pragma`，因此 `cache_size(-16000)`（约 16 MB）与 `mmap_size(67108864)`（64 MB）是**每连接**开销；三库各 8 连接的上限（`:54`）意味着极端情况下 page cache 可达 GB 量级。

## 结论

监控数据存储是"三层落盘 + 一层内存 + 一层可选 Redis 旁路"的组合，分层本身相当清楚：配置与状态在 `dm_tasks`，高频历史独立在 `logs.db` 的 `dm_check_logs`，低频事件在 `dm_logs`，心跳在 `sys_configs`，实时解析快照只在进程内存；`logstore` 明确不参与 `DM` 数据，只分流 `RequestLog` 与系统 `Log`。

问题集中在三处契约脱钩，而非存储选型。其一，**写入契约与模型脱钩**：引擎按 map 写四列，模型不声明，`Updates` 返回值又不检查（`monitor.go:334`），旧库存量列掩盖了故障，新库静默失效，且直接终结"切换—告警—回切"整条链路。其二，**读写索引契约脱钩**：所有历史与在线率查询都是 `task_id + created_at` 双谓词，表上只有三个单列索引，其中 `success` 单列索引无读收益却持续放大写入。其三，**展示与存储时间语义脱钩**：`*time.Time` 写入的 `fault_time` / `recover_time` 被前端按秒时间戳解释，4000 点截断让"30 天曲线"实际覆盖约 1.7 天，Overview 的昨日窗口与 Uptime 的近 24 小时是两个时间轴。

按修复收益排序的建议：补齐 `DMTask` 四列并检查 `Updates` / `Create` 错误 → 为 `dm_check_logs` 增加 `(task_id, created_at)` 复合索引并评估 `success` 单列索引去留 → 收敛 history 截断与前端时间轴口径 → 删除任务时级联清理历史 → 让运行状态阈值与 60 秒心跳对齐 → 给 `dm_check_logs` 的写入加上错误日志，使停机窗口的丢失可见。
