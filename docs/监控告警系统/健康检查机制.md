## 简介

健康检查是容灾监控的数据入口：引擎按任务配置对主源与备用源发起探测，把「可达 / 不可达」压缩为布尔量，再喂给连续失败阈值判定与 DNS 记录改写。探测实现集中在 `main/internal/monitor` 包的三个文件——`check.go` 承载探针本体，`ssrf.go` 承载出站目标拦截，`capabilities.go` 承载平台能力查询（决定探测结论如何转化为记录操作）。

任务用 `CheckType` 选探针，取值 0/1/2/3（`models.go:146`），对外表现为 `Ping` / `TCP` / `HTTP` / `HTTPS` 四种类型名（`utils.ts:80-85`）。HTTPS 不是独立探针，而是 HTTP 探针的 TLS 变体：两者共用 `CheckHTTP`（`check.go:206`），仅在 URL 缺省时拼接的协议头不同（`monitor.go:361`、`monitor.go:375`）。

| CheckType | 探针名 | 入口函数 | 判定成功 | 判定失败 | 定义位置 |
|:---:|---|---|---|---|---|
| 0 | Ping（ICMP） | `CheckPing` → `checkPingICMP` / `checkPingWindows` | 收到 ID 与 Seq 均匹配的 EchoReply | 超时、`destination unreachable`、发包失败、解析失败 | `check.go:55-130` |
| 0（降级） | TCP:80 | `checkTCPFallback` | 到目标 80 端口的 TCP 握手成功 | 握手失败，错误前缀 `icmp unavailable, tcp80 failed` | `check.go:151-161` |
| 1 | TCP | `CheckTCP` | 到 `TCPPort`（0 时回退 80）的握手成功 | 连接失败 `tcp connect failed` | `check.go:163-174` |
| 2 | HTTP | `CheckHTTP` | 状态码落在 `[200,400)`，或命中 `ExpectStatus` 白名单，且正文含 `ExpectKeyword` | 状态码不符、关键词缺失、请求异常、重定向超限 | `check.go:206-343` |
| 3 | HTTPS | `CheckHTTP` | 同上，另受证书校验约束（`AllowInsecureTLS` 可关闭） | 同上，另有 TLS 握手失败 | `check.go:206-343`、`monitor.go:372-385` |
| 其他 | 未知 | — | 不可能成功 | 恒定返回 `unknown check type` | `monitor.go:386-388` |

三条需预先建立的边界认知：**探测层没有重试语义**，单次失败即返回，「重试」由调度器下一轮重新派发实现（`monitor.go:150-153`），间隔等于 `Frequency`；**SSRF 拦截只覆盖类型 2/3**，`validateCheckURL` 仅在 case 2/3 调用（`monitor.go:363`、`monitor.go:378`），类型 0/1 走裸 `net.Dialer`（`check.go:153`、`check.go:166`）无私网判定，这是已验证的能力缺口而非设计意图；**不调用系统 `ping` 命令**，Linux 走 `x/net/icmp` 原始套接字（`check.go:68`），Windows 走 `iphlpapi.dll` 的 `IcmpSendEcho`（`check_ping_windows.go:20-23`），`internal/monitor` 全量检索无 `os/exec` 或 `exec.Command` 命中。

### Probe：探测单元与结果契约

`CheckResult` 是探针唯一输出契约（`check.go:44-50`），五个字段各有明确消费方：

| 字段 | 填充方 | 消费方 | 说明 |
|---|---|---|---|
| `Success` | 三类探针 | 主源健康位聚合（`monitor.go:210-212`）、备用健康图（`monitor.go:232`） | 唯一影响切换判定的字段 |
| `Duration` | 三类探针 | `DMCheckLog.Duration`（`monitor.go:257`） | 探针起点到结果生成 |
| `Error` | 失败路径 | 首个失败主源拼为 `errMsg`（`monitor.go:245-250`），截断 500 字节（`monitor.go:258`） | 成功时为空 |
| `StatusCode` | 仅 `CheckHTTP`（`check.go:321`） | 当前无消费方，`ResolveStatus` 与 `DMCheckLog` 均无对应字段 | 推断为可观测性缺口 |
| `BodyPreview` | 仅 `CheckHTTP`，前 8192 字节（`check.go:22`、`:313-317`） | 关键词匹配在探针内完成后不外传 | 局部使用 |

探测粒度是**地址**而非任务：`checkAddress(ctx, task, addr)`（`monitor.go:338`）对单地址探测一次。主源可为逗号分隔多值，`parseValues` 拆分后逐值探测（`monitor.go:197`、`monitor.go:952-965`）；备用值是域名时先经 `resolveToAddrs` → `resolveCNAME` 递归解析为 IPv4 再逐地址探测（`monitor.go:979-1017`）。聚合规则只有一条：**任一主源地址失败即整体不健康**（`monitor.go:210-212`），无比例阈值、无多数仲裁。

### Timeout：三层超时与一处退化

| 层级 | 定义位置 | 取值 | 覆盖范围 |
|---|---|---|---|
| 任务级上下文 | `monitor.go:192` | `Timeout + 10` 秒 | 整个 `processTaskAsync`，含排队、全部探测与落库前 |
| 排队等待 | `monitor.go:342-347` | 复用任务级 ctx | 取 `checkSem` 令牌期间，超时判失败 |
| 探针级 | `check.go:74-75`、`:153`、`:166`、`:221`、`:288` | `Timeout` 秒 | ICMP 读截止、TCP 拨号、HTTP 拨号与整请求 |

`Timeout` 默认 2 秒（`models.go:151`），创建接口零值兜底 2（`handler/monitor.go:241-243`），表单下限 1 秒（`page.tsx:1581-1582`）。Windows ICMP 分支有额外退化保护：`timeout * 1000` 为 0 时强制 5000 毫秒（`check_ping_windows.go:36-39`）。

退化点在 `Timeout = 0` 未被兜底到底：`net.Dialer{Timeout: 0}` 与 `http.Client{Timeout: 0}` 在 Go 语义中均为「不超时」（`check.go:166`、`check.go:288`），而更新接口对 `timeout` 是无条件覆盖写入（`handler/monitor.go:370-391`），因此经对外 API 传入 `timeout=0` 时只剩任务级 `0 + 10 = 10` 秒兜底。这是已验证代码路径，实际影响取决于调用方是否绕过控制台。

### Retry：无探针内重试，靠调度重入

实现中没有重试环：探针一次成败即定论（`check.go:89-91` 发包失败立刻返回；`check.go:306-310` 请求失败立刻返回）。所谓「重试」由三处协作等价实现：`dispatchTasks` 每 1 秒 tick 扫描 `active = 1 AND check_next_time <= now`（`monitor.go:110`、`monitor.go:150`），派发后把 `check_next_time` 顺延 `now + Frequency`（`monitor.go:174-178`）；`processing` 这张 `sync.Map` 提供任务级不重入锁（`monitor.go:165`、`monitor.go:185`）；阈值 `Cycle` 区分偶发失败与持续故障，仅 `errCount >= task.Cycle && task.Status == 0` 才切换（`monitor.go:311`）。

抖动容忍度等价于 `Frequency × Cycle` 秒。默认 `Frequency` 由表单给 60、`Cycle` 给 3（`page.tsx:1574-1578`、`handler/monitor.go:238-243`），最坏 180 秒判定故障。

必须记入的放大效应：**切换失败后 `status` 仍为 0**（`monitor.go:325-330`），下一轮条件继续成立，于是每个 `Frequency` 周期重复调用 DNS 写接口并重复推送告警。代码中不存在退避、最大重试次数或告警冷却——`sendNotification` 调用点仅 `monitor.go:301`、`monitor.go:324`、`monitor.go:329` 三处。

### SSRF Guard：三段拦截

`ssrf.go` 头部注释标注设计动因（`ssrf.go:11-13`）：`CheckURL` 由可添加域名的普通用户提供，未过滤即发起出站请求，可被用作访问云厂商 IMDS、内网服务、Kubernetes API 的跳板。防护由三段组成：

| 拦截段 | 函数 | 触发点 | 拒绝条件 | 可绕局面 |
|---|---|---|---|---|
| URL 字面校验 | `validateCheckURL`（`ssrf.go:31-59`） | `monitor.go:363`、`monitor.go:378` | 协议非 http/https（`:40-43`）、主机为空（`:44-47`）、`localhost`/`.localhost`/`.internal`/`.local`（`:48-52`）、IP 字面量属私网或保留段（`:53-57`） | 域名形式不解析，可指向 `127.0.0.1` |
| 连接期校验 | `ssrfDialControl`（`ssrf.go:99-112`），注入 `Dialer.Control`（`check.go:222`） | 每次 `connect(2)` 之前 | 解析后的实际目标 IP 落入 `isPrivateOrReservedIP`（`:108-110`） | 覆盖 DNS rebinding；代理场景只校验到代理的连接 |
| HostIP 校验 | `validateHostIP`（`ssrf.go:115-127`） | `check.go:216-218` | 非合法 IP（`:119-122`）或私网/保留地址（`:123-125`） | 空值直接放行（`:116-118`） |

`ssrf.go:29-30` 的注释解释了 URL 校验阶段刻意不做 DNS 解析的理由：避免慢解析与 TOCTOU 漂移，把解析后地址判定交给连接期回调。同仓通知侧 `ValidateOutboundURL`（`safe_url.go:15-43`）只有第一段的字面校验、无连接期回调，两条出站链路强度不同。

Windows 路径要点（`check_ping_windows.go:14-77`）：`syscall.NewLazyDLL("iphlpapi.dll")` 取 `IcmpCreateFile` / `IcmpSendEcho` / `IcmpCloseHandle`（`:20-23`），句柄用 `defer procClose.Call` 释放（`:30`）；`IcmpSendEcho` 是阻塞调用，被放进 goroutine 与 `ctx.Done()` 竞争以保证取消语义（`:46-60`）；结果从 256 字节回复缓冲区按固定偏移读取，status 在 `replyBuf[4]`、RTT 在 `replyBuf[8]`（`:70-71`），依赖 `ICMP_ECHO_REPLY` 结构布局；状态码文案映射覆盖 11002 / 11003 / 11010 / 11013（`:79-94`）。

### TCP 探测：地址拼装与握手判定

`CheckTCP` 是最薄的一类探针（`check.go:163-174`），四行核心逻辑：`net.JoinHostPort(host, strconv.Itoa(port))` → `net.Dialer{Timeout: ...}` → `DialContext` → 出错即返回 `tcp connect failed`。

端口来自 `task.TCPPort`，为 0 时由**分派层**回退 80（`monitor.go:353-356`）；`models.go:148` 本身没有默认值标签，因此「0 视为 80」这一约定只存在于代码而非模型。成功判定为握手完成即成功，随即 `conn.Close()`（`check.go:172`）——不发送任何应用层数据，因此无法证明服务真正可用，只证明端口可达。

`JoinHostPort` 是刻意选择：IPv6 字面量必须带方括号，裸拼会产出 `::1:80` 这类多冒号地址，`net.Dial` 以 `too many colons in address` 拒绝，任务将永久判失败。回归用例 `TestCheckTCPAcceptsIPv6Literal` 起真实 IPv6 回环监听并断言对端确实收到连接，而非只比对地址字符串（`check_tcp_test.go:18-53`）；`TestCheckTCPRejectsUnreachablePort` 断言失败路径给出的是拨号错误而非格式错误（`check_tcp_test.go:61-78`）。

TCP 探针与 Ping 的降级路径共用风格但不共用实现：`checkTCPFallback`（`check.go:151-161`）是 Ping 专用的固定 80 端口版本，`CheckTCP` 接受端口参数。两者都不经过 SSRF 回调——两个 `net.Dialer` 构造都没设置 `Control`（`check.go:153`、`check.go:166`），这是「类型 0/1 可探测内网」结论的直接来源。

`CheckHTTP`（`check.go:206-343`）是唯一带业务判定语义的探针，`HTTPCheckOptions` 由分派层从任务字段装配（`httpCheckOptionsFromTask`，`monitor.go:391-408`）。判定链条按序为：`validateHostIP`（`check.go:216-218`）→ 构造带 `Control` 的 `baseDialer`（`check.go:220-223`）→ TLS 配置 `InsecureSkipVerify: opts.InsecureSkipTLS`（`check.go:225`，`check.go:38-40` 注释把默认校验与安全审计项 H-3 绑定，字段来自 `models.go:175`）→ 代理三选一（`check.go:232-284`）→ `GET` 请求带 `User-Agent: DNSPlane-Monitor/1.0`（`check.go:300-306`）→ 正文只取前 8192 字节（`check.go:313-315`）→ 状态码判定（`check.go:325-332`）→ 关键词判定（`check.go:334-339`）。

|:---:|:---:|---|---|
| `0` | 3 | 最多跟随 3 次，超出返回 `重定向过多(最多 3 次)` | `check.go:211-214`、`:293-295` |

## 性能考虑

**并发控制分两级。** 任务级：每 tick 最多派发 `maxDispatchPerTick = 100`（`monitor.go:24`、`monitor.go:152`），按 `check_next_time` 升序取，未进入本轮的任务保留原时间戳等下一 tick（`monitor.go:147-149` 注释），超量时形成排队而非丢弃。地址级：全局信号量 `checkSem` 容量 64、所有任务共享（`monitor.go:29`、`monitor.go:70`），取令牌期间 `ctx.Done()` 命中即返回失败（`monitor.go:342-347`）。`monitor.go:26-28` 注释给出容量存在的原因：每个探测持有 socket 或特权 ICMP 句柄，无上限会在任务密集时耗尽文件描述符。

需正视的副作用是**排队超时会被计入主源失败**。任务数与备用值数量共同放大探测次数（主源多值 + 每个备用值解析出的多个地址，`monitor.go:203-236`），64 令牌打满后排队失败会推进与目标主机无关的 `err_count`，批量任务下可能出现同步误切换。

**超时层级按最紧者评估：**

| 场景 | 单任务最坏耗时 | 构成 |
|---|---|---|
| 主源 1 值、目标无响应 | 约 `Timeout` 秒 | 探针超时（`check.go:166`、`:221`、`:288`） |
| 主源 N 值 | 与单值同级 | 并发发起，`mainWg`（`monitor.go:203-215`、`:238`） |
| 主源 + 备用 M 值 | 两组各自 `Wait`，可并行 | `backupWg`（`monitor.go:223-241`） |
| 令牌排队 | 最长 `Timeout + 10` 秒 | 任务 ctx（`monitor.go:192`、`:342-347`） |
| API 传入 `Timeout=0` | 最长约 10 秒 | 只剩任务 ctx 兜底 |

`Timeout + 10` 的余量（`monitor.go:192`）同时容纳排队与探针，使单任务总时长被硬约束在十几秒级，不因慢目标拖垮整轮。

**数据库侧压力。** 每条到期任务在派发阶段参与批量 `UPDATE check_next_time`，按 `Frequency` 分组合并为一条语句（`monitor.go:159-178`），这是对高频 tick 的显式优化；调度查询 `active = ? AND check_next_time <= ?`（`monitor.go:150`）命中 `models.go:162`/`models.go:157` 声明的复合索引 `idx_dm_tasks_active_next`（`active` 前缀列 + `check_next_time`），tick 扫描不退化为全表扫。每轮探测写一条 `dm_check_logs` 到 `LogDB`，且放在未受控的裸 goroutine 中（`monitor.go:253-265`），既不占 `checkSem` 也不进 `wg`：好处是不阻塞探测主路径，代价是停机可能丢写入、高频任务把写压力转给 SQLite（字段清单 `models.go:179-190`，保留期由 `database/maintenance.go` 配置项控制，具体默认值本次未实读，标注未知）。

**HTTP 正文与连接复用。** 关键词匹配只读前 8192 字节（`check.go:22`、`check.go:313`），其余 `io.Copy(io.Discard, ...)` 排空（`check.go:315`），超大响应不会造成内存膨胀；排空而非直接 `Close` 是为了让 `Transport` 的 10 个空闲连接与 30 秒空闲超时能复用（`check.go:226-230`）。

**DNS 解析是隐性成本。** `resolveIPv4`（`check.go:133-148`）与 `resolveToAddrs` → `resolveCNAME`（`monitor.go:979-1017`）都会触发解析，递归深度上限 3（`monitor.go:984`、`:992-995`）。备用值的 `resolveToAddrs` 在主 goroutine 内联执行（`monitor.go:224`），不受 `checkSem` 约束，慢解析会直接推迟该任务整轮结论；`CheckPing` 内的 `resolveIPv4` 在探针函数内，受任务 ctx 约束。

### ICMP 权限专项

排查顺序按证据强度排列：

1. **确认探针实际走了哪条路**——错误串是决定性线索：含 `icmp unavailable, tcp80 failed` 即降级 TCP:80（`check.go:157`）；含 `ping timeout` 说明套接字创建成功但无回包（`check.go:104`、`check.go:127`）；含 `send:` 前缀说明发包失败（`check.go:90`）。
2. **确认部署形态**——`Dockerfile:32` 用 `gcr.io/distroless/static-debian12:nonroot`，`Dockerfile:35` 显式 `USER nonroot:nonroot`，容器内无 `CAP_NET_RAW`，`ip4:icmp` 必然创建失败，因此容器化生产环境下 Ping 类型实际等同 TCP:80 探测。
3. **Linux 宿主机直跑**——内核 `net.ipv4.ping_group_range` 决定 UDP 探测套接字的可用组，但本实现用 `ip4:icmp` 原始套接字而非 `udp4`（`check.go:68`），调整该参数对此路径无效，必须 root 或 `CAP_NET_RAW`（推断依据为套接字类型，未在本仓库实测内核行为）。
4. **Windows 部署**——`IcmpCreateFile` 无需管理员权限，但句柄获取失败返回 `IcmpCreateFile: ...`（`check_ping_windows.go:27-29`）。

推荐处置：把健康检查目标改为显式 TCP 端口探测或 HTTPS 探测，将 Ping 类型限定在裸机部署；不要依赖降级路径判断站点存活，因为 80 端口开放与业务可用之间没有因果关系。

### SSRF 误杀专项

误杀的实质通常是「合法目标落在保留段判定内」，逐项核对：

1. **CGNAT 段 `100.64.0.0/10`**（`ssrf.go:78-81`）——自建 VPN / 内网穿透常用此段，标准库 `IsPrivate()` 不覆盖而本实现显式补齐，因此该段 IP 字面量会被拒；改用域名形式可过字面校验（`ssrf.go:29-30`），但连接期回调仍会拦截（`ssrf.go:108-110`），最终仍需公网地址。
2. **`0.0.0.0/8` 与 `240.0.0.0/4`**（`ssrf.go:75-77`、`:90-91`）判定偏保守，内部测试环境使用非常规段会被拒。
3. **CDN 回源的 `HostIP`**（`ssrf.go:115-127`）只接受公网 IP 字面量（空值除外），填内网 CDN 节点 IP 直接失败，错误为 `拒绝 host_ip 指向私网/保留地址`。
4. **保留 TLD**：`.internal` / `.local` / `.localhost` 后缀无条件拒绝（`ssrf.go:48-52`），公司内网常用 `.internal`，此类域名只能换公网等价入口或改检测类型。
5. **代理转发不被监控**：字段级 HTTP 代理下拦截只作用于到代理的连接（`check.go:244-247`），因此不会出现「代理可达但目标被误杀」；若报 `ssrf guard:` 且代理本身是内网地址，失败原因其实是代理地址。

反向缺口同样需记录（属风险而非误杀）：CheckType 0/1 完全不受 SSRF 约束（`check.go:153`、`check.go:166` 的拨号器无 `Control`），任何可创建监控任务的账号都能对任意地址发起 TCP 端口探测；备用值 DNS 解析同样不做私网判定（`monitor.go:979-989`）。缓解优先级应是把带 `Control` 的拨号器复用到 `checkTCPFallback` 与 `CheckTCP`，此项未实现，记为待办。

## 结论

健康检查机制的分派与判定部分清晰自洽：`checkAddress` 把四种类型收敛到三个探针函数（`monitor.go:338-389`、`check.go:55-343`），探针只输出 `CheckResult`（`check.go:44-50`），判定层只看 `Success` 一位（`monitor.go:210-212`），超时按「任务 ctx → 排队等待 → 探针」三层收敛（`monitor.go:192`、`monitor.go:342-347`、`check.go:166`）。SSRF 防护采用「字面校验 + 连接期回调」双层结构，后者覆盖 DNS rebinding（`ssrf.go:29-30`、`ssrf.go:99-112`），是同仓两条出站链路中更严格的一条（对照 `safe_url.go:15-43`）。

按设计原则评估：**KISS** 体现在探针契约极简，新增类型只需加一个 switch 分支；**SRP** 体现在 `check.go` / `ssrf.go` / `capabilities.go` / `monitor.go` 四分且探针层零业务依赖、可单测；**OCP** 基本成立，`HTTPCheckOptions` 以选项结构承载扩展位（`check.go:25-42`）。违反点集中在**契约脱钩**与**静默退化**：前者是探测结论写入的列不在模型中（`models.go:134-176` 对 `monitor.go:275-283`、`monitor.go:316`）且 `Updates` 返回值未检查（`monitor.go:334`），后果是新库上整套判定链路静默失效；后者包括 ICMP 静默降级 TCP:80（`check.go:70`）、未探测备用值默认健康（`monitor.go:948`）、排队超时计入主源失败（`monitor.go:346`）。三者共同特征是「不报错但结论错」，对容灾系统而言风险高于显式失败。

改进优先级（建议，未实施）：补齐 `DMTask` 缺失字段并检查 `Updates` / `Create` 返回值以恢复状态持久化契约；把「ICMP 不可用」显式化为可查询状态而非只藏在错误串里；将 SSRF 连接期回调扩展到类型 0/1；为切换失败加退避与告警冷却；补 Ping / HTTP 判定 / SSRF 三段的单元测试。

```mermaid
    Counting --> Counting: fail && err_count + 1 < cycle
    Counting --> Normal: success (reset err_count)
    Counting --> Switching: fail && err_count + 1 >= cycle && status == 0
    Switching --> Switched: smartSwitch ok (status = 1)
    Switching --> Counting: smartSwitch failed (status stays 0)
    Switched --> Restoring: success && auto_restore
    Restoring --> Normal: restoreRecord ok
    Restoring --> Switched: restoreRecord failed
```
