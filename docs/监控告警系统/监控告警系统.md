## 简介

监控告警系统是 dnsplane 的容灾核心域，由三个能力闭环构成：

- **多协议健康检查**：对监控任务的主源地址执行 Ping（ICMP）、TCP、HTTP、HTTPS 四类探测，
  探测参数（间隔、连续失败阈值、超时、期望状态码/关键词、代理）逐任务可配
  （`main/internal/monitor/check.go`，`main/internal/monitor/monitor.go:338-389`）。
- **自动容灾切换**：主源连续失败达到阈值后，按任务策略改写云端 DNS 记录——暂停/恢复、
  删除/重建、或切换到备用值；主源恢复且开启自动回切时自动还原
  （`main/internal/monitor/monitor.go:411-477`）。
- **多渠道通知**：切换、切换失败、恢复三类事件经任务级开关、渠道开关与任务白名单三层筛选后，
  由 13 个已注册通知渠道（邮件/Telegram/Webhook/Discord/钉钉/飞书/QQ 机器人等）串行扇出
  （`main/internal/monitor/monitor.go:767-873`，`main/internal/notify/channel_adapters.go:330-344`）。

与之相邻的**定时切换**子域（`main/internal/api/handler/schedule.go` +
`main/internal/service/schedule.go`）复用同一套 DNS 写记录链路，按日期时间或周期到点执行
启用/暂停/删除/修改，但不进通知渠道，仅写操作日志。

本文所有行号均以当前工作区文件实测为准（版本 1.0.11，工作区存在未提交修改）。
涉及机密值（代理口令、渠道密钥）一律以 `{占位}` 表述。

## 核心组件

### 调度器

调度器是常驻协程：`run()` 以 1 秒 ticker 驱动派发、以 60 秒 statusTicker 刷新心跳
（`monitor.go:107-127`）。`dispatchTasks()` 每轮查询 `active=1 AND check_next_time<=now`
的任务，按 `check_next_time` 升序最多取 `maxDispatchPerTick = 100` 个（`monitor.go:24`），
用 `processing.LoadOrStore` 防止同一任务并发处理，派发后立即顺延
`check_next_time = now + Frequency`（`monitor.go:144-179`）。任务体经
`utils.SafeGoWithName` 起裸 goroutine 执行 `processTaskAsync`，不受 `Stop()` 的
`wg.Wait()` 覆盖（`monitor.go:171`，`monitor.go:93-104`）。

**章节来源**
- `main/internal/monitor/monitor.go:19,24,93-104,107-127,144-179`

### 检测器

`check.go` 提供三类平台无关探测与一个 Windows 原生 ICMP 分支：Ping 收到 ID+Seq 匹配的
EchoReply 判成功，非 Windows 或权限不足时静默降级为 TCP:80（`check.go:55-130,151-161`）；
TCP 探测握手成功即健康，`TCPPort=0` 回退 80（`check.go:148,163-174`）；HTTP(S) 探测
`2xx/3xx` 或命中 `ExpectStatus` 白名单、且正文（前 8192 字节）含关键词才成功
（`check.go:22,206-343`）。每次探测受任务级 ctx 超时 `Timeout + 10` 秒约束（`monitor.go:192`）。

**章节来源**
- `main/internal/monitor/check.go:22,55-130,148-174,206-343`
- `main/internal/monitor/monitor.go:192,338-389`

### 决策器

`processTaskAsync` 的判定分支（`monitor.go:285-331`）：主源全健康则清零 `err_count`，
若任务处于已切换态且 `auto_restore` 开启则触发回切；主源异常则 `err_count + 1`，
达到 `Cycle` 阈值且尚未切换时触发 `smartSwitch(task, true)`。多主源语义为
**任一地址失败即判主源故障**，无比例仲裁（`monitor.go:210-212,952-965`）。

**章节来源**
- `main/internal/monitor/monitor.go:210-212,285-331,952-965`

### 执行器

`smartSwitch`（`monitor.go:411-477`）按 `task.Type` 分派三种策略：暂停/恢复
（`disableRecord` :479-510，能力不支持暂停时回退删除+存原值）、删除/重建
（`DeleteDomainRecord` :452-466，先存 `OriginalValue`/`DeletedRecord`）、
切换备用值（`switchToBackup` :555-661，选首个健康备用值，CNAME 备用先解析 IPv4 再加 A，
记录类型不一致时删/停主记录再建新记录）。回切经 `restoreRecord`/`recreateRecord`
（:521-553,706-708）。手动路径为 `ManualSwitch(taskID, toBackup)`（:711-740）。

**章节来源**
- `main/internal/monitor/monitor.go:411-510,521-553,555-661,706-740`

### 存储

运行期数据分五处落点（详见[历史数据](#历史数据)与[清理策略](#清理策略)）：任务状态列写主库
`dm_tasks`（`monitor.go:334`），逐次探测结果异步写 LogDB `dm_check_logs`
（`monitor.go:252-265`），切换事件写主库 `dm_logs`（`monitor.go:931`），实时解析快照存进程内存
`sync.Map`（`monitor.go:274`），运行心跳 `run_time`/`run_count` 写 `sys_configs`
（`monitor.go:130-141`）。

**章节来源**
- `main/internal/monitor/monitor.go:130-141,252-274,334,931`
- `main/internal/models/models.go:134-199`

### 通知装配

`sendNotification(task, eventType, errMsg)` 依次执行：`NotifyEnabled` 门禁 → 反查域名拼
完整域名 → 生成 `fault`/`fault_switch_failed`/`recover` 三种纯文本文案 → `buildNotifyManager`
按 `notify.NotifyConfigKeys()` 一次 `IN` 查询直读 `sys_configs`，遍历 13 个注册渠道，
套 `notice_*` 开关与任务白名单两层筛选 → 10 秒 ctx 内 `manager.Send` 串行扇出，
失败仅记日志（`monitor.go:767-873`，`notify.go:688-704`）。

**章节来源**
- `main/internal/monitor/monitor.go:767-873`
- `main/internal/notify/notify.go:688-704`
- `main/internal/notify/channel_adapters.go:330-344`

### SSRF 防护

`ssrf.go` 提供两道拦截：建探测任务/执行探测时校验 URL scheme 与 IP 字面量私网段
（`validateCheckURL` :31，`isPrivateOrReservedIP` :62），并在 Dialer 的 `Control` 钩子里对
**解析后的实际连接地址**二次拦截，防 DNS rebinding（`ssrfDialControl` :99，`check.go:220-223`）。
覆盖范围仅限 CheckType 2/3 与 CDN 回源 HostIP（`monitor.go:363,378`，`check.go:216-218`）；
CheckType 0/1 与备用值解析 `resolveToAddrs` 不做私网判定（详见故障排查）。

**章节来源**
- `main/internal/monitor/ssrf.go:31,62,99`
- `main/internal/monitor/check.go:216-223`
- `main/internal/monitor/monitor.go:363,378`

### capabilities 平台能力表

`capabilities.go` 以静态表登记各 DNS 平台是否支持暂停/删除/混合记录（:10-26），
未登记平台回退默认值 `{Pause:false, Delete:true, Mixed:false}`（:28-32）。当前表只登记
15 家，而 `providers` 目录实有 22 家；且仅 `Pause` 字段被 `monitor.go:481,594,643` 消费，
`Delete`/`Mixed` 无读取方。

**章节来源**
- `main/internal/monitor/capabilities.go:10-32`
- `main/internal/monitor/monitor.go:481,594,643`

## 详细组件分析

### 任务模型

监控任务对应 `models.DMTask`（表 `dm_tasks`，主库，`models.go:134-176`）。字段按职责分组：

| 分组 | 字段（列名） | 语义与默认值 |
| --- | --- | --- |
| 定位 | `DomainID`(did) / `RR`(rr) / `RecordID`(record_id) / `RecordType` / `RecordLine` | 域名与云端记录锚点；RecordID 在删除重建后会变更（:136-140） |
| 切换策略 | `Type`(type) | 0 暂停/恢复、1 删除/重建、2 切换备用值，默认 0（:141） |
| 源值 | `MainValue` / `BackupValue` / `BackupValues` / `BackupType` | 主源逗号分隔多值；`BackupValues` 非空时优先于单备用值；BackupType 为 ip 或 cname（:142-145） |
| 探测参数 | `CheckType` / `CheckURL` / `TCPPort` / `Frequency` / `Cycle` / `Timeout` | 0 ping/1 tcp/2 http/3 https；间隔默认 3 秒阈值连续失败 3 次超时 2 秒（:146-151） |
| HTTP 判定 | `ExpectStatus` / `ExpectKeyword` / `MaxRedirects` | 状态码白名单、正文关键词；0=默认跟随 3 次重定向，-1=不跟随（:164-166） |
| 代理/CDN | `UseProxy` / `CDN` / `ProxyType`/`ProxyHost`/`ProxyPort`/`ProxyUsername`/`ProxyPassword` | 代理口令 `json:"-"` 且落库加密（:153-154,167-171） |
| 运行状态 | `CheckTime` / `CheckNextTime` / `SwitchTime` / `ErrCount` / `Status` / `MainHealth` / `Active` / `RecordInfo` | Status 0 正常/1 已切换；CheckNextTime 是调度唯一依据；RecordInfo 存 TaskState JSON（:155-163） |
| 通知/回切 | `NotifyEnabled` / `NotifyChannels` / `AutoRestore` / `AllowInsecureTLS` | 告警总开关、渠道白名单 JSON 数组、主源恢复自动回切、探测跳过证书校验（:172-175） |
| 备注 | `Remark` / `AddTime` | 备注 100 字符、创建时间戳（:152,155） |

`RecordInfo` 的 JSON 载体是 `TaskState`（`monitor.go:42-53`）：`backup_record_ids[]`、
`original_value`、`deleted_record{type,line,ttl,mx,remark}`、`was_deleted`，声明容量
`size:200`（`models.go:163`），批量创建时可能溢出（详见故障排查）。

辅助模型：`DMCheckLog`（表 `dm_check_logs`，LogDB，`models.go:179-190`）、

### 检测类型

检测类型在 `processTaskAsync` 内按 `CheckType` 分派（`monitor.go:338-389`）：

| CheckType | 名称 | 入口函数 | 关键参数 | 成功判据 | 失败判据 |
| --- | --- | --- | --- | --- | --- |
| 0 | Ping(ICMP) | `CheckPing` → `checkPingICMP`/`checkPingWindows` | MainValue、Timeout | 收到 ID+Seq 匹配的 EchoReply | 超时、`destination unreachable`、发送失败 |
| 0(降级) | TCP:80 | `checkTCPFallback` | 固定端口 80 | TCP 握手成功 | 握手失败 |
| 1 | TCP | `CheckTCP` | TCPPort（0 回退 80）、Timeout | 连接建立 | 连接失败 |
| 2 | HTTP | `CheckHTTP` | CheckURL（空则 `http://`+addr）、ExpectStatus、ExpectKeyword、MaxRedirects、代理、CDN→HostIP | 2xx/3xx 或命中状态码白名单，且正文含关键词 | 状态码不符、关键词缺失、请求错误 |
| 3 | HTTPS | `CheckHTTP` | 同上，空 URL 回退 `https://`+addr | 同上，另受 TLS 校验约束 | 同上 |

### 判定阈值

- **主源聚合**：`parseValues` 按逗号拆分多主源（`monitor.go:952-965`），逐地址并发探测，
  任一失败即 `mainHealthy=false`，无比例或仲裁阈值（`monitor.go:210-212`）。
- **备用源聚合**：`getBackupValues` 优先 `BackupValues`、回退 `BackupValue`（:968-976）；
  非 IP 值经 `resolveToAddrs` 解析（:979-989）；同一值解析出多地址时结果 map 被后写覆盖
  （:227-234）。
- **切换阈值**：`errCount = task.ErrCount + 1`，`errCount >= Cycle` 且 `status == 0` 才触发
  切换（`monitor.go:308-318`）。`Cycle=0`（经对外 API 零值覆盖可达）时首次失败即切换。
- **回切阈值**：仅 `status==1 && auto_restore` 且本轮主源全绿即回切（`monitor.go:292`），
  无“备用源保持 N 轮再回切”的二次确认，也无回切冷却。
- **兜底超时**：任务级 ctx = `Timeout + 10` 秒（:192）；全局并发信号量 64（:29），
  等待信号量期间 ctx 超时直接判该次探测失败（:342-347）。

### 切换策略

`smartSwitch` 先做空值守卫与 `Domain → Account → Provider` 载入，再读平台能力
`GetPlatformCaps(account.Type)`，解析 `record_info` 为 `TaskState` 后按 `task.Type` 分派
（`monitor.go:411-477`）。三种策略的状态迁移如下：

```mermaid

    Normal --> Normal: check success, err_count reset
    Normal --> Suspect: main failed, err_count increments
    Suspect --> Normal: success before reaching Cycle
    Suspect --> Switched: err_count >= Cycle and smartSwitch success
    Suspect --> Suspect: switch failed, notify fault_switch_failed, status stays Normal
    Switched --> Normal: auto_restore on and main fully healthy, restoreRecord success
    Switched --> Switched: restore failed, only error logged
```

- **Type 0 暂停/恢复**：平台 `caps.Pause` 为真时走 `SetStatus(false)`；不支持暂停的平台

  type/line/ttl/mx/remark 重建（`monitor.go:452-466,521-553`）。

## 性能考虑

- **派发吞吐**：1 秒 tick × 每轮 100 任务上限（`monitor.go:24,144-153`），理论上支撑
  每秒新起约 100 个任务协程；实际瓶颈在探测信号量 `maxConcurrentChecks = 64`（:29），
  满员排队期间 ctx 超时即误判失败（:342-347），任务规模大时形成与目标无关的批量误切换风险。
- **SSRF 检查开销**：`validateCheckURL` 为纯字符串/字面 IP 解析（`ssrf.go:31-77`），成本可忽略；
  Dialer `Control` 钩子（`ssrf.go:99`）在每次连接建立时执行一次私网判定，属常数级开销。
  设计上刻意不做前置 DNS 解析以避免慢解析与 TOCTOU 漂移（`ssrf.go:28-30` 注释）。
- **通知链放大**：每次告警新增一次 `WHERE key IN (71 键)` 主库直查（`monitor.go:832`），
  且 `sendNotification` 同步执行——邮件 SMTP 分支拨号 12s+阶段 15s 不受 10s ctx 约束
  （`notify.go:173-174`），最坏情况拖延 `Updates` 落库、放大重复切换窗口（`monitor.go:324-334`）。
- **观测查询**：`GetMonitorOverview` 以 9 个 goroutine 并发统计（`handler/monitor.go:606-643`），
  但 `GetMonitorUptime` 9 次查询串行（:890-917）；前端每 15 秒轮询后对每个任务并发拉
  `history?period=1h`，最多 200 任务即 200 次 LogDB 扫描（`monitor/page.tsx:292-309,360-369`），
  仅靠三个单列索引支撑，缺 `task_id+created_at` 复合索引。
- **内存增长**：`resolveStatuses`/`processing` 两个 sync.Map 只增不减，删除任务与停启用
  均不清理（`handler/monitor.go:402-470`），长期运行残留失效条目。

## 故障排查指南

### 误切（主源正常却触发切换）

- 全新安装库上 `err_count` 可能永远写不进去也永远读不出来：`DMTask` 缺
  `last_error`/`backup_health`/`fault_time`/`recover_time` 字段，`Updates(map)` 报
  `no such column` 且返回值被丢弃（`monitor.go:334`），表现为“永不切换”的反向症状亦由
  同根因引发——先核对表结构再下结论。
- ICMP 权限缺失时静默降级 TCP:80（`check.go:68-71`），只监听 443 的源会被判故障；
  容器 distroless nonroot 环境基本必触发该降级。
- 探测并发满 64 时排队超时直接计入主源失败（`monitor.go:342-347`）。
- 编辑任务会把 `proxy_password` 清空：模型 `json:"-"` 使列表不回显
  （`models.go:171`），前端回填 undefined 后提交空串被无条件覆盖
  （`handler/monitor.go:383`），认证代理探测随即失败并误判主源。
- 对外 API 更新未传字段时写零值：`Frequency=0` 导致每秒重复探测、`Cycle=0` 导致首次
  失败即切换、`Timeout=0` 使探测只剩 10 秒 ctx 兜底（`handler/monitor.go:370-391`，
  `monitor.go:177,311`，`check.go:220-221,288`）。
- CheckType 0/1 与备用值解析无 SSRF 私网拦截，`tcp` 类型可探测内网端口
  （`monitor.go:363,378` 仅覆盖 2/3），排查异常目标时注意该边界。

- 回切条件极窄：仅 `status==1 && auto_restore` 且本轮主源全绿（`monitor.go:292`），

## 结论

监控引擎的**决策逻辑本身完整且可读**：阈值判定 → 三策略切换 → 云端记录改写 → 恢复回切 →
事件通知，主干全部收敛在 `monitor.go` 一个 1049 行文件内，符合 KISS；通知侧通过渠道注册表
实现“新增渠道只需注册”，对 monitor 满足开闭原则（`channel_registry.go:20-33`）。

但**状态持久化契约已与模型脱钩**：新库上探测结果与切换状态写不进 4 个未声明列
（`no such column`，返回值被丢弃），形成“旧库看似正常、新库静默失效”的分叉。叠加更新接口
零值覆盖、告警无节流、运行状态判定自相矛盾，该域当前处于高危状态。建议优先级：

1. 补齐 `DMTask` 缺失字段并检查 `Updates` 返回值（P-1 根因，牵动 P-2/P-7 排障可信度）。
2. 收敛 `UpdateMonitorTask` 字段覆盖范围，非零/显式传入才写（P-5/P-4）。
3. 为告警增加冷却与并发扇出（P-7/P4：串行饿死 + 只回传首个错误）。
4. 补能力表缺口（15 家 vs 22 家）并删除 `Delete`/`Mixed` 死字段（P-12）。
5. 补 `dm_check_logs` 复合索引、任务删除级联、监控切换/回切路径测试
   （现 27 个测试全部集中在通知装载与 TCP，判定/切换/派发零覆盖）。
